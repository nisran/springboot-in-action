02CAS 原理 ⭐

三个操作数：V、E、N

CAS（Compare-And-Swap，比较并交换）需要三个操作数：内存地址 V、预期旧值 E、新值 N。执行时：当且仅当 V 处的当前值等于 E，才把 N 写入 V；不相等说明被人改过，什么都不做并返回失败。"比较 + 写入"是一条 CPU 原子指令完成的，中间不可能有其他核心插入——这就是它原子性的全部来源。

// CAS(V, E, N) 的语义伪代码 —— 比较与写入必须是原子的
boolean compareAndSwap(long V, long E, long N) {
    if (read(V) == E) {   // 比较
        write(V, N);      // 交换 —— 与比较合成一条指令，不可分割
        return true;
    }
    return false;         // 失败不重试、不阻塞：策略交给调用方（通常自旋）
}

硬件层：x86 的 lock cmpxchg

x86:  lock cmpxchg [V], reg   // lock 指令前缀 + 比较交换指令，一条完成
ARM:  ldaxr / stxr            // ARM 没有 cmpxchg，用 LL/SC（独占加载/条件存储）
                               // 成对指令实现：加载时标记独占，存储时发现
                               // 期间被写过就失败重试 —— 效果等价于 CAS

lock 前缀保证原子性的两种实现（演进史）：
  老一代 CPU：总线锁（bus lock）—— 锁住前端总线，其他核全部停摆，代价巨大
  现代 CPU：  缓存锁定（cache locking）—— 依赖 MESI 缓存一致性协议，
              把目标缓存行置为独占状态，其他核上同一缓存行直接失效
              —— 锁的粒度从"整条总线"缩小到"一个 64B 缓存行"
  • 缓存锁定比总线锁先进在哪：总线锁牺牲的是整颗 CPU 的访存能力；缓存锁定只让"正在被 CAS 的那一行"在其他核心失效，无关内存访问完全不受影响——CAS 从"全局停摆"进化成"行级独占"。
  • 这也是"乐观锁快"的硬件解释：不加锁不阻塞，靠缓存一致性协议协调，比内核挂起/唤醒线程（微秒级）便宜一到两个数量级。

答题口径："CAS 的原子性不是 JVM 保证的，是 CPU 指令保证的——x86 上是带 lock 前缀的 cmpxchg，lock 前缀在现代 CPU 上走缓存锁定而非总线锁"。这两句话能瞬间把你和背"三个操作数"的候选者区分开。

03Java 侧：Unsafe 与自旋重试

Unsafe：JVM 调用 CPU 指令的桥

  • Java 侧的 CAS 入口是 Unsafe 类的 native 方法：compareAndSwapInt / compareAndSwapLong / compareAndSwapObject（JIT 会把它内联为上面的 CPU 指令）。
  • 参数不是字段名而是内存偏移量（对象地址 + offset 定位字段）——所以 AtomicInteger 在类加载时用反射算好 value 字段的偏移并缓存。
  • JDK 9 起 Unsafe 路线被 VarHandle（变量句柄）取代，标准 API 化，但"读最新值 + CAS 失败自旋"的结构没变。

AtomicInteger.getAndIncrement 源码（JDK 8，必背）

public class AtomicInteger extends Number implements java.io.Serializable {
    private volatile int value;              // volatile：每次读都拿最新值（可见性）
    private static final Unsafe unsafe = Unsafe.getUnsafe();
    private static final long valueOffset;   // value 字段相对对象头的内存偏移量

    static {                                 // 类加载时算好偏移量，只算一次
        try {
            valueOffset = unsafe.objectFieldOffset(
                    AtomicInteger.class.getDeclaredField("value"));
        } catch (Exception ex) { throw new Error(ex); }
    }

    public final int getAndIncrement() {
        return unsafe.getAndAddInt(this, valueOffset, 1);   // 委托给 Unsafe
    }
}

// Unsafe.getAndAddInt —— do-while 自旋：读最新值，CAS 失败就重读再试
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);                     // ① volatile 读最新值
    } while (!compareAndSwapInt(o, offset, v, v + delta)); // ② CAS 失败则循环
    return v;
}
  • 为什么要自旋：CAS 失败说明值被别人改了，正确做法不是阻塞而是基于最新值立刻重试——多数时候下一轮就成功，全程不挂起线程、不进内核。
  • 为什么 value 必须是 volatile：CAS 只保证"比较交换"原子，可见性（第 ① 步读到的是最新值）靠 volatile 读保证，二者各管一段。
  • 追问"那它和 synchronized 的 i++ 差在哪"： synchronized 失败者挂起（上下文切换）；CAS 失败者自旋（低中竞争下便宜得多，高竞争下反而烧 CPU——见第 05 节局限）。

04ABA 问题 ⭐

问题：值"变回来了"≠ 没变过

CAS 只比较"当前值 == 预期值"。如果值经历了 A→B→A：中间确实被改过两次，但 CAS 一比较——还是 A，认为"没变过"，交换成功。值的历史被抹掉了。

  • 纯数值场景通常无害：余额 100 → 50 → 100，最后 CAS "100 变 90"结果仍正确——数值运算只关心终值。
  • 指针/结构场景致命：无锁栈要把栈顶从 A 换成 C；期间别的线程弹出 A、弹出 B、又把 A 压回——栈顶"还是 A"，但 A 节点已被弹出/复用，链表结构早就不是线程 1 认识的样子，CAS 成功的瞬间结构损坏（典型如 Treiber 栈的回收复用问题）。
  • 本质：CAS 比较的是值相等，而引用相等不能证明对象没被经历过中间状态。

解法：给值加个版本

// AtomicStampedReference：值 + int 版本号（stamp），两者必须同时对上才交换
AtomicStampedReference<Node> top = new AtomicStampedReference<>(aNode, 0);

int stamp = top.getStamp();                          // 记住动手时的版本号
// ... 此期间别的线程把栈顶 A->B->A，但 stamp 已从 0 涨到 2 ...
top.compareAndSet(aNode, cNode, stamp, stamp + 1);   // 值对、版本不对 -> 失败
// ABA 被版本号拦下，走失败重试分支

// AtomicMarkableReference：不关心改了几次，只标记"被动过没有"（一个布尔位）
AtomicMarkableReference<Node> top2 = new AtomicMarkableReference<>(aNode, false);
  • 数据库乐观锁的 version = version + 1 WHERE version = ? 与StampedReference 同一思想——"比较键"从值换成了（值 + 版本）二元组（第 04 章乐观锁）。
  • 为什么日常业务代码很少感知 ABA：线程手里捏着期望引用 A，A 就不会被 GC 回收——"同地址分配新对象"这种原生内存复用在普通 Java 代码里基本造不出来。ABA 的破坏力主要出现在无锁数据结构和带内存池/SLAB 分配（如 Netty）的场景——能把这层说清是明显加分项。

05CAS 三大局限

局限表现缓解手段
① 自旋开销竞争激烈时 CAS 长期失败，do-while 空转烧 CPU（重试风暴，第 04 章乐观锁隐藏成本）竞争烈度高就别硬 CAS——改用锁或 LongAdder 分散热点
② 只能保证单个变量CAS 一次只动一个内存位置，两个字段的"一起变"做不到多字段包成不可变对象用 AtomicReference 整体替换，或退回加锁
③ ABA值变回去就认不出"变过"AtomicStampedReference / AtomicMarkableReference（上一节）
// 局限②的标准解法：把多个字段包进一个不可变对象，对"引用"做 CAS —— 整体原子替换
record Point(int x, int y) {}                       // 不可变 record（JDK 16+）
AtomicReference<Point> ar = new AtomicReference<>(new Point(0, 0));

Point old = ar.get();
Point next = new Point(old.x() + 1, old.y() + 1);   // 新值先造好
boolean ok = ar.compareAndSet(old, next);           // x、y 一起原子生效
// 失败说明别人先改了 -> 重新 get 再试（还是自旋）

06Atomic 家族全景

类别代表定位
基本类型AtomicInteger / AtomicLong / AtomicBoolean（int 承载）单个数值的原子读-改-写
引用类型AtomicReference / AtomicStampedReference / AtomicMarkableReference对象引用 CAS、ABA 防护
数组AtomicIntegerArray / AtomicLongArray / AtomicReferenceArray数组元素的原子更新（不是数组引用）
字段更新器AtomicIntegerFieldUpdater / AtomicLongFieldUpdater / AtomicReferenceFieldUpdater对已有类的 volatile 字段 CAS；反射实现、偏慢，如今基本弃用（被 VarHandle 取代）
累加器LongAdder / DoubleAdder / LongAccumulator / DoubleAccumulator高并发统计计数（下一节主角）
AtomicInteger ai = new AtomicInteger();
ai.getAndIncrement();          // 原子 i++（返回旧值）
ai.incrementAndGet();          // 原子 ++i（返回新值）
ai.compareAndSet(0, 10);       // 当前值 == 0 才改成 10（CAS）
ai.getAndSet(5);               // 原子设新值，返回旧值

AtomicLong al = new AtomicLong();
// 笔记口径：64 位 JVM 上 long 读写天然原子；32 位 JVM 上非 volatile 的
// long 读写可能拆成两次 32 位操作 —— AtomicLong 用 volatile + CAS
// 保证在任何平台上的原子性
al.addAndGet(1_000_000L);

AtomicReference<User> ref = new AtomicReference<>(alice);
ref.compareAndSet(alice, bob); // 注意：比较的是"同一个引用"，不是 equals

选型直觉：状态机/开关用 AtomicBoolean，计数与阈值判断用 AtomicLong，替换"整个对象"用 AtomicReference，纯累加统计直接上 LongAdder。Atomic 家族只覆盖单变量——多变量一致性要么 AtomicReference 包对象，要么老实加锁。

数组三兄弟：把 CAS 打到元素上 ⭐

为什么存在：volatile int[] 的 volatile 只修饰数组引用，元素读写完全不享受 volatile 语义——AtomicIntegerArray / AtomicLongArray / AtomicReferenceArray 三件套就是把 volatile 读 + CAS 补到元素级。原理仍是 §03 那套 Unsafe，只是地址从"单个字段偏移"换成"数组基址 + 下标 × 元素步长"：

// AtomicIntegerArray 内部骨架（JDK 8 源码；JDK 9+ 内部换 VarHandle，原理不变）
private final int[] array;                                            // 普通数组，非 volatile！
private static final int base  = U.arrayBaseOffset(int[].class);      // 第 0 个元素的字节偏移（跳过对象头）
private static final int scale = U.arrayIndexScale(int[].class);      // 元素步长：int=4、long=8、引用=4/8（压缩指针）
private static final int shift = 31 - Integer.numberOfLeadingZeros(scale); // 4 → 2：乘法变移位

private long byteOffset(int i) { return ((long) i << shift) + base; }      // 元素 i 的真实字节地址

public final int get(int i) { return U.getIntVolatile(array, byteOffset(i)); } // 元素级 volatile 读
public final boolean compareAndSet(int i, int expect, int update) {
    return U.compareAndSetInt(array, byteOffset(i), expect, update);           // CAS 打到元素 i 上
}

AtomicIntegerArray arr = new AtomicIntegerArray(10);
arr.compareAndSet(3, 0, 1);          // 只对下标 3 原子；对下标 5 的 CAS 与它毫无关系
  • AtomicReferenceArray 完全同构：scale = 引用宽度（压缩指针 4 字节 / 未压缩 8 字节），CAS 换成比引用版——== 语义、不比 equals（同 §08 陷阱）。
  • 原子性边界 = 单个下标：swap(i, j)、"读两元素算和再写回"这类跨元素复合操作不原子，需要加锁；也不能扩容（Java 数组定长 + array 是 final 引用）。
  • 热点下标别用它：并发挤同一个下标 = 退化成单点 CAS，纯累加统计换 LongAdder（下一节）。

面试口径：说"AtomicIntegerArray 保证数组原子"是错的——它不保证数组整体，只保证每个元素的单次读-改-写。变长、跨元素一致性都不是它的职责：变长换 CopyOnWriteArrayList / AtomicReference<Queue>，跨元素一致性加锁。它和字段更新器（反射改任意对象字段）是两条平行路线。

07LongAdder vs AtomicLong ⭐

AtomicLong 的瓶颈：单点 CAS

AtomicLong.incrementAndGet() 让所有线程挤同一个 value 做 CAS：同一时刻只有一个线程成功，其余全部失败自旋重来；这个 value 所在的缓存行还在多核之间反复失效/同步（缓存行弹跳）——竞争越烈，CPU 越多是在给缓存一致性协议打工。

LongAdder：热点分离（Striping）

LongAdder 内部结构：base + Cell[]，把一个热点拆成多个冷点

  ┌──────────┐   无竞争时：只 CAS base
  │ base(64b)│ ←──────────────
  └──────────┘
  ┌────┬────┬────┬────┐   有竞争时：线程按 hash 散列到不同 cell
  │c[0]│c[1]│c[2]│c[3]│   各自累加自己的 —— 各改各的缓存行，互不失效
  └────┴────┴────┴────┘
  sum() = base + c[0] + c[1] + ...     ← 读取时才汇总
LongAdder adder = new LongAdder();
adder.increment();             // 无竞争落在 base；有竞争散列到某个 cell
adder.add(42);
long total = adder.sum();      // base + Σ cells —— 弱一致：求和瞬间别人可能还在写

// 对照：AtomicLong 所有人挤一个 value
AtomicLong al = new AtomicLong();
al.incrementAndGet();          // 单点 CAS：高并发下大量失败自旋 + 缓存行弹跳

// LongAccumulator：LongAdder 的泛化 —— 累加函数和初值可自定义（如求 max）
LongAccumulator max = new LongAccumulator(Long::max, Long.MIN_VALUE);
max.accumulate(latencyMs);
  • 弱一致是关键词：sum() 不加锁、不在同一瞬间冻结所有 cell，得到的是非精确瞬时值（求和过程中别的线程还在改）。低并发下 LongAdder 与 AtomicLong 性能相近；高并发写场景 LongAdder 明显更好——空间换时间（Cell[] 就是拿内存买吞吐）。
  • 代价：没有"当前精确值"语义（sum 是近似快照）、只有 add 没有 CAS 语义、内存占用大。

源码追问：add() 的完整路径（pdai 原子类篇补全）⭐

被追"LongAdder 内部怎么决定写哪"时，答得出三段路径就是源码级：

public void add(long x) {
    Cell[] as; long b, v; int m; Cell a;
    if ((as = cells) != null || !casBase(b = base, b + x)) {  // ① 无竞争：直接 CAS base
        longAccumulate(x, null, uncontended);                 // ② base 上竞争失败 → 进 longAccumulate
    }
}
// longAccumulate 干的三件事：
//   a. cells 还没建      → 初始化（容量 2，之后逐步翻倍）
//   b. 用线程的 probe（hash 种子）定位 cell[m & probe]，对该 cell 做累加 CAS；
//      失败说明这个槽位也在竞争 → 换槽（对 probe 重新 hash）再试
//   c. 持续失败且未到上限 → 扩容 cells（n << 1，上限 = 最接近 CPU 核数的 2 的幂）
//   扩到上限还在竞争：不再扩，靠换槽自旋硬扛 —— 热点已分到"每核一格"，物理极限

把"热点分离"讲到这段的层次感：base 是第一层（绝大多数低竞争场景在这一层就结束，Cells 根本不创建，LongAdder 并不比 AtomicLong 费多少内存）；Cell[] 是第二层，只在真实竞争出现后才逐步升级——惰性分摊，和 synchronized 的锁升级是同一个设计哲学。

伪共享与 @Contended（追问深水区）

  • 缓存行（Cache Line，通常 64 字节）是缓存一致性的最小单位：两个不相干的变量落在同一缓存行时，核 A 改其一，核 B 上整行失效——B 访问另一个变量也得重新加载。明明没有共享变量却互相拖累，这就是伪共享（False Sharing）；Cell[] 相邻元素若挤在同一行，"热点分离"直接白做。
  • 解法：Cell 类标注 @Contended，JVM 在其前后填充（padding），保证每个 cell 独占一个缓存行——JDK 内部类默认生效；自己的代码要用 @Contended 需要 -XX:-RestrictContended。
维度AtomicLongLongAdder
原理单 value 点 CASbase + Cell[] 分散累加，读时求和
高并发写性能差（自旋 + 缓存行弹跳）好（热点分离 + @Contended）
读取语义精确瞬时值弱一致（近似快照）
内存一个 longCell[] 数组（空间换时间）
典型场景限流阈值判断、需要精确比较的计数QPS/监控打点等纯累加统计

选型口径（背下来）："要拿这个数做判断（限流阈值、配额剩余）用 AtomicLong——必须精确；只是统计上报（QPS、打点计数）用 LongAdder——高并发下快一个数量级。"这句答完，LongAdder 这道题就闭环了。

08高频追问与陷阱

  • 追问链：CAS 原子性谁保证的 →→ CPU 指令（x86 lock cmpxchg / ARM LL-SC），JVM 只是经 Unsafe 调用；lock 前缀现代实现是缓存锁定而非总线锁。
  • 追问链：换 LongAdder 一定更快吗 →→ 不。低并发下无优势还多耗内存；需要 sum() 精确语义（阈值判断）的场景根本不能换。
  • 追问链：AtomicBoolean 怎么存布尔 →→ 内部 int（0/1），没有 AtomicDouble——用 DoubleAdder 或 AtomicReference<Double>。
  • 陷阱：get() 和 set() 组合不是原子→ atomic.set(atomic.get() + 1) 两个原子方法的组合仍然有缝，必须用 getAndAdd / compareAndSet 这类复合原子方法。
  • 陷阱：AtomicReference 的 CAS 比引用不比 equals→ 两个"内容相等"的新对象不是同一个引用，CAS 永远失败——每次都要基于 get() 拿到的原对象做期望值。
  • 追问链：AtomicIntegerArray 能"两个元素一起原子换"吗 →→ 不能，CAS 边界是单个下标，跨元素复合操作加锁；顺带补两句：不能扩容（数组定长）、热点下标退化成单点 CAS 该换 LongAdder。
  • 陷阱：数据库乐观锁更新失败不重试→ WHERE version = ? 影响行数为 0 就当成功返回，等于静默丢更新（第 04 章SQL 版 CAS）。
  • 陷阱：拿 LongAdder.sum() 做限流→ 弱一致读 + 求和期间仍在累加，可能短暂放行超额；精确阈值用 AtomicLong。
  • 陷阱：ABA 只在面试题里出现？→ 无锁数据结构、对象池/Netty 内存池的"弹出到复用"才是真实事故现场；说清"为什么 JVM 普通业务代码少感知（GC 兜底）"是亮点。
  • 追问链：LongAdder 的 Cell[] 会无限扩吗？→ 不会，上限 = 最接近 CPU 核数的 2 的幂；到顶后仍竞争就换槽（rehash probe）自旋硬扛——热点分到"每核一格"已是物理极限（第 07 节源码路径）。

09面试自查清单

  1. 能写出 CAS(V, E, N) 的语义，说清"比较 + 交换"是一条 CPU 原子指令、原子性来自硬件。
  2. 知道 x86 是 lock cmpxchg、ARM 是 LL/SC；能讲缓存锁定相对总线锁的进步（锁粒度从总线缩到缓存行）。
  3. 能默写 AtomicInteger.getAndIncrement → Unsafe.getAndAddInt 的 do-while 自旋结构，并解释 value 为什么是 volatile。
  4. 能用"无锁栈弹出到复用"讲清 ABA 的危害场景，说出 Stamped（版本号）/Markable（布尔）两种解法与 DB version 字段的同构关系。
  5. CAS 三大局限（自旋开销 / 单变量 / ABA）张口就来，多变量问题能给 AtomicReference 包不可变对象的解法。
  6. Atomic 家族五类（基本 / 引用 / 数组 / 字段更新器 / 累加器）能报全，知道 FieldUpdater 反射慢、基本被弃用。
  7. 能讲清 AtomicIntegerArray 元素级原理：arrayBaseOffset + 下标×步长定位字节地址、内部普通数组靠 getIntVolatile 补 volatile、原子性边界 = 单个下标（swap 要加锁、不能扩容）。
  8. 能画 LongAdder 的 base + Cell[] 结构，解释 sum() 弱一致与空间换时间。
  9. 能解释伪共享：64B 缓存行、核间失效传导、@Contended 填充独占缓存行。
  10. 选型口径一句话：精确判断用 AtomicLong，高并发统计用 LongAdder，LongAccumulator 是它的泛化。
  11. LongAdder 能讲到源码路径：casBase → longAccumulate → probe 散列定位 cell / 换槽重试 / 扩容上限（≈CPU 核数），以及"base → Cells 惰性升级"与锁升级的同构。
