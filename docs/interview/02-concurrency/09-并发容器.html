02ConcurrentHashMap：并发使用视角 ⭐

⚠️ 去重约定：putVal 的 CAS + synchronized、树化阈值 8、sizeCtl、CounterCell 计数等源码细节已在 01-java/08 集合框架完整拆解（含 JDK 7 分段锁 → JDK 8 CAS + synchronized 的演进），本章不重复——只讲面试更常考的"并发使用视角"：复合操作、迭代器、null、缓存场景。

复合操作原子性：putIfAbsent / computeIfAbsent / merge ⭐

第 01 章讲过 check-then-act 不原子——在容器上最典型的形态就是"先查后放"：

ConcurrentHashMap<String, Integer> counter = new ConcurrentHashMap<>();

// ❌ 先查后放：containsKey 和 put 两步之间，别的线程可能已经 put 了 —— 竞态
if (!counter.containsKey("uv")) counter.put("uv", 1);

// ✅ 原子复合操作：判断与写入在一个锁定范围内一步完成
counter.putIfAbsent("uv", 1);                       // 不存在才放；返回旧值可判断是否真的放进去了
counter.computeIfAbsent("uv", k -> loadFromDb(k));    // ⭐ 不存在才"计算 + 放入"，计算期间锁住该桶
counter.merge("uv", 1, Integer::sum);                // ⭐ 计数聚合最惯用：存在则按函数合并，不存在则放入
counter.compute("uv", (k, v) -> v == null ? 1 : v + 1);  // 新旧值都要参与时用
方法语义典型用途
putIfAbsent(k, v)没有才放（v 是现成的值）注册表：已存在就保留旧的
computeIfAbsent(k, fn)没有才计算并放入⭐ 惰性初始化、嵌套 map、本地缓存（见下）
merge(k, v, fn)没有就放 v，有就用 fn 合并旧值与 v⭐ 计数/求和聚合，一行顶四行
compute(k, fn)读写都基于旧值做函数需要"看旧值再决定"的更新
操作类别并发安全吗说明
单个 get / put / remove✅ 原子CAS + synchronized 保证的桶级原子性（链 01-java/08）
size / contains / 迭代⚠️ 弱一致不是"坏了"，是估计值 / 某一刻的快照
get + 判断 + put 的组合❌ 竞态两步之间 map 可能被改——必须换成上面的复合操作

putIfAbsent 的返回值别浪费：它返回"实际存进去的值"——已存在就返回旧值，不存在返回你传入的新值。因此 V prev = map.putIfAbsent(k, v) 一次调用就能知道"是不是我放进去的"，常用来实现"只有一个线程能注册成功"的语义。

弱一致迭代器

for (String k : counter.keySet()) {    // 弱一致（weakly consistent）迭代器
    process(k);                        // 遍历期间别的线程 put/remove：不抛 CME
}                                      // 但不保证看到迭代开始后的最新修改
  • 与 HashMap 对比：HashMap 迭代中修改会抛 ConcurrentModificationException（fail-fast）；CHM 的迭代器是弱一致 fail-safe：不抛异常，但反映的是"某一刻"的状态，之后的写入可能看不到。
  • CHM 迭代器支持 remove()（注意与 CopyOnWriteArrayList 迭代器不支持 remove 对比——后面第 04 节）。
  • 口径：弱一致不是缺陷而是设计——强一致迭代需要全局锁，与高并发读写的设计目标矛盾。

size() 与 mappingCount()：弱一致的估计值

long approx = counter.mappingCount();   // 大 map 用它：返回 long，语义同为"估计值"
int  maybe = counter.size();            // int 版；并发下两者都只是"接近真值"

并发下的 size() 是估计值（各桶/计数单元的瞬时不完全统计，CounterCell 分散计数就是为了不让计数成为热点，细节链 01-java/08）；大 map 用返回 long 的 mappingCount()。结论口径：别用 CHM 的 size 做精确的业务判断（比如"队列满没满"），它只适合监控展示。

为什么 key 和 value 都不许 null ⭐

  • 核心：并发下 null 有二义。get(k) 返回 null，无法区分"key 不存在"还是"key 存在但值就是 null"。
  • 追问"HashMap 不是可以用 containsKey 再查一次吗"：单线程可以，并发不行——get 和 containsKey 两次调用之间 map 可能已被别的线程改掉，二次确认本身又是 check-then-act 竞态。与其留一个用不对的口子，不如直接禁止。
  • HashMap 允许一个 null key（hash 定位到 0 号桶的特殊处理）；CHM 里 null key 同理被禁。

用做本地缓存与缓存击穿防护 ⭐

// computeIfAbsent 天然防缓存击穿：同 key 的并发请求只有一次真正回源
ConcurrentHashMap<String, Product> cache = new ConcurrentHashMap<>();
Product p = cache.computeIfAbsent(sku, this::loadFromDb);   // 相同 sku 的并发线程等这一次计算完成

// 计算很重时：值放 Future，把计算丢进线程池，阻塞范围缩到最小
ConcurrentHashMap<String, CompletableFuture<Product>> cache2 = new ConcurrentHashMap<>();
cache2.computeIfAbsent(sku, k -> CompletableFuture.supplyAsync(() -> loadFromDb(k), pool))
     .thenAccept(this::render);    // 防重复回源，又不长时间占住桶锁
  • 缓存击穿：热点 key 过期瞬间大量请求同时回源打垮 DB。computeIfAbsent 是 JVM 内的 single-flight——同 key 并发只算一次，其余线程等结果。
  • 返回 Future 的意义：computeIfAbsent 的计算期间锁住桶，如果计算本身很慢（回源 DB 几百毫秒），会阻塞落在同一个桶上的其他 key——把计算塞进 CompletableFuture，computeIfAbsent 里只是"放个 Future"（微秒级），重活异步跑。

陷阱：computeIfAbsent 的函数里不能再改同一个 map——递归更新会在 JDK 9+ 抛 IllegalStateException: Recursive update，即便不抛也可能自锁。函数要求：纯计算、要快、不碰容器本身。

03BlockingQueue 家族 ⭐

定位：队列 + "满时写阻塞、空时读阻塞"——正是 第 08 章 生产者-消费者模式的标准载体。面试考两件事：四组 API 的行为差异 + 各实现的结构取舍。

四组 API（背熟 ⭐）

组入队出队查看队首失败行为
抛异常add(e)remove()element()队满/队空抛 IllegalStateException
返回特殊值offer(e)poll()peek()立即返回 false / null，不等待
阻塞put(e)take()—阻塞直到成功（可被中断）
超时offer(e, t, unit)poll(t, unit)—阻塞至多 t，超时返回 false / null

选组口径：生产代码默认 put/take（满则背压、空则等待，语义最清晰）；要"满了就丢弃/降级/记日志"的策略用返回特殊值组；add/remove 基本只在测试和"违反约定就该炸"的场景用；等待要有上限（怕对端挂掉）用超时组。

// 生产模板：有界队列 + 满则背压 + 消费侧带超时
BlockingQueue<Event> queue = new ArrayBlockingQueue<>(500);

queue.put(event);                              // 队列满：生产者阻塞 —— 天然背压（backpressure）
Event e = queue.poll(2, TimeUnit.SECONDS);     // 队列空：最多等 2 秒，返回 null 可做健康检查/优雅退出

六个实现：结构、锁、容量的取舍

1. ArrayBlockingQueue —— 单锁双条件，有界

  • 底层环形数组 + 一把 ReentrantLock + 两个 Condition（notEmpty / notFull）：put 在 notFull 上等待，take 在 notEmpty 上等待；入队唤醒 notEmpty，出队唤醒 notFull。
  • 有界，构造必须传容量；数组预分配、无每元素结点 GC，内存紧凑行为可预测。
  • 代价：put 和 take 共用一把锁互相排斥——同一时刻生产和消费只能有一个在动。

2. LinkedBlockingQueue —— 两把锁分离，⚠️ 默认无界陷阱

  • 底层单向链表，两把 ReentrantLock（putLock / takeLock）分离：生产和消费各锁各的（用原子 count 协调满/空判断）——生产者与消费者可真正并行，吞吐高于 ArrayBlockingQueue。
  • ⚠️ 默认容量 Integer.MAX_VALUE ≈ 无界：生产快消费慢时队列无限堆积直至 OOM。更危险的是 Executors.newFixedThreadPool / newSingleThreadExecutor 用的就是无参 LinkedBlockingQueue——这是阿里规约"不许用 Executors 创建线程池"的直接原因，案例展开见 第 06 章 线程池。
  • 正确姿势：永远显式给容量 new LinkedBlockingQueue<>(1000)，把背压留在自己手里。

3. SynchronousQueue —— 零容量直接交接

  • 没有容量，不存元素：每个 put 必须等待一个 take，元素在两个线程手里直接交接（类似 Exchanger 的单向版）。
  • offer(e) 此刻没有消费者等着就立即返回 false——Executors.newCachedThreadPool 正是借这个语义判断"没空闲线程就新建线程"，展开链 第 06 章。
  • 适合"任务不该排队、要么立刻被接手要么触发扩容/拒绝"的直通场景。

4. PriorityBlockingQueue —— 二叉堆，无界

  • 无界阻塞队列，内部二叉堆（小顶堆）存储，take 每次取出优先级最高的元素；元素必须实现 Comparable 或构造时传 Comparator。
  • 两个坑：① 无界——入队永不阻塞（put 等价 offer），堆积风险自己兜；② 堆只保证堆首最小，遍历不全局有序——要有序输出得 drain 出来排序。

5. DelayQueue —— 延时取

  • 元素实现 Delayed（getDelay 剩余延时）；take 阻塞直到队首元素到期，未到期就算队列非空也取不到——本质是 PriorityBlockingQueue（按到期时间排序）+ 延时等待（leader/follower 模式减少无效定时唤醒）。
  • 场景：订单超时未支付自动关闭、失败重试的退避排队、本地延时任务。与 Redis ZSet / 时间轮的选型对比在 第 13 章 并发设计题（延时队列设计）。
class DelayedTask implements Delayed {                 // 入队元素要实现 Delayed
    private final long deadline = System.currentTimeMillis() + delayMs;

    public long getDelay(TimeUnit u) {                 // 剩余等待时间 —— 到 0 才可被 take
        return u.convert(deadline - System.currentTimeMillis(), TimeUnit.MILLISECONDS);
    }
    public int compareTo(Delayed o) { /* 按 deadline 比大小 */ return 0; }
}

delayQueue.put(new DelayedTask(30_000));   // 30 秒后到期
delayQueue.take();                         // 队首未到期就阻塞，到点自动醒来 —— 不需要定时器轮询

6. LinkedTransferQueue —— 直接交付（一句）

  • 无锁（CAS）链表结构，兼有 LinkedBlockingQueue 的容量语义与 SynchronousQueue 的交接语义：除了 put/offer 还有 transfer(e)——阻塞直到消费者直接取走这个元素（不进队列）。需要"生产者必须确认消费者已拿到"的消息语义时用它，一般了解即可。
实现结构容量锁策略一句话场景
ArrayBlockingQueue环形数组有界（必传）单锁 + notEmpty/notFull内存紧凑、行为可预测的有界队列
LinkedBlockingQueue单向链表默认 MAX_VALUE ⚠️put/take 两把锁高吞吐，但必须显式设容量
SynchronousQueue无0（直接交接）CAS + 队列不排队、直接交接（cachedThreadPool）
PriorityBlockingQueue二叉堆无界单锁按优先级出队
DelayQueue堆（按到期时间）无界单锁 + leader/follower延时任务（超时关单、重试退避）
LinkedTransferQueue链表无界（可预占）无锁 CAStransfer 直接交付语义
  • Array 还是 Linked？要"行为完全可预测、内存紧凑"（嵌入式/低 GC 敏感）选 Array；要"生产消费并行的高吞吐"选 Linked，但容量必须显式给——默认无界是事故不是特性。
  • 背压视角：有界队列 + put = 满了让生产者慢下来；无界队列 = 把过载延迟成 OOM——前者是即时疼痛，后者是半夜告警。
  • JDK 7 起还有 LinkedTransferQueue 一个"全家桶"选项：既当普通队列又当交接队列，多数场景它是 LinkedBlockingQueue 的等价替代，但面试记住前六个的名字和差异就够用。

旁支：非阻塞的 ConcurrentLinkedQueue

BlockingQueue 全家靠"锁 + 条件等待"实现阻塞语义；ConcurrentLinkedQueue（CLQ）走另一条路：CAS 无锁链表（Michael-Scott 无锁队列算法）——入队出队都是 CAS 自旋，不阻塞、不挂起，也没有容量概念。JavaGuide 常这么问："ConcurrentLinkedQueue 是 BlockingQueue 吗？"

  • 两族的分界：要"满了背压、空了等待"的协调语义 → BlockingQueue；只要一个线程安全队列、节奏由调用方自己管（配合自己的限流/自旋消费）→ CLQ。
  • size() 是 O(n)：没有计数器字段（维护精确计数会重新制造 CAS 热点），每次 size 都遍历整条链，并发下仍是估计值——高频调 size 是性能事故。
  • 不允许 null：与 CHM 同理——poll 返回 null 是"队空"的约定信号，存 null 就无法区分"空"和"值是 null"。
  • 迭代器弱一致不抛 CME；JDK 7 起的 ConcurrentLinkedDeque 是它的双端版本。

04CopyOnWriteArrayList：写时复制

模型：读操作完全无锁；写操作加锁后复制整个数组、改副本、把 volatile 引用指向新数组。任何时刻读到的都是某一版本的不可变快照，天然线程安全。

// 写：lock -> 复制整个数组 -> 改副本 -> 引用换新（volatile 保证立即可见）
private transient volatile Object[] array;

// 读：不加任何锁，直接遍历当前引用指向的数组快照
for (Listener l : listeners) { l.onEvent(e); }
  • 适合：读极多、写极少的场景——监听器/订阅者列表（注册一次，广播千万次）、配置白名单、灰度开关、路由表。读写比越高，"读零开销"摊薄写成本越划算。
// 监听器列表：注册/注销一天没几次，广播每秒上万次 —— COW 的教科书场景
private final List<Listener> listeners = new CopyOnWriteArrayList<>();

void register(Listener l) { listeners.add(l); }      // O(n) 复制——无所谓，极少发生
void fire(Event e) {
    for (Listener l : listeners) l.onEvent(e);       // 无锁广播；迭代中有人注销也不抛异常
}
  • 三个代价 ⚠️：① 写是 O(n) 全量复制，写频繁 = 内存和 CPU 双重灾难；② 复制瞬间新旧两个数组并存，内存翻倍（还制造大量 GC 垃圾）；③ 迭代器是创建那一刻的快照——弱一致（之后的写看不到），且 iterator.remove() 直接抛 UnsupportedOperationException（快照改不动）。
  • 对比：要"迭代时抛异常"的强一致没有，要"读写都多"该用 ConcurrentHashMap（当 set 用 keySet）或 Collections.synchronizedList（全表锁，读写都排队）。
  • COW 的思想：读写分离 + 最终一致——不锁读者，用"版本切换"让读者看旧版、写者造新版。这个思想在 Linux fork、Redis RDB 持久化、Git 分支里反复出现，CHM 与 COW 的完整源码级对比在 01-java/08 集合框架。
  • CopyOnWriteArraySet 一句：底层就是 COWArrayList，add 要 O(n) 扫描查重——只适合小集合（比如监听器去重）。

读多写少场景的四方案对比

方案读写迭代中修改适用
CopyOnWriteArrayList无锁锁 + O(n) 复制不抛异常（快照）读极多写极少
Collections.synchronizedList全表锁全表锁迭代需手动包 synchronized，否则 CME低并发通用
ConcurrentHashMap.newKeySet()桶级无锁桶级锁弱一致不抛异常读写都多、当 set 用
ReadWriteLock + ArrayList读锁（仍有开销）写锁需自己控制读多写不算少、要强一致

05ThreadLocal ⭐⭐

定位：不是同步，是"以空间换隔离"

ThreadLocal 不是用来解决共享变量竞争的，它是从根上避开共享：每个线程一份独立副本，线程内随手可得、线程间互不可见——把"共享 + 同步"的问题转化成"每线程私有 + 隔离"的问题。代价是每线程一份内存（空间），换来的是读写的零竞争。

开场口径：先纠正一句"ThreadLocal 不是同步工具，是隔离工具"——很多面试者上来就答"解决线程安全"，方向就错了；先定性再展开，这道题的起点分就拿满了。

  • currentUser 上下文（笔记原始场景）：网关/过滤器里 set 登录用户，后续 controller、service、mapper 深层调用随手 get，不用层层传参。
  • SimpleDateFormat：它线程不安全（Calendar 字段共享），new 又贵——每线程持有一个实例，或干脆换不可变的 DateTimeFormatter（见第 07 节追问）。
  • traceId 全链路追踪：日志框架 MDC 的底层就是一个 ThreadLocalMap；Spring 事务把 Connection 绑定到线程（TransactionSynchronizationManager）也是——框架视角链 04-spring。
// SimpleDateFormat 线程不安全的经典止血：每线程一个实例（withInitial 是 JDK8 起的便捷写法）
private static final ThreadLocal<SimpleDateFormat> SDF =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd HH:mm:ss"));

SDF.get().format(new Date());      // 线程内随手用，无竞争；新代码请直接换 DateTimeFormatter（见追问）
private static final ThreadLocal<UserContext> CTX = new ThreadLocal<>();   // ⭐ 推荐 static final

CTX.set(currentUser);       // 过滤器入口
UserContext uc = CTX.get(); // 调用链任意深处
CTX.remove();               // 出口清理（后面细讲为什么必须）

底层：数据不在 ThreadLocal 里，在每个 Thread 身上

  • 每个 Thread 对象里有一个字段 ThreadLocal.ThreadLocalMap threadLocals——set 时以 ThreadLocal 实例为 key、值为 value，存进当前线程自己的这个 map；get 也是从当前线程身上取。所以同一份 ThreadLocal 在 100 个线程里各有独立的一条记录。
  • 这个设计解释了两件事：线程结束 → map 随线程对象一起回收（数据自然消亡）；线程被池复用 → map 长存（数据残留，泄漏温床）。
// ThreadLocal.set 的真实路径（源码示意）—— 三个 this/Thread 的指向要看清
public void set(T value) {
    Thread t = Thread.currentThread();            // ① 拿当前线程
    ThreadLocalMap map = t.threadLocals;          // ② map 是线程身上的字段，不是 ThreadLocal 的
    if (map != null) map.set(this, value);        // ③ 以 ThreadLocal 实例（this）为 key 存入
    else t.threadLocals = createMap(this, value);
}
// get / remove 同理：Thread.currentThread() -> threadLocals -> 以 this 为 key 定位 Entry

纠错（面试高频错答）：ThreadLocalMap 不是 HashMap。它是数组 + 开放定址（线性探测）：hash 冲突不拉链表，而是向后找下一个空槽位；HashMap 用的是链地址法（数组 + 链表，长链转红黑树）。另外散列也不一样：每个 ThreadLocal 实例持有 threadLocalHashCode，从随机初始值起、每 new 一个自增 0x61c88647（黄金分割增量）——让相邻实例均匀散布在 2 的幂长度的数组上，配合开放定址减少堆积。

Entry 源码：key 弱引用、value 强引用（笔记原码）

static class Entry extends WeakReference<ThreadLocal<?>> {   // Entry 本身就是一个弱引用
    Object value;

    Entry(ThreadLocal<?> k, Object v) {
        super(k);  // 将 key 作为弱引用，注意super方法
        value = v; // value 是强引用
    }
}
  • WeakReference 语义（笔记 471-475）：弱引用不阻止 GC——一旦 ThreadLocal 实例的外部强引用断开，下次 GC 时实例被回收，此后 weakRef.get() 返回 null。
  • 所以每个 Entry 里：key（ThreadLocal 实例）是弱引用，value 是强引用——这个不对称就是内存泄漏问题的全部来源。

为什么 key 用弱引用

  • 反证：若 key 是强引用——外部对 ThreadLocal 的引用没了（局部变量出栈、静态字段被置换），但 Entry 还强引用着它，这个 ThreadLocal 实例只要线程活着就永远回收不了（key 泄漏，连带它的 Class 元数据）。
  • 用了弱引用：外部引用一断，key 就可被 GC；死掉的 Entry 变成 key == null 的 stale entry——它成了"待清理"的标记（探测式清理的依据，见下）。
  • 口径：弱引用是"自救"，不是泄漏的原因。把泄漏归咎于弱引用是这道题最常见的反向答案。

内存泄漏链条 ⭐（画得出这张图就是满分）

GC Root（线程池的 worker 长存不销毁）
  └─ Thread
       └─ threadLocals (ThreadLocalMap)        ← Map 挂在线程身上
            └─ Entry[]
                 └─ Entry
                      ├─ key   --弱引用--> ThreadLocal 实例    外部引用断开后，下次 GC 即回收 ✅
                      └─ value --强引用--> 大对象              key 死了它还活着 ⚠️ 泄漏点
  • 链条：线程池线程长存 → Thread → ThreadLocalMap → Entry → value 这条强引用链不断 → value 虽然再也没有代码能访问到（key 已死，get 定位不到它），GC 却回收不掉——典型内存泄漏。
  • 弱引用只救了 key，没救 value（笔记 490-492 的要点）：key 能被回收恰恰是因为弱引用；value 是强引用，没人 remove 就一直挂着。
  • JDK 的自救（不可靠）：set / get / remove 走到 stale entry（key == null）附近时，会顺手触发 expungeStaleEntry 把 value 置 null、清理死 Entry（插入新元素时还有启发式的 cleanSomeSlots 小步扫描）——但探测式清理只发生在"之后还有线程调同一个 map 的 set/get/remove"且"恰好扫到邻近槽位"时。线程归还池后若再没人 set/get，清理永远不会发生（笔记 493：线程复用，ThreadLocalMap 不会自动销毁）。
  • 结论（背这句）：泄漏的根因是"长存线程 + value 强引用 + 忘记 remove"三者叠加，弱引用只是缓解了 key 那一半——所以必须手动 remove。

最佳实践：try-finally 中 remove（笔记 495）

try {
    CTX.set(currentUser);
    // ... 整条调用链随取随用 CTX.get()
} finally {
    CTX.remove();   // ⭐ 线程池场景必须：切断 value 的强引用，同时清掉残留状态
}
  • 线程池场景 remove 不是"可选的优化"而是必须：除了泄漏，还有更凶的"串号"业务事故——忘了 remove，下一个复用该线程的请求会 get 到上一个请求的用户上下文，等于拿别人的身份做事（数据越权级故障）。
  • 定义处用 private static final：类级一份 ThreadLocal；写成实例字段则每个对象一个 ThreadLocal，白白占用数组槽位还增加泄漏面。

常见误用清单（自查）：① 定义成实例字段而非 private static final；② remove 不放 finally——异常路径必漏清理；③ 往上下文里塞大对象/大集合——泄漏时损失按线程数放大；④ 指望"线程结束自动回收"——线程池里线程几乎不结束；⑤ 拿 ThreadLocal 存数据库连接做事务——Spring 事务管理已经替你绑定了，重复造轮子还容易和事务边界打架。

06InheritableThreadLocal 与 TTL

父传子：创建子线程时拷贝

InheritableThreadLocal<String> ctx = new InheritableThreadLocal<>();
ctx.set("trace-001");
new Thread(() -> log(ctx.get())).start();   // 创建子线程时（Thread 构造里）拷贝父线程的值 → "trace-001"
  • 机制：Thread 初始化时把父线程的 inheritableThreadLocals 拷贝给子线程（注意是拷贝引用——value 若是可变对象，父子改的是同一个，这也是坑）。
  • 它只解决"每次 new Thread"的老代码；线程池下基本必翻车。
  • 典型可用场景一句话：main 线程解析好的配置/用户身份，随 new Thread 传给子线程可见——注意是"创建时快照"，之后父线程再改，子线程看不到。

坑：线程池复用破坏传递 ⭐

// worker 线程在池初始化时就创建了，拷贝的是"当年创建它时"那个父线程的值
pool.execute(() -> log(ctx.get()));   // 大概率是 null，或者 —— 更糟 —— 别人很久以前留下的 traceId
  • 原因：拷贝发生在 Thread 对象构造的那一刻，而任务提交时线程早就存在、被反复复用——上下文传的是"线程的历史"，不是"任务的当下"。污染（拿到别人的值）比丢失（null）更危险：日志串链路、串号事故。

解法：阿里 TransmittableThreadLocal（TTL）——生产实践加分点

TransmittableThreadLocal<String> ttl = new TransmittableThreadLocal<>();
Runnable task = TtlRunnable.get(() -> log(ttl.get()));   // 提交时 capture → 执行时 replay → 结束 restore
pool.submit(task);
  • TTL 把传递时机从"线程创建"挪到"任务提交"：包装 Runnable/Callable（或用 ttl-agent 字节码增强线程池类，业务零侵入），提交时快照（capture）当前父线程上下文，任务执行前回放（replay）覆盖到 worker 线程，执行完还原（restore）——既传对了值，又不污染后续任务。
  • 配套 TtlExecutors.getTtlExecutorService(pool) 包装整个池；这是链路追踪、异步上下文框架（以及多数公司的内部 starter）的标准做法。

四种"线程上下文"方案横向对比（总结背诵）

方案传递语义线程池安全一句话
ThreadLocal线程内隔离，不传递✅（须 remove）默认答案，配 try-finally
InheritableThreadLocal创建子线程时拷贝一次❌ 复用即失效/串值只适合每次 new Thread 的老代码
TransmittableThreadLocal任务提交时快照回放✅capture/replay/restore，生产正解
ScopedValue（JDK 21+）作用域绑定，不可变✅（绑定随结构化并发走）虚拟线程时代替代 ThreadLocal

虚拟线程时代的答案（一句）：百万级虚拟线程时，"每线程一份副本"的 ThreadLocal 内存与克隆成本被急剧放大，JDK 21+ 给出 ScopedValue——不可变、绑定作用域、用完自动失效，不需要 remove——完整对比见 第 10 章 虚拟线程。

07高频追问与陷阱

  • 追问链（ThreadLocal 标准四连，背熟）：原理（Thread 身上的 ThreadLocalMap）→ 为什么 key 弱引用（防 key 泄漏的自救）→ 那为什么还会泄漏（value 是强引用，链路 Thread→Map→Entry→value 不断）→ 怎么办（try-finally remove，线程池必须，还有串号风险）。一环扣一环，答断任何一环都会被追到底。
  • 追问链：ThreadLocalMap 是 HashMap 吗 → 不是：开放定址（线性探测）vs 链地址法；hash 用 0x61c88647 黄金分割增量。答"就是 HashMap"基本宣告这题报废。
  • 追问链：CHM 为什么不许 null → HashMap 为什么可以 → 并发下 get 返回 null 有二义；单线程可用 containsKey 二次确认，并发下二次确认本身又是竞态。
  • 追问：遍历 CHM 时别的线程 put → 不抛 CME（弱一致迭代器），但可能看不到新值；size() 也只是弱一致估计。
  • 陷阱：computeIfAbsent 里做重活/递归改 map → 慢计算长时间占桶锁、递归更新抛 IllegalStateException；重计算用"存 Future"的变体。
  • 陷阱：new LinkedBlockingQueue() 不传容量 → 默认 Integer.MAX_VALUE 无界，生产慢时任务堆积 OOM；newFixedThreadPool 的事故就是这个（链第 06 章）。
  • 陷阱：SynchronousQueue 的 offer 立即返回 false → 不是失败 bug，是 cachedThreadPool 判断"要不要扩线程"的依据；别拿 add 的异常语义去用它。
  • 陷阱：COW 迭代器上 remove → UnsupportedOperationException（快照不可变）；写频繁场景用 COW 是内存灾难。
  • 追问：SimpleDateFormat 现在还用 ThreadLocal 包吗 → 新代码直接换 DateTimeFormatter（不可变、线程安全，static 共享即可）；ThreadLocal 是给存量代码不安全不改逻辑的止血方案——能说出这层选型才算懂。
  • 追问：PriorityBlockingQueue 遍历有序吗 → 不。堆只保证堆首是当前最小/最大；要有序输出必须 drain 后排序。
  • 陷阱：把 BlockingQueue 当业务列表用 → remove(Object) / contains 都是 O(n) 且要锁全表——队列就是通道，不是存储；要检索就该用 CHM 或数据库。
  • 追问：ThreadLocalMap 会扩容吗 → 会：负载超过数组长度的 2/3 就 rehash 扩容一倍——又一条"set/get 顺手做的事"，也是清理时机之一；这个细节知道即可，别主动展开。
  • 追问：ConcurrentLinkedQueue 是 BlockingQueue 吗 → 不是：CAS 无锁队列（Michael-Scott），没有 put/take 的阻塞协调语义；要背压/等待必须上 BlockingQueue；它的 size() 是 O(n) 估计值、不允许 null。
  • 追问：InheritableThreadLocal 失效了怎么办 → TTL：capture/replay/restore 三步，agent 或 TtlRunnable 接入——能说到"提交时快照、执行时回放"就是生产级答案。

08面试自查清单

  1. CHM 复合操作四件套（putIfAbsent / computeIfAbsent / merge / compute）语义与场景张口就来，能写 merge 计数和 computeIfAbsent 缓存。
  2. 能论证 CHM 为什么 key/value 都不许 null（并发二义 + 二次确认竞态），并知道迭代器弱一致不抛 CME、size 是估计值。
  3. BlockingQueue 四组 API 表（抛异常/特殊值/阻塞/超时）+ 六个实现的结构、容量、锁差异；LinkedBlockingQueue 默认无界陷阱能讲成事故故事。
  4. 知道非阻塞旁支 ConcurrentLinkedQueue：CAS 无锁、size() 是 O(n) 估计值、不许 null，与 BlockingQueue 的语义分界。
  5. COW 三代价（写 O(n) 复制、内存翻倍、快照迭代器）与适用判据（读极多写极少）说得出，COW 思想能举一反三（读写分离 + 最终一致）。
  6. ThreadLocal：数据在每个 Thread 身上的 threadLocals，不是 ThreadLocal 里；ThreadLocalMap 是开放定址不是 HashMap，能说出 0x61c88647。
  7. Entry 源码背得出：key 弱引用（super(k)）、value 强引用；弱引用救 key 不救 value 的逻辑讲得清。
  8. 内存泄漏链条能画：长存线程 → Map → Entry → value；知道 expungeStaleEntry 只是不可靠的自救；最佳实践 static final + try-finally remove + "串号"事故。
  9. InheritableThreadLocal 池化失效的原因（拷贝在线程创建时）+ TTL 的 capture/replay/restore + ScopedValue 一句（链第 10 章）。
