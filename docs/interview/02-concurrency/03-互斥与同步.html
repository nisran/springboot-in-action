02synchronized：三种用法与锁对象

synchronized 是 Java 的内置锁（intrinsic lock / monitor lock），属于悲观锁（独占资源，多写场景；乐观锁/CAS 见 05 无锁编程，完整分类见 04 锁策略）。合并笔记 533-538 行：

用法锁对象互斥范围
① 修饰实例方法当前实例 this同一实例的所有实例方法互斥；不同实例之间不互斥
② 修饰静态方法类的 Class 对象（全局唯一）该类的所有实例、所有静态方法互斥（跨实例全局互斥）
③ 同步代码块synchronized(obj) 括号里指定的对象锁同一对象的代码块互斥；粒度最细，生产首选
public class SyncDemo {
    // ① 实例方法：锁 this
    public synchronized void m1() { /* ... */ }

    // ② 静态方法：锁 SyncDemo.class
    public static synchronized void m2() { /* ... */ }

    private final Object lock = new Object();

    // ③ 代码块：锁指定对象
    public void m3() {
        synchronized (this)             { /* 等价于① */ }
        synchronized (SyncDemo.class)   { /* 等价于② */ }
        synchronized (lock)             { /* 私有 final 锁对象：最可控 */ }
    }
}
  • 可重入：同一线程可以重复获取自己已持有的锁（monitor 计数 +1，退出 -1，归零才真释放）——锁方法里调用另一个同锁方法不会把自己锁死。
  • 陷阱：加了锁还是线程不安全→ 常见原因就是锁对象不一致：两个线程操作同一份数据，却分别走不同实例的实例方法（各锁各的 this）；或一个锁 this、一个锁 Class。
  • 陷阱：锁对象选错→ 用 String 字面量（常量池共享）、Integer.valueOf 小值缓存对象当锁，可能和别人代码锁到同一个对象，出现诡异互斥。
  • 陷阱：锁引用中途被换（final 的根因）→ monitor 按对象身份（==）分配、不看 equals——内容相等的两个对象就是两扇门。所以锁引用一旦被重新赋值，新旧线程各锁各的对象，互斥形同虚设；这就是锁必须 final 的根本原因。另：括号里只能是引用类型且非 null——synchronized(1) 编译不过（primitive 没有对象头、没有 monitor），传 null 运行时 NPE。
// 非 final 锁引用翻车：中途换门，互斥失效
private static Object lock = new Object();   // 坏写法：没 final

// 线程A：synchronized (lock) { i++ }   // 锁的是旧对象
lock = new Object();                     // 某处代码把引用换了
// 线程B：synchronized (lock) { i++ }   // 锁的是新对象
// → A、B 各持一把锁同时进临界区，i 照样错

实战口径：锁对象一律 private final Object lock = new Object()——不暴露（防止外部恶意锁）、不可变引用（防止重新赋值后锁失效，见上）。JDK 16+ 有更轻的 ReentrantLock 替代，但同步代码块仍是粒度控制首选。

03底层实现：字节码与 ObjectMonitor

两条实现路径

  • 同步代码块：编译为字节码 monitorenter / monitorexit 指令。进入时计数 +1，退出 -1；编译器会生成两个 monitorexit——正常路径一个、异常路径兜底一个，保证抛异常也能解锁（这就是 synchronized"自动释放锁"的真相）。
  • 同步方法：没有 monitorenter，而是在方法 flags 里置 ACC_SYNCHRONIZED 标志，JVM 调用方法时检查该标志，等价地做加锁/解锁。
public static void main(java.lang.String[]);
  Code:
     0: aload_0
     4: monitorenter          // 进入临界区，计数 +1
     5: ...（临界区代码）
    10: monitorexit           // 正常路径：计数 -1
    11: astore_2
    12: monitorexit           // 异常路径兜底再放一次 —— 保证异常时也解锁

ObjectMonitor：monitor 的真身（HotSpot C++ 实现）

字段作用线程状态
_owner当前持有 monitor 的线程RUNNABLE
_recursions重入计数—
_EntryList（含 _cxq 竞争队列）阻塞等锁的线程队列，解锁时从中唤醒BLOCKED
_WaitSet调了 wait() 的线程集合，被 notify 后移入 EntryList 重新竞争WAITING
  • 这套结构和 第 01 章的线程状态完全对上：抢锁失败进 EntryList 是 BLOCKED；wait 释放锁进 WaitSet 是 WAITING——jstack 里 waiting to lock vs in Object.wait() 就是在看这两个队列。
  • 为什么说它是"重量级"：EntryList 里的线程要用内核的互斥量（pthread mutex）挂起/唤醒，涉及用户态↔内核态切换和上下文切换——这条代价正是锁升级要优化的对象。

04对象头与锁升级 ⭐⭐

JDK 1.6 对 synchronized 做了大量优化，核心是锁升级（lock inflation/escalation）：按竞争强度从低到高换更便宜的实现（补全笔记 539-540 的 todo）。一切状态都记录在对象头的 Mark Word 里：

锁状态标志位Mark Word 存的内容（64 位 JVM）
无锁01（可偏向位=0）hashCode(31) + 分代年龄(4)
偏向锁01（可偏向位=1）线程 ID(54) + epoch(2)
轻量级锁00指向栈中 Lock Record 的指针
重量级锁10指向 ObjectMonitor 的指针
GC 标记11—
  • 为什么一个字段装得下所有状态：Mark Word 是对象自带的 8 字节元数据槽位，堆里对象以亿计、头开销按字节计较——各开字段吃不消，于是分时复用，靠末 2 位标志位判别当前含义（字段全貌与 JOL 实测见 03-jvm/03 对象与内存）。
  • GC 标记（11）不是锁：GC 运行期临时征用 Mark Word 存标记位/转发指针——"Mark Word" 名字里的 Mark 就源于 GC 标记用途。
无锁(01) --同一线程反复进入--> 偏向锁(101：Mark Word 记下线程 ID)
偏向锁 --第二个线程来竞争--> 轻量级锁(00：栈上 Lock Record + CAS 自旋)
轻量级锁 --自旋失败/竞争加剧--> 重量级锁(10：ObjectMonitor + 内核互斥量)
                       —— 只升不降，膨胀不可逆 ——

逐级拆解

  • 偏向锁（Biased Locking）：针对"锁总是被同一线程获取"的场景——第一次 CAS 把线程 ID 写进 Mark Word，之后该线程再进入连 CAS 都不用，直接放行。一旦有第二个线程竞争，偏向状态要撤销（revocation）：必须等所有线程到达全局安全点（safepoint）再检查持有线程是否存活、是否仍持锁——撤销代价大，是它后来被废弃的主因。
  • 轻量级锁：当前线程在栈帧里建一个 Lock Record，CAS 尝试把 Mark Word 换成指向它的指针（原 Mark Word 存进 Lock Record，解锁时换回）。CAS 成功就拿到锁；失败则自旋重试（自适应自旋：上次自旋成功过就多转一会儿）。自旋是"占着 CPU 空转等锁"，适合临界区极短的场景。
  • 重量级锁：自旋拿不到，膨胀为重量级锁——后续线程不再自旋，直接挂起进 ObjectMonitor 的 EntryList，靠内核互斥量唤醒。切换成本高但省 CPU，适合临界区长、竞争激烈的场景。

轻量级锁完整流程：加锁与解锁都是"换字"（CAS）

加锁：
  ① 当前栈帧压入一个 Lock Record（线程私有，不碰任何共享结构）
  ② Lock Record 留出 Displaced Mark Word 的坑位，对对象头做一次 CAS：
        Mark Word(01)  →  指向 Lock Record 的指针(00)
     √ 成功：持锁，进入临界区（成本 = 一次 CAS，纯用户态）
     × 失败：说明有人持有 → 自旋重试（见下）→ 反复失败 → 膨胀(10)
解锁：
  ① CAS 把 Displaced Mark Word 换回对象头（00 → 01）
  ② 若期间已膨胀，头里已是 Monitor 指针——换不回，转重量级解锁
  • Lock Record / Displaced Mark Word：62 位 Mark Word 全让给指针后，hash 和分代年龄没地方放——加锁前把整个无锁态 Mark Word 复制进栈上 Lock Record，解锁时原样抄回。03-jvm/03 的 JOL 实测 ③④ 快照（hash 值分毫未损地回来）就是本机制的实证。
  • "轻量"轻在哪：全程用户态 CAS——不碰内核互斥量、不发生线程挂起/上下文切换，成功路径的开销就是一条 CAS 指令。
  • 与偏向锁的本质区别：偏向锁赌"永远同一线程"（第二次起连 CAS 都省）；轻量级锁赌"不同线程交替持有"（每次进出都要 CAS，但没有同时竞争）；重量级锁面对"真·同时竞争"。三者是竞争强度同一维度上的递进，不是并列选项。
维度偏向锁轻量级锁重量级锁
竞争模型始终同一线程不同线程交替持有多线程同时竞争
每次加锁成本首次 1 次 CAS，之后 0每次 1 次 CAS内核互斥量，挂起/唤醒
Mark Word 内容线程 ID栈上 Lock Record 指针ObjectMonitor 指针
适合场景无竞争且重入（已废弃）临界区极短、交替访问临界区长、竞争激烈

自旋与适应性自旋（轻量级锁的"等"，美团锁事补全）

  • 自旋（spin）：轻量级锁 CAS 失败后不立刻挂起，而是空转循环重试——赌持锁线程马上释放，省掉挂起/唤醒两次上下文切换。JDK 1.6 之前自旋次数写死（默认 10 次，-XX:PreBlockSpin 可调）。
  • 适应性自旋（Adaptive Spinning，1.6 默认）：次数不再固定——同一把锁上次自旋成功过，这次允许多转；曾经自旋失败导致膨胀，这次直接跳过自旋去挂起。用历史预测这一次值不值得等。
  • 代价口径：自旋是占着 CPU 的忙等。临界区短、竞争温和是收益区；临界区长或竞争激烈时自旋纯属烧 CPU 还推迟膨胀——这正是"自适应"存在的意义：止损要快。

加分点：JDK 15 默认废弃偏向锁（JEP 374）。原因：偏向锁的撤销要 safepoint、有全局停顿副作用，维护成本高；而它优化的场景（无竞争的同步，如老版本集合类的大量 synchronized）在现代应用里已大幅减少，撤销开销经常大于收益。JDK 15 起默认禁用（-XX:+UseBiasedLocking 可手动开），升级路径变为无锁→轻量级→重量级。能说出"废弃原因 = 撤销成本 + 场景消失"，就是这题的满分答案。

锁粗化与锁消除（JIT 层面的另外两刀）

  • 锁粗化（coarsening）：相邻的多次加锁解锁合并成一次——for 循环里反复 synchronized 追加字符串，JIT 直接合并为整块一次加锁。
  • 锁消除（elimination）：基于逃逸分析，证明锁对象不可能被其他线程访问（如方法内局部 StringBuffer），直接把锁删掉。

锁升级只发生在 synchronized 上；ReentrantLock 走的是 AQS 的"CAS + 队列 + park"，没有这套分层。另外 volatile （第 02 章）与锁是两套机制：volatile 管可见性/有序性，不互斥、不保证原子性。

05LockSupport：park / unpark——线程"睡与醒"的最终出口

java.util.concurrent.locks.LockSupport 是一组静态方法，本质是 Unsafe.park / unpark 的薄封装：park() 把当前线程挂起，unpark(t) 把指定线程叫醒。J.U.C 里凡是线程要"等"——AQS 的同步队列与条件队列（下一节）、FutureTask.get()、CompletableFuture.join()、SynchronousQueue、ForkJoinPool 的空闲工人——最后一步都落到它。先把它讲透，下一节 AQS 四字口诀里的"睡"才有着落。

方法作用Thread.State
park() / park(Object blocker)挂起当前线程，直到被 unpark / 被中断 / 无故返回WAITING (parking)
parkNanos(nanos) / parkUntil(deadlineMillis)带超时：相对纳秒 / 绝对毫秒时间戳（都有带 blocker 的重载）TIMED_WAITING (parking)
unpark(Thread t)给 t 一张许可：t 正在 park 就唤醒；否则 t 下一次 park 不阻塞—
getBlocker(Thread t)读取 t 挂起时登记的 blocker（纯诊断，见下）—

许可（permit）机制：为什么 unpark 可以先于 park ⭐

每个线程自带一张许可——Javadoc 原话：像 Semaphore，但最多只攒 1 张。unpark = 把许可置为"有"（已经有就什么都不做）；park = 有许可就消费掉、立刻返回，没有才真挂起。所以两者的调用先后不重要：

Thread t = new Thread(() -> {
    sleep(1000);                        // 故意让 main 的 unpark 跑在前面（Thread.sleep，略去 try/catch）
    LockSupport.park();                 // ① 许可已在 → 直接通过，根本不挂起
    System.out.println("第一次 park 直接通过");
    LockSupport.park();                 // ② 许可已被 ① 消费 → 这次真挂起（WAITING）
    System.out.println("第二次 park 被唤醒");
});
t.start();
LockSupport.unpark(t);                  // 先于 park 发出：许可留着，不丢
LockSupport.unpark(t);                  // 再发一次：不累积，仍然只有 1 张
sleep(2000);
LockSupport.unpark(t);                  // ② 要等到这张新许可才醒

这正是它比 wait/notify 强的地方：notify 先于 wait → 信号丢失，线程永远睡；unpark 先于 park → 许可留着，park 直接通过。代价是只有 1 张：连发 N 次 unpark 只够 1 次 park 通过，把它当计数信号量用就错了——要计数去 AQS 的 state 里计（Semaphore 就是这么做的：许可数在 state，park 只负责"没抢到就睡"）。

两个边界：对尚未 start 的线程 unpark，Javadoc 明确"不保证有任何效果"；线程结束后许可随之作废。许可只在线程存活期间有意义。

park 的三种返回与中断语义：为什么必须放在循环里 ⭐

park() 返回只有三种原因，而且不告诉你是哪一种：① 别人 unpark 了你；② 别人 interrupt 了你；③ 无故返回（spurious return——底层 pthread_cond_wait 本来就允许假醒，HotSpot 在 park 与 unpark 抢内部 mutex 撞上时也会干脆返回）。所以 park 不是"信号"本身，只是"省 CPU 的等待"：条件要自己查、要在循环里查。

// 标准用法骨架：条件 + 循环 + 自己处理中断
while (!condition) {                    // ① 先查条件：许可可能早就在，不查就白睡一趟 / 误醒
    LockSupport.park(this);             // ② 不满足才睡；三种返回都回到 while 重查
    if (Thread.interrupted()) {         // ③ 中断要自己看、自己清、自己决定怎么办
        throw new InterruptedException(); // 当场抛，或先记下来、事后补发（AQS 的做法，见下）
    }
}

中断语义是 park 与 wait / sleep / join 最大的分水岭：

wait / sleep / joinLockSupport.park
挂起中被 interrupt抛 InterruptedException静默返回，不抛任何异常
中断标志位抛异常前清掉不清，仍为 true
标志位已置时再调用立刻抛异常（标志位清掉）立刻返回——之后每次 park 都秒回，直到有人 Thread.interrupted() 把标志清掉

经典事故：线程被 interrupt 过一次，之后代码里所有 park() 集体"失效"，等待循环变成空转，CPU 直接打满——原因就是上表第三行：标志位不清，park 永远秒回。写 park 循环时，中断分支不能省。

AQS 怎么处理这件事——这就是 lock() 与 lockInterruptibly() 差异的真相（第 07 节对比表"可中断性"一行的底层）：

// AQS.acquireQueued（JDK 8，简化）：为什么是 for(;;)，中断去哪了
for (;;) {
    if (p == head && tryAcquire(arg)) { setHead(node); return interrupted; }  // 抢到锁才出循环
    if (shouldParkAfterFailedAcquire(p, node) && parkAndCheckInterrupt())
        interrupted = true;              // ⭐ 中断只"记下来"，继续排队抢锁，不退出
}
private final boolean parkAndCheckInterrupt() {
    LockSupport.park(this);              // 三种返回都走到下一行
    return Thread.interrupted();         // 读并清标志位——不清的话下次 park 秒回，整条队列空转
}
// acquire()：抢到锁后把中断补发回去 —— lock() "不可中断"的真相是"延迟响应"
if (!tryAcquire(arg) && acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) selfInterrupt();
// acquireInterruptibly()：同一个循环，只是 parkAndCheckInterrupt() 为 true 时
//                         当场 throw new InterruptedException()，不再排队

答题口径："park 有三种返回且不区分原因，所以 AQS 用 for(;;) 包着它、醒来就重试 tryAcquire；中断由 parkAndCheckInterrupt 读并清标志位——lock() 记下来、拿到锁后 selfInterrupt() 补发，lockInterruptibly() 当场抛。所谓 lock() 不响应中断，准确说是等锁期间不中断、拿到锁后补发。"

blocker 参数：jstack 里那行 "parking to wait for"

底层：HotSpot 的 Parker——一个计数器 + 一把 mutex + 一个条件变量

每个 Java 线程在 JVM 里配一个 Parker 对象（与 synchronized / Object.wait 用的 ParkEvent 是两套），核心就是 volatile int _counter（0 / 1，即"那张许可"）。读懂下面十几行，前面所有"为什么"都有了答案（简化自 hotspot/os/posix/os_posix.cpp）：

void Parker::park(bool isAbsolute, jlong time) {
    if (Atomic::xchg(&_counter, 0) > 0) return;    // ① 快路径：有许可 → 原子清零即返回，不进内核
    if (thread->is_interrupted()) return;            // ② 已中断 → 直接返回（不抛异常、不清标志）
    if (pthread_mutex_trylock(_mutex) != 0) return;   // ③ 与 unpark 撞锁 → 干脆返回（"无故返回"之一）
    if (_counter > 0) { _counter = 0; unlock; return; }   // ④ 再查一次：拿锁期间 unpark 可能刚到
    pthread_cond_wait / timedwait(_cond, _mutex);     // ⑤ 真挂起：OS 条件变量（Linux 基于 futex）
    _counter = 0;                                     // ⑥ 醒来，消费许可
    pthread_mutex_unlock(_mutex);
}
void Parker::unpark() {
    pthread_mutex_lock(_mutex);
    int s = _counter;  _counter = 1;                  // ⭐ 恒置 1 而不是 +1 —— 许可不累积的原理
    pthread_mutex_unlock(_mutex);
    if (s < 1) pthread_cond_signal(_cond);            // 之前没许可、可能有人睡着 → 叫一下
}
// Thread.interrupt() 的 native 侧 = 置中断标志 + 对该线程的 Parker 调一次 unpark() —— 中断能叫醒 park 的原因
  • unpark 为什么能先于 park：许可是状态（_counter），不是事件——先到先存，park 来了消费；notify 是事件，没人在等就丢了。
  • 为什么不累积：_counter = 1 是赋值不是自增。
  • 为什么快：有许可时走 ①，一次用户态原子操作就返回，不碰 mutex、不进内核；只有真要等才在 ⑤ 系统调用挂起。这也是 AQS "入队前先自旋试几次再 park" 划算的物理基础。
  • 中断也会留下一张许可：interrupt 内部调了 unpark，_counter 变 1。即使随后 Thread.interrupted() 清了标志，下一次 park 仍会因 ① 秒回——又一个"park 必须在循环里"的理由。
  • 虚拟线程（JDK 21）：LockSupport.park() 先判断 isVirtual()，是则走 VirtualThread.park()——卸载（unmount）让出载体线程，而不是挂起 OS 线程；unpark 则把它重新提交给调度器。同一个 API、两套实现，详见 第 10 章。

06AQS：JUC 同步器的骨架 ⭐

AbstractQueuedSynchronizer 是 J.U.C 里大多数同步类的基石——ReentrantLock、ReentrantReadWriteLock、Semaphore、CountDownLatch 都基于它实现（合并笔记 577-591 行）。三个关键词：

  • 一个状态：volatile int state（同步状态，配合 CAS 无锁修改，volatile 保证可见性——第 02 章的知识在这落地）。不同同步器赋予它不同含义：
同步器state 的语义模式
ReentrantLock重入次数（0 未锁，N 重入 N 层）独占
ReentrantReadWriteLock一个 32 位 int：高 16 位读锁持有数，低 16 位写锁重入数共享 + 独占
Semaphore剩余许可数共享
CountDownLatch倒数计数器的值共享
  • 一个队列：CLH 变体的 FIFO 双向等待队列。获取 state 失败的线程包装成 Node 入队，然后 LockSupport.park() 挂起；队首（head 的后继）在释放时被 unpark 唤醒后重试 CAS——FIFO 保证公平性可插拔。（严格说这是同步队列；Condition 的条件队列是另一条，两者分工与 signal 的"搬家"见 第 09 节。）
  • 两种模式：
    • 独占模式（Exclusive）：同一时刻只有一个线程能获取资源——ReentrantLock、写锁。
    • 共享模式（Shared）：多个线程可同时获取资源——Semaphore、CountDownLatch、读锁。实现上就是模板方法 tryAcquire/tryRelease 与 tryAcquireShared/tryReleaseShared 的区别。
// 一次独占获取的骨架流程（ReentrantLock.lock 的视角）

      │ 失败

答题口径：AQS = "volatile state（状态）+ CLH 变体队列（排队）+ CAS（抢）+ LockSupport（睡）"，用四个词概括，再按同步器各举 state 含义。面试官追源码时，讲 ReentrantLock 的 nonfairTryAcquire（重入就是 state+1 且 owner 相等判断）和公平版的 hasQueuedPredecessors() 检查即可。

源码追问：waitStatus 与唤醒协议 ⭐（美团 AQS 文补全）

队列里每个 Node 都有一个 waitStatus。面试官问"AQS 怎么知道该唤醒谁"，考的就是它：

值含义
SIGNAL(-1)对后继的承诺：我释放资源时会 unpark 我的后继（唯一必须掌握的值）
CANCELLED(1)该节点因超时/中断被取消，后续出队时跳过
CONDITION(-2)节点在 Condition 条件队列上——AQS 的第二条队列；它与同步队列的分工、signal 怎么把节点搬回同步队列见 第 09 节 · 两条队列
0 / PROPAGATE(-3)初始状态 / 共享模式的传播唤醒

入队三步 + 唤醒一句话：CAS 尾插入队 → 把前驱的 waitStatus 改成 SIGNAL（登记"释放时记得叫我"）→ park 自己。持锁线程 release 时 state CAS 归零，看到后继挂着 SIGNAL 就 unpark 它；后继从 park 处醒来，重新尝试 CAS 获取。所以 SIGNAL 的本质不是"我的状态"，而是"我对后继的唤醒承诺"——被取消的节点（CANCELLED）在出队时被跳过清理。

独占 vs 共享：tryAcquireShared 的返回值约定与传播唤醒 ⭐

两种模式的差异全部收敛在模板方法上——AQS 的排队 / CAS / park 骨架完全复用：

独占模式共享模式
获取模板tryAcquire(arg) → booleantryAcquireShared(arg) → int
返回值约定true / false负数 = 失败；0 = 成功且无余量；正数 = 成功且还有余量（要向后传播）
释放模板tryRelease → booleantryReleaseShared → boolean（true = 状态变了，去唤醒）
唤醒范围只唤醒后继一个级联唤醒：放行一个后若余量仍够 / 计数已归零，接力唤醒下一个
代表类ReentrantLock、写锁Semaphore、CountDownLatch、读锁（落地走读见 第 08 章 §02/§03）
// 共享获取：acquireShared → doAcquireShared（简化）
Node node = addWaiter(Node.SHARED);         // ① 抢不到先入队，节点标记 SHARED 模式
do {
    if (node.prev == head) {
        int r = tryAcquireShared(arg);      // ② 子类实现：如 Semaphore 的 CAS(state-1)
        if (r >= 0) {
            setHeadAndPropagate(node, r);   // ③ 成功：设新 head；r>=0 且后继是共享节点 → 继续唤醒
            return;
        }
    }
    parkAndCheckInterrupt();                // ④ 拿不到：前驱置 SIGNAL → park（第 05 节三种返回）
} while (node 在队列中);

传播唤醒（setHeadAndPropagate）是共享模式最关键的一步：拿到资源的线程把自己设成新 head 之后，若返回值 ≥ 0 且（自己还有余量 或 后继也是共享节点），就接着 doReleaseShared 唤醒后继；被唤醒者重走 tryAcquireShared，成功了又接力传播。效果：latch 归零的一瞬间、Semaphore 一次还回多张许可时，所有满足条件的等待者被"接力"放行，而不是只放一个、剩下干等下一轮。waitStatus 表里的 PROPAGATE(-3) 就是给这条链兜底的：并发 release 的间隙里保证传播信号不丢（JDK 6 修复的丢失唤醒 bug）。独占模式没有这一步——setHead 设完就结束，一次只放一个。

  • 追问链：为什么 latch 要用共享模式？→ 语义是"state == 0 时所有人都能过"——独占一次只放一个，等 N 个任务要被唤醒 N 轮；共享 + 传播唤醒，归零瞬间全员放行。
  • 追问：Semaphore.release(5) 怎么实现？→ tryReleaseShared 循环 CAS 把 state 加 5，返回 true 触发 doReleaseShared；后续 5 个等待者靠传播唤醒逐个接力消费许可。
  • 追问：读锁为什么必须共享模式？→ 高 16 位读计数允许任意多线程同时非零：tryAcquireShared 只要有读余量就返回正数继续传播——"读读共享"四个字就是这条传播链（第 08 节）。

07ReentrantLock 与对比 ⭐

ReentrantLock 是实现了 Lock 接口的显式锁（JDK 层面的类，基于 AQS），用 lock() / unlock() 手动控制。合并笔记 543-550 行，对比表原样如下：

ReentrantLock 的四个高级能力（对应表尾三行展开）

  • 可中断抢锁：lockInterruptibly()——等锁期间能被 interrupt 打断，避免死等的线程无法取消（笔记"可中断等待"）。
  • 超时获取：tryLock(timeout, unit)——限时尝试，拿不到就返回 false 走降级逻辑，是打破死锁的常用手段（链 11 并发挑战 · 死锁）。
  • 公平/非公平：构造参数 new ReentrantLock(true) 即公平锁（先来先得，查队列 hasQueuedPredecessors()）；默认非公平——新来的线程直接 CAS"插队"，省去唤醒→就绪的空窗期，吞吐更高，代价是可能饥饿。
  • 多个 Condition：一把锁配多个条件队列（lock.newCondition()），await/signal 可精确唤醒某一类线程——生产者消费者实战见第 09 节。
ReentrantLock lock = new ReentrantLock();        // new ReentrantLock(true) = 公平锁
if (lock.tryLock(1, TimeUnit.SECONDS)) {          // 超时获取：拿不到就放弃，不死等
    try {
        doWork();
    } finally {
        lock.unlock();                            // ⭐ 必须放 finally，异常时锁泄漏
    }
}

选型口径（高频追问）：默认用 synchronized——JDK 6 锁优化后性能已相当，且自动释放不会漏；需要可中断、超时、公平、多条件队列四件事任一件，才换 ReentrantLock。这个"先说默认、再列例外"的答法比无脑夸 ReentrantLock 专业。

08读写锁与 StampedLock

ReadWriteLock：读读共享，读写/写写互斥

合并笔记 560-565 行：互斥规则——读读共享、读写互斥、写写互斥。读多写少的场景（配置、缓存、元数据）用读写锁替代互斥锁，读并发不再互相排队。实现类 ReentrantReadWriteLock（RRWL，基于 AQS 共享+独占双模式）：

  • 实现要点：AQS 的一个 32 位 int state 拆成两半——高 16 位维护进入的读锁（共享持有数），低 16 位维护写锁（独占重入数），一把锁两种模式（笔记原文口径）。
  • 可重入：读线程可重复拿读锁；写线程可重复拿写锁，也可在持写锁时拿读锁（这就是降级）。

锁降级与不能升级

  • 写→读（允许）：持有写锁期间可以直接获取读锁，再释放写锁。用途：更新完数据后降级为读锁继续读，保证在切换瞬间没有别的写线程插进来，读到的一定是自己刚写的值（缓存刷新的经典写法）。
  • 读→写（不允许）：持读锁再申请写锁会永远等待——写锁要等所有读者退出，而自己就是读者之一且被挂起不放，等价于自锁（其他读者也可能同时持有），构成死锁。
Object data;
ReentrantReadWriteLock rwl = new ReentrantReadWriteLock();
Lock r = rwl.readLock(), w = rwl.writeLock();

w.lock();               // ① 先拿写锁，独占刷新数据
try {
    data = load();
    r.lock();           // ② 持写锁期间拿读锁（降级开始）
} finally {
    w.unlock();         // ③ 释放写锁：此后仍持读锁，别人能读不能写
}
try {
    use(data);
} finally {
    r.unlock();         // ④ 最后释放读锁
}

StampedLock：乐观读加分项

JDK 8 加入。读写锁的痛点：读也要 CAS 改 state，高并发读仍有争用；StampedLock 的乐观读（optimistic read）让读完全不加锁——读前取一个版本 stamp，读完验证 stamp 期间没有发生过写，通过则读数有效，不通过再升级为悲观读锁重读：

class Point {
    private double x, y;
    private final StampedLock sl = new StampedLock();

    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();   // ① 乐观读：不加锁，只取版本号
        double cx = x, cy = y;                 // ② 读普通字段（此刻可能有写）
        if (!sl.validate(stamp)) {             // ③ 校验：期间发生过写则失效
            stamp = sl.readLock();             // ④ 升级悲观读锁，重读
            try { cx = x; cy = y; }
            finally { sl.unlockRead(stamp); }
        }
        return Math.sqrt(cx * cx + cy * cy);
    }
}

StampedLock 两个坑：不可重入（持读锁的线程再调读锁会死锁）；不支持 Condition。且不要调用中断的悲观读（write 时被 interrupt 可能导致 CPU 飙升，官方文档明示）。它换来的是读吞吐比 RRWL 高一个量级，适合读极多写极少的点态场景。

09wait·notify 陷阱 ⭐

sleep vs wait 的主对比在第 01 章（合并笔记 457-459 的 TODO 时已覆盖），这里补全 wait/notify 的完整陷阱链——每条都可能单独出一道题：

陷阱一：不持有锁就 wait/notify → IllegalMonitorStateException

wait/notify 操作的是锁对象的 monitor，必须在对应的 synchronized(obj) 内调用，且必须是同一个对象的 monitor；否则运行时抛 IllegalMonitorStateException。ReentrantLock 体系对应的是 Condition.await()/signal()，同样必须先持锁。

陷阱二：虚假唤醒 → 必须用 while 守卫

synchronized (lock) {
    while (!ready) {       // ⭐ while 不是 if：醒来后重新检查条件
        lock.wait();       // 被 notify 唤醒后从 wait 处继续，回到 while 再验一次
    }
    consume();
}
// 为什么不能用 if：
// ① 虚假唤醒（spurious wakeup）：Object.wait 的 Javadoc 明确写了
//    线程可能"无 notify 也被唤醒"，这是底层 futex/信号机制允许的；
// ② 多个等待者被 notifyAll 全部唤醒后，第一个消费者已把条件吃掉，
//    后续线程醒来时条件又不满了 —— if 会直接穿透执行

陷阱三：notify 随机唤醒 → 信号丢失 → notifyAll

notify() 只唤醒 WaitSet 里随机一个等待线程：如果该线程等的是"另一个条件"，本条件的等待者没被唤醒——信号丢失，程序可能永久卡死。保守正解是 notifyAll() 全叫醒、让 while 条件各自过滤（代价是无谓唤醒和锁竞争）。

正解：两个 Condition 精确唤醒（生产者消费者完整代码）

ReentrantLock 的多 Condition 能力根治"随机唤醒"：生产者只睡在 notFull 上、消费者只睡在 notEmpty 上，谁的空间就绪就 signal 谁，零无效唤醒：

class BoundedBuffer {
    private final Object[] items = new Object[10];
    private int putIdx, takeIdx, count;

    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();  // 生产者等：队列不满
    private final Condition notEmpty = lock.newCondition();  // 消费者等：队列不空

    public void put(Object x) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) {
                notFull.await();              // 满了：睡在 notFull 上
            }
            items[putIdx] = x;
            if (++putIdx == items.length) putIdx = 0;
            count++;
            notEmpty.signal();                // 精确叫醒一个消费者
        } finally {
            lock.unlock();
        }
    }

    public Object take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) {
                notEmpty.await();             // 空了：睡在 notEmpty 上
            }
            Object x = items[takeIdx];
            if (++takeIdx == items.length) takeIdx = 0;
            count--;
            notFull.signal();                 // 精确叫醒一个生产者
        } finally {
            lock.unlock();
        }
    }
}
  • wait/await 的三段式：释放锁 → 进 WaitSet/条件队列等待 → 被 signal 后重新竞争锁，拿到才从 wait 调用处继续——"醒来"和"继续跑"之间还隔一次抢锁。
  • 更多同步编排题（交替打印、顺序执行）见 12 经典同步题；ObjectMonitor 的 WaitSet 视角回看第 03 节。

追问：ReentrantLock 为什么要两条队列？——分工与 signal 的"搬家" ⭐

把上面的 await/signal 放回 AQS 的结构里看：一把 ReentrantLock 身上长着 1 条同步队列 + N 条条件队列（每 newCondition() 一次就多一条），第 06 节讲的 CLH 队列只是其中的同步队列：

锁 lock（一个 AQS 实例）
├── 同步队列（1 条，CLH 双向链表，第 06 节）:           [T2]→[T3]→[T4]   ← 卡在 lock() 抢锁的
├── 条件队列 notFull （单向链表 firstWaiter→lastWaiter）: [P1]→[P2]        ← notFull.await() 挂起的生产者
└── 条件队列 notEmpty（同上）:                           [C1]             ← notEmpty.await() 挂起的消费者

另一把锁 lock2 = 另一个 AQS 实例 = 完全独立的另外几条队列
同步队列（1 条）条件队列（N 条）
队列里的人卡在 lock() 抢锁的await() 挂起等信号的
等什么等前驱释放锁等 signal() / 超时 / 中断
等待期间持锁吗从没拿到过拿到过，await() 时全额释放（记住重入数）
谁来唤醒unlock() 时 unpark 队头后继（waitStatus=SIGNAL 协议）持锁者调 signal()
唤醒后去哪直接 CAS 抢锁先搬回同步队列重新排队，抢到锁才能从 await() 返回

为什么不能合成一条队列——三个理由，答出第二条就算理解了：

  1. 驱动事件不同：unlock 该叫"等锁的"，signal 该叫"等某个条件的"。混在一条队列里，unlock 发生时没法挑人只能全叫——等条件的人被白叫醒，条件不满足、锁也拿不到，还得睡回去，纯惊群。
  2. await 的语义要求：await() = "原子地释放锁 + 挂起"，醒来后必须重新持锁才能返回（要持锁检查条件、改状态）。所以被 signal 的人注定要变回"抢锁的人"——那就必须有同步队列来接。
  3. 分组唤醒的根基：条件队列按"等待的条件"分堆（notFull/notEmpty 各养各的），signal 才能指名道姓。只有一条等待队列就退化成 synchronized 的 notifyAll 全叫醒 + 每人重查条件。

signal 的本质 = 一次队列搬家（AbstractQueuedSynchronizer.ConditionObject 的源码路径）：

// await() 骨架（简化自 ConditionObject.await）
Node node = addConditionWaiter();        // ① 包成 Node 挂到本条件队列尾（waitStatus = CONDITION）
int saved = fullyRelease(node);          // ② 全额释放锁，记住重入数（state 归零 → unpark 同步队列后继）
while (!isOnSyncQueue(node))
    LockSupport.park(this);              // ③ 挂起（Thread.State = WAITING）
acquireQueued(node, saved);              // ④ 被 signal 搬到同步队列后：重新抢锁，抢不到继续 park（仍是 WAITING）
                                         //    抢到才返回 → 回到 while(条件) 重查

// signal() 骨架（简化自 ConditionObject.signal / transferForSignal）
if (!isHeldByCurrentThread()) throw new IllegalMonitorStateException();   // 不持锁不许叫人
Node first = firstWaiter;                // 取条件队列头
CAS(first.waitStatus, CONDITION → 0);    // 摘下"条件队列"标记
enq(first);                              // ⭐ 尾插进同步队列——搬家
LockSupport.unpark(first.thread);        // 叫醒它去抢锁（signalAll = 循环把整条条件队列搬完）

注意 signal() 不让任何线程直接跑，它只做"从条件队列摘下 → 塞进同步队列 → unpark"三件事；被叫醒的线程回到 await 里重新走一遍抢锁流程。这也解释了第 06 节 waitStatus=CONDITION(-2) 的用途：标记"这个 Node 此刻在条件队列上"，搬家时 CAS 成 0。

队列归属 ⇒ 唤醒隔离：每条队列都长在某一把锁 / 某一个 Condition 对象身上，signal() 只遍历自己这条链表，别的锁、别的 Condition 的等待者物理上碰不到——锁 A 的 signal 永远叫不醒锁 B 上等待的线程。synchronized 同理：notify() 只搬自己 ObjectMonitor 的 _WaitSet，对象天然隔离。

两个体系不互通：ReentrantLock 没有 notify——lock.notify() 会直接抛 IllegalMonitorStateException，因为它要求持有的是 lock 这个对象的监视器，而你持的是 AQS 的 state。synchronized 配 wait/notify，Lock 配 Condition.await/signal，一一对应不能混搭。

对照 ObjectMonitor 就通了：第 03 节的 _EntryList/_cxq（抢锁）+ _WaitSet（等 wait）同样是两条队列——"等锁队列 + 等条件队列"是锁模型的必然结构，不是 AQS 的怪癖；AQS 的进步只是把条件队列从 1 条扩展到 N 条，换来精确分组唤醒。两者在 Thread.State 上的差异见第 01 章 BLOCKED vs WAITING 对比：synchronized 下 wait 被 notify 后重抢锁期是 BLOCKED（进了 EntryList），AQS 下被 signal 后重抢锁期仍是 WAITING（还是 park）。

答题口径："两条队列对应两种等待语义：同步队列等锁、由 unlock 驱动；条件队列等信号、由 signal 驱动。await 释放锁挂条件队列，signal 把节点从条件队列搬回同步队列重新竞争——因为从 await 返回的前提是重新持锁。队列长在锁对象身上，所以唤醒天然隔离；一把锁 N 个 Condition 则是精确分组唤醒的根基。"

10高频追问与陷阱

  • 追问链：synchronized 原理 → monitorenter 做了什么 → 重量级为什么贵 → 锁升级→ 标准四级追问，沿第 02-04 节主线走即可，终点抛出 JEP 374。
  • 追问：偏向锁为什么废弃，为什么撤销要 safepoint？→ 撤销要检查"偏向的线程是否还在持锁"，必须在全局安全点做一致性检查；高并发下反复撤销（批量重偏向也救不了）成本超过收益（JEP 374）。
  • 追问：轻量级锁自旋有什么代价？什么时候反而更慢？→ 自旋占 CPU 空转；临界区长或竞争激烈时，自旋烧完时间片还得膨胀，白烧 CPU——所以自旋次数自适应。
  • 陷阱：同步方法内调 this.wait() 锁的是谁？→ 实例方法锁 this，wait 也在 this 上，合法；静态方法里调 this.wait() 直接编译不过/运行异常——锁对象与监视对象必须一致。
  • 追问：公平锁更好吗？→ 公平锁防饥饿但吞吐低：释放锁到唤醒线程存在空窗，非公平允许新线程插队（barging）填满空窗；默认非公平是性能选择。
  • 追问：AQS 为什么用 CLH 变体？→ 出队/取消 O(1)、仅前驱唤醒（避免惊群）、结合 park 避免内核态自旋；"变体"指阻塞用 LockSupport.park 而非 CLH 原生的自旋。
  • 追问：synchronized 块里能直接 park 吗？→ 能调，但 park 不释放 monitor——持锁睡，别人全 BLOCKED。需要"释放锁 + 等待"语义的，用 wait 或 Condition.await（它们内部都是先全额释放再 park）（第 05 节对比表）。
  • 陷阱：线程被 interrupt 过一次之后，所有 park 都秒回、等待循环空转打满 CPU→ park 不清中断标志，必须 Thread.interrupted() 读并清；AQS 的 parkAndCheckInterrupt 就是干这个的（第 05 节）。
  • 陷阱：读写锁下"读方法没加锁"可以吗？→ 读也必须持读锁：写锁释放后新读线程才能进；不持锁读可能撞上写过程（可见性问题），链 第 02 章 JMM。
  • 追问：Condition 和 wait/notify 什么关系？→ 语义一一对应（await/wait、signal/notify、signalAll/notifyAll），但 Condition 绑定 Lock、可多个、可指定超时与不响应中断模式（awaitNanos/awaitUninterruptibly）。
  • 追问链：AQS 怎么知道该唤醒谁？→ waitStatus：入队后把前驱置 SIGNAL(-1) → release 时看到 SIGNAL 就 unpark 后继 → 醒来重试 CAS → 再追问：取消的节点怎么办？CANCELLED(1)，出队时跳过清理（第 06 节）。
  • 追问链：latch 归零为什么能一次放行所有 await？→ 共享模式的传播唤醒：tryReleaseShared 减到 0 返回 true → doReleaseShared 唤醒队首 → setHeadAndPropagate 见返回值 ≥0 继续接力，一条链放完全部等待者 → 再追问：独占模式为什么不行？setHead 就结束，一次只放一个（第 06 节）。
  • 追问：自旋次数是写死的吗？→ 1.6 后是适应性自旋：同一把锁自旋赌赢过就多转、赌输过就直接挂起，按历史动态定（第 04 节）。
