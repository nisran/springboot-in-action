02JMM 是什么：主内存与工作内存

先给准确定义：JMM 是规范，不是实现

  • JMM（Java Memory Model）是定义在 Java 语言规范（JLS 17.4，JSR-133）里的一套内存访问规范，不是 JVM 里的某块内存。它屏蔽了各种硬件和操作系统的内存访问差异，让同一份 Java 程序在 x86、ARM、单核、多核上都能得到一致的内存访问语义。
  • 它规定了两样东西：内存抽象（主内存/工作内存）和可见性语义（happens-before 规则）。JVM 实现方在各 CPU 架构上用"插入内存屏障"等手段兑现这套语义。

主内存与工作内存

  • 主内存：所有共享变量（实例字段、静态字段）存放的地方，所有线程共享。
  • 工作内存：每个线程私有的一块抽象内存——是寄存器、CPU 缓存（L1/L2/L3）、写缓冲区（store buffer）等硬件的统一抽象，不是 JVM 的哪块区域。线程对变量的任何操作（读/写）都必须在自己的工作内存中进行，不能直接读写主内存。
  • 核心规则（笔记原文）：线程间传递变量值，必须通过主内存来完成——线程 A 把工作内存里的修改刷回主内存，线程 B 再从主内存读取，线程之间没有直接的数据通道。
                主内存（所有共享变量）
               ↗      ↑      ↖
     read/load        store/write
        ↕                 ↕
  线程A 工作内存     线程B 工作内存     ← CPU 缓存/寄存器/写缓冲的抽象
  （拷贝了共享变量的副本）              ← 对变量的读写都发生在这里

高频混淆：JMM ≠ JVM 运行时数据区。堆/栈/方法区是 JVM 对内存的物理划分（哪里放对象、哪里放局部变量，见 03-jvm）；JMM 是并发语义的抽象模型（多线程读写共享变量时什么可见、什么有序）。一个讲"放哪"，一个讲"可见性"，被问"JMM 是不是就是堆和栈"时这正是送分点。

旧版教材（如《深入理解 JVM》）把主/工作内存的数据流转拆成 read/load/use/assign/store/write/lock/unlock 八种原子操作；现行 JLS 已改用 action + happens-before 来描述同一件事。面试提一句"八操作是通俗化说法，JLS 的正式口径是 happens-before"，是明显加分项。

03三大性质：原子性 · 可见性 · 有序性

JMM 要解决的就是多线程环境下的三大问题（合并笔记 505-520 行），每个性质都要能"定义 + 反例 + 解药"三连答：

性质定义典型事故保证手段
原子性一个操作（或一组操作）不可分割——执行中不会被其他线程交错/打断，要么全做要么不做count++ 是"读-改-写"三步，两线程交错执行丢更新锁（synchronized / Lock）互斥保证临界区整体原子；原子类靠 CPU 的 CAS 实现无锁原子操作
可见性一个线程对共享变量的修改，能被其他线程立即感知，而不是一直读自己工作内存里的旧副本一个线程改了 flag=false，另一个线程的 while(flag) 永远不退出volatile（写立刻对其他核可见）；synchronized（进入时清空工作内存、退出前刷回主内存）；final（构造完成后对所有线程可见）
有序性禁止指令重排导致的"代码顺序 ≠ 执行顺序"意外——单线程看似串行，多线程观察到乱序DCL 单例读到"已分配内存但未初始化"的对象（本章第 06 节）volatile 禁止重排；synchronized 的监视器规则；final 字段语义
  • synchronized 一把锁同时管三件事（笔记）：原子性靠互斥（同一时刻只有一个线程进临界区）；可见性靠 monitor 规则（解锁前把工作内存的修改刷回主内存，加锁时使本线程的工作内存失效重新读）；有序性也随之获得（临界区间无法交错观察）。
  • volatile 只管两件：可见性 + 有序性，不保证原子性——下一节展开。
  • final 管一件：正确构造的对象，其 final 字段对所有线程可见且可见正确值（JLS 17.5，见第 06 节）。

可见性被破坏的现场（先看反例再背定义）

static boolean flag = true;    // 不加任何同步手段的普通变量

// 线程A（停机线程）           // 线程B（工作线程）
flag = false;                  while (flag) {
                                   doWork();    // JIT 可能把 flag 提升(hoist)到寄存器
                               }               // 线程B 可能永远感知不到 false，死循环
// 两个修法：flag 加 volatile（轻量，推荐）；或读写都进同一把锁（重）

答题技巧：先一句话定义三性，再主动给"解药矩阵"——原子性用锁/CAS、可见性用 volatile/synchronized/final、有序性用 volatile/synchronized。能把"哪个工具解决哪几性"说成矩阵而不是流水账，面试官就知道你成体系。

04happens-before ⭐

定义：可见性的推理工具，不是时间顺序

happens-before（hb）是 JMM 判断"一个操作的结果对另一个操作是否可见"的规则：若 A happens-before B，则 A 的结果对 B 可见，且 A 的效果排在 B 之前。两个要点必须主动讲清：

  • hb 是逻辑上的可见性保证，不是物理时间先后：A hb B 不要求 A 在时钟上先发生；反过来说，没有 hb 关系的两个操作是"并发"的，谁先谁后、看不看得到，JMM 都不做保证。
  • 它的价值是推理工具：拿到任意两行代码，沿 hb 规则连一条链，就能证明"这行的新值对那行可见"，而不用去想 CPU 缓存和屏障。

八条规则（JLS 17.4.5）

规则内容实用场景
程序顺序规则单线程内，按程序顺序前面的操作 hb 后面的操作同一线程里 data=42; ready=true; 前者 hb 后者
监视器锁规则对同一个锁的 unlock hb 后续每一次对该锁的 lock上一个线程临界区里的写，对下一个进锁的线程可见
volatile 规则对 volatile 变量的写 hb 后续每一次对该变量的读volatile 是"跨线程可见性的传送门"
线程 start 规则调用 Thread.start() 的操作 hb 新线程内的所有操作start 之前主线程的准备数据，子线程一定看得到
线程终止规则线程内的所有操作 hb 其他线程检测到它结束（join() 返回）子线程算完的结果，join 之后主线程一定看得到
中断规则一个线程调用 interrupt() hb 被中断线程检测到中断取消标志 + isInterrupted 不需要额外同步
对象终结规则构造器结束 hb finalize() 开始了解即可
传递性A hb B 且 B hb C，则 A hb C把上面的规则串成链的关键胶水 ⭐

用传递链推理：普通变量怎么"蹭"到可见性

int data = 0;                    // 普通变量
volatile boolean ready = false;  // volatile 变量

// 线程A（写）                  // 线程B（读）
data = 42;                      if (ready) {              // ③
ready = true;   // ②               int r = data;          // ④ 保证读到 42
                                }
// 推理链：① hb ②（程序顺序规则）
//         ② hb ③（volatile 规则：写 hb 后续读）
//         ③ hb ④（程序顺序规则）
// 传递性 ⇒ ① hb ④：data=42 对线程B可见，虽然 data 不是 volatile

答题口径：happens-before 是 JMM 提供给程序员的可见性契约——只要两个操作之间连得出 hb 链，JMM 就保证前者的结果对后者可见；连不出链且至少一方是写，就是数据竞争（data race），程序行为未定义。上面这条例子能白板写出来，"hb 是推理工具"就不是空话。

start / join 规则的实战：不用同步也能安全交接

int[] holder = new int[1];
int base = 40;                                       // ① main 线程的准备

Thread t = new Thread(() -> holder[0] = base + 2);   // start 规则：① hb 子线程内所有操作
t.start();                                           //   base=40 对子线程必然可见
t.join();                                            // 终止规则：子线程的写 hb join 返回
System.out.println(holder[0]);                       // 42 —— 无需 volatile、无需锁
// 但注意：join 只保证"交接这一次"；线程跑起来后改普通变量仍要靠 volatile/锁

05volatile 深挖 ⭐⭐

三板斧：可见性 + 有序性 + （不保证原子性）

① 可见性：靠缓存一致性协议，不是"刷回主内存"

  • 线程写 volatile 变量时，通过 CPU 的缓存一致性协议（如 MESI）把其他核里该变量所在的缓存行置为无效（Invalidate）；其他线程随后读取时发现缓存行已失效，必须重新加载最新值。
  • 不严谨说法，别在面试里讲："volatile 写立即刷回主内存、读强制从主内存读"——主内存只是兜底，真正的主角是各核缓存间的一致性流量。HotSpot 在 x86 上对 volatile 写生成 lock 前缀指令，正是靠它触发缓存行回写并让其他核失效。
  • 顺带的严谨结论：volatile 还保证 long/double 的 64 位读写原子（不加 volatile 时 JMM 允许 JVM 把 64 位读写拆成两次 32 位，这是著名的非原子协议漏洞）。

MESI 四态速查（被追"一致性协议是什么"时的底牌）

状态含义本核能干嘛
Modified（已修改）只有本核持有，且已被改过、与内存不一致可读可写
Exclusive（独占干净）只有本核持有，与内存一致可读可写（写它无需通知任何核）
Shared（共享）多核都持有，均与内存一致可读；写之前必须先让其他核的副本失效
Invalid（无效）本核缓存行已失效不可用，读必须重新加载

所以 volatile 写"让其他核看到最新值"的完整动作是：一致性消息把别核的 S 态行打回 I，别核再读时发现是 I，触发重新加载——全程主要发生在核间缓存一致性流量里，主内存只是兜底。这也是"伪共享"问题的机制源头（见本章追问链）。

② 有序性：内存屏障禁止重排

JMM 对 volatile 采用保守的屏障策略（JSR-133 Cookbook）：volatile 操作与普通操作的重排被按序隔开——

位置插入的屏障作用
volatile 写之前StoreStore保证前面的普通写先于 volatile 写对其他处理器可见
volatile 写之后StoreLoad最重的屏障，保证 volatile 写对后续所有读/写有序（x86 上只有它能禁止写读乱序）
volatile 读之后LoadLoad + LoadStore保证 volatile 读先于后续的普通读和普通写，防止读到旧数据配新标志

③ 不保证原子性：count++ 反例

private static volatile int count = 0;

public static void main(String[] args) throws Exception {
    Runnable r = () -> {
        for (int i = 0; i < 1000; i++) count++;   // volatile 也救不了 count++
    };
    Thread[] ts = new Thread[10];
    for (int i = 0; i < 10; i++) { ts[i] = new Thread(r); ts[i].start(); }
    for (Thread t : ts) t.join();
    System.out.println(count);   // 10 线程 × 1000，结果大概率 < 10000
}
// 原因：count++ 是 读→改→写 三步（getfield / iadd / putfield）
// 两个线程都读到旧值 1000 → 各自 +1 → 都写回 1001，丢一次更新
// volatile 只保证"每次读到最新值"，挡不住两步之间的交错

适用场景与不适用场景

场景为什么行示例
状态标志位单写多读、单次赋值天然原子volatile boolean running 优雅停机
单写多读一个写线程刷新，多个读线程可见，无读改写配置热更新引用、上下文开关
DCL 单例的字段禁止"分配→初始化→赋引用"重排（见第 06 节）01-java/15 单例模式 ⭐
计数器 / 累加器 ✗读改写不原子，必须用 AtomicLong / LongAdder05 无锁编程
// 状态标志位：volatile 最经典的正确用法
private volatile boolean running = true;

public void run() {
    while (running) { doWork(); }     // volatile 读：能看到别的线程置 false
}
public void shutdown() { running = false; }

06指令重排与内存屏障

重排发生在三个层面

  • 编译器重排：javac/JIT 在不改变单线程语义的前提下调整指令顺序（表达式重排、消除冗余）。
  • CPU 乱序执行：现代 CPU 指令级并行（ILP），无依赖的指令可乱序发射、写回。
  • 内存系统重排：store buffer / invalidate queue 让"写"在其他核看来到达顺序与提交顺序不一致——即便 CPU 不乱序，多核观察仍可能乱序。

经典双线程乱序示例

int a = 0;
boolean flag = false;

// 线程A                 // 线程B
a = 1;                   if (flag) {
flag = true;                 int i = a * 2;   // a 可能是 1，也可能是 0！
                         }
// 意外①（有序性）：A 内两行无数据依赖，可能被重排为
//   flag=true 先于 a=1 —— B 进了 if 却读到 a=0
// 意外②（可见性）：即使不重排，B 的工作内存里 a 还是旧副本 0
// 解法：flag 加 volatile —— 写读之间建立 hb，同时屏障挡住 a=1 溢出

两个豁免牌：as-if-serial 与数据依赖

  • as-if-serial：无论怎么重排，单线程的执行结果不能被改变——所以单线程永远感觉不到重排，重排只在多线程观察下暴露问题。
  • 数据依赖：同一变量存在写后读/写后写/读后写依赖的两个操作，编译器与 CPU 不会重排它们（a=1; b=a; 不会被倒过来）。但跨线程、跨变量的依赖不在保护范围内——这正是 volatile 屏障要补的洞。

DCL 不加 volatile 的后果 ⭐

public class Singleton {
    private static volatile Singleton instance;   // ⭐ 去掉 volatile = 半初始化陷阱

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查：无锁快速路径
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查：防重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
// instance = new Singleton() 实际是三步：
//   ① 分配对象内存   ② 调用构造器初始化   ③ instance 指向该内存
// ②③ 无数据依赖，可能被重排为 ①③②：
//   线程A 执行到 ③（引用已非 null、还没执行 ②），
//   线程B 第一次判 null 不成立，直接 return —— 拿到
//   "已分配内存但字段还是默认值"的半成品对象
// volatile 的写屏障保证 ③ 之前的 ② 对读到 ③ 的线程可见

final 字段的内存语义（一句话版）

JLS 17.5：只要对象正确构造（构造器中 this 没有逃逸），final 字段的写入与构造器结束存在 hb 保证，所有线程无需任何同步就能看到 final 字段的正确值——这是不可变对象线程安全的基石，展开在 01-java/05 封装与不可变。

四种内存屏障速查

屏障语义
LoadLoad屏障前的读 先于 屏障后的读
StoreStore屏障前的写 先于 屏障后的写
LoadStore屏障前的读 先于 屏障后的写
StoreLoad屏障前的写 先于 屏障后的读；开销最大，x86 上近似全能屏障（mfence / lock 指令）

07高频追问与陷阱

  • 追问链：volatile 能保证可见性 → 那全用 volatile 行不行？→ 不行。读改写不原子（count++）；而且每个 volatile 读写都插屏障、破坏 JIT 优化，滥用有实打实的性能税。
  • 陷阱："volatile 写会立即刷回主内存"→ 严谨说法是"通过 MESI 等缓存一致性协议使其他核的缓存行失效，写线程与读线程经由缓存一致性流量看到最新值"，主内存只是抽象兜底。
  • 陷阱：volatile 修饰数组/引用→ 只保证引用本身的可见性与有序性，不保证数组元素、对象内部字段的写对其他线程可见（元素要 AtomicXxxArray，字段要逐个 volatile 或用不可变对象）。
  • 经典数字题：volatile int i，10 个线程各 i++ 100 次，i 是多少？→ 介于 100~1000 的不确定值（通常远小于 1000）。追问"为什么不是 1000"引回读改写三步；追问"怎么修"引到 AtomicLong/锁。
  • 追问：long/double 为什么要专门讲原子性？→ JMM 的 64 位非原子协议允许 32 位平台上拆两次读写，可能读到"高低位各一半"的脏值；volatile 强制 64 位原子，商用 64 位 JVM 的普通 long 读写实际也是原子的。
  • 追问：happens-before 和时间顺序什么关系？→ 无必然关系：A hb B 不代表 A 物理上先执行；有 hb 链 ⇒ 结果可见，无 hb 链 ⇒ 数据竞争、结果未定义。
  • 追问：final 一定安全吗？→ 构造器里 this 逃逸（如注册监听器、开线程），final 的初始化保证就破了——"正确构造"是前提。
  • 追问链：MESI → 那伪共享（false sharing）是什么？→ 两个无关变量挤在同一个缓存行（64B），一个核写自己的变量就把整行打回 I，另一个核的变量跟着"陪葬"，互相乒乓 → 解法？缓存行填充（padding）、@Contended（需 JVM 参数开启）、或像 LongAdder 那样把热点分散到多个 Cell（05 无锁编程）。
  • 深挖方向（加分）：MESI 之下还有 store buffer/invalidate queue 带来的伪共享、缓存行填充问题，见 14 并发数据结构 与 04 锁策略。

08面试自查清单

  1. 能说清 JMM 是 JLS 里的规范而非内存区域，并讲出它"屏蔽硬件差异 + 定义可见性语义"两大职责。
  2. 主内存/工作内存的抽象能画出来，知道工作内存是缓存/寄存器/写缓冲的抽象、线程通信必须经主内存。
  3. 三性 = 定义 + 反例 + 解药三连答，能给出"synchronized 管三性、volatile 管两性、final 管一件"的矩阵。
  4. 能默写 happens-before 至少五条规则，并解释"hb 是可见性推理工具，不是时间顺序"。
  5. 能用程序顺序 × volatile × 传递性写出"data 蹭 ready 可见性"的白板推导。
  6. volatile 可见性讲得出 MESI 口径（而非"刷回主内存"），有序性讲得出四类屏障的插入位置。
  7. 能写 count++ 反例并解释为什么 volatile 不救；知道状态标志位、单写多读、DCL 是它的正确场景。
  8. 能完整讲出 DCL 不加 volatile 时"分配→初始化→赋引用"被重排的后果。
  9. 知道 as-if-serial、数据依赖例外、final 字段语义（JLS 17.5）一句话口径。
  10. MESI 四态（M/E/S/I）能各自一句话说清，能顺着 MESI 讲出伪共享的机制与三种解法。
