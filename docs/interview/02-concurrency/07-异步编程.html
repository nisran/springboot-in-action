第 07 章 · 异步编程：Future 与 CompletableFuture

Future 的三大局限 · supplyAsync 与 commonPool 大坑 · 链式编排 · allOf 聚合 · 异常传播三剑客 · 回调线程问题 —— 从"能等到结果"进化到"能编排异步流"

01面试怎么考

  1. Future 接口有什么局限？为什么还需要 CompletableFuture？⭐（几乎必问的开场）

  4. 两个 CompletableFuture 的结果怎么合并？多个呢？allOf 之后怎么取结果？⭐
  5. exceptionally / handle / whenComplete 三者有什么区别？⭐（经典对比题）
  6. 链上某个任务抛了异常，后面的 thenApply 还执行吗？异常什么时候抛出来？

本章答题心法：Future 挑毛病 → CF 给解法。三大局限（阻塞、不能组合、异常处理不便）正好对应 CF 的三大卖点（回调非阻塞、链式组合、异常传播可控）——把这条对应线讲顺，整章的题都是它的展开。生产经验集中在两处：默认线程池的坑和回调线程不确定性，这两处能讲到事故案例就是高级岗水平。

02Future 的三大局限 ⭐

Future 是"异步结果的凭据"：submit 拿到凭据，将来用它取结果。但它只有"取"的能力，没有"编排"的能力（笔记三大局限并入）：

  • 阻塞获取结果：get() 会一直挂起调用线程；轮询 isDone() 既浪费又延迟。
  • 缺乏组合能力：不能声明"完成后自动做 X"，两个 Future 相互依赖时只能层层 get 嵌套，异步写成了同步。
  • 异常处理不便：任务里的异常被包成 ExecutionException，只有调 get() 时才抛出——不 get 就永远不知道出了错。
ExecutorService pool = Executors.newFixedThreadPool(2);   // 演示用，生产见第 06 章手动创建
Future<User> f1 = pool.submit(() -> queryUser(id));    // 任务 1
Future<List<Order>> f2 = pool.submit(() -> queryOrders(id)); // 任务 2
// 局限 1：任务虽并行了，取结果还是得阻塞串行等
User u = f1.get();
List<Order> o = f2.get();
// 局限 2：做不到"f1 完成后自动转换再接 f2"，只能 get 完手动串
// 局限 3：任务里抛的异常只在 get() 时以 ExecutionException 抛出，cause 才是真实异常
try { f1.get(); }
catch (ExecutionException e) {
    Throwable real = e.getCause();     // ⚠️ 真实异常在 cause 里，别只打 e
}

一句话总结：Future 把"任务的提交"和"结果的取得"解耦了，但结果的取得仍是同步思维；CompletableFuture 补上的正是"完成后自动怎样"的回调编排能力——它是 Future 的实现类，同时实现了 CompletionStage 接口（所有 thenXxx 都定义在这里）。

03创建与默认线程池的坑 ⭐

两个静态工厂

  • supplyAsync(Supplier)：任务有返回值，返回 CompletableFuture<T>。
  • runAsync(Runnable)：任务无返回值，返回 CompletableFuture<Void>。
  • 两者各有重载：不传 Executor 时默认提交到 ForkJoinPool.commonPool()；传了 Executor 就用你的池。

默认 commonPool 的坑（生产重灾区）：commonPool 大小 = CPU 核数 − 1，且是守护线程、全 JVM 共享。把 IO/RPC 任务默认丢上去会发生两件事：① 池被慢 IO 占满，全应用的并行流和其他默认用 commonPool 的组件一起饿死；② 守护线程随 JVM 退出被硬杀，收尾逻辑不可靠。结论：生产代码必须显式传自定义线程池（笔记结论 + 阿里规约同口径）。

// ⚠️ 反面教材：默认 commonPool（核数-1、守护线程、全局共享）
CompletableFuture<String> bad = CompletableFuture.supplyAsync(() -> slowRpc());

// ✅ 生产写法：显式传线程池（IO 密集给足线程数，见第 06 章怎么定）
ThreadPoolExecutor rpcPool = new ThreadPoolExecutor(
        20, 40, 60L, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(200),
        r -> new Thread(r, "rpc-pool-" + seq.incrementAndGet()),
        new ThreadPoolExecutor.CallerRunsPolicy());

CompletableFuture<String> userF =
        CompletableFuture.supplyAsync(() -> slowRpc(), rpcPool);  // ← 第二个参数传池

追问"为什么 commonPool 大小是核数−1"：设计定位是 CPU 密集分治（Fork/Join），留 1 核给调用线程本身，避免提交者被饿死——详见 第 06 章 Fork/Join 节。再追"虚拟线程出来后 CF 默认池变了吗"→ 没变，仍是 commonPool；IO 链路要自己显式传虚拟线程 executor（10 章 §05）。

04串行编排：then 系四兄弟

方法入参（拿什么）返回语义（类比）
thenApply(fn)上游结果 TCF<R>转换：结果 → 结果（map）
thenAccept(fn)上游结果 TCF<Void>消费：结果 → 副作用（落库、发通知）
thenRun(fn)不看结果CF<Void>执行：上游完成 → 做件事
thenCompose(fn)上游结果 T → 新的 CFCF<R>（扁平化）串联下一个异步任务（flatMap）
// 串行链：查 id → 转成 User → 创建订单 → 发通知（每步拿上一步的结果）
CompletableFuture<Void> flow = CompletableFuture
    .supplyAsync(() -> queryUserId(), pool)   // CF<Long>
    .thenApply(id -> loadUser(id))            // 转换：CF<User>
    .thenApply(user -> createOrder(user))     // 再转换：CF<Order>
    .thenAccept(order -> notify(order));      // 消费：无返回，链终止于 CF<Void>

// thenCompose：下一步"本身也是异步的"
// 用 thenApply 会嵌套：CF<CF<Order>> —— 拆包裹才能用
CompletableFuture<CompletableFuture<Order>> nested =
    queryUserIdAsync(pool).thenApply(id -> loadUserAsync(id, pool));
// 用 thenCompose 直接扁平化成 CF<Order> ✅
CompletableFuture<Order> flat =
    queryUserIdAsync(pool).thenCompose(id -> loadUserAsync(id, pool));

thenApply vs thenCompose 一句话：回调返回"值"用 thenApply，返回"又一个 CF"用 thenCompose——与 Stream/Optional 的 map vs flatMap 完全同款区分，面试可以用这个类比秒答。笔记里的"一次排序（串行），then..."就是这组。

05组合与聚合 ⭐

两两组合与竞速

  • thenCombine(other, (r1, r2) -> ...)：两个都完成才走，拿两个结果合并成一个（笔记 thenCombine）。
  • applyToEither(other, fn) / acceptEither(other, fn)：任一完成就用谁的结果（转换 / 消费），另一个被忽略——竞速、多机房就近读的写法。

多任务聚合：allOf / anyOf

  • allOf(cf...)：等全部完成才完成；返回 CompletableFuture<Void>——泛型丢了，结果要回到各个子 CF 上取。
  • anyOf(cf...)：等任一完成；返回 CompletableFuture<Object>，注意类型收窄。
CompletableFuture<User> userF  = CompletableFuture.supplyAsync(() -> rpcUser(id), pool);
CompletableFuture<List<Order>> orderF = CompletableFuture.supplyAsync(() -> rpcOrders(id), pool);
CompletableFuture<Integer> pointF = CompletableFuture.supplyAsync(() -> rpcPoints(id), pool);

// 两两合并（都完成才走）
CompletableFuture<String> two = userF.thenCombine(orderF, (u, o) -> render(u, o));

// 竞速（任一完成）：主备两个源，谁先回用谁
CompletableFuture<User> first = primaryRpc.applyToEither(backupRpc, u -> u);

// 全部完成再聚合 ⭐（allOf 只返回 CF<Void>，回到各自 CF 上 join）
CompletableFuture<Detail> all = CompletableFuture.allOf(userF, orderF, pointF)
    .thenApply(v -> new Detail(
        userF.join(),    // 此时已全部完成，join 不会阻塞；若某个子任务失败，join 在这里抛异常
        orderF.join(),
        pointF.join()));

// 想对"未完成/失败"的子任务兜底，可用 getNow(null) 判空替代 join
Detail safe = new Detail(
    Optional.ofNullable(userF.getNow(null)).orElse(User.DEFAULT), ...);

allOf 的两个坑：① 泛型丢失——返回 CF<Void>，必须在 thenApply 里回头 join 各子 CF（join 时已全部完成，不阻塞）；② 一损俱损——任何一个子任务异常，allOf 整体异常、join 抛 CompletionException。要"部分失败不影响整体"，得给每个子任务先套 handle/exceptionally 兜底，再进 allOf（第 10 节实战就是这么写的）。

06异常传播三剑客 ⭐

CF 的核心卖点之一：异常不用等 get() 才处理，在链上就能接住（笔记"优雅处理异常，无需在 get 时捕获"）。三者区别是经典对比题：

方法回调签名正常时异常时能否改变结果
exceptionallye → 兜底值跳过不执行执行，返回兜底值（恢复）能：异常 → 恢复成默认值
handle(result, e) → 新值执行（e = null）执行（result = null）能：正常异常都走，可统一转换
whenComplete(result, e) → void执行（e = null）执行（result = null）不能：只旁观，原结果原样传下游（打点/日志用）
CompletableFuture<Integer> safe = CompletableFuture
    .supplyAsync(() -> 100 / n, pool)        // n = 0 → ArithmeticException 沿链下传
    .handle((r, e) -> {                      // 正常/异常都走：记日志 + 给默认值
        if (e != null) { log.warn("failed", e); return 0; }
        return r;
    })
    .exceptionally(e -> -1);                 // 再兜一层（前面已恢复，通常不会再触发）

// whenComplete 只旁观：打点埋点用，改不了结果
safe.whenComplete((r, e) -> metrics.count("calc.done"));

异常怎么传播、何时抛出

  • 异常发生后，链上后续的 thenApply / thenAccept 等全部跳过，直接流向最近的异常回调（exceptionally / handle）；恢复了就继续正常走。
  • 一路没人拦截 → 异常一直存到终端：join() 抛 CompletionException（非受检），get() 抛受检的 ExecutionException（真实异常在 cause）。

最隐蔽的线上事故：子任务抛了异常、链上没有 exceptionally/handle、又从不 join/get——异常被静默吞掉，任务"看起来没执行"。防御：每个异步链的末端要么消费异常，要么统一挂一个兜底 whenComplete 打日志。

07超时控制：orTimeout / completeOnTimeout

  • orTimeout(long, unit)（JDK 9）：到时未完成 → 以 TimeoutException 异常完成，走 exceptionally/handle 兜底。
  • completeOnTimeout(T, long, unit)（JDK 9）：到时未完成 → 直接用给定值正常完成——一步到位的超时兜底，更常用。
  • 老办法 get(timeout)：超时抛 TimeoutException 但阻塞的是调用方线程，不如上面两个异步优雅。
// 写法一：completeOnTimeout —— 超时给默认值，链上无异常（推荐）
CompletableFuture<String> f1 = CompletableFuture
    .supplyAsync(() -> rpcCall(), pool)
    .completeOnTimeout(DEFAULT_VALUE, 500, TimeUnit.MILLISECONDS);

// 写法二：orTimeout —— 超时以异常完成，再自己兜底
CompletableFuture<String> f2 = CompletableFuture
    .supplyAsync(() -> rpcCall(), pool)
    .orTimeout(500, TimeUnit.MILLISECONDS)
    .exceptionally(e -> DEFAULT_VALUE);

注意：orTimeout / completeOnTimeout 只是让结果作废，不会中断或取消底层任务——那个慢 RPC 还在池里占着线程。所以超时兜底要配"池容量按超时预算设计"（最坏情况：池被慢任务占满，靠第 06 章的水位告警发现），真要终止任务得任务内部响应 interrupt 或用可取消的 HTTP 客户端。

08回调在哪个线程执行 ⭐（高频坑）

thenApply 系列（不带 Async 后缀）的回调执行线程不确定，只有两种可能，取决于注册时上游是否已完成：

  • 上游已完成 → 回调由注册回调的线程（调用 thenApply 的那个线程）立即执行。
  • 上游未完成 → 回调被压入栈，由完成任务的线程（跑 supplyAsync 的池线程，或事后调 complete() 的线程）触发执行。
  • 要确定性 → 用 thenApplyAsync(fn, pool)：回调强制切换到指定线程池执行。
ThreadLocal<String> ctx = new ThreadLocal<>();
ctx.set("trace-123");

CompletableFuture
    .supplyAsync(() -> "data", pool)       // 在 pool 的线程执行
    .thenApply(d -> {
        // ⚠️ 这里可能是 pool 线程，也可能是注册回调的主线程——不确定！
        // ctx.get() 大概率是 null（换了线程）→ traceId / MDC 上下文丢失
        log.info("trace={}", ctx.get());   // 经典事故：日志没 traceId，链路断了
        return d;
    });
// 需要固定执行线程时：thenApplyAsync(fn, callbackPool)

推论必背：CF 的链会跨线程，不能依赖 ThreadLocal 传上下文——用户信息、traceId 要显式传参，或用阿里 TransmittableThreadLocal（TTL）在提交任务时捕获快照。MDC 丢失是 CF 上线后第一名的事故，ThreadLocal 细节见 第 09 章 并发容器。

09原理：result + Completion 栈（观察者模式）

CompletableFuture 内部只有两个核心字段（笔记 693-696 并入）：

  • volatile Object result：结果（值或异常），CAS 写入——写入成功即"完成"。
  • volatile Completion stack：完成后要触发的操作栈——所有注册的回调（依赖）以 Treiber 栈（无锁 CAS 栈）形式挂在这里。
注册阶段（thenApply/thenAccept/...）：
    上游未完成 → 把"这个回调 + 下一步"包装成节点，CAS 压入 stack
    上游已完成 → 不入栈，直接在当前线程执行回调

完成阶段（任务跑完 / complete() / completeOnTimeout 到时）：
    CAS 写入 result 成功
      → postComplete()：从 stack 逐个弹出节点，触发里面挂着的依赖
      → 依赖完成后又会触发它的 stack —— 一环扣一环传播下去

这就是观察者模式：回调是观察者，注册即订阅，任务完成即通知——比起 Future 的"你必须来取"，CF 是"完成了我叫你"。

每个 Completion 节点既持有"要执行的回调"，又持有"下游的 CompletableFuture"（依赖），触发时算出下游结果、完成下游、再触发下游的栈——所以一条 thenApply(...).thenApply(...) 链在数据结构上就是一串节点，异常跳过正常回调、直达异常回调的传播行为也由此而来。

10实战：并行调 3 个 RPC 再聚合 ⭐

商品详情页：并行取用户、库存、推荐三个 RPC，各自超时兜底 + 异常降级，allOf 等齐后聚合，整链再留一道总闸——三层防御的标准生产写法：

public CompletableFuture<Detail> loadDetail(long itemId) {
    // 第一层：每个子任务独立兜底 —— 失败/超时降级为默认值，不带着异常进 allOf
    CompletableFuture<User> userF = CompletableFuture
        .supplyAsync(() -> userRpc.get(itemId), rpcPool)
        .completeOnTimeout(User.DEFAULT, 300, TimeUnit.MILLISECONDS)
        .exceptionally(e -> { log.warn("userRpc failed, itemId={}", itemId, e); return User.DEFAULT; });

    CompletableFuture<Stock> stockF = CompletableFuture
        .supplyAsync(() -> stockRpc.get(itemId), rpcPool)
        .completeOnTimeout(Stock.DEFAULT, 300, TimeUnit.MILLISECONDS)
        .exceptionally(e -> Stock.DEFAULT);

    CompletableFuture<List<Item>> recF = CompletableFuture
        .supplyAsync(() -> recRpc.get(itemId), rpcPool)
        .completeOnTimeout(List.of(), 500, TimeUnit.MILLISECONDS)   // 推荐可降级为空列表
        .exceptionally(e -> List.of());

    // 第二层：allOf 等齐 → 聚合（子任务都已兜底，join 不会抛）
    // 第三层：整链总闸 orTimeout + 总兜底（三级全挂 → 降级页）
    return CompletableFuture.allOf(userF, stockF, recF)
        .thenApply(v -> new Detail(userF.join(), stockF.join(), recF.join()))
        .orTimeout(800, TimeUnit.MILLISECONDS)
        .exceptionally(e -> Detail.degraded(itemId));
}

答题模板：先说架构（三个子任务并行、各自兜底、allOf 聚合、总闸兜底），再解释为什么每个子任务先兜底（避免一损俱损，见第 05 节的坑），最后补一刀"超时不取消底层任务，池容量要按超时预算设计"。这套讲完，场景题基本满分。

11高频追问与陷阱

  • 追问链：Future 局限 → CF 怎么解决 → 回调写多了不也是"回调地狱"？→ thenCompose 扁平化串联 + 类型安全的链式 API，比嵌套回调可读得多。
  • 追问链：不传线程池用哪个池 → commonPool 多大、什么线程 → 为什么 IO 任务不能放→ 核数−1、守护线程、全局共享 → 占满后并行流全饿死 → 生产传自定义池。
  • 追问链：thenApply vs thenCompose → 回调返回什么决定用哪个→ 值用 thenApply，CF 用 thenCompose（map vs flatMap）→ thenApply vs thenApplyAsync → 执行线程是否强制切池。
  • 追问链：allOf 之后怎么拿结果→ 返回 CF<Void> 泛型丢失 → 在 thenApply 里回头 join 各子 CF（已全部完成，不阻塞）→ 某个子任务可能失败 → join 抛 CompletionException → 要部分容错就先给每个子任务 handle。
  • 陷阱：异常静默吞掉→ 无异常回调 + 不 join/get = 异常无人知晓；防御：链末端统一挂 whenComplete 记日志。
  • 陷阱：join vs get→ join 抛非受检的 CompletionException（适合 Stream/lambda 里用），get 抛受检的 ExecutionException + InterruptedException。
  • 陷阱：ThreadLocal / MDC 丢失→ 回调线程不确定（第 08 节），上下文显式传参或用 TTL。
  • 陷阱：orTimeout 不取消任务→ 只是结果作废，慢任务还占着线程；池会被拖满，要配水位监控。
  • 场景题：CF 任务"不执行"怎么排查？→ 先看是不是默认 commonPool 被别的组件占满 → 再看自定义池是否队列满触发 CallerRuns → 最后看是不是异常被吞（末端 whenComplete 没挂日志）。

12面试自查清单

  1. Future 三大局限（阻塞、不能组合、异常要 get 才拿到）+ ExecutionException 的 cause 细节，能配代码佐证。
  2. supplyAsync / runAsync 区别；默认 commonPool 的大小（核数−1）、守护线程属性、IO 任务饿死并行流的坑。
  3. then 系四兄弟各自语义；thenApply vs thenCompose 能用 map/flatMap 类比一句话讲清。
  4. thenCombine / acceptEither / applyToEither / allOf / anyOf 场景对应；allOf 后 join 取结果 + 泛型丢失原因。
  5. exceptionally / handle / whenComplete 三列对比表（正常走不走、异常走不走、能否改结果）张口就来。
  6. 异常传播规则：中间回调跳过、直达异常回调；终端 join 抛 CompletionException、get 抛 ExecutionException。
  7. orTimeout / completeOnTimeout 的差异，且知道超时不取消底层任务。
  8. 回调执行线程的两种可能 + ThreadLocal/MDC 丢失事故 + thenApplyAsync 解决法。
  9. 原理：result + Completion 栈（Treiber 栈）、注册压栈 / 完成弹栈、观察者模式口径。
