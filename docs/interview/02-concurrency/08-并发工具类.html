第 08 章 · 并发工具类

Semaphore · CountDownLatch · CyclicBarrier · Exchanger —— 建在 AQS 之上的四个"线程协作"工具，外加一张场景选型表和两个并发模式
⭐ 高频：CountDownLatch vs CyclicBarrier · Semaphore 限流 蓝本：AlgoMaster Concurrency · Synchronizers 已合并：Java/java 基础.md 高级并发工具节 ✅

01面试怎么考

  1. CountDownLatch 和 CyclicBarrier 有什么区别？⭐（几乎必问，答不出对比表直接扣分）
  2. Semaphore 是干什么的？怎么用它对下游接口做并发保护？公平和非公平有什么区别？
  3. 主线程要等 N 个并行任务全部完成再汇总，有几种写法？各自优劣？⭐
  4. CyclicBarrier 的 barrierAction 是哪个线程执行的？
  5. 多线程分阶段迭代计算（每轮算完汇总再进下一轮）用什么同步？听说过 Phaser 吗？
  6. 两个线程之间要互相交换一批数据，用什么？
  7. 生产者-消费者模式的本质是什么？不用 BlockingQueue 手写一个要小心哪些坑？
  8. 工作密取（work stealing）是什么？Fork/Join 和普通线程池的区别？

这一章的特点是："会用"不难，难在"选型"和"边界"。四个工具的 API 五分钟就能学会，面试官真正考的是：给你一个场景（等任务、限并发、多轮同步、交换数据），你能不能立刻说对工具并讲清"为什么不用另外三个"。7 年经验的答法：先一句话给模型（比如"Semaphore 就是 N 个车位"），再讲自己的业务场景和踩过的坑（countDown 忘了放 finally、barrier 被中断全员失败），最后主动补一张对比表——把对比表说全，这道题就从"及格"变"加分"。

四个工具全部建在 第 03 章 的 AQS 之上（latch 用共享模式、Semaphore 也用共享模式、barrier 用 ReentrantLock + Condition），底层没新东西——新的是"协作语义"。被追问底层时往 AQS 的 state 上引即可。

02Semaphore：许可数模型

一句话模型：N 个许可证（permits），acquire() 拿走一个（没了就阻塞），release() 还回一个——像一座只有 N 个车位的车场。构造时指定许可数，不设置就是"同时最多 N 个线程通过这段代码"。

Semaphore permits = new Semaphore(10);            // 默认非公平
// Semaphore permits = new Semaphore(10, true);   // 公平：先到先得 FIFO

if (permits.tryAcquire(500, TimeUnit.MILLISECONDS)) {  // ⭐ 超时版：等不到就快速失败
    try {
        callDownstream();          // 任意时刻最多 10 个线程同时执行到这里
    } finally {
        permits.release();         // ⭐ 必须与 acquire 严格配对，用完归还
    }
} else {
    throw new BizException("系统繁忙，请稍后重试");   // 过载保护：不排队、不堆积
}

两个核心用途

  • 限流（瞬时并发上限）：保护自身或下游——比如下游接口最多扛 10 个并发，超过就挡在门外。注意 tryAcquire(timeout) 的价值：等不到许可时快速失败而不是无限排队，请求堆积本身也是一种事故。
  • 资源池化：限制同时使用某个昂贵资源的线程数——数据库连接、文件句柄、License 数量，本质上连接池的"最大连接数"就是一个 Semaphore。

公平 vs 非公平

  • 非公平（默认）：许可释放后被唤醒的线程和新来的线程直接抢——吞吐高（少了队列调度开销），但可能饥饿；语义与 第 04 章 的非公平锁完全一致。
  • 公平（new Semaphore(n, true)）：严格 FIFO，先到先得；吞吐略低，适合对顺序敏感的场景（比如排队刷票）。

陷阱一：Semaphore 限的是"并发数"，不是"速率"。10 个许可 = 最多 10 个同时在跑，每秒放进多少波无所谓；要限 QPS 得用令牌桶（Guava RateLimiter / Sentinel）。陷阱二：release 可以多调——Semaphore 不检查持有者，多 release 一次许可数就会超过初始值（许可超发），所以 acquire/release 必须像锁一样 try-finally 严格配对。

实现走读：state 就是剩余许可（AQS 共享模式落地）

Semaphore 的全部逻辑就是"把 CAS 的对象换成许可数"，公平 / 非公平只是获取前要不要查队列（模式约定见 03 章 §06 · 独占 vs 共享）：

// Semaphore.Sync（AQS 子类）：公平与非公平共用这两个方法
protected final int tryAcquireShared(int acquires) {      // acquire() 最终落到这
    for (;;) {
        int available = getState();
        int remaining = available - acquires;             // ① 剩余 = 许可数 - 1
        if (remaining < 0 || compareAndSetState(available, remaining))
            return remaining;                             // ② 负数 → AQS 让你入队 park；≥0 拿到
    }                                                     // ③ CAS 失败（被别人抢了）→ 自旋重试
}
protected final boolean tryReleaseShared(int releases) {  // release() 落到这
    for (;;) {
        int current = getState();
        int next = current + releases;                    // ④ 还许可：不校验持有者（超发陷阱的根源）
        if (compareAndSetState(current, next))
            return true;                                  // ⑤ true → AQS doReleaseShared 唤醒等待者
    }
}
  • ②⑤ 正是共享模式的返回值约定：负数入队、true 触发传播唤醒——一次 release 还回多张许可时，多个等待者被接力放行，而不是每张许可醒一个轮一轮。
  • 追问：tryAcquire(timeout) 怎么实现？→ doAcquireSharedNanos：入队后 parkNanos 按 deadline 限时睡，醒来先看时间到没到再决定重试还是放弃。
  • 追问：公平版差在哪一行？→ 非公平的 tryAcquireShared 直接 CAS（上面的代码）；公平版先 hasQueuedThreads()——队列有人就 return -1 老实排队去，与 ReentrantLock 的 hasQueuedPredecessors() 同一思想（03 章 §06 答题口径）。

03CountDownLatch：一次性计数器 ⭐

模型：内部维护一个计数器，构造时指定 N；countDown() 使计数减 1（不阻塞，可重复调用到 0 以下无副作用）；await() 阻塞当前线程，直到计数减为 0（或超时/被中断）。计数到 0 后"门闩"永久打开，不可重置、不可重用——下一批任务要 new 一个新的。

角色语义上，latch 是"旁观者等事件"：await 的人通常不是 countDown 的人，各个任务数完数就各自走人，不互相等。

场景 1：主线程等 N 个并行任务聚合 ⭐

int n = 5;
List<Price> results = new CopyOnWriteArrayList<>();     // 聚合容器也要并发安全
CountDownLatch latch = new CountDownLatch(n);
for (int i = 0; i < n; i++) {
    final int idx = i;
    pool.execute(() -> {
        try {
            results.add(querySupplier(idx));            // 子任务
        } catch (Exception e) {
            results.add(FALLBACK_PRICE);                // 失败兜底：绝不能让 latch 卡住
        } finally {
            latch.countDown();                          // ⭐ 必须 finally：异常路径也要减计数
        }
    });
}
latch.await(3, TimeUnit.SECONDS);   // ⭐ 带超时：防止某个任务异常退出没 countDown，主线程永卡
merge(results);

与 CompletableFuture.allOf 对比（追问率极高）：latch 是"纯等待"，拿结果要自己聚合容器，异常也要自己兜；allOf（第 07 章）直接编排 Future——有返回值、异常传播、超时、编排组合都是现成的。选型口径：新代码/要结果用 allOf；任务来自老代码或回调式 API（拿不到 Future）、只是简单等待时用 latch。能说出 allOf 异常会"提前穿透"而 latch 需要自己兜底，就是加分答案。

场景 2：服务启动等依赖就绪

CountDownLatch ready = new CountDownLatch(3);   // 3 个依赖：DB、缓存、MQ
new Thread(() -> { initDb();   ready.countDown(); }).start();
new Thread(() -> { initRedis(); ready.countDown(); }).start();
new Thread(() -> { initMq();    ready.countDown(); }).start();
ready.await();                                   // 阻塞到三个依赖全部就绪
startServer();

反过来把计数设为 1 就是"发令枪"：N 个 worker 先 await 等着，主线程一声 countDown 全体同时起跑——压测预热、并行任务的统一起跑线都这么写。

两个必背事故点：① countDown 不放 finally——任务抛异常后计数永远到不了 0，await 全体永卡（所以 await 一定带超时兜底）；② latch 用完即弃，想"再来一轮"却复用旧实例——它不会报错，只是永远立即通过（计数已经是 0），看起来"代码正常跑"实则同步已失效，比报错更难排查。

实现走读：AQS 共享模式最短的一份作业

CountDownLatch 是 AQS 共享模式最精简的示范实现——tryAcquireShared 只有一行判断（模式约定见 03 章 §06 · 独占 vs 共享）：

private static final class Sync extends AbstractQueuedSynchronizer {
    Sync(int count) { setState(count); }               // ① state = 计数器初值
    protected int tryAcquireShared(int acquires) {
        return (getState() == 0) ? 1 : -1;             // ② 到 0 才放行（正数 = 继续传播）
    }
    protected boolean tryReleaseShared(int releases) {
        for (;;) {
            int c = getState();
            if (c == 0) return false;                  // ③ 已归零：再 countDown 无副作用
            int nextc = c - 1;
            if (compareAndSetState(c, nextc))
                return nextc == 0;                     // ④ 只有减到 0 那次返回 true → 触发级联唤醒
        }
    }
}
  • 方法对号：await() = acquireSharedInterruptibly → ②，state ≠ 0 返回负数 → 入队 park（响应中断版，超时版走 doAcquireSharedNanos）；countDown() = releaseShared → ④。
  • "减到 0 全员放行"就是传播唤醒的效果：归零那次 release 返回 true → AQS 唤醒队首 → 队首 tryAcquireShared 拿到 1 → setHeadAndPropagate 接力唤醒下一个，一条链放完全部 await。
  • "不可重置"在源码里一目了然：③④ 只会减、没有任何 setState(count) 的路径——复用要 new 新实例是 API 设计而非缺陷。
  • 追问：为什么用共享不用独占？→ 独占一次只放一个，等 N 个任务要被唤醒 N 轮；共享 + 传播唤醒，归零瞬间全员放行（03 章 §06 追问链）。

04CyclicBarrier：可重用屏障（与 latch 对比 ⭐）

模型：N 个线程（parties）互相等待，每个调 await() 报到；最后一个到达的线程触发"到齐"，全体放行，屏障自动重置，进入下一代（generation）。构造时可传 barrierAction——由最后到达的那个线程在放行前执行，此时其他线程还阻塞在 await，正好用它做各分片结果的聚合。

场景：分阶段计算（多轮迭代同步）

CyclicBarrier barrier = new CyclicBarrier(N, () -> {
    // barrierAction：最后到达的线程执行，其他 N-1 个还在 await —— 安全地聚合
    combinePartialResults();               // 聚合各分片本轮的阶段性结果
});

for (int t = 0; t < N; t++) {
    final int id = t;
    new Thread(() -> {
        for (int round = 0; round < ROUNDS; round++) {
            partials[id] = computeChunk(id, round);    // ① 各自算自己分片
            try {
                barrier.await();                        // ② 到齐放行，自动重置进入下一轮
            } catch (Exception e) {
                Thread.currentThread().interrupt(); return;
            }
            nextRoundInit(id);                          // ③ 用聚合后的结果开启下一轮
        }
    }).start();
}

这类"N 方多轮同步"（多线程各算各的分区，每轮末全员对齐一次再用全局结果开下一轮）正是 latch 做不到的：latch 一轮就废，barrier 一局可以玩 ROUNDS 轮。

CountDownLatch vs CyclicBarrier 对比表 ⭐（背熟）

维度CountDownLatchCyclicBarrier
角色语义旁观者等事件：await 的人与 countDown 的人通常不是一批参与者互相等：每个线程既是等待者也是被等者，到齐一起走
计数机制计数器只减不增，减到 0 门闩打开等待"到达数"凑满 N，凑满即放行
可重用一次性，到 0 后无法复位可重用，放行后自动重置进入下一代
附加动作无barrierAction，由最后到达的线程执行
失败行为忘 countDown 则 await 永卡，只能靠超时自救一方中断/超时 → 屏障 broken，全员抛 BrokenBarrierException（快速失败，不留僵局）
底层实现AQS 共享模式（state = 剩余计数）ReentrantLock + Condition（generation 代际标记）

一句话总结（面试官最爱听）：latch 是倒计时门闩——减到 0 永远开着，"等事件"；barrier 是人齐开闸——放行后复位，"互相等"，还能一轮接一轮。再补一句"barrier 一损俱损（broken 全员异常）、latch 一忘全卡"就是满分版。

陷阱：BrokenBarrierException。任何一个参与线程在 await 时被中断/超时，屏障进入 broken 状态，其余所有等待线程立即抛 BrokenBarrierException——这是设计上的快速失败，但要接好异常处理：本轮作废后要么 reset() 重建屏障，要么直接终止任务，别让 N-1 个线程拿着旧代屏障继续等下一轮（等不齐，只会再 broken 一次）。

05Exchanger：两线程交换数据

模型：一个"交换点"，两个线程各调 exchange(v)，先到的阻塞等后到的；两边都到了就互换数据，各自拿到对方给的东西继续走。只支持两方——这是它和前面三个最大的区别。

Exchanger<List<Order>> exchanger = new Exchanger<>();

// 线程 A：往缓冲区填数据，填满后换回一个"空"缓冲区继续填
new Thread(() -> {
    List<Order> buffer = new ArrayList<>();
    while (true) {
        fill(buffer);                              // 生产
        buffer = exchanger.exchange(buffer);       // 阻塞直到换回消费者的空缓冲区
    }
}).start();

// 线程 B：拿到的永远是装满的缓冲区，排空后换回去 —— 双向管道
new Thread(() -> {
    List<Order> buffer = new ArrayList<>();      // 一开始就是空的
    while (true) {
        buffer = exchanger.exchange(buffer);       // 换到满的
        drain(buffer);                             // 消费、清空
    }
}).start();
  • 典型场景：① 双向管道/双缓冲——一个线程填缓冲区、另一个排空，交换缓冲区引用，免去了同一个缓冲区的同步开销；② 遗传算法——两个线程各持一组"基因"，两两配对交换后各自演化。
  • 超时版：exchange(v, timeout, unit)——对方失联（崩溃/逻辑漏调）时自己能脱身，否则永久阻塞。
  • 多于两方就需要换工具：多方数据交换用队列或 Phaser 编排。

06场景选型表 ⭐

场景首选要点
等 N 个任务完成后聚合CountDownLatch / allOf纯等待用 latch；要返回值/异常传播/超时编排用 allOf
服务启动等 N 个依赖就绪CountDownLatch(N)就绪一个 countDown 一个；count=1 反用作"发令枪"
多轮全员同步（分阶段迭代）CyclicBarrier自动重置；barrierAction 由最后到达者做聚合
多阶段 + 参与者动态增减Phaser加分项，见下方一句展开
限制瞬时并发（限流/资源池）Semaphore限并发 ≠ 限速率；tryAcquire 超时快速失败
两个线程交换数据Exchanger双缓冲管道、遗传算法；超过两方不适用
定时/周期调度ScheduledExecutorService与上面互补——按"时间"触发而非按"到齐"触发

加分项：Phaser 一句话——Phaser 是 barrier 的泛化版：多阶段（一个 Phaser 管很多轮，不用像 barrier 那样一代代重复）+ 动态参与者（register() / arriveAndDeregister() 中途加入退出）+ onAdvance() 钩子可编程控制每一阶段的推进与终止。低并发面试能说出这个名字和"动态 parties"就够用了。

07并发模式

笔记里的三个模式（生产者-消费者、工作线程、Fork/Join）是这一节的骨架。面试考"模式"不是背名字，而是说清它解耦了什么、代价是什么、生产里用什么现成实现。

生产者-消费者模式

  • 本质：用缓冲区解耦"生产速率"与"消费速率"。队列满则生产者阻塞（天然背压 backpressure），队列空则消费者阻塞——两边各跑各的速度，峰值由队列吸收。
  • BlockingQueue 一句话版：阻塞队列把 wait/notify 的全部坑（虚假唤醒、锁对象配对、notify 随机唤醒、必须 while 判断）封装掉，生产环境直接用：
BlockingQueue<Task> queue = new LinkedBlockingQueue<>(1000);   // ⚠️ 必须显式给容量（第 09 章讲为什么）

new Thread(() -> { while (true) queue.put(produce()); }, "producer").start();  // 满则阻塞
new Thread(() -> { while (true) consume(queue.take()); }, "consumer").start(); // 空则阻塞
  • 面试常要求手写 wait/notify 版（考察锁与条件语义），完整实现与三大陷阱在 第 12 章 经典同步题。
  • 追问"有界还是无界"：无界队列在消费变慢时无限堆积直至 OOM——这正是第 09 章 LinkedBlockingQueue 默认容量陷阱要展开的。

工作线程模式（Worker Thread）

固定一组常驻 worker 反复从任务队列取活干——这就是线程池的全部：任务提交与任务执行解耦，线程复用削峰。生产实现、参数与拒绝策略在 第 06 章 线程池。

工作密取（Work Stealing）与 Fork/Join

  • 与共享队列的区别：线程池是"一个共享队列，所有 worker 抢同一把锁"；工作密取是每个线程一条自己的双端队列 deque——自己从头部取（LIFO，刚压栈的任务数据还在 CPU 缓存里），空闲线程去别人队列尾部偷（FIFO，偷最老的、也最不容易和主人撞车）。
  • Fork/Join 框架：分治 + 工作密取——任务递归拆分（fork）再合并结果（join），适合可二分、子任务开销均衡的计算（大数组聚合、树的遍历、归并排序）。parallelStream 底层就是公共的 ForkJoinPool.commonPool()。
  • 不适合的场景也要会说：子任务极轻（拆分开销大于计算）或严重不均（一个长任务没有可偷的），密取反而劣化——所以 parallelStream 的建议是"数据量大、单元素计算便宜才开并行"。
  • 完整展开（commonPool 的坑、与 ThreadPoolExecutor 对比、手动用 ForkJoinPool）在 第 06 章 线程池。

08高频追问与陷阱

  • 追问链：latch vs barrier → 一句话区分→ "latch 是倒计时门闩，减到 0 永远开着，旁观者通过；barrier 是人齐开闸，放行后复位再来一轮，参与者互相等"——先语义再重用性再失败行为，三层递进。
  • 追问链：Semaphore → 公平与非公平 → 非公平吞吐高（免队列调度、唤醒即抢），可能饥饿；公平 FIFO 保序但慢。和 ReentrantLock 的公平性是同一套权衡（第 04 章）。
  • 追问链：等 N 个任务 → 为什么有了 allOf 还要 latch → allOf 需要任务是 CompletableFuture；老代码/回调式任务拿不到 Future，latch 是通用粘合剂。反向答"新代码优先 allOf"更显工程判断。
  • 陷阱：countDown 不在 finally→ 异常路径漏减，await 永卡；且 await 不带超时 = 双保险全失。两个都要修。
  • 陷阱：复用已经到 0 的 latch→ 不报错但同步失效（立即通过），比异常更隐蔽。
  • 陷阱：Semaphore 许可超发→ release 多于 acquire 不报错，许可数悄悄超过初始值；tryAcquire 失败后误走 finally 的 release 是典型写错姿势——只在成功分支里配对。
  • 陷阱：barrier 的 broken 传染→ 一方中断全员 BrokenBarrierException；barrierAction 里抛异常同样会把屏障 break 掉，action 里必须自己兜异常。
  • 陷阱：Exchanger 单方失联→ 另一方永久阻塞；一律用带超时的 exchange(v, timeout, unit)。
  • 陷阱：拿 Thread.sleep 伪造同步→ "睡 100ms 等它算完"是竞态不是同步；所有"等别人做完"的语义都该用本章工具表达——这本身就是一道面试题。

09面试自查清单

  1. 四个同步器各自的"一句话模型 + 一句话场景"张口就来（许可/倒计时/屏障/交换）。
  2. latch vs barrier 对比表六维背熟：角色语义（旁观者等事件 vs 参与者互相等）、计数方向、重用性、barrierAction、失败行为、底层。
  3. countDown 必须放 finally、await 必须带超时——能各讲一个对应的事故形态。
  4. Semaphore：tryAcquire 超时快速失败、公平参数、release 配对；分得清"限并发"与"限速率"。
  5. 能对照源码讲两个共享模式实现：Semaphore 的 state = 剩余许可（CAS 减、release 不校验持有者）、CountDownLatch 的 tryAcquireShared 一行（state==0 ? 1 : -1）；"归零全员放行"能挂到传播唤醒（链 03 章 §06）。
  6. barrierAction 由最后到达的线程执行、BrokenBarrierException 何时全员抛、reset 的使用时机。
  7. 选型表：等 N 个 → latch/allOf；多轮同步 → barrier；动态多阶段 → Phaser（加分）；限并发 → Semaphore；两两交换 → Exchanger。
  8. 生产者-消费者能三行 BlockingQueue 写出，也能说清为什么手写 wait/notify 版容易错（链第 12 章对照）。
  9. 工作密取能讲出 deque 头 LIFO / 偷尾 FIFO 的原因，以及 parallelStream 与 commonPool 的关系（链第 06 章展开）。
