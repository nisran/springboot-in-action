02背景与定位：Project Loom

  • 项目来源：OpenJDK Project Loom，孵化多年后随 JDK 21（2023.9）由 JEP 444 正式交付（JDK 19/20 曾两轮预览）。目标不是"更快的线程"，而是让"每任务一线程"（thread-per-task）这个最自然的编程模型重新可用。
  • 它要解决的痛点：平台线程（platform thread）采用 1:1 模型——每个 new Thread() 背后是一个内核线程，创建走系统调用、栈默认预留约 1MB（按 -Xss，且一出生就占住），可运行全靠 OS 内核调度。于是"线程数 ≈ 并发度"被锁死在千级：1 万线程就是约 10GB 栈内存 + 内核调度器不堪重负。
  • 追问预备：Java 1.1 不是有过绿色线程吗，为什么失败？当年的绿色线程是纯用户态实现，没有任何内核线程可用：用不上多核，一个线程的阻塞系统调用会把整个进程拖住。Loom 的关键创新正是加了"载体线程"这一层——平时借内核线程执行，阻塞时还回去，两条路都不耽误。
  • 此前的两条歪路：① 线程池 + 异步任务（回调地狱，第 07 章）；② 响应式框架（Flux/Mono 链，复杂度转嫁给代码）。Loom 的思路：复杂度交给 JVM——把线程做便宜，让同步代码拿到异步的吞吐。

历史脉络一句话：Go 的 goroutine、Kotlin 的 coroutine 先证明了"廉价并发单元"可行，Java 直到 21 才交出自己的答案，且选择不改语法、不动内存模型——虚拟线程就是 java.lang.Thread 的另一种实现，现有代码几乎零改造。

03原理：挂载与卸载 ⭐

先背下来的一段话：虚拟线程是由 JVM 调度、而不是内核调度的轻量线程；它的栈帧存在堆上、按需增长；运行时"挂载（mount）"到某个载体线程上执行，一旦阻塞就"卸载（unmount）"，载体线程立刻去跑别的虚拟线程。

三个关键机制

  • 栈在堆上：平台线程的栈是连续内存、出生即预留约 1MB；虚拟线程的栈是堆上的对象（由栈帧串成的块链），初始只有几百字节，调用加深才增长，返回即收缩——这就是"百万个也不爆内存"的根源（百万级大约对应 GB 以下的堆开销）。
  • 挂载与卸载：虚拟线程自己不是 CPU 调度单元，必须搭载体线程（carrier thread，本质是平台线程）的"车"。挂载 = 载体线程执行这个虚拟线程的栈帧；当虚拟线程阻塞在受支持的操作上（网络 IO、sleep、LockSupport.park、ReentrantLock/Semaphore 等 java.util.concurrent 阻塞点），JDK 内部把阻塞调用改写为"挂起虚拟线程 + 注册唤醒回调"，栈帧拷回堆，载体线程当场还回调度器去执行下一个虚拟线程；IO 完成后虚拟线程重新排队，可能挂载到另一个载体上。
  • 阻塞成本被重定义：平台线程阻塞 = 白白占住一个内核线程等 IO；虚拟线程阻塞 = 只是一个堆对象在等事件，内核线程零浪费。这就是"每个阻塞调用自动变非阻塞"的含义——不是调用不阻塞了，是阻塞不再昂贵。
  • 线程身份跟虚拟线程走，不跟载体：换载体不换 currentThread()，ThreadLocal 也始终挂在虚拟线程上——这同时解释了为什么 ThreadLocal 副本数 = 虚拟线程数（第 07 节的隐患根源）。
虚拟线程 vt-42                     载体线程 worker-1（平台线程，ForkJoinPool）
    │   ──── mount（挂载）────▶      正在执行 vt-42 的栈帧（帧本体在堆上）
    │
    │  vt-42 调 socket.read() 阻塞
    │   ◀─── unmount（卸载）────     worker-1 立刻切去跑 vt-43、vt-44…
    │
    └── IO 完成 → 重新进入调度队列 → mount 到任意空闲载体（未必是 worker-1）

答题技巧：面试官问"原理"时，把"栈在堆、按需增长"和"mount/unmount"两个词说出来，再补一句"阻塞的实现被 JDK 内部改写成 park + 回调，载体线程不跟着等"，基本就是满分结构。

04调度器与 M:N 模型

  • M:N 模型：M 个虚拟线程映射到 N 个载体线程。载体线程住在一个专用的 ForkJoinPool 里（和并行流的 commonPool 不是同一个），FIFO 模式（commonPool 是递归任务为主的模式）、默认并行度 = CPU 核数。可用 -Djdk.virtualThreadScheduler.parallelism / maxPoolSize（默认 256）调节，但绝大多数场景不动它。
  • 非抢占式：调度器不做时间片抢占——虚拟线程只有阻塞或结束时才让出载体。所以一个虚拟线程里跑长 CPU 循环，会把同载体的其他虚拟线程饿到没人管（对应"CPU 密集无收益"）。
  • 公平排队：卸载后重新入队是 FIFO，新任务不会永远插队——与响应式框架里"回调饿了没人管"形成对比。
  • 身份细节（可当加分点）：虚拟线程永远是守护线程、优先级恒为 NORM_PRIORITY，setDaemon/setPriority 调了也没效果；Thread.currentThread() 照常可用。
  • pin 时调度器不补偿 ⚠：JEP 444 原文明确——"调度器不会为 pin 扩容"（does not compensate for pinning）。载体被钉住就是实打实被占住，钉满 N 个载体就全体排队，极端情况直接死锁（官方 bug JDK-8334304 案例：pin 线程数 ≥ 载体数；JDK 24 JEP 491 消掉了 synchronized 这一最大 pin 来源）。-Djdk.virtualThreadScheduler.maxPoolSize（默认 256）只是池上限参数，不是 pin 的解药。另注意 ForkJoinPool.managedBlock 的"补偿线程"机制是给平台线程池用的老设计，在虚拟线程上不触发补偿（JDK 21 Javadoc 明确），别把它和虚拟线程调度混为一谈。

把调度记忆成一句话："用户态的 ForkJoinPool 当 CPU 调度器，虚拟线程当任务，载体线程当 CPU"——OS 调度 N 个载体，JVM 调度 M 个虚拟线程，两层各管各的。

05commonPool：虚拟线程前后的变与不变 ⭐

06/07 章讲过：并行流和 CompletableFuture 默认共用 ForkJoinPool.commonPool()（大小 = 核数 − 1、守护线程、全 JVM 共享）。学完虚拟线程，面试官极爱顺手追一句："虚拟线程出来之后，commonPool / 并行流 / CF 的默认池变了吗？"——考的是你有没有把新旧两套机制装进同一张地图。答案骨架两层：库的默认行为一个没变；变的是 ForkJoinPool 多了一个新身份，以及 pin 的规则书。

前后对照表

维度虚拟线程之前（JDK 8 ~ 20）虚拟线程之后（JDK 21 ~ 25）
parallelStream()提交到 commonPool不变：仍是 commonPool 平台线程，不会因为在虚拟线程里调用就"变虚"
CF.supplyAsync 不传池默认 commonPool不变：没有切成 newVirtualThreadPerTaskExecutor
commonPool 本体核数 − 1、守护线程、CPU 分治定位不变：老坑原样存在（IO 占满 → 全应用并行流饿死）
ForkJoinPool 的角色只做分治 / 并行流 / CF 的执行池新增身份：另起一个专用实例当虚拟线程调度器（FIFO、并行度 = 核数）
阻塞的代价阻塞 = 占住一个平台线程虚拟线程里阻塞 = 卸载、载体复用；但 commonPool 里的阻塞照旧占线程
pin 规则无此概念21：synchronized 内阻塞 pin、调度器不补偿 → 24（JEP 491）解除 synchronized pin；native 始终 pin

一句话口径背下来："虚拟线程改的是 Thread 的实现和阻塞的成本，不改任何库的默认线程池选择。"——凡是"虚拟线程来了所以 XX 自动变快 / 自动切换"的说法，先打个问号。

变了的三处（区分度所在）

  • 同一个类，两个实例：调度器和 commonPool 都是 ForkJoinPool，但互不相干——调度器是 FIFO（asyncMode，保证卸载后重新入队的公平性），commonPool 是 LIFO 本地队列（递归分治的缓存友好）；参数也分家：调度器走 jdk.virtualThreadScheduler.*，commonPool 走 java.util.concurrent.ForkJoinPool.common.*；两边线程互不借用（见 第 04 节）。
  • 为什么调度器选 ForkJoinPool（加分点）：每载体一个工作队列 + work-stealing，天然贴合"M 个任务抢 N 个 CPU"。虚拟线程在调度器眼里就是一个任务（runContinuation）：卸载 = 任务暂时返回、载体回池接下一个；唤醒（unpark）= 把 continuation 重新提交入队。ThreadPoolExecutor 那种单共享队列，百万级任务下锁竞争扛不住。
  • 补偿机制的分野：ForkJoinPool.managedBlock 原本让平台 FJP 在 worker 阻塞时补一个 spare 线程；在虚拟线程上不触发补偿（JDK 21 Javadoc 明确）——虚拟线程阻塞靠卸载解决，用不着补线程；而真正卸载不了的 pin，调度器也不补偿（JEP 444），这正是 21 里"pin 满载体即死锁"的根源（第 08 节）。

组合坑：虚拟线程里嵌套 commonPool 任务

// ⚠️ 坑：海量虚拟线程里各跑一段 parallelStream
try (var ex = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Order o : orders) {
        // fork 出的子任务全挤进 commonPool 的 7 个 worker（8 核机器）；
        // RPC 一阻塞 worker 就占满 → 并行段塌缩 + 全应用并行流陪葬
        ex.submit(() -> o.items().parallelStream().forEach(item -> rpc(item)));
    }
}

// ✅ 对：IO 段显式交给虚拟线程 executor，CPU 段才落 commonPool
var vexec = Executors.newVirtualThreadPerTaskExecutor();
CompletableFuture.supplyAsync(() -> callRpc(), vexec)     // IO → 虚拟线程，阻塞即卸载
                 .thenApplyAsync(this::heavyCompute)      // CPU → 不传池仍落 commonPool（合理）
                 .join();                                 // 在虚拟线程里 join：park 卸载，不 pin
  • 退化但不 pin：嵌套时调用方虚拟线程会亲自执行一份子任务（阻塞照常卸载），fork 出去的份额则挤在 commonPool 平台线程上；等结果的 CF.join()/get() 底层走 park（Signaller），正常卸载不钉载体——不会因此死锁，但并行段的虚拟化收益归零。
  • 真正要防的是饿死：把 RPC / DB 这类阻塞调用塞进 commonPool（不论发起方是不是虚拟线程），核数 − 1 个 worker 一占满，全应用的并行流和默认 CF 一起瘫——老坑在新时代原样复发，虚拟线程救不了它。
  • 迁移口径：升 JDK 21 后并行流不用改、也不该改；要改的只有"IO 任务默认丢 commonPool"这一类 CF 代码——显式传池：IO 用虚拟线程 executor，CPU 用 commonPool 或自定义有界池（07 章 CF 默认池的坑）。

追问链：①"虚拟线程调度器就是 commonPool 吧？"→ 不是，同类不同实例：FIFO vs LIFO、参数分家、线程不互借。②"那并行流在虚拟线程里跑会更快吗？"→ 不会，fork 出去的活还是 commonPool 平台线程在干，虚拟线程只是个壳。③"老服务升了 21，并行流 / CF 代码要动吗？"→ 并行流不动；只改默认池上跑 IO 的 CF，显式传虚拟线程 executor。④"能不能让 commonPool 直接用虚拟线程？"→ 不能：FJP 的 worker 必须是 ForkJoinWorkerThread（平台 Thread 的子类），threadFactory 造不出虚拟线程；也不该换——commonPool 定位是 CPU 分治，虚拟线程对 CPU 密集零收益（第 07 节）。

06三种创建方式

// ① 构建器：最灵活，可命名、可先不启动（unstarted）
Thread vt = Thread.ofVirtual().name("vt-", 0).start(() -> handleRequest(socket));

// ② 静态快捷方法：一行起一个
Thread.startVirtualThread(() -> System.out.println("hello from " + Thread.currentThread()));

// ③ 每任务一线程的 Executor：生产推荐写法（try-with-resources 自动等待收尾）
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {          // 百万任务 = 百万虚拟线程，平台线程池早已 OOM
        executor.submit(() -> {
            var resp = httpClient.send(req, BodyHandlers.ofString()); // 阻塞 IO：自动卸载
            return process(resp.body());
        });
    }
}   // close() 隐式 awaitTermination：所有任务结束后才继续
  • 三者关系：startVirtualThread 是 ② 的极简版；③ 是服务端主入口——Tomcat/Jetty 每个请求就是一个虚拟线程（见 第 09 节 Spring 开关）。
  • 注意它不叫 newVirtualThreadPool：名字就在告诉你"每任务新建一个，不复用"。继续用 newFixedThreadPool 跑虚拟线程是方向性错误。
  • 经典搭配：外部由虚拟线程承接收并大并发，内部用 StructuredTaskScope 做结构化并发——父子任务同生共死，取消不泄漏（JDK 21 起预览，JDK 25 的 JEP 505 仍是第五轮预览、API 尚在演进，生产慎用）。被追问"虚拟线程怎么管理生命周期"时甩这个。

命名与观测：海量线程下逐个命名没意义，.name("vt-", i) 只在低量调试时用；生产观测靠 trace-id 贯穿日志 + Micrometer 埋 executor 指标，别指望线程名。

07使用原则：主场与禁区 ⭐

主场：IO 密集 + 高并发

  • 典型场景：百万长连接、每请求一线程的 Web 服务、调一堆下游 RPC/DB 的聚合接口。并发度不再受线程数限制，而受下游与带宽限制——瓶颈回归到它该在的地方。
  • 最大红利是代码风格回归同步直写：阻塞 JDBC、阻塞 HTTP client 直接用，不需要 R2DBC/WebClient 全链路非阻塞，可读性和调试体验全面回潮。

禁区与原则

  • CPU 密集无收益：核数才是上限，虚拟线程不增加并行度，反而白吃调度开销（还可能因非抢占互相拖累）。CPU 密集继续用固定大小平台线程池（第 06 章）。
  • 内存仍要算总账：单个栈虽是 KB 级，百万线程每人挂上任务对象、ThreadLocal 上下文就是 GB 级——"廉价"是相对的，容量仍靠压测说话，不是无中生有。
  • 不要池化虚拟线程 ⭐：池化的意义是"复用贵的资源"，虚拟线程便宜到没有复用价值，池化反而把它的优势（廉价、海量）锁死。限并发用 Semaphore：
// 限并发的正确姿势：不池化线程，池化"许可"
private static final Semaphore DB_PERMITS = new Semaphore(50);   // 最多 50 并发打 DB

exec.submit(() -> {
    DB_PERMITS.acquire();                        // 阻塞在信号量上同样会卸载，不占载体线程
    try (var conn = dataSource.getConnection()) {
        return query(conn, req);                 // 保护的是下游 DB，不是线程
    } finally {
        DB_PERMITS.release();
    }
});
  • 不要滥用 ThreadLocal ⭐：百万虚拟线程 = 百万份 ThreadLocal 副本，里面再放缓冲区、格式化器这类重对象就是内存事故；而且虚拟线程海量短命，"每线程一份缓存"的假设失效。正解是 JDK 25 的 ScopedValue（JEP 506 正式）：不可变、按作用域绑定、作用域结束自动还原，天生适配"一次请求一份上下文"：
// JDK 25：ScopedValue 替代 ThreadLocal 传上下文（不可变 + 自动作用域）
private static final ScopedValue<UserContext> CTX = ScopedValue.newInstance();

ScopedValue.where(CTX, currentUser)              // 绑定
           .run(() -> service.handle());         // 绑定期内任意调用深度读 CTX.get()，出作用域自动失效

迁移清单：老服务上虚拟线程前扫五件事

  1. synchronized 热点：高并发路径先换 ReentrantLock，或直接升 JDK 24+（第 08 节）。
  2. ThreadLocal 重对象：Formatter/缓冲区类改共享不可变对象，上下文传递换 ScopedValue。
  3. 依赖里的 native 阻塞：老 SDK 的 JNI 调用会 pin 载体，隔离到独立平台线程池跑。
  4. 隐性依赖线程池限流的代码：池化一撤限流就没了，补 Semaphore / 熔断器（第 10 节）。
  5. 监控与排障体系：thread dump 换 jcmd Thread.dump_to_file -format=json，executor 指标重新埋点。

陷阱：虚拟线程不改变 Java 内存模型——共享可变状态照样要加锁/CAS（第 02 章）；它也不让单个任务变快，提升的是吞吐和容量。答"有了虚拟线程还需要并发安全吗"时，答案是斩钉截铁的"需要"。

08pin（钉住）问题 ⭐

pin = 虚拟线程阻塞时无法卸载，只能连着载体线程一起等——退回平台线程的老问题：载体被占住，调度池被抽干，吞吐突然掉回千级并发。这段版本演进史是本章最强加分项：

版本synchronized 内阻塞说明
JDK 21（JEP 444）会 pin 住载体monitor 实现当时无法在挂起时释放载体；官方建议热点路径把 synchronized 换成 ReentrantLock
JDK 24（JEP 491）已修复，可正常卸载重写了 monitor 挂起机制，synchronized 内阻塞/wait 不再 pin——历史包袱正式清除
任何版本native 帧（JNI 调用中阻塞）仍 pin老依赖里 native 方法内阻塞，载体照样被占；只能隔离到独立平台线程池
  • JDK 21 时代怎么排查：JVM 参数 -Djdk.tracePinnedThreads=full 打印 pin 发生的位置；jcmd <pid> Thread.dump_to_file -format=json 能看到虚拟线程（普通 jstack 看不到，见追问节）。
  • 为什么 ReentrantLock 没事：它基于 AQS/LockSupport.park，park 是 JDK 自己实现的阻塞点，天然支持卸载；synchronized 的 monitor 依赖 JVM 内部的旧挂起路径——所以 JDK 21 的建议本质是"避开 JVM 还没改造完的那部分"。
  • 面试口径：先说结论（"21 里 synchronized 内阻塞会 pin，24 已修"），再给证据（JEP 491），最后补 native 例外——三层递进，比背结论高一档。

实战话术："我们评估 JDK 21 迁移时专门扫过 synchronized 热点，QPS 高的路径先换 ReentrantLock 或升 24；JNI 阻塞的旧 SDK 隔离到单独的平台线程池。"——一句话证明你真评估过，不是看文章背的。

09对比：线程池与响应式

平台线程 vs 虚拟线程

维度平台线程虚拟线程
映射模型1:1（一个内核线程）M:N（M 个虚拟线程共享 N 个载体）
栈独立内存，预留约 1MB，固定堆上，初始几百字节，按需增长
调度者OS 内核调度器JVM（专用 ForkJoinPool，FIFO，并行度=核数）
创建成本高：系统调用 + MB 级内存极低：微秒级、KB 级以内
舒适数量级数百 ~ 数千百万级
阻塞的代价浪费一个内核线程干等卸载，载体还回调度器
适用负载CPU 密集、常驻后台任务IO 密集、高并发短任务

虚拟线程 vs WebFlux / 响应式

维度响应式（WebFlux/Reactor）虚拟线程
编程模型Flux/Mono 链 + lambda 套 lambda同步直写，阻塞调用随便用
复杂度去向转嫁给业务代码转嫁给 JVM
调试/栈堆栈被 operator 切碎，排障痛苦完整同步调用栈
生态要求全链路非阻塞（R2DBC、WebClient）直接用 JDBC 等阻塞库
背压/流控原生优势（bounded demand）没有背压语义，需自己限流
  • Spring Boot 3.2+ 一键切换：spring.threads.virtual.enabled=true——Tomcat/Jetty 请求处理、@Async、任务调度改走虚拟线程，同步 MVC 直接吃满。框架层细节见 04-spring。
  • 公道话：响应式没死——需要流式聚合、背压、复杂事件组合的中间件场景仍是它的主场；但对绝大多数 CRUD/聚合型服务，虚拟线程用 1/10 的心智成本拿到同等的吞吐，这就是"回归"的含义。
  • 别忘了我方短板：虚拟线程只放大了"接得住"，打不打得动还看资源池——Hikari 连接池 50 个连接，前面挂一百万虚拟线程也没用（第 07 节的 Semaphore 保护的正是它）。答"虚拟线程能扛多少 QPS"时，先反问下游容量，这是架构师视角。

一句总结口径：响应式把"等 IO"翻译成一串回调让你自己串，虚拟线程让 JVM 替你串——前者考验团队，后者只考验 JDK 版本。

10高频追问与陷阱

  • 追问链：有了虚拟线程，线程池还有用吗？→ 三类保留：① CPU 密集的固定池；② 隔离专用（如 JNI 阻塞依赖放独立平台线程池防 pin 传染）；③ 线程池原来的三大治理语义怎么替代——隔离：按业务拆多个 newVirtualThreadPerTaskExecutor；限流：Semaphore；监控：Micrometer 对 executor 的指标照常埋。这套"语义平移"答案是新热点的标准追问。
  • 追问链：百万虚拟线程打下游 → 下游怎么办？→ 线程不设限后压力直给 DB/RPC，必须自己上闸门：Semaphore、Bulkhead、Sentinel 任选——"线程便宜了，限流反而更重要"是体现架构思维的一句。
  • 陷阱：jstack 看不到虚拟线程 → 默认 thread dump 只含载体线程；要看虚拟线程用 jcmd <pid> Thread.dump_to_file -format=json（新格式专用转储）。
  • 陷阱：长 CPU 循环占住载体 → 调度不抢占，同载体其他虚拟线程被拖住；重计算请交回平台线程池，别混进来。
  • 陷阱：ThreadLocal 重对象 → 百万副本内存爆炸 + 短命线程缓存失效；上下文传递换 ScopedValue（JDK 25 正式，JEP 506），与 第 09 章 ThreadLocal 泄漏连起来答。
  • 陷阱：把虚拟线程当"更快的线程" → 它优化的是吞吐/容量（阻塞不再占线程），单任务延迟没有任何改善，甚至略增调度开销。方向答反这题就零分。
  • 陷阱：Executors 混用 → newFixedThreadPool 装虚拟线程 = 用池锁死海量优势；正确入口只有 newVirtualThreadPerTaskExecutor（或 StructuredTaskScope）。
  • 追问链：虚拟线程会取代 CompletableFuture 吗？→ 不会取代"编排"这一层：并发扇出（同时调 3 个下游取最快）用虚拟线程 + StructuredTaskScope 更直白，但异步流水线、超时组合、跨线程结果传递仍是 CF 的主场——大批量任务提交到虚拟线程 executor 后拿 Future，也天然衔接 CF。二者是分工不是替代（第 07 章；CF 默认池在虚拟线程时代为何没变，见 第 05 节）。
  • 追问链：虚拟线程抛异常谁接？→ 和平台线程一样：未捕获异常走 Thread.UncaughtExceptionHandler，线程直接终结（不复存在"重试"）；所以业务方要自己在任务体内 try-catch，或用 executor.submit 让异常留在 Future 里——这一问考察"虚拟线程仍是线程"的本体感。
  • 追问链：和 Go 的 goroutine 有什么区别？→ 模型同源（都是 M:N + 用户态调度 + 栈在堆/可增长），差异在四点：① 调度——goroutine 自 Go 1.14 起有异步抢占（signal 打断长 CPU 循环），Java 虚拟线程纯协作式，只在阻塞点让出载体；② 栈——goroutine 用连续栈整体拷贝扩容，Java 用堆上栈块链按需增长；③ 通信——Go 主张 channel/CSP 分享内存，Java 刻意不改共享内存模型 + JMM 原样；④ 兼容——Java 的杀手锏是"零改造跑全部现有生态（Thread API、JDBC、调试器）"。能答到这层基本是追问天花板。
  • 追问：Thread.sleep 会 pin 吗？Object.wait 呢？→ sleep、BlockingQueue.take、LockSupport.park 这些纯 JDK 阻塞点走 park 路径，正常卸载不 pin；JDK 21 里会 pin 的是 synchronized 块内阻塞（含 Object.wait——它必须持有 monitor 才能等）和 native 调用。前者 JDK 24（JEP 491）已修，后者永远只能隔离到平台线程池。"sleep 不 pin、wait 在 21 pin、24 都不 pin、native 永远 pin"这组对比是细节识别题，答对了直接拉开档次。

11面试自查清单

  1. 能一句话定位：JDK 21 / JEP 444 / Project Loom，解决"平台线程 1:1 内核线程、栈预留 1MB、千级即瓶颈"。
  2. 能画出 mount/unmount：栈帧在堆上按需增长，阻塞在受支持操作上就卸载，载体线程立刻复用。
  3. 知道调度细节：专用 ForkJoinPool、FIFO、并行度=核数、M:N、非抢占（长 CPU 任务占载体）。
  4. 能答 commonPool 的"变与不变"：并行流 / CF 默认池都没变；调度器是 ForkJoinPool 的另一个实例（FIFO vs LIFO、参数分家）；虚拟线程里嵌套并行流 = fork 段塌缩回 commonPool，IO 链路要显式传虚拟线程 executor。
  5. 三种创建方式手写得出，知道生产主入口是 newVirtualThreadPerTaskExecutor。
  6. 能答"主场与禁区"：IO 密集高并发为主场；CPU 密集无收益；不池化，限并发用 Semaphore。
  7. 能完整讲 pin 的演进：21 里 synchronized 阻塞 pin（热点换 ReentrantLock）→ 24 JEP 491 修复 → native 帧始终 pin。
  8. 平台 vs 虚拟对比表至少背五维：映射、栈、调度者、成本、数量级。
  9. 能对比响应式（复杂度去向、栈、生态、背压），知道 Spring Boot 3.2 的开关与局限。
  10. 能答"线程池语义怎么平移"：隔离拆 executor、限流 Semaphore、监控 Micrometer。
  11. 知道 pin 时调度器不补偿（JEP 444 原文；钉满载体即死锁，JDK-8334304），maxPoolSize 不是解药；以及"吞吐靠虚拟线程、容量瓶颈看下游连接池"的边界感。
  12. 知道 ThreadLocal 在百万线程下的问题与 ScopedValue（JEP 506 / JDK 25）的替代逻辑。
