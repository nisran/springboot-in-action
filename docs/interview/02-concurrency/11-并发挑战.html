02死锁四必要条件 ⭐⭐

死锁（Deadlock）：一组线程互相持有对方需要的资源、互相等待，谁都无法推进。四个条件必须同时成立（Coffman 条件）——缺任何一个，死锁都不成立，这也是全部预防手段的理论根据：

条件含义口语记忆
互斥（Mutual Exclusion）同一资源同一时刻只能被一个线程占用（笔记：相互条件）资源独占，不能共享
请求与保持（Hold and Wait）线程因请求新资源而阻塞时，对已获得的资源保持不放占着碗里的，等锅里的
不可剥夺（No Preemption)线程获得的资源在用完之前不能被强行剥夺，只能自己释放抢不走，只能等他放手
循环等待（Circular Wait）存在等待环：T1 持 L1 等 L2，T2 持 L2 等 L1（可推广到 N 个线程成环）首尾相接的等
  • 为什么"缺一不成死锁"是题眼：四个条件是死锁的充要刻画（在资源分配图成环的意义上），所以预防 = 破坏任意一条。而现实中互斥通常破坏不了（锁本身就是互斥的），工程上主要打后三条——其中锁排序打"循环等待"，成本最低、最常用。
  • 辨析：死锁线程全部静止（都在等，不耗 CPU）；活锁线程还在动（空转重试，耗 CPU）。面试里"卡死"两个字两种病都指，先分辨是哪一种再谈解法。

进阶口径：死锁处理三学派——预防（事前破坏条件，本文主线）、避免（运行时判断资源分配是否安全，银行家算法，面试提一句即可）、检测+恢复（事后：检测等待环，牺牲一个线程回滚——数据库引擎就是这么干的）。

03死锁现场与预防

最小可跑的死锁示例（两线程交叉拿两把锁）

public class DeadlockDemo {
    private static final Object LOCK_A = new Object();
    private static final Object LOCK_B = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (LOCK_A) {
                sleep(100);                                  // 放大时间窗，保证 t2 已拿到 B
                synchronized (LOCK_B) { System.out.println("t1: A+B"); }   // 等 B —— 死锁
            }
        }, "t1");
        Thread t2 = new Thread(() -> {
            synchronized (LOCK_B) {
                sleep(100);
                synchronized (LOCK_A) { System.out.println("t2: B+A"); }   // 等 A —— 死锁
            }
        }, "t2");
        t1.start(); t2.start();                              // 两线程永远挂起，进程不退出
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}

预防三板斧（对应破坏哪一条）

// ① 锁排序：全局约定按固定顺序加锁 —— 破坏"循环等待"（最常用，成本最低）
void transfer(Account from, Account to) {
    Account first  = from.id < to.id ? from : to;    // 永远先锁 id 小的
    Account second = from.id < to.id ? to : from;
    synchronized (first) { synchronized (second) { doTransfer(from, to); } }
}

// ② tryLock 超时：拿不到就放手重试，不死等 —— 破坏"请求与保持"（已持有的可释放）
if (lock1.tryLock(1, TimeUnit.SECONDS)) {
    try {
        if (lock2.tryLock(1, TimeUnit.SECONDS)) {
            try { doTransfer(); } finally { lock2.unlock(); }
        } else {
            backoffAndRetry();                            // 拿不到第二把：放手，退避后整体重来
        }
    } finally { lock1.unlock(); }                         // ⭐ 第一把必须释放，否则白搭
}

// ③ 一次性申请全部资源：要么全拿到，要么一个不占 —— 从根上破坏"请求与保持"
  • 锁排序的实现要点：顺序依据必须全局全序（自增 id、hashCode 排序都行，但任何两处代码对同一对资源的排序必须一致）。动态排序的坑：对象没有天然 id 时用 System.identityHashCode，极小概率相等再退化为第三把锁——这条说出来是加分项。
  • tryLock 细节追问：超时拿不到时必须释放已拿到的锁再整体重试，否则只是把死锁变成了"占着第一把等第二把"；重试要带随机退避防止同步化（否则会逼近活锁，见下节）。
  • 破坏"不可剥夺"在纯 Java 里只有 tryLock 一种近似（不能从外部强行 unlock 别人的锁）；破坏"互斥"的思路是干脆不用锁：无锁结构（第 05 章）、单线程 Actor 化。锁策略全景见 第 04 章。

答题模板：先背四个条件名（互斥/请求与保持/不可剥夺/循环等待），再补"工程上主要破坏循环等待（锁排序）和请求与保持（tryLock/一次性申请）"，最后一句"我们代码里转账就是这么做的"——理论、手段、实践三层齐了。

04检测与排查 ⭐

先认出现象（监控层）

  • 典型曲线：吞吐量断崖式下降、接口超时（RT）飙升、线程数只涨不落；死锁线程永远不会自愈，表现为"某个功能从某时刻起 100% 超时"。
  • 线程池视角：活跃线程打满且任务队列持续堆积——疑似全员卡死（不一定是死锁，也可能是下游全慢）。

工具链（笔记 600-605 并入）

# ① jstack：JDK 自带，末尾直接给出判定
jstack <pid>
#   关键输出：
#   "t1" ... locked <0x... LOCK_A>, waiting to lock <0x... LOCK_B>
#   "t2" ... locked <0x... LOCK_B>, waiting to lock <0x... LOCK_A>
#
#   Found one Java-level deadlock:        <-- 一行实锤，jstack 能自动检测 JVM 内 monitor 死锁
#   =============================
#   "t1":
#     waiting to lock object ... held by "t2"

# ② arthas：线上更顺手，直接指认阻塞源头
thread -b          # 找出"阻塞其他线程最多"的线程 —— 直接给出死锁/阻塞元凶的堆栈
thread --lockedMonitors   # 列出各线程持有的 monitor，自己拼等待环

# ③ 数据库层死锁（for update 相互锁定）
mysql> SHOW ENGINE INNODB STATUS\G
#   看 LATEST DETECTED DEADLOCK 段：两个事务各自持有和等待的索引/行、谁被回滚
  • jstack 的边界：它能自动检测的是 monitor（synchronized）死锁；ReentrantLock 互相等待不会被打上 "Found deadlock" 标记，要靠人肉看 waiting on condition + locked 持有列表拼环——这个差异是高频追问。
  • arthas thread -b 的适用面：它找的是"持有锁并阻塞了最多线程"的元凶，对 synchronized 和 AQS 锁都有效，且能看到具体堆栈行号——生产优先用它，比传 dump 文件快。
  • 数据库死锁特征：应用侧不是线程挂死，而是很快抛 DeadlockLoserDataAccessException（MySQL 挑一个事务回滚）——所以 DB 死锁排查看错误日志 + innodb status，而不是 jstack。两者别混。

陷阱：jstack 单次抓到 BLOCKED 不等于死锁（可能只是竞争激烈）。判定标准是多次采样（间隔几秒抓 3 次）同一批线程还在等同一批锁、且互相持有——成环才是死锁，单向等待只是慢。

05活锁与饥饿

活锁（Livelock）

  • 定义：线程没有阻塞、一直在运行（不停改变自身状态），但整体任务永远推进不了——典型是两个线程互相检测到冲突后"互相礼让"，各自重试，节奏完全同步，于是永远再次撞车。
  • 与死锁的区别一句话：死锁是"都在睡"，活锁是"都在空转"——活锁还白吃 CPU。
  • 解法：引入随机性——重试前加随机延迟（随机退避），把两个线程的节奏打散；以太网 CSMA/CD、消息队列重试抖动（jitter）都是这个原理。
// 活锁原型：两个消费者同时抢两条资源，失败就"全放重试"
while (!done) {
    if (!tryAcquireBoth()) {
        releaseAll();                 // 两个线程每次都在同一拍失败、同一拍重试 → 永远同步失败
        sleep(100);                   // 固定退避：节奏仍同步，无解
        // sleep(100 + random.nextInt(200));   // ✅ 随机退避：节奏错开，活锁破解
        continue;
    }
    doWork(); done = true;
}

饥饿（Starvation）

  • 定义：线程长期抢不到资源（CPU 或锁）而无法推进——不是不能跑，是轮不上。成因：优先级太低被高优先级线程持续压制；非公平锁下"手速慢"的线程可能永远抢不到；临界区太长把别人饿死。
  • 解法：公平锁（new ReentrantLock(true)，按排队顺序发放，代价是吞吐略降）、缩短临界区、控制线程优先级策略（Java 优先级只是 hint，别依赖）。

三者对比（一张表收口）

维度死锁活锁饥饿
线程状态阻塞，完全静止运行中，不停重试等待中或抢不到调度
能否自愈不能（无限期）运气好可能偶然解开压力降了可能缓解
CPU 表现不消耗（都在等）空转消耗 CPU不一定
根因循环等待互相礼让/同步重试优先级/公平性失衡
解法锁排序、tryLock、一次申请随机退避公平锁、短临界区

06伪唤醒 ⭐

伪唤醒（spurious wakeup）是真实存在的：OS 底层（Linux futex 等）出于性能考虑允许 wait 在没有任何 notify 的情况下返回——JLS 也明确允许 JVM 这样做。所以铁律是：wait() 返回 ≠ 条件已满足，醒来后必须重查条件，因此 wait 必须写在 while 里而不是 if 里。

// 血案版本：if 只查一次条件
synchronized (queue) {
    if (queue.isEmpty()) {
        queue.wait();          // 被"伪唤醒"或被 notify 后条件又被别人消费 —— 醒来时未必非空
    }
    queue.remove();            // 空队列上 remove：IndexOutOfBoundsException / 返回 null 污染下游
}

// 正确版本：while 守卫，每次醒来重查
synchronized (queue) {
    while (queue.isEmpty()) {  // ⭐ 醒来第一件事：重查条件，不满足继续睡
        queue.wait();
    }
    queue.remove();            // 走到这里时条件必然成立
}
  • 除了 OS 层伪唤醒，还有两个"类伪唤醒"来源同样被 while 兜住：① notifyAll 唤醒多个线程，先醒的把数据消费光（"偷唤醒"）；② notify 唤醒的是"错误"条件的线程。while 一招防三害。
  • 底层为什么要允许伪唤醒：futex 的等待/唤醒在内核高并发路径上做精确条件判定代价太高，实现上允许"顺带唤醒"，把条件校验成本还给用户态——用 while 重查一次远比内核做复杂匹配便宜。能答到这层是区分度。
  • 同理推广：Condition.await()、LockSupport.park() 的返回都不承诺原因，park 醒来后都要重新校验条件——AQS 源码里全是这个模式。
  • wait/notify 的完整机制（为什么在 Object、notify 随机性、两阶段释放锁）见 第 03 章 互斥与同步；生产者-消费者的完整实现见 第 12 章。

面试官最爱设的套："既然没人 notify，wait 不就不会醒，用 if 也安全？"——错。futex 允许虚假唤醒、interrupt 会打断、notifyAll 会群醒，任何一种都让 if 版本爆炸。答案永远是 while。

07优先级反转与线程泄漏

优先级反转（Priority Inversion）

  • 场景：低优先级线程持有锁 → 高优先级线程等这把锁 → 中优先级线程抢占低优先级线程的 CPU。结果：高优先级被"中优先级"间接压制——优先级名义上反转了。锁本该传递依赖，被第三方插了队。
  • 经典事故：1997 火星探路者（Mars Pathfinder）——低优先级的气象任务持有共享总线锁，高优先级的总线管理任务等锁，中优先级的通信任务频繁抢占气象任务，导致高优先级任务超时、看门狗不断复位探测器。地面团队远程启用优先级继承（Priority Inheritance, PI）才解决。
  • 优先级继承：持锁线程临时继承等锁线程中的最高优先级，让它尽快干完释放锁，把锁的依赖传递下去。RTOS 普遍内置（VxWorks 的互斥量可选 PI 标志）；Linux 有 PTHREAD_PRIO_INHERIT。
  • Java 侧的现实：Java 线程优先级只是提示（映射到 OS 也未必生效），JDK 内不提供带 PI 的锁；工程上的替代思路是别让低价值任务持有高价值任务需要的锁——锁粒度按业务等级拆分、关键路径不与杂务共锁。答出"Java 无 PI、要靠架构规避"即是亮点。

线程泄漏（Thread Leak）

  • 忘记 shutdown：new 了线程池/Thread 没收尾，核心线程常驻——反复发布后线程数阶梯上涨，最终 unable to create new native thread。防御：ExecutorService 用 try-with-resources 或注册 shutdown 钩子；周期任务统一收口到调度中心。
  • 无界队列堆积：newLinkedBlockingQueue() 不传容量 = Integer.MAX_VALUE，任务只进不出时内存被队列吃光——线程没漏，内存漏了（第 06 章）。防御：有界队列 + 拒绝策略。
  • ThreadLocal 未 remove：线程池线程长存 → Entry 的 value 强引用滞留 → 经典内存泄漏链（完整机制在 第 09 章 ThreadLocal）。防御：finally 里 remove，或换 ScopedValue（第 10 章）。
  • 怎么发现：监控线程数趋势（右掉不归零、重启前创新高）+ jstack 看同名业务线程数量是否随发布次数增长。

08场景收尾：接口 RT 突增的排查序列

把本章串成一条实战动线——面试官问"某接口 RT 从 50ms 突增到 3s，说下你的动作序列"：

  1. 定范围：看监控是全接口还是单接口（全接口 → 先怀疑自身进程/GC/线程池；单接口 → 先怀疑下游和 SQL），同时看错误率与线程数曲线。
  2. jstack 多次采样：间隔 5-10 秒抓 3 次，看线程状态分布：
    • 大量 BLOCKED（waiting to lock …）→ 锁竞争或死锁：找成环（互相持有）→ 死锁按 第 04 节处理；单向等待 → 热点锁，考虑锁拆分/降临界区。
    • 大量 WAITING (on condition) 停在下游调用 → 线程池被慢下游占满，本质是容量/熔断问题。
    • RUNNABLE 且 CPU 高 → 另一条线：死循环 or GC——切到 03-jvm 的 CPU 排查与 GC 日志。
  3. arthas 快速验证：thread -n 3 看 CPU 前 3、thread -b 看阻塞源头，省去传 dump 的往返。
  4. DB 侧核对：慢 SQL 日志 + SHOW ENGINE INNODB STATUS 看 LATEST DETECTED DEADLOCK / 锁等待。
  5. 恢复与复盘：先重启/摘流量止血，再按根因落修复（锁排序、超时、熔断），沉淀成规范。

评分点：这个序列的隐藏考点是"多次采样"和"状态分布先行"——单次 jstack 说明不了任何问题，先看 BLOCKED/WAITING/RUNNABLE 的构成再下钻，才是做过事的人的顺序。

09高频追问与陷阱

  • 追问链：四条件 → 为什么破坏互斥不可行？→ 临界资源天然独占（共享变量写就是互斥的）；能做的"去互斥"是无锁化/单线程化（CAS、Actor、Disruptor）——顺势把话题带到 第 05 章。
  • 追问链：jstack 能查出所有死锁吗？→ 只能自动识别 monitor（synchronized）环；ReentrantLock 的环要人肉拼"持有+等待"；分布式锁死锁 JVM 层根本看不见 → 引出 Redis/DB 锁的超时与续期。
  • 陷阱：死锁线程会占 CPU 吗？→ 不会，都在 WAITING/BLOCKED——所以"CPU 不高但接口全超时"反而更像死锁，这是反直觉的判据。
  • 陷阱：tryLock 就一定防死锁吗？→ 前提是拿不到就释放已持有的全部锁再整体重试；只超时第二把不放手第一把，照样锁死。且固定间隔重试有活锁风险，要加随机退避。
  • 陷阱：公平锁能防饥饿，能防死锁吗？→ 不能。公平只改变"谁下一个拿锁"，循环等待照样成环——公平锁防饥饿、tryLock/锁排序防死锁，别答串。
  • 陷阱：notify 之后条件一定成立？→ notify 只意味着"有人可能改了条件"，多个等待者竞争 + 伪唤醒都存在 → while 重查是唯一正解（第 06 节）。
  • 追问：虚拟线程时代这些病有变化吗？→ 病理不变（锁语义、JMM 都没变），死锁照样发生且载体线程被 pin 时更隐蔽（第 10 章）；排查改用 jcmd Thread.dump_to_file -format=json。

10面试自查清单

  1. 四必要条件名 + 含义逐条背得出，并能说出"缺一不成死锁 → 预防=破坏任一条"的推理。
  2. 三板斧与条件的对应：锁排序↔循环等待、tryLock/一次性申请↔请求与保持，锁排序的"全局全序"要点。
  3. 能写最小死锁 demo，也能现场改写成锁排序版和 tryLock 版。
  4. 排查链路完整：现象（吞吐/RT/线程数）→ jstack 多次采样 + "Found one Java-level deadlock" → arthas thread -b → innodb status，且知道 jstack 只自动认 monitor 环。
  5. 死锁/活锁/饥饿三列对比表能默写，活锁解法是随机退避。
  6. 伪唤醒：futex 真实存在、wait 返回≠被 notify、while 守卫 + 三个"类伪唤醒"来源。
  7. 优先级反转：火星探路者故事 + 优先级继承原理 + Java 无 PI 要架构规避。
  8. 线程泄漏三来源：忘 shutdown、无界队列、ThreadLocal 未 remove，各自的防御动作。
  9. RT 突增排查序列能按顺序说 5 步，突出"多次采样 + 状态分布先行"。
