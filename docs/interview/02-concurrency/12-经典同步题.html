02解题总纲 ⭐

第一步：分清两类需求

互斥（Mutual Exclusion）协作（Coordination）
本质保护共享资源：同时只许一个（或一类）线程进入控制执行顺序：等某个事件 / 信号发生再走
判断口诀"不能一起动""轮到我了吗"
典型场景count++、队列入队出队、叉子的占用交替打印、满等空 / 空等满、凑齐成键
对应原语synchronized · Lock · Semaphore(1)wait/notify · Condition · Semaphore(0) · Latch/Barrier

几乎所有题都是两类需求的复合：生产者-消费者 = 互斥（保护队列）+ 协作（满等空、空等满）；哲学家 = 互斥（叉子）+ 协作（拿叉策略防死锁）。动手前先拆成"互斥清单 + 接力图"两张账。

第二步：三套原语的分工

原语当互斥锁用当协作信令用特点
synchronized + wait/notify（管程）任意对象当 monitor一把锁一个等待队列，notify 无法指定叫醒谁 → 只能 notifyAll + while 守卫零依赖、白板首选；唤醒不精确
Semaphorepermits=1 就是互斥锁permits=0 预置"尚未发生"的信号，谁干完谁 release 放行下一棒轮次 / 配额题最直观；本身不保护代码块，互斥需另配
Lock + ConditionReentrantLock一把锁挂多个条件队列，signal 精确唤醒某一类等待者notFull/notEmpty 这类双条件场景之王
CountDownLatch / CyclicBarrier—到齐 / 会合：N 个线程互相等Barrier 可重用、可带 action；Latch 一次性

第三步：解题三板斧

  1. 找共享变量：谁在读改写什么（队列、计数、轮次标志、叉子占用表）——它们就是需要互斥保护的资产。
  2. 定同步关系：画出"接力图"——每个动作完成后 release/signal 谁、谁正 acquire/await 等谁。12 道题的差别只在接力图的形状。
  3. 选原语：纯互斥 → synchronized / Lock；固定轮次接力 → Semaphore(0) 链；多角色精确唤醒 → Lock+Condition；到齐开会 → CyclicBarrier。

信号量语义：把 Semaphore 当计数器——acquire() 减 1（不够就阻塞排队），release() 加 1（有欠账就唤醒队头）。负值的绝对值 = 正在排队等待的线程数；release 不要求先 acquire（可以先发信号再等人），也不必由拿走许可的线程来还——FooBar 用 1/0 两个信号量互推正是靠这一点。

铁律：任何 wait / await 的条件判断永远是 while 不是 if——虚假唤醒 + notifyAll 会惊醒不该醒的人，if 版本会在被意外唤醒后直接冲过条件（原因详见 第 03 章）。本章所有代码都按这条铁律写。

03打印协调三连（题 1-3）

打印类是最友好的入口：几乎没有共享数据要保护，考点全在协作接力。三道 LeetCode 原题从两角色一路加到四角色，覆盖"轮次接力"的全部形态。

题 1 · 交替打印 FooBar（LeetCode 1115）⭐

题意：两个线程并发跑，foo 线程打印 "foo"、bar 线程打印 "bar"，各 n 次，输出 "foobarfoobar..."。

  • 同步关系：foo 先行 → 打完放行 bar → bar 打完再放行 foo，两节点循环接力。
  • 管程版：一把锁 + 布尔轮次标志，没轮到的 wait；信号量版：两个信号量 1/0 互推——连 while 守卫和 notifyAll 都省了，体会"信号量当信令"的简洁。

版本一：synchronized + wait/notify（管程）

class FooBar {
    private int n;
    private final Object lock = new Object();
    private boolean fooTurn = true;              // 轮次标志（都在锁内读写，无需 volatile）
    public FooBar(int n) { this.n = n; }
    public void foo(Runnable printFoo) {
        for (int i = 0; i < n; i++) {
            synchronized (lock) {
                while (!fooTurn)                 // 没轮到我：睡
                    try { lock.wait(); } catch (InterruptedException e) { return; }
                printFoo.run();
                fooTurn = false;                 // 交棒
                lock.notifyAll();                // 叫醒 bar
            }
        }
    }
    public void bar(Runnable printBar) {
        for (int i = 0; i < n; i++) {
            synchronized (lock) {
                while (fooTurn)
                    try { lock.wait(); } catch (InterruptedException e) { return; }
                printBar.run();
                fooTurn = true;
                lock.notifyAll();
            }
        }
    }
}

版本二：Semaphore 交替放行（推荐）

class FooBar {
    private int n;
    private final Semaphore fooSem = new Semaphore(1);   // foo 先行：预置一张票
    private final Semaphore barSem = new Semaphore(0);   // bar 后行：先欠一张票
    public FooBar(int n) { this.n = n; }
    public void foo(Runnable printFoo) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            fooSem.acquire();       // 拿到"该打 foo"的信号（第一轮直接通过）
            printFoo.run();
            barSem.release();       // 放行 bar
        }
    }
    public void bar(Runnable printBar) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            barSem.acquire();       // 没票就睡，直到 foo release
            printBar.run();
            fooSem.release();       // 还票给 foo
        }
    }
}
  • 追问：为什么管程版用 notifyAll 不用 notify？→ 两线程时 notify 恰好叫醒对方，看似安全，实属撞大运：一旦有第三类等待者共用这把锁，notify 可能叫醒同类。口径：默认 notifyAll，只有明确"等待者只有对方一类"时才可 notify。
  • 追问：fooTurn 要 volatile 吗？→ 不用。读写全在 synchronized 内，锁的 happens-before 已保证可见性（第 02 章）。
  • 追问：信号量版为什么没有 while 守卫？→ acquire 本身就是"票不够就睡"，release 精确对应"条件成真"，不存在被错误唤醒后冲过条件的窗口——信令语义天然免虚假唤醒。

题 2 · ZeroEvenOdd 打印 0 与奇偶数（LeetCode 1116）

题意：三个线程：zero 每轮打印一个 0，even 打印偶数，odd 打印奇数，输出 "0102030405..."（到 n）。

  • 同步关系：zero 是总调度——每打一个 0，按第 i 个数的奇偶决定下一棒给 odd 还是 even；打完数字还票给 zero。三条放行闸，一张总票。
class ZeroEvenOdd {
    private int n;
    private final Semaphore zSem = new Semaphore(1);   // 0 的闸：先发一张票
    private final Semaphore oSem = new Semaphore(0);   // 奇数闸
    private final Semaphore eSem = new Semaphore(0);   // 偶数闸
    public ZeroEvenOdd(int n) { this.n = n; }
    public void zero(IntConsumer printNumber) throws InterruptedException {
        for (int i = 1; i <= n; i++) {
            zSem.acquire();                    // 拿到"该打 0"的票
            printNumber.accept(0);
            if (i % 2 == 1) oSem.release();    // 第 i 个数是奇数 → 放行 odd
            else            eSem.release();    // 是偶数 → 放行 even
        }
    }
    public void odd(IntConsumer printNumber) throws InterruptedException {
        for (int i = 1; i <= n; i += 2) {      // 起点 1 步长 2，天然只跑奇数次
            oSem.acquire();
            printNumber.accept(i);
            zSem.release();                    // 还票给 zero
        }
    }
    public void even(IntConsumer printNumber) throws InterruptedException {
        for (int i = 2; i <= n; i += 2) {
            eSem.acquire();
            printNumber.accept(i);
            zSem.release();
        }
    }
}
  • 追问：为什么三个信号量？→ 三岔路口需要三条独立放行闸：一个信号量表达不了"下一个该谁"的分派逻辑；zSem 是总票，o/e 是两条支线闸。
  • 追问：单锁 + state 取模能写吗？→ 能，就是题 12 的模式（while (state % 3 != who) await），代码更少，代价是三类线程挤一个条件队列、signalAll 惊群。
  • 追问：n 为奇数时 even 少跑一轮怎么处理？→ 循环写成起点 2、步长 2、条件 i <= n，自动少一次，不需要特判。

题 3 · FizzBuzz 多线程版（LeetCode 1195）

题意：四个线程分别只打印 fizz（3 的倍数）、buzz（5 的倍数）、fizzbuzz（15 的倍数）、数字本身，从 1 到 n 按序输出。

  • 同步关系：关键认知——"当前该打谁"本身就是共享状态，必须有人持有调度权。number 线程兼任调度员：按 i 的整除性把打印权发出去，工人打完归还令牌。四个信号量 = 一张令牌 + 三条工位闸。
class FizzBuzz {
    private int n;
    private final Semaphore token = new Semaphore(1);       // 调度令牌，number 先持
    private final Semaphore fizzSem = new Semaphore(0);
    private final Semaphore buzzSem = new Semaphore(0);
    private final Semaphore fizzbuzzSem = new Semaphore(0);
    public FizzBuzz(int n) { this.n = n; }
    // number 线程兼任调度员
    public void number(Runnable printNumber) throws InterruptedException {
        for (int i = 1; i <= n; i++) {
            token.acquire();                       // 拿到调度权
            if (i % 3 != 0 && i % 5 != 0) {
                printNumber.run();                 // 普通数字：自己打
            } else {
                if (i % 15 == 0)      fizzbuzzSem.release();
                else if (i % 3 == 0)  fizzSem.release();
                else                  buzzSem.release();
                token.acquire();                   // 等工人打完归还令牌
            }
            token.release();                       // 放行下一轮
        }
    }
    public void fizz(Runnable printFizz) throws InterruptedException {
        for (int j = 0, times = n / 3 - n / 15; j < times; j++) {  // 3 倍数挖掉 15 倍数
            fizzSem.acquire();
            printFizz.run();
            token.release();                       // 归还调度权
        }
    }
    public void buzz(Runnable printBuzz) throws InterruptedException {
        for (int j = 0, times = n / 5 - n / 15; j < times; j++) {
            buzzSem.acquire(); printBuzz.run(); token.release();
        }
    }
    public void fizzbuzz(Runnable printFizzBuzz) throws InterruptedException {
        for (int j = 0, times = n / 15; j < times; j++) {
            fizzbuzzSem.acquire(); printFizzBuzz.run(); token.release();
        }
    }
}
  • 追问：四个线程为什么不各自判断 i 自己打？→ 没有共享游标 i：谁也不知道"现在轮到第几个"，必须有唯一的调度权持有者（token）串行分发。
  • 追问：times = n / 3 - n / 15 是什么？→ fizz 的打印次数：3 的倍数里挖掉 15 的倍数（那部分归 fizzbuzz）。buzz 同理是 n / 5 - n / 15。
  • 追问：更省事的写法？→ 一个锁 + state 分发（题 12 模式）把整除 if-else 链放进一个统一循环；调度员模式胜在职责清晰、和 OS 题（理发师、吸烟者）同构。

04配额与生产消费（题 4-7）

这一组开始互斥与协作复合：H2O 是配额 + 会合；读者-写者是互斥调度；有界缓冲区与生产者-消费者是同一问题的两个深度——后者是面试出现率最高的并发手写题。

题 4 · H2O 生成水分子（LeetCode 1117）

题意：氢线程打印 "H"、氧线程打印 "O"（线程数不限），保证输出按 "HHO" / "HOH" 分组——每 3 个字符一组恰为 2 个 H、1 个 O。

  • 同步关系：配额（每批 2 氢 1 氧）+ 会合（凑齐 3 个才能"成键"放行）。两个信号量管比例，CyclicBarrier(3) 管成键，缺一不可。
  • 纯管程替代：锁内两个计数当"氢 / 氧队列"（while (h == 2) wait / h++，氧对称 o == 1），barrier 照旧凑批——结构等价，信号量版更短。
class H2O {
    private final Semaphore hSem = new Semaphore(2);          // 每批 2 个氢名额
    private final Semaphore oSem = new Semaphore(1);          // 每批 1 个氧名额
    private final CyclicBarrier bond = new CyclicBarrier(3);  // 凑齐 2H+1O 才放行
    public void hydrogen(Runnable releaseHydrogen)
            throws InterruptedException, BrokenBarrierException {
        hSem.acquire();           // 抢氢名额（第 3 个氢在这里等到下一批）
        releaseHydrogen.run();    // 打印 H
        bond.await();             // 等成键：本批 3 个线程到齐才一起过
        hSem.release();           // 归还名额，放行下一批
    }
    public void oxygen(Runnable releaseOxygen)
            throws InterruptedException, BrokenBarrierException {
        oSem.acquire();
        releaseOxygen.run();      // 打印 O
        bond.await();
        oSem.release();
    }
}
  • 追问：只有两个信号量、没有 barrier 行不行？→ 不行。名额立刻归还，第 3 个氢会提前挤进"下一批"，输出可能串成 HHHO——名额管比例，barrier 把 2H+1O 焊成一个分子再放行。
  • 追问：只有 barrier 行不行？→ 也不行。barrier(3) 只知道"来了 3 个线程"，3 个氧也能凑满放行，比例就失控了。
  • 追问：为什么用 CyclicBarrier 不用 CountDownLatch？→ 分子一个接一个生成，凑批点要可重复使用；Latch 一次性，到 0 就废（对比见 第 08 章）。

题 5 · 读者-写者问题 ⭐

题意：多个读者可同时读共享数据；写者必须独占（读写互斥、写写互斥、读读并行）。互斥调度的经典考题。

版本一：ReadWriteLock（工程口径）

class ReadersWritersRW {
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private int data = 0;                       // 被保护的共享数据
    public int read() {
        rw.readLock().lock();                   // 读锁：读者之间不互斥，与写互斥
        try {
            return data;
        } finally {
            rw.readLock().unlock();
        }
    }
    public void write(int v) {
        rw.writeLock().lock();                  // 写锁：独占一切
        try {
            data = v;
        } finally {
            rw.writeLock().unlock();
        }
    }
}

两个高频深挖点：

  • "读锁内修改共享计数"是经典陷阱：读锁只保证与写互斥，读者之间照样并发——在读锁里做 readCount++ 统计并发读者是竞态。要数就上 AtomicInteger（CAS）；或者干脆别自己数——RRWL 内部自带读计数（AQS state 高 16 位记读、低 16 位记写，见 第 04 章）。
  • 锁升降级：读锁"升级"为写锁会死锁（两个读者同时申请升级互等），RRWL 直接不支持；写锁降级读锁是支持的：
// 写 → 读降级：先拿读锁、再放写锁；反向"读升级写"会死锁，RRWL 拒绝
rw.writeLock().lock();
try {
    data = recompute();
    rw.readLock().lock();      // ① 持写锁期间先拿好读锁
} finally {
    rw.writeLock().unlock();   // ② 再放写锁：降级完成，无人能看到中间态
}
try { return data; }           // 之后按读锁语义继续读
finally { rw.readLock().unlock(); }

版本二：Semaphore + 互斥信号量（OS 教科书口径）

class ReadersWriters {
    private final Semaphore mutex = new Semaphore(1);  // 互斥信号量：保护 readCount
    private final Semaphore wrt = new Semaphore(1);    // "房间门"：读写真正互斥处
    private int readCount = 0;                         // 房间里当前的读者数
    public void read() throws InterruptedException {
        mutex.acquire();
        readCount++;
        if (readCount == 1) wrt.acquire();   // 第一个读者进门：替全体读者锁门
        mutex.release();
        // ……读共享数据（多个读者同时在此，读锁语义）
        mutex.acquire();
        readCount--;
        if (readCount == 0) wrt.release();   // 最后一个读者出门：开门放写者
        mutex.release();
    }
    public void write() throws InterruptedException {
        wrt.acquire();                       // 独占房间（有读者在时阻塞在这）
        // ……写共享数据
        wrt.release();
    }
}

这是读者优先版：只要有读者在读，新读者直接进，写者必须等读者清零——读者流量大时写者饥饿。写优先版给写者也配"计数 + 一道门"（新读者看到有写者排队就在门外等），牺牲读者并发换写者不被饿；更工程化的答案是公平模式。

  • 追问：为什么第一个读者要 acquire(wrt)？→ 它代表全体读者把房间锁上挡住写者，最后一个离开的读者再开门——readCount 的增减全程在 mutex 保护下，两个信号量配合完成"读可重入、写独占"。
  • 追问：读者优先怎么改成不饿写者？→ 写优先挡门（如上），或 new ReentrantReadWriteLock(true) 公平模式——队列里谁先到谁上，读写都不饿，代价是吞吐降。
  • 追问：读写锁适合什么场景？→ 读多写少且读临界区不能太短：临界区太短时，锁状态维护（CAS 竞争）的开销会吃掉并发读的收益。

题 6 · 手写有界缓冲区（ArrayBlockingQueue 的骨架）

题意：实现线程安全的定长缓冲区：put 满则阻塞、take 空则阻塞——这正是 第 09 章 ArrayBlockingQueue 的内部结构本身。

  • 一把锁、两个条件队列：notFull（生产者睡这）+ notEmpty（消费者睡这），put 成功 signal 一个消费者、take 成功 signal 一个生产者。
class BoundedBuffer<T> {
    private final Object[] items;
    private int putIdx, takeIdx, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull  = lock.newCondition();   // 生产者等"不满"
    private final Condition notEmpty = lock.newCondition();   // 消费者等"不空"
    public BoundedBuffer(int capacity) { items = new Object[capacity]; }
    public void put(T e) throws InterruptedException {
        lock.lock();
        try {
            while (count == items.length)       // ⭐ while 守卫
                notFull.await();                // 满：睡在 notFull 队列上
            items[putIdx] = e;
            if (++putIdx == items.length) putIdx = 0;   // 环形数组
            count++;
            notEmpty.signal();                  // 精确唤醒一个消费者
        } finally {
            lock.unlock();
        }
    }
    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lock();
        try {
            while (count == 0)
                notEmpty.await();               // 空：睡在 notEmpty 队列上
            T e = (T) items[takeIdx];
            items[takeIdx] = null;              // 帮 GC
            if (++takeIdx == items.length) takeIdx = 0;
            count--;
            notFull.signal();                   // 精确唤醒一个生产者
            return e;
        } finally {
            lock.unlock();
        }
    }
}
  • 追问：为什么必须两个 Condition？→ 一个条件队列里混着等"不满"的生产者和等"不空"的消费者，signal() 可能叫醒同类——被唤醒者发现条件不满足又睡回去，功能对但空转；两个队列才能指名道姓，这是 Condition 相对 Object.wait 的核心增益。
  • 追问：这就是 ArrayBlockingQueue 源码吗？→ 是：items / putIndex / takeIndex / count / notFull / notEmpty 一一对应（第 09 章拆过源码）。
  • 追问：while 换 if 行不行？→ 不行：从被 signal 到自己重新拿到锁之间，条件可能又被别的线程打破；虚假唤醒同理（第 03 章）。

题 7 · 生产者-消费者（三版对比）⭐

题意：生产者往共享队列放数据、消费者取数据，队列有界；满时生产者等、空时消费者等——面试出现率最高的并发手写题。

版本一：synchronized + wait/notifyAll

class ProducerConsumerSync {
    private final Queue<Integer> queue = new LinkedList<>();
    private final int cap = 10;
    private final Object lock = new Object();
    public void put(int v) throws InterruptedException {
        synchronized (lock) {
            while (queue.size() == cap)     // ⭐ while 守卫，不是 if
                lock.wait();                // 满：放锁等待
            queue.offer(v);
            lock.notifyAll();               // 叫醒所有等待者——对面才该醒
        }
    }
    public Integer take() throws InterruptedException {
        synchronized (lock) {
            while (queue.isEmpty())
                lock.wait();                // 空：放锁等待
            Integer v = queue.poll();
            lock.notifyAll();
            return v;
        }
    }
}

版本二：Lock + Condition（精确唤醒）

// 两个条件队列，signal 指名道姓（完整实现就是题 6 的 BoundedBuffer）
private final ReentrantLock lock = new ReentrantLock();
private final Condition notFull  = lock.newCondition();
private final Condition notEmpty = lock.newCondition();
public void put(int v) throws InterruptedException {
    lock.lock();
    try {
        while (queue.size() == cap) notFull.await();   // 只睡在"不满"队列
        queue.offer(v);
        notEmpty.signal();                             // 只叫消费者，不惊动同类
    } finally { lock.unlock(); }
}
// take 对称：notEmpty.await() + notFull.signal()

版本三：直接用 BlockingQueue（工程首选）

BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);
queue.put(1);               // 满了自动阻塞（内部就是 notFull/notEmpty）
Integer v = queue.take();   // 空了自动阻塞
// 生产代码：线程池 + 有界队列 = 生产者-消费者架构本体（第 06 章）
  • 追问：版本一的 notifyAll 换 notify 行不行？→ 不行。notify 叫醒的可能是同类（唤醒另一个生产者），它检查条件不满足又睡回去，真正该醒的消费者永远等不到——极端下全员互睡。
  • 追问：三版怎么选？→ v1 展示基本功（while 守卫 + notifyAll 的原因能讲清），v2 讲精确唤醒，v3 表明工程判断——生产代码没有理由手写第四版。
  • 追问：队列满了还不停提交怎么办？→ 有界队列 + 拒绝策略，或 put 阻塞形成背压，链 第 06 章线程池。

题 8 · 哲学家进餐 ⭐

题意：5 位哲学家围桌，两两之间一把叉子；进餐须同时拿起左右两把叉，吃完放下。人人先拿左叉不放 = 死锁教科书现场。

死锁现场（反面教材）

class Philosopher extends Thread {
    private final Object left, right;
    Philosopher(int id, Object[] forks) {
        left = forks[id];
        right = forks[(id + 1) % forks.length];  // 5 号的右叉 = 0 号的左叉 → 成环
    }
    public void run() {
        while (true) {
            synchronized (left) {           // ① 先拿左叉
                synchronized (right) {      // ② 再拿右叉
                    eat();                  // 5 人同时走到① → 全员卡死在②
                }
            }
        }
    }
    private void eat() { /* 进餐 */ }
}

五人同时到达"已拿左叉、等右叉"：每人持有别人要的叉、等别人持有的叉——循环等待成立，死锁四条件（互斥 / 持有并等待 / 不可剥夺 / 循环等待，详见 第 11 章）全部凑齐。四种解法各破坏其中一条：

解法破坏的条件代价
① 只许 4 人入座 Semaphore(4)循环等待（4 人 5 叉，鸽笼原理必有一人能凑齐两把）并发度降为 4，入座要排队
② 奇偶编号拿叉顺序相反循环等待（资源有序分配的变体）几乎零成本
③ tryLock 超时，拿不到就放持有并等待（近似实现"可剥夺"）活锁风险，需随机退避
④ 管程服务员集中分发持有并等待（两把叉原子获取）服务员是单点，竞争集中

解法 ① 只许 4 人同时上桌

class PhilosopherRoom extends Thread {
    private static final Semaphore room = new Semaphore(4);   // 桌旁只放 4 把椅子
    private final Object left, right;
    PhilosopherRoom(int id, Object[] forks) {
        left = forks[id]; right = forks[(id + 1) % forks.length];
    }
    public void run() {
        while (true) {
            try {
                room.acquire();             // 先抢座位：最多 4 人同时伸手拿叉
                synchronized (left) {
                    synchronized (right) { eat(); }
                }
            } catch (InterruptedException e) {
                return;
            } finally {
                room.release();             // 离桌让位 —— 第 5 人进不来，环不成型
            }
        }
    }
    private void eat() { /* 进餐 */ }
}

解法 ② 奇偶反序拿叉（最常用）

// run() 内：偶数号先左后右、奇数号先右后左（破坏"人人先拿同一侧"的对称）
Object first, second;
if (id % 2 == 0) { first = left;  second = right; }
else             { first = right; second = left; }
// 效果：相邻两人必在"同一把叉"上正面相遇，输家两手空空、不持有任何叉 → 环被斩断
synchronized (first) {
    synchronized (second) { eat(); }
}

解法 ③ tryLock 超时放弃

// forks 改用 ReentrantLock[]；100ms 内凑不齐两把就全部放弃、随机退避后重试
if (forks[id].tryLock(100, TimeUnit.MILLISECONDS)) {
    try {
        if (forks[(id + 1) % 5].tryLock(100, TimeUnit.MILLISECONDS)) {
            try { eat(); } finally { forks[(id + 1) % 5].unlock(); }
        }
        // 右叉没抢到：什么都不做，finally 放掉左叉
    } finally {
        forks[id].unlock();       // 拿不到右叉就放左 —— 不做"半持有"的人
    }
}

解法 ④ 管程服务员（集中分发）

class Waiter {                              // 要么两把都给，要么一把都不给
    private final boolean[] used = new boolean[5];
    public synchronized void take(int i) throws InterruptedException {
        while (used[i] || used[(i + 1) % 5])
            wait();                         // 缺任何一把就空手等待
        used[i] = true;
        used[(i + 1) % 5] = true;           // 两把叉原子到手
    }
    public synchronized void put(int i) {
        used[i] = false;
        used[(i + 1) % 5] = false;
        notifyAll();                        // 叫醒邻居们重新检查
    }
}
// 哲学家线程体：waiter.take(id); eat(); waiter.put(id);
  • 追问：四种解法各破坏哪个条件？→ 见上表。先背死锁四条件，再"任选其一破坏"给解法——这是标准答题路线（四条件详见 第 11 章）。
  • 追问：工程上像什么？→ 奇偶反序 = 资源有序分配（分布式锁按排序后的 key 依次加锁）；tryLock 超时 = 数据库锁等待超时；管程服务员 = 集中式锁 / 事务管理器。
  • 追问：解法 ③ 的活锁怎么破？→ 退避时间加随机抖动，避免所有人同频"拿起-放下-再拿起"。

题 9 · 睡眠理发师

题意：理发店无顾客时理发师睡觉；顾客到店，有等待椅（N 把）就坐下等，满了扭头就走；理发师依次招待。

  • 同步关系：customers 是"叫号铃"（理发师没人就睡在它上面）；barberReady 是"上椅令"；waiting 计数配互斥信号量保护——check-then-act 必须原子。
class BarberShop {
    private static final int CHAIRS = 5;                    // 等待椅数
    private int waiting = 0;                                // 正在等的顾客数
    private final Semaphore customers  = new Semaphore(0);  // 叫号铃
    private final Semaphore barberReady = new Semaphore(0); // 上椅令
    private final Semaphore mutex = new Semaphore(1);       // 保护 waiting
    public void customer() throws InterruptedException {
        mutex.acquire();
        if (waiting == CHAIRS) {            // 没椅子：扭头就走（不等待）
            mutex.release();
            return;
        }
        waiting++;                          // 坐下排队
        mutex.release();
        customers.release();                // 按叫号铃（理发师在睡就唤醒）
        barberReady.acquire();              // 等理发师招呼自己上理发椅
        // ……坐上理发椅开始剪发
    }
    public void barber() throws InterruptedException {
        while (true) {
            customers.acquire();            // 没顾客就睡在这里
            mutex.acquire();
            waiting--;                      // 队头离队、上理发椅
            mutex.release();
            barberReady.release();          // 招呼顾客
            // ……剪发，剪完回到 customers.acquire 叫下一个
        }
    }
}
  • 追问：waiting 为什么必须配 mutex？→ "看还有没有椅子"和"坐下"是 check-then-act，不原子的话满员后还继续放人进队。
  • 追问：两张信号量的语义？→ customers：顾客到店的信令（理发师等它）；barberReady：服务就绪的信令（顾客等它）——两张信号量完成一次双向握手。
  • 追问：扩展成 k 个理发师？→ 等待椅不变；barberReady 的 permits 初始化为 k，顾客 acquire 到哪把椅就哪位剪——Semaphore 天然是资源池。

题 10 · 吸烟者问题

题意：三个吸烟者分别持有烟草、纸、火柴中的一种（各不相同且不补货）；供应者每轮往桌上摆另外两种材料，恰好凑齐三种材料的人卷烟抽掉，抽完通知供应者摆下一桌。

  • 同步关系：三种桌面组合 → 三条信令，每条恰好对应"唯一不缺这两样"的吸烟者，一对一、无需判断；smoked 是"抽完了"回执——供应者串行摆桌。
class Cigarette {
    // 三种"桌面组合"信令：摆什么就按哪条铃
    private final Semaphore tobaccoPaper = new Semaphore(0);  // 有火柴的吸烟者等这
    private final Semaphore tobaccoMatch = new Semaphore(0);  // 有纸的等这
    private final Semaphore paperMatch   = new Semaphore(0);  // 有烟草的等这
    private final Semaphore smoked = new Semaphore(0);        // "抽完了"回执
    public void supplier() throws InterruptedException {
        for (int round = 0; round < 10; round++) {
            int k = round % 3;                      // 0/1/2 轮流摆三种组合（随机同理）
            if (k == 0)      tobaccoPaper.release();   // 摆 烟草+纸
            else if (k == 1) tobaccoMatch.release();   // 摆 烟草+火柴
            else             paperMatch.release();     // 摆 纸+火柴
            smoked.acquire();                        // 等抽完，再摆下一桌
        }
    }
    // 吸烟者 A：手里有火柴，只等"烟草+纸"这一桌
    public void smokerWithMatch() throws InterruptedException {
        while (true) {
            tobaccoPaper.acquire();   // 桌上出现了自己缺的两样
            // ……卷烟、点烟、抽
            smoked.release();         // 通知供应者可以摆下一桌
        }
    }
    // 另两位对称：有纸的等 tobaccoMatch，有烟草的等 paperMatch
}
  • 追问：桌面信令为什么是三个？→ 三种组合各对应唯一的吸烟者，一对一信令不需要任何条件判断——比"一个信号量+轮询"干净得多。
  • 追问：smoked 回执去掉会怎样？→ 供应者可能连摆两桌，材料混桌、"一桌一烟"的语义被破坏——这是"完成信号"的标准用法（和第 08 章线程间协作同款）。
  • 追问：本质是什么？→ 事件驱动调度：每个 worker 等自己关心的那种事件，调度者按序发事件、收回执再发下一个——MQ 消费路由是它的工程放大版。

题 11 · 圣诞老人问题

题意：圣诞老人睡觉，被唤醒只可能是两件事之一：3 只精灵凑成一队来咨询，或 9 只驯鹿全部归队要出发送礼。驯鹿优先：两边同时来先送礼。

  • 同步关系：CyclicBarrier(3) 带自动按铃的 action 凑精灵队；驯鹿用互斥保护的计数凑 9 只；圣诞老人醒来先查驯鹿——优先级就是检查顺序。
class SantaClaus {
    private static final int ELF_TEAM = 3;                    // 精灵 3 只一队
    private final Semaphore wakeSanta = new Semaphore(0);     // 圣诞老人起床铃
    private final Semaphore fly = new Semaphore(0);           // 出发令
    private final Semaphore help = new Semaphore(0);          // 咨询放行令
    private final Semaphore mutex = new Semaphore(1);         // 保护 deerCount
    private int deerCount = 0;                                // 已归队驯鹿数
    private final CyclicBarrier elfTeam =
            new CyclicBarrier(ELF_TEAM, () -> wakeSanta.release());  // 凑齐自动按铃
    public void elf() throws InterruptedException, BrokenBarrierException {
        elfTeam.await();        // 凑满 3 只一队（barrier 可重用，下一队自动开凑）
        help.acquire();         // 等圣诞老人放行 —— 驯鹿在场时会被优先晾着
        // ……咨询
    }
    public void reindeer() throws InterruptedException {
        mutex.acquire();
        if (++deerCount == 9) {     // 第 9 只驯鹿归队
            mutex.release();
            wakeSanta.release();    // 按起床铃
        } else {
            mutex.release();
        }
        fly.acquire();              // 等出发令
        // ……拉雪橇送礼
    }
    public void santa() throws InterruptedException {
        while (true) {
            wakeSanta.acquire();                    // 睡到有人按铃
            mutex.acquire();
            boolean deerReady = (deerCount == 9);
            if (deerReady) deerCount = 0;           // 清零：本批已出发，下一批重凑
            mutex.release();
            if (deerReady) fly.release(9);          // 优先：先送礼物
            else           help.release(3);         // 否则：接见精灵队
        }
    }
}
  • 追问：驯鹿优先体现在哪？→ santa 被叫醒后先查 deerCount：即使两边同时按铃（铃上积了两张许可），第一轮也先送礼、第二轮再咨询——优先级就是"检查顺序 + 信号量许可可累积"。
  • 追问：驯鹿为什么用计数变量不用 CountDownLatch？→ Latch 一次性：getCount() 一旦到 0 就永远是 0，santa 会反复误判"驯鹿到齐"；计数变量能在每批出发后清零复用。
  • 追问：CyclicBarrier 的 action 参数干嘛的？→ 第 3 只精灵到达的瞬间自动执行 run（按起床铃），省掉"第 N 个到达者手动 release"的判断——对比题 4 手动 release 的写法。

06收官：ABC 轮转与条件队列（题 12）

题 12 · 三个线程按 A/B/C 顺序各打印 n 轮

题意：三个线程分别只打印 A、B、C，输出 "ABCABC..." 共 n 轮——题 1 的三线程版，也是管程收尾题。

  • 同步关系：三节点环形接力。这里故意用一个 Condition + state 取模：三个线程睡在同一个条件队列上，signalAll 后谁的状态匹配谁走——正确但有惊群；想精确唤醒就拆成三个 Condition（追问里展开）。
class PrintABC {
    private final int n;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition cond = lock.newCondition();   // 一个条件队列：三人共睡
    private int state = 0;                                // state % 3 == 0/1/2 → 该打 A/B/C
    public PrintABC(int n) { this.n = n; }
    public void printA(Runnable p) throws InterruptedException { loop(0, p); }
    public void printB(Runnable p) throws InterruptedException { loop(1, p); }
    public void printC(Runnable p) throws InterruptedException { loop(2, p); }
    private void loop(int who, Runnable p) throws InterruptedException {
        for (int i = 0; i < n; i++) {
            lock.lock();
            try {
                while (state % 3 != who)     // 没轮到我：继续睡
                    cond.await();
                p.run();                     // 打印 A/B/C
                state++;                     // 交棒
                cond.signalAll();            // 叫醒同伴：谁的状态匹配谁走
            } finally {
                lock.unlock();
            }
        }
    }
}
  • 追问：一个 Condition 为什么也够？→ 轮转是全序：signalAll 之后谁的状态匹配谁走、其余继续睡。正确，但每棒惊醒两人、多两次无谓唤醒。
  • 追问：怎么改精确唤醒？→ 拆成 turnA/turnB/turnC 三个 Condition，A 打完只 signal turnB 的队列——与题 6 的 notFull/notEmpty 同一思想：条件队列按"等待的条件"分堆。
  • 追问：和题 2 的三信号量版怎么选？→ 信号量把"轮到谁"藏进 permits 计数，代码最短；Condition 版 state 显式可见，改需求（如某角色连打两次、插入新角色）更直观。

07追问套路：写完之后的"改需求"怎么接

  • 改线程数 / 轮数→ 信号量链跟着角色走：几个角色几条放行闸（题 2/3）；单锁 + state 版只需改取模基数和判断分支（题 12）。面试官最爱用这招看你是不是真理解结构。
  • 加超时→ tryAcquire(timeout) / tryLock(timeout) / awaitNanos：拿不齐资源就放弃已持有的并重试，既防永久卡死，也顺手破坏"持有并等待"（哲学家解法 ③）。
  • 问饥饿与公平→ 读者-写者、哲学家必被追问：new Semaphore(k, true)、公平 ReentrantLock / ReentrantReadWriteLock(true)，以及"写优先挡门"的手写计数。
  • 问异常→ InterruptedException 永远别吞：恢复中断标志（Thread.currentThread().interrupt()）或直接上抛，否则线程池的取消机制失灵。
  • 问性能→ 惊群（notifyAll 滥用）换多 Condition 精确唤醒；锁粒度（管程服务员的单点 vs 分散叉子）按竞争强度权衡。
  • 问生产落地→ 手写是面试题，工程直接 BlockingQueue / 线程池 / MQ。能主动补这句，才是"写过生产代码的人"。

08面试自查清单

  1. 任给一题，30 秒内判断"互斥为主还是协作为主"，说出用哪套原语。
  2. FooBar 两版都能白板写全，讲清两个信号量 1/0 互推的语义（release 不要求先 acquire）。
  3. ZeroEvenOdd / FizzBuzz 的多路分发：信号量链或令牌调度员，能口述完整接力关系。
  4. H2O 说清"信号量管比例、barrier 管成键，缺一不可"。
  5. 读者-写者：ReadWriteLock 版 + Semaphore 读者优先版，讲清"读锁内改计数的竞态、写降读支持 / 读升级死锁、写者饥饿与公平模式"。
  6. 有界缓冲区能手写：一把锁两个 Condition（notFull/notEmpty），知道它就是 ArrayBlockingQueue 的骨架。
  7. 生产者-消费者三版对比：notifyAll 为什么必须、Condition 精确唤醒的优势、工程直接 BlockingQueue。
  8. 哲学家：先写死锁现场，再按"破坏四条件之一"给出四种解法并说清各破坏哪条。
  9. 理发师 / 吸烟者 / 圣诞老人：能画出"谁按铃、谁等铃"的信令接力图。
  10. PrintABC：单 Condition + state 取模会写，也知道拆三 Condition 精确唤醒的改法。
  11. 写完自查两件事：所有 wait/await 都在 while 里；InterruptedException 没被吞。
