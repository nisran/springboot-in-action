02并发 vs 并行 ⭐

并发（Concurrency）并行（Parallelism）
本质任务调度：同一时间段内多个任务交替推进（宏观同时、微观分时）同时执行：同一时刻多个任务真正同时跑
硬件前提单核即可（时间片轮转）必须多核（或多 CPU / 超线程）
关注点任务如何拆分、调度、通信（结构）任务如何同时算得快（执行）
典型例子单核上一边听歌一边打字（快速切换）8 核 CPU 8 个线程各算各的
  • 单核 CPU 谈得上并发吗？能。并发是逻辑上的"都在推进"，靠时间片轮转（几十毫秒一级）实现；并行是物理上的同时执行。二者不冲突：4 核跑 100 个线程 = 并行度 4 + 并发度 100。
  • 为什么并发对 IO 密集型收益巨大：线程等 IO 时会让出 CPU，切换给别的任务，吞吐量近似叠加；而 CPU 密集型任务并发过度反而因上下文切换变慢——这条直接决定后面 线程池大小怎么定。

一句话口径（Rob Pike）：并发是关于结构的，并行是关于执行的。并发把程序拆成可交错的部分，并行是这些部分真的同时跑。

03进程 vs 线程 ⭐⭐

基本定义

  • 进程（Process）：操作系统分配资源的基本单位，拥有独立的地址空间、文件描述符等，隔离性好，代价是创建 / 切换 / 通信都重。一个独立运行的 JVM 就是一个进程。
  • 线程（Thread）：操作系统调度的基本单位（CPU 执行的基本单位），共享所属进程的堆、方法区、文件等资源，只拥有自己私有的栈和寄存器上下文——轻量，但共享也带来了竞态问题。
维度进程线程
根本定位资源分配的基本单位CPU 调度的基本单位
地址空间独立，互不可见（隔离性好）共享所在进程的地址空间
切换成本高：切页表、刷 TLB、内核栈切换低：保存/恢复寄存器 + 私有栈
通信方式管道 / 消息队列 / 共享内存 / socket直接读写共享变量（需同步）
健壮性一进程崩溃不影响其他进程一线程崩溃整个进程挂掉

从 JVM 内存区域看进程与线程（高频追问）

被问"从 JVM 角度分析进程和线程"时的标准展开——进程私有整块 JVM 内存，线程只私有其中三小块：

  • 进程级（所有线程共享）：堆（对象实例与数组，GC 主战场）、方法区 / 元空间（JDK 8 起类信息、运行时常量、静态变量）、直接内存（NIO DirectBuffer 等，不属于 JVM 但由 JVM 管理）。
  • 线程私有：虚拟机栈（每次方法调用压一个栈帧，局部变量表就在这里——所以局部变量天然线程安全）、程序计数器（记录当前执行到的字节码位置，线程切换回来从这继续，唯一不会 OOM 的区域）、本地方法栈（native 方法用）。

答题技巧：先说"进程管资源、线程管执行"，再补这句"反映在 JVM 里就是：堆和方法区是进程级共享的，栈、PC、本地方法栈是线程私有的"——把两个考点串起来，比分开背两个答案高一个档次。GC 细节在 03-jvm 展开。

用户线程 vs 内核线程

  • 内核线程（KLT）由 OS 直接调度；用户线程（ULT）在用户态库 里调度，内核无感知。
  • Java 的 platform thread 采用 1:1 模型：每个 new Thread() 底层对应一个内核线程，能真正用上多核，代价是创建/切换走系统调用、栈默认约 1MB——这正是线程池和 虚拟线程（JDK 21，M:N 混合模型）要解决的问题。
  • 内核态/用户态切换是上下文切换贵的根源：保存寄存器、切换内核栈，且切换后 CPU 缓存（L1/L2）大概率失效。

04线程生命周期与状态

Java 6 种状态定义在 Thread.State 枚举里（注意是语言级状态，和 OS 的五状态模型不完全对齐）：

状态含义怎么进入
NEW创建了还没调 start()new Thread()
RUNNABLE可运行（含 OS 层的 Running 和 Ready）start()；被唤醒 / 分到时间片
BLOCKED等待获取 monitor 锁（synchronized）抢 synchronized 锁失败
WAITING无限期等待，需被显式唤醒wait() / join() / LockSupport.park()
TIMED_WAITING限时等待，到时自动醒sleep(ms) / wait(ms) / join(ms) / parkNanos
TERMINATEDrun() 执行完（正常或异常）run() 结束

三个易被追问的点

  • JAVA 没有 Running 状态：RUNNABLE 把"正在 CPU 上跑"和"就绪等时间片"合在一起了——是否正在运行由 OS 决定，JVM 不感知。
  • BLOCKED 只属于 synchronized：等 ReentrantLock 的线程在 AQS 队列里 park，状态是 WAITING 而不是 BLOCKED——jstack 里看到的 waiting on condition。用 Blocked/WAITING 的分布可以反推代码用的是哪种锁。
  • IO 阻塞时 Java 线程仍是 RUNNABLE：socket read 阻塞在 native，JVM 层看还是 RUNNABLE——所以"RUNNABLE 很安全"是错觉，排查时要结合线程栈里的 native 帧。

BLOCKED vs WAITING：五个维度 ⭐

一句话：BLOCKED 是"想进门但门从里面锁着"，WAITING 是"自己把自己挂起来等人来叫"——前者没人叫你，持锁者出来你自动进去；后者不来 notify/unpark 就永远睁不开眼。进入 BLOCKED 有两条路，第二条最容易漏：① 抢 synchronized 失败；② wait() 被 notify() 唤醒后，必须先重新抢回 monitor 才能从 wait 返回，这段抢锁期也是 BLOCKED（不是 WAITING）——对应 ObjectMonitor 里"从 WaitSet 搬进 EntryList"。

维度BLOCKEDWAITING / TIMED_WAITING
触发等 synchronized 监视器锁（含 wait 醒后重抢锁）wait() / join() / LockSupport.park()；带超时的是 TIMED_WAITING（sleep / wait(ms) / parkNanos）
谁来结束持锁者释放，JVM 从 EntryList 挑一个唤醒——被动，不需要任何人"叫"别的线程 notify / unpark / 目标线程结束 / 超时——需要显式信号
能否被 interrupt() 打断不能：只置中断标志位，继续死等锁；拿到锁后标志位仍在，由后续代码处理能：wait/join/sleep 抛 InterruptedException（并清标志位），park 直接返回
底层ObjectMonitor _EntryList/_cxq 排队，内核 mutex 挂起（03 章 §03）park（Parker，底层 futex，03 章 §05）；AQS 的同步队列、条件队列都在这里（03 章 §09 两条队列）
jstack 长相BLOCKED (on object monitor) + - waiting to lock <0x…>；持有者那行是 - locked <0x…>，两者成环即死锁WAITING (on object monitor) + in Object.wait()；或 WAITING (parking) + waiting on condition（JUC 锁）
// sleep(ms) = 吞掉 InterruptedException 的 Thread.sleep 封装
Object lock = new Object();
Thread t1 = new Thread(() -> { synchronized (lock) { sleep(5000); } });
Thread t2 = new Thread(() -> { synchronized (lock) { } });
t1.start(); sleep(100); t2.start(); sleep(100);
System.out.println(t2.getState());   // BLOCKED

// 同样场景换成 ReentrantLock.lock()  → 打印 WAITING（AQS 内部是 LockSupport.park）
// 同样场景换成 socket.read() 卡住    → 打印 RUNNABLE（JVM 看它在跑 native 代码）

所以 Thread.State 是JVM 层视角而非 OS 视角：BLOCKED 专指 synchronized，JUC 的锁阻塞（lock() / BlockingQueue.take() / CountDownLatch.await()）全是 WAITING，I/O 阻塞是 RUNNABLE——拿到 jstack 先按这三条分流，再去看栈。

追问延伸：这个区分在虚拟线程时代有新含义——JDK 21 里虚拟线程在 synchronized 内 BLOCKED/wait 会把载体线程 pin 住，JUC 锁的 WAITING（park）则能正常卸载；JDK 24（JEP 491）才抹平。这正是"虚拟线程下优先 ReentrantLock"的根因，见 10 章 · pin 问题。

状态转换速记

NEW --start()--> RUNNABLE --run()结束--> TERMINATED
RUNNABLE --抢sync锁失败--> BLOCKED --拿到锁--> RUNNABLE
RUNNABLE --wait()--> WAITING --notify/notifyAll--> BLOCKED（重抢 monitor）--拿到锁--> RUNNABLE   ⭐ 中间多一跳
RUNNABLE --join()/park()--> WAITING --目标线程结束/unpark--> RUNNABLE
RUNNABLE --sleep(ms)/wait(ms)/parkNanos--> TIMED_WAITING --超时或唤醒--> RUNNABLE（wait(ms) 醒后同样先过 BLOCKED）

陷阱：调 start() 两次会抛 IllegalThreadStateException（线程不可重启）；调 run() 不抛错但只是普通方法调用——在调用者线程同步执行，完全不并发。这对"start 和 run 的区别"就是标准答案。

05竞态条件与临界区

竞态条件（Race Condition）：结果依赖于线程执行的相对时序，就称为竞态。最经典的 count++：

private int count = 1000;

// 10 个线程各执行 100 次 count--，最后大概率不是 0
count--;   // 字节码三步：getfield 读值 -> iadd/isub 计算 -> putfield 写回
// 两个线程交错执行：都读到 1000，各自减 1，都写回 999 —— 丢了一次更新
  • 临界区（Critical Section）：访问共享资源的代码段。竞态的解法就是让临界区互斥执行：synchronized / Lock（第 03 章）、CAS 原子类（第 05 章）。
  • 除了"读-改-写"，"检查-再行动（check-then-act）"同样不原子：if (map.get(k) == null) map.put(k, v);、懒加载单例的 if (instance == null) 都在此列——后者引出双重检查锁（见 01-java/15 单例）。
  • 面试让举例时，说业务里的：库存超卖、重复下单、余额扣成负数、限流计数不准，比教科书例子有说服力（完整方案在 第 13 章 并发票务系统）。

三大特性在此埋个伏笔：count++ 破坏的是原子性；一个线程改了标志位另一个看不见是可见性（第 02 章 JMM）；指令顺序被优化打乱是有序性——并发的一切工具都在解决这三件事，这是后面所有章节的总纲。

06创建线程的方式

先给面试官爱听的"纠错版"答案

常见回答"四种：Thread、Runnable、Callable、线程池"。更严谨的口径：创建线程的方式只有一种——new Thread().start()；其余都是"任务的提交方式"或"线程的管理方式"。

方式本质要点
extends Thread真线程（重写 run）占用唯一继承名额，任务与线程耦合，不推荐
implements Runnable任务，还要包给 Thread任务与线程解耦，无返回值、不抛受检异常
Callable + Future任务（有返回值）call() 有返回值可抛异常；需配套 FutureTask / 线程池
线程池 Executor管理方式线程复用、削峰、统一治理——生产唯一正解（第 06 章）
CompletableFuture编排方式异步回调、组合、异常传播（第 07 章）
虚拟线程（JDK 21）新的线程实现百万级廉价线程，见第 10 章
// Runnable：任务与线程分离，同一个任务可丢给任意线程/线程池
Thread t = new Thread(() -> System.out.println("run"), "worker-1");
t.start();

// Callable：有返回值
ExecutorService pool = Executors.newFixedThreadPool(2);
Future<Integer> f = pool.submit(() -> 1 + 2);
Integer r = f.get();   // 阻塞取结果
  • Runnable vs Callable 追问：run() 无返回值、不能抛受检异常（只能内部 catch）；call() 有返回值、可抛异常，异常由 Future.get() 包装成 ExecutionException 抛出。
  • Thread vs Runnable 选型：Runnable 解耦任务与执行器、避免继承占用、多个 Thread 可共享同一份任务状态——一律优先 Runnable。

生产警告：直接 new Thread() 的三大问题——无复用（创建/销毁开销 + 资源耗尽）、无命名无治理（排查时一堆 thread-1）、无队列缓冲（瞬时流量直接打满）。生产代码只有线程池一种写法。

07sleep vs wait ⭐

维度Thread.sleep(ms)object.wait()
所属类Thread 静态方法Object 的方法（所有对象都有）
是否释放锁不释放（抱着锁睡）释放 monitor 锁，醒来还要重新抢
使用位置任意必须在 synchronized(obj) 内，否则 IllegalMonitorStateException
唤醒方式到时自动醒（interrupt 可提前打断并抛 InterruptedException）需 notify()/notifyAll()（或 wait(ms) 超时）
设计意图让当前线程暂停多久（不涉及协作）线程间协作：条件不满足就让出锁等通知
synchronized (lock) {
    while (!condition) {      // ⭐ 必须用 while 不是 if —— 防虚假唤醒
        lock.wait();          // 释放锁、进入 WAITING，被 notify 后从这里醒来
    }
    doWork();
}

// sleep 抱着锁睡的现场：其他线程全部卡在 BLOCKED
synchronized (lock) {
    Thread.sleep(10_000);     // 10 秒内谁都进不来
}
  • 一句话总结：sleep 是"我睡 N 毫秒，锁还是我的"；wait 是"条件不满足，我把锁让出来等通知"——一个是暂停，一个是协作。
  • 为什么 wait 定义在 Object 而不是 Thread：wait/notify 作用于锁对象（monitor），Java 每个对象都能当锁，所以这对方法必须放在 Object 里。
  • wait 的完整陷阱链（虚假唤醒、notify 随机唤醒、notifyAll 的必要性、wait 放在循环里的原因）在 第 03 章 wait·notify 陷阱展开。

加分项：能主动对比 LockSupport.park/unpark——不需持锁、不需临界区、unpark 可以先于 park 调用（许可机制），精确唤醒指定线程；AQS 与虚拟线程调度都建立在它之上。许可机制、三种返回与中断语义、Parker 底层在 03 章 §05 LockSupport 专讲。

08yield 与 join：一个"让"、一个"等"

sleep / wait 问完，面试官常顺手追 Thread.yield() 和 t.join()——它们和 sleep / wait / park 一起构成线程控制的"五兄弟"，但语义是两码事：yield 是"我让出 CPU，但我还想跑"，join 是"我等你跑完我再跑"。两者都不释放调用者持有的任何锁（join 内部释放的只是目标线程对象自己的 monitor，见下）。

yield()：让出 CPU 的"建议"，不是命令

Javadoc 原话："A hint to the scheduler that the current thread is willing to yield its current use of a processor. The scheduler is free to ignore this hint." 四个要点：

  • 只是 hint：调度器可以完全不理；就算理了，下一个被调度的也可能还是自己（多核下别的核根本不缺 CPU）。
  • 状态仍是 RUNNABLE：OS 层从 Running 回到 Ready 队列，Java 层 Thread.State 不变——它不是阻塞、不是等待，jstack 里不会出现在 WAITING 名单上。
  • 不释放任何锁：synchronized 块里 yield，锁还是你的。
  • 不检查中断、不抛异常：和 sleep "先查中断标志再睡"不同，yield 对 interrupt 完全无感。
// JDK 里 yield 的典型用法（ConcurrentHashMap.initTable）：输掉初始化竞争的线程
// "让一下"再回来重查 —— 比空转礼貌、比 park 轻，这是它为数不多的正当场景
while ((tab = table) == null || tab.length == 0) {
    if ((sc = sizeCtl) < 0)
        Thread.yield();                       // lost initialization race; just spin
    else if (U.compareAndSwapInt(this, SIZECTL, sc, -1)) { /* 初始化 */ }
}

底层：JVM_Yield → os::naked_yield() → Linux sched_yield()，把自己挂回就绪队列（CFS 下只是标记为"可跳过"，效果更弱）。HotSpot 甚至留了个开关 -XX:+DontYieldALot 把 yield 直接变 no-op——可见 JVM 自己都不把它当回事。虚拟线程（JDK 21）是例外：Thread.yield() 走 VirtualThread.tryYield()，真的卸载并重新排队，让其他虚拟线程上载体线程跑——在虚拟线程里它反而是有效的让步手段。

陷阱：用 yield 控制执行顺序。"T1 先 yield 让 T2 先跑"——不可靠：hint 可被忽略、多核下 T2 可能早就在别的核上跑了、让出后调度回来的可能还是 T1。顺序只能靠 join / CountDownLatch / 条件队列这类带同步语义的工具，yield 一个都保证不了。同理，自旋等待里"礼貌让步"的正确工具是 Thread.onSpinWait()（JDK 9，x86 落到 PAUSE 指令，省电省总线），不是 yield。

  • 追问：yield 和 sleep(0) 有什么区别？→ HotSpot 里平台线程的 sleep(0) 进 JVM_Sleep，时长为 0 时直接 naked_yield()——行为上就是一次 yield；区别只在 sleep 入口会先检查中断标志（已中断则抛 InterruptedException 并清标志），yield 不检查。所以 sleep(0) ≈ "带中断检查的 yield"。
  • 追问：yield 会释放锁吗？会进 WAITING 吗？→ 都不会：不释放锁、状态仍 RUNNABLE——这是和 wait 的本质区别，也是它不能用于协作的原因。
  • 追问：那 yield 到底什么时候用？→ Javadoc 自己说 "It is rarely appropriate"：测试里制造线程交错复现竞态 bug；JUC 内部少数自旋让步（initTable）。业务代码里出现 yield 基本是误用。

join()：等目标线程结束——本质是在它身上 wait

t.join() = 当前线程等 t 进入 TERMINATED 再继续；join(millis) 最多等 millis，join(0) 等于无限等。源码（JDK 8~20）短到可以背：

// Thread.join(long)，JDK 8~20 —— ① synchronized：锁的是 t 这个 Thread 对象
public final synchronized void join(long millis) throws InterruptedException {
    long base = System.currentTimeMillis(), now = 0;
    if (millis == 0) {
        while (isAlive())            // ② while 守卫：防虚假唤醒，和 wait 的规矩一样
            wait(0);                 // ③ 在 t 的 monitor 上 wait，放的是 t 的锁而非调用者的锁
    } else {
        while (isAlive()) {
            long delay = millis - now;
            if (delay <= 0) break;   // 超时直接返回：返回值 void，分不清超时还是结束
            wait(delay);
            now = System.currentTimeMillis() - base;
        }
    }
}
// 谁来 notify？没有任何 Java 代码调它 —— 是 JVM，线程退出时：
// JavaThread::exit() → ensure_join() → 置 TERMINATED、清 native 线程（isAlive 变 false）
//                                   → notify_all(threadObj)

由此引出 Javadoc 的一条明文警告："As a thread terminates the this.notifyAll method is invoked. It is recommended that applications not use wait, notify, or notifyAll on Thread instances."——别拿 Thread 对象当锁做 wait/notify：线程一退出 JVM 就在它身上 notifyAll，你的等待者会被莫名其妙叫醒。

两个标准场景：

// 场景 1：主线程 fork 出子线程算，join 回来聚合（手写版 fork-join）
Thread[] workers = new Thread[4];
for (int i = 0; i < 4; i++) { workers[i] = new Thread(task(i)); workers[i].start(); }
for (Thread w : workers) w.join();   // ⭐ 先全部 start，再逐个 join（边 start 边 join = 串行）
merge(results);                      // join 返回 ⇒ 子线程的写入对 main 全部可见（线程终止规则）

// 场景 2：T1 → T2 → T3 严格顺序执行（一次性顺序，join 最省）
// joinQuietly(t) = t.join() 略去 InterruptedException 处理
Thread t1 = new Thread(() -> print("T1"));
Thread t2 = new Thread(() -> { joinQuietly(t1); print("T2"); });
Thread t3 = new Thread(() -> { joinQuietly(t2); print("T3"); });
t1.start(); t2.start(); t3.start();
// ⚠ start 顺序不能反：t2 若去 join 一个还没 start 的 t1，isAlive=false → join 秒回，顺序就乱了
// 更稳的写法：在 main 里串着来，不依赖 start 顺序
t1.start(); t1.join();  t2.start(); t2.join();  t3.start();
// 变体：A/B/C 各打印 n 轮（多轮循环）靠 join 不行 → 条件队列，见 12 章题 12

状态与可见性：join 期间调用者是 WAITING (on object monitor)，jstack 栈是 Object.wait → Thread.join、"waiting on <…> (a java.lang.Thread)"；join 返回后，目标线程的全部写入对调用者可见——JLS 的线程终止规则，这是不加锁也能安全交接结果的依据（第 02 章 happens-before · start/join 规则）。

陷阱现象原因 / 正解
自己 join 自己Thread.currentThread().join() 永远不返回isAlive() 恒为 true，while 永远不退出——除非被中断
start 之前 join立刻返回，等于没等，顺序全乱NEW 状态 isAlive() 为 false，循环一次都不进；必须先 start 再 join
指望 join 拿到子线程异常子线程抛了，join 正常返回，主线程毫无察觉未捕获异常只到 UncaughtExceptionHandler；要异常用 Future.get()（包成 ExecutionException）
join(millis) 超时后以为线程停了返回值 void，超时与结束无法区分，线程其实还在跑返回后用 isAlive() 判断；join 不会也不能终止线程
对线程池里的线程 join永远等不到池线程循环 getTask 不结束；等"任务"完成用 Future / CountDownLatch / awaitTermination
两个 join 混淆cf.join() 和 t.join()前者是 CompletableFuture 的 get 免检异常版（第 07 章），与 Thread.join 只是同名

JDK 21 变化：虚拟线程的 join 不再走 monitor/wait，VirtualThread.joinNanos 用内部的 CountDownLatch termination 等——避免在 Thread 对象上 synchronized 把载体线程 pin 住（第 10 章）；平台线程仍是上面的 wait 循环。

  • 追问链：join 底层？→ 在目标线程对象上 synchronized + while(isAlive) wait → 谁 notify？→ JVM 退出时 notifyAll → 所以？→ 别拿 Thread 对象当锁。这条链答完整，join 这题就到头了。
  • 追问：join 和 CountDownLatch 怎么选？→ join 绑定"线程结束"，只能等 Thread 对象、线程池用不了；latch 绑定"事件计数"，任何线程 countDown、可等 N 个、池里照用——池化时代默认 latch / Future，join 只在手写 Thread 的小场景。
  • 追问：join 释放锁吗？→ 释放的是目标线程对象 t 的 monitor（wait 的副作用），调用者自己持有的其他锁一个都不放——持锁 join 一个慢线程，等于持锁睡。

09高频追问与陷阱

  • 追问链：进程 vs 线程 → 线程越多越好吗？→ 不是。线程过多：内存（每线程 ~1MB 栈）、上下文切换开销、锁竞争加剧（线程都堵在锁上，CPU 却在空转切来切去）→ 引出线程池和虚拟线程。
  • 追问链：创建线程几种方式 → 那线程池算创建方式吗？→ 算"管理方式"。池里的线程也是 worker 循环 + 阻塞队列实现的——能讲到这层说明你看过 ThreadPoolExecutor 的 Worker 源码。
  • 陷阱：调 run() 不调 start()→ 同步执行，毫无并发；start() 两次 → IllegalThreadStateException。
  • 陷阱：WAITING 线程被中断→ wait/sleep/join 都响应 interrupt 抛 InterruptedException 并清除中断标志位；吞掉中断（catch 空着）会破坏调用方的取消逻辑，正确姿势是恢复标志或上抛——线程池 shutdown 依赖这个机制。
  • 陷阱：守护线程→ setDaemon(true) 必须在 start 前调；JVM 只剩守护线程时就退出，守护线程被硬杀（finally 都不保证执行）——别在守护线程里做落盘操作。
  • 对比题：sleep/wait 之外的 yield()、join() 在第 08 节专讲，五兄弟表一张答完；最常追的两刀——"yield 能保证顺序吗"（不能，只是 hint）、"join 底层是什么"（目标线程对象上 synchronized + while(isAlive) wait，JVM 退出时 notifyAll）。
  • 追问：直接调 run() 会怎样？→ 只是普通方法调用，代码串行跑在当前线程里，没有新线程；start() 才是向 JVM 注册新线程、由它回调 run()——一字之差是"多线程"与"方法调用"的差别。
