02手写题的考察意图

面试官出"手写 XXX"不是为了听你背 API——是为了看三件事：①能不能先做设计决策而不是上来就写代码；②能不能把锁策略 / CAS / 队列这些积木拼成正确且高效的结构；③能不能主动讲清 trade-off 和边界。写对了但说不出为什么，和背答案没有区别。

答题四步法

  1. 复述目标与约束：要支持哪些操作（put/get、offer/poll、前缀查询…）、一致性要求（单键原子就够还是要全局快照）、读写比、并发量级——把模糊的题面问清楚，本身就是加分项。
  2. 先给设计决策再动笔：锁粒度选多细、乐观还是悲观、要不要借助不可变性——三句话说清"为什么这样设计"（见下表）。
  3. 只写并发正确性相关的核心代码：加锁位置、CAS 目标、volatile 字段这几行必须写并注释；CRUD 细节一句"略"没人关心。
  4. 主动补边界：扩容怎么做、size 是精确值吗、什么场景下这个方案会退化——面试官正打算问的，你先说了。

设计决策三维度（所有手写题的选型表）

维度选项谱系（粗 → 细）选择依据
锁粒度全局一把锁 → 分段锁 → 桶级/节点级锁 → 无锁（纯 CAS）冲突概率 × 临界区大小；粒度越细吞吐越高，但代码复杂度陡增
乐观 vs 悲观悲观：synchronized / Lock 阻塞等待
乐观：CAS 自旋重试		临界区短、冲突低 → CAS 赢；临界区长或逻辑复杂 → 锁保护更简单更对
可变性可变共享（加锁保护修改）
不可变节点 + 写时复制（COW / 持久化结构）		读多写少 → 不可变性让读路径完全无锁，代价是写的复制开销

答题技巧：拿到题第一句话先说设计："这道题我会用桶级锁，读写比高的话再让 get 走 volatile 无锁读。"——这一句就把你和闷头写代码的人区分开了。写代码时把并发关键行注释出来，面试官扫的就是那几行。

03专题 1 · 手写 ConcurrentHashMap 思路 ⭐

目标

线程安全的 key-value 表：不同 key 的写操作互不阻塞，get 尽量无锁，put/get 单 key 操作原子。约束：不能用 java.util.concurrent。

设计决策（先说这三句）

  • 数据结构：分桶数组（Node 数组 + 链表），key 哈希定位桶——冲突被分散到不同桶。
  • 锁粒度：每桶一把独立锁（细粒度）——只有哈希到同一个桶的线程才竞争，不同桶完全并行。
  • 读写路径：写走锁；读走 volatile 读不加锁——用 AtomicReferenceArray 承载桶数组，槽位读写天然带 volatile 语义。

核心代码（简化版：分桶数组 + 桶级锁 + 无锁读）

class MyConcurrentHashMap<K, V> {
    private static final int CAPACITY = 16;                     // 桶数（示意，暂不扩容）
    private final AtomicReferenceArray<Node<K,V>> buckets;     // 桶槽读写自带 volatile 语义
    private final Object[] locks;                               // ⭐ 独立锁数组：只建一次，与数据分离

    static class Node<K,V> {
        final K key;
        volatile V value;                                       // ⭐ value 必须 volatile：get 不加锁也要可见
        Node<K,V> next;
        Node(K key, V value) { this.key = key; this.value = value; }
    }

    public MyConcurrentHashMap() {
        buckets = new AtomicReferenceArray<>(CAPACITY);
        locks = new Object[CAPACITY];
        for (int i = 0; i < CAPACITY; i++) locks[i] = new Object();
    }

    private int hash(Object key) {                              // 高位扰动 + 位取模，减少碰撞
        int h = key.hashCode();
        return (h ^ (h >>> 16)) & (CAPACITY - 1);
    }

    public void put(K key, V value) {
        int i = hash(key);
        synchronized (locks[i]) {                               // ⭐ 只锁目标桶：不同桶完全并行
            for (Node<K,V> n = buckets.get(i); n != null; n = n.next)
                if (n.key.equals(key)) { n.value = value; return; }  // 命中：覆盖旧值
            Node<K,V> node = new Node<>(key, value);
            node.next = buckets.get(i);                         // 头插示意（JDK 8 实为尾插 + 链转树）
            buckets.set(i, node);                               // volatile 写：立刻对无锁 get 可见
        }
    }

    public V get(K key) {                                       // ⭐ 全程不加锁
        Node<K,V> n = buckets.get(hash(key));                  // volatile 读：看到完整写入的最新桶头
        for (; n != null; n = n.next)
            if (n.key.equals(key)) return n.value;
        return null;
    }
}

既有笔记（Java/java 基础.md）对此只记了一句话——"分段锁到 CAS + Synchronized 的演进"。下面把它展开成能过关的完整答案。

JDK 7 → JDK 8 演进（把笔记一句话讲成三分钟）

维度JDK 7：Segment 分段锁JDK 8：CAS + synchronized
数据结构Segment[] → HashEntry[]（两层，Segment 即"段"）Node[] 一层（链表 / 红黑树）
锁对象Segment 继承 ReentrantLock，锁住整段空桶：CAS 直插；非空桶：synchronized 锁桶头节点
锁粒度段级：默认 16 段，并发度上限就是 16桶级：并发度 ≈ 桶数，随扩容持续变细
getSegment 内 volatile 读，不加锁全程 volatile 读（table / val / next），无锁
内存每个 Segment 一个完整 AQS 对象，偏重去掉 Segment 层，省内存
size先无锁加总试两次，再锁全部 SegmentbaseCount + CounterCell[] 分散计数（LongAdder 思想）

为什么 JDK 8 敢把 ReentrantLock 换成 synchronized？粒度细到桶级后，同桶冲突概率极低，绝大多数竞争用 synchronized 的轻量级路径（CAS 自旋）就能解决，只有真冲突才膨胀为重量级锁；而 ReentrantLock 的优势（可中断、超时、公平、Condition）在桶级场景根本用不上，却要为每个桶背上 AQS 对象的内存与语义开销。这是"并发结构设计要跟着实际竞争强度选同步原语"的最佳教材。

resize 与 get：两个一句话考点

  • 协助迁移：扩容时线程把迁完的旧桶头换成 ForwardingNode（hash=MOVED）；put 线程遇到它不傻等——先认领一段桶帮着迁移（transfer，最小步长 16），迁完再回来干自己的活。多线程扩容 = 分段认领 + 汇合。
  • get 为什么无锁还正确：table 引用、Node.val、Node.next 全是 volatile，写线程的每次修改都 happens-before 读线程的 volatile 读；引用赋值本身原子，读到的要么是旧值要么是完整新值，绝不会是"半个"。这条直接连回 第 02 章 JMM 的 happens-before。

追问

  • 追问链：手写版怎么扩容？→ 简单版：拿全表锁（或依次锁所有桶）重新散列，全局停顿；JDK 版：协助迁移 + ForwardingNode——你能说出"简单版为什么不行"再引出协助迁移，就是完整答案。
  • 追问链：size() 是精确值吗？→ 不是，弱一致近似值：baseCount + CounterCell[] 分散热点再求和（LongAdder 思想见第 05 章），口径详见 第 09 章。
  • 追问链：为什么不允许 null key / null value？→ get 返回 null 分不清"不存在"还是"存的就是 null"；单线程可用 containsKey 复核，并发下复核就是 check-then-act 竞态——所以干脆禁止。

04专题 2 · 无锁队列：Michael-Scott 算法

目标

实现 lock-free 的 FIFO 队列：全程不用锁，任何线程在任意时刻被暂停，其余线程仍能完成入队/出队（系统级前进性）。JDK 的 ConcurrentLinkedQueue 就是这一算法（Michael & Scott, 1996）的工程化版本。

设计决策

  • 单链表 + 哑节点，head / tail 都是 AtomicReference——队列的全部状态压缩在两个引用和 next 指针上，每次状态变更只动一个位置，这是能用 CAS 的前提。
  • 入队两步 CAS：①CAS 把新节点链到 tail.next 上——这一步成功，数据就"逻辑上入队"了；②CAS 推进 tail。两步之间允许不一致（tail 暂时落后），由后来者"帮忙推进"自愈。
  • 允许中间态 + helping：无锁算法的通用哲学——不追求每步全局一致，而是让每个线程顺手修复看到的不一致；对比互斥锁：锁内不许任何中间态被看见。

核心代码

class LockFreeQueue<T> {
    static class Node<T> {
        final T value;
        final AtomicReference<Node<T>> next = new AtomicReference<>();
        Node(T v) { value = v; }
    }

    private final AtomicReference<Node<T>> head, tail;         // 队列状态全押在这两个引用上
    LockFreeQueue() {                                           // 哑节点：head/tail 永不指空，边界简单
        Node<T> dummy = new Node<>(null);
        head = new AtomicReference<>(dummy);
        tail = new AtomicReference<>(dummy);
    }

    public void offer(T value) {
        Node<T> node = new Node<>(value);
        while (true) {
            Node<T> curTail = tail.get();
            Node<T> next = curTail.next.get();
            if (curTail != tail.get()) continue;                // 采样期间 tail 变了：重读
            if (next == null) {                                 // tail 指向真正的最后节点
                // 第一步 CAS：把新节点链上去 —— 成功即"数据已入队"
                if (curTail.next.compareAndSet(null, node)) {
                    tail.compareAndSet(curTail, node);          // 第二步 CAS：推进 tail
                    return;                                     // ⭐ 失败也没关系：后来者帮忙推进
                }
            } else {
                tail.compareAndSet(curTail, next);              // tail 落后了：先帮忙推进（helping）
            }
        }
    }

    public T poll() {
        while (true) {
            Node<T> curHead = head.get();
            Node<T> curTail = tail.get();
            Node<T> next = curHead.next.get();
            if (curHead != head.get()) continue;
            if (curHead == curTail) {                           // 空，或 tail 落后（哑节点后还有数据）
                if (next == null) return null;                  // 真·空队列
                tail.compareAndSet(curTail, next);              // 帮忙推进 tail 后重试
            } else {
                T v = next.value;
                if (head.compareAndSet(curHead, next)) return v;// CAS 摘头；旧 head 成垃圾，GC 负责
            }
        }
    }
}

追问

  • 追问链：第二步 CAS 失败为什么直接 return？→ 语义已由第一步建立：节点已经在链上，所有读者都能遍历到它；tail 只是"指向最后一个节点的缓存指针"，暂时落后不影响正确性，下一个线程的 helping 会把它推正。能识别"哪些状态是逻辑已定、哪些只是缓存滞后"，是手写无锁结构的核心功力。
  • 追问链：ABA 问题？→ 同一地址被释放又复用，CAS 误判"没变过"。C/C++ 要靠 tag pointer / hazard pointer；Java 有 GC，节点不会被复用成同地址，天然免疫最坏情形——但面试标准答案仍是 AtomicStampedReference（引用+版本号一起 CAS），详见 第 05 章 无锁编程。
  • 追问链：无锁一定比加锁快吗？→ 不。低竞争下锁版本往往更快（CAS 自旋空转烧 CPU）；无锁的赢面在高竞争下吞吐不悬崖式下降、没有死锁和优先级反转。ArrayBlockingQueue（双锁+Condition）与 ConcurrentLinkedQueue（无锁）的选型正是这组 trade-off——要不要阻塞语义才是第一问。

05专题 3 · 并发优先队列

目标

支持并发 insert 与取最小值（delete-min）的优先队列。这题的关键不在写代码，在方案对比与选型论证——面试官想听的是"堆为什么难并发化"。

设计决策：三方案对比

方案思路优点缺点
全局单锁二叉堆数组堆 + 一把 ReentrantLock 保护所有操作简单、正确、单操作 O(log n)所有线程竞争同一把锁，吞吐封顶——JDK 的 PriorityBlockingQueue 就是它
跳表（ConcurrentSkipListMap 思路）概率层级索引 + 底层 CAS 拼接插入天然有序、无全局 rebalance、读写可重叠多级索引费空间；删除要两阶段标记
分片堆 + 合并K 个小堆各配一把锁，取 min 时各堆 peek 后归并并发度 = K，可水平扩展代码复杂，K 的取值难调（一句带过即可）

为什么堆难无锁化（本题的灵魂）

二叉堆的 sift-up / sift-down 沿路径连续改多个位置，一次操作牵动半棵树；而 CAS 只能原子地改一个位置——多点原子性做不到。这就是 JDK 至今没有 ConcurrentPriorityQueue 的原因：不是没写，是堆结构天生不适合 CAS 化。跳表绕开了这一点：插入只改路径上几个局部前驱指针，每处一个 CAS，树形结构的"全局再平衡"被概率层级替代了。

record Task(long deadline) { }

// 方案A：全局单锁二叉堆 —— JDK PriorityBlockingQueue 的做法
class LockedHeap {
    private final ReentrantLock lock = new ReentrantLock();
    public void offer(Task t) {
        lock.lock();                          // 所有线程排队过同一把闸门：正确但吞吐受限
        try {
            // sift-up 上滤插入，O(log n)（堆本体略）
        } finally { lock.unlock(); }
    }
}

// 方案B：跳表当并发优先队列用（按 deadline 取最小 = 最高优先级）
ConcurrentSkipListMap<Long, Task> pq = new ConcurrentSkipListMap<>();
Task task = new Task(1000L);
pq.put(task.deadline(), task);               // 概率建索引层 + 底层 CAS 拼接，无全局 rebalance
Task top = pq.pollFirstEntry().getValue();   // 取出并删除最小键，期望 O(log n)

追问

  • 追问链：跳表插入怎么做到无锁？→ 自顶向下找各层前驱 → 先 CAS 拼进第 0 层（数据层，插入生效）→ 按概率（JDK 用 1/4）逐层补索引节点，每处独立 CAS；删除用标记节点分"逻辑删/物理摘"两阶段，避免把链摘断。
  • 追问链：需要"队列空就阻塞"的语义呢？→ 优先队列 + 阻塞 = PriorityBlockingQueue（单锁 + notEmpty Condition）；要按 key 有序遍历 = ConcurrentSkipListMap。选型先问语义，再谈性能。

06专题 4 · 线程安全 Trie

目标

前缀树做敏感词库 / 路由表：读（search / startsWith）极高频，写（词库更新）低频。典型读多写少场景——方案按读写比选。

设计决策：三方案

方案做法读路径写路径适用
整树读写锁一把 ReentrantReadWriteLock 包住根读锁共享，可并行写锁独占，写时全树读都堵5 分钟写完；读写比 1000:1 且写毫秒级，完全够用
按子节点并发化每个节点的 children 用 ConcurrentHashMap 装载无锁（CHM.get）computeIfAbsent 桶级原子写相对频繁、要求读不阻塞
不可变节点 + 写时复制节点字段全 final，改一个词只复制"根→叶"路径，最后 CAS 换根完全无锁：拿到旧根 = 拿到完整旧树快照写放大 O(词长)；写写冲突在换根处 CAS 定胜负读绝对不能阻塞（低延迟路由），读极多写极少

核心代码（方案二：子节点并发化，最实用的平衡点）

class ConcurrentTrie {
    static class Node {
        final ConcurrentHashMap<Character, Node> children
                = new ConcurrentHashMap<>();             // 子节点表本身是并发结构
        volatile boolean isWord;                          // volatile 写：立刻对读可见
    }
    private final Node root = new Node();

    public void insert(String word) {
        Node cur = root;
        for (char c : word.toCharArray()) {
            // computeIfAbsent 是复合原子操作：并发下每层恰好一个线程建节点成功
            cur = cur.children.computeIfAbsent(c, k -> new Node());
        }
        cur.isWord = true;                                // 最后一级打词尾标记
    }

    public boolean search(String word) {                  // 读路径完全无锁
        Node cur = root;
        for (char c : word.toCharArray()) {
            cur = cur.children.get(c);
            if (cur == null) return false;
        }
        return cur.isWord;
    }
}

方案三思路（不可变 + COW，示意）

// 不可变节点 + 写时复制路径（persistent trie）：
//   1. insert 沿根到叶"只复制要改的节点"（写放大 = 词长），未触及的子树直接共享引用
//   2. 构建出新根后，AtomicReference.compareAndSet(oldRoot, newRoot) 一次换根
//   3. CAS 失败说明别的写者先换了根：基于最新根重试整个复制
// 读侧：拿到哪个版本的根，就看到哪份完整快照，永远无锁无阻塞
final class TNode {
    final TNode[] child;          // 全 final：天生线程安全
    final boolean isWord;
    TNode(TNode[] child, boolean isWord) { this.child = child; this.isWord = isWord; }
}

追问

  • 追问链：COW 版为什么读可以零锁？→ 不可变性：所有可达节点永不修改，读者持有的根引用就是一份持久快照——与 CopyOnWriteArrayList 同理（第 09 章 COW 思想）；写者之间的竞争被压缩到"换根"一个 CAS 点上。
  • 追问链：insert 是原子的吗？→ 方案二的 insert 跨多层，中途 readers 能看到"半个词"（前缀已建、isWord 未置）——最终一致而非线性一致；单线程逐词更新、且 search 容忍瞬时旧值时没问题。要批量原子更新，用方案三：一批词全部构建完再一次性换根（版本化发布）。

07专题 5 · 并发布隆过滤器

目标

海量 key 的存在性判断：内存极省、高并发 add / 查询；语义上允许误判"存在"（false positive），绝不漏判"不存在"（no false negative）——所以适合放缓存穿透、黑名单的入口当闸门。

设计决策

  • 位数组用 AtomicLongArray：每个 long 装 64 个位；"按位置 1"用"读整个字 → CAS 换整个字"实现——CAS 粒度是 64 位字，不是单个 bit（硬件也不支持位级 CAS）。
  • k 个哈希函数不真的写 k 个：双重散列 h_i = h1 + i·h2，只算一次 64 位散列拆成两半（生产用 MurmurHash3 / xxHash）。
  • contains 只读：不需要 CAS，get 即可。

核心代码

class ConcurrentBloomFilter {
    private final AtomicLongArray bits;                   // 位数组：每个 long 装 64 位
    private final int m;                                  // 总位数
    private final int k;                                  // 哈希函数个数

    ConcurrentBloomFilter(int m, int k) {                 // m、k 按误判率公式反推
        this.m = m; this.k = k;
        this.bits = new AtomicLongArray((m + 63) >>> 6);   // 位数向上取整成 long 个数
    }

    public void add(String key) {
        long h = hash64(key);                             // 只算一次 64 位散列
        int h1 = (int) h, h2 = (int) (h >>> 32);
        for (int i = 0; i < k; i++)
            setBit(Math.floorMod(h1 + i * h2, m));        // 双重散列模拟 k 个哈希函数
    }

    private void setBit(int bitIdx) {
        int word = bitIdx >>> 6;                          // 除以 64：定位 long 下标
        long mask = 1L << (bitIdx & 63);                  // 对 64 取模：定位具体位
        while (true) {
            long old = bits.get(word);
            if ((old & mask) != 0) return;                 // 已是 1：幂等返回
            // ⭐ CAS 整字替换实现"按位置 1"：失败=别人并发改了同一字，重读重试
            if (bits.compareAndSet(word, old, old | mask)) return;
        }
    }

    public boolean mightContain(String key) {             // 只读：无 CAS
        long h = hash64(key);
        int h1 = (int) h, h2 = (int) (h >>> 32);
        for (int i = 0; i < k; i++) {
            int bitIdx = Math.floorMod(h1 + i * h2, m);
            if ((bits.get(bitIdx >>> 6) & (1L << (bitIdx & 63))) == 0)
                return false;                             // 任一位为 0 → 一定不存在（不漏判）
        }
        return true;                                      // 全为 1 → 可能存在（可能误判）
    }

    private long hash64(String key) {                     // 示意实现；生产换 MurmurHash3 128 位
        long h = key.hashCode() * 0x9E3779B97F4A7C15L;    // 黄金分割散列常数
        h ^= (h >>> 32);                                  // 高低位混合
        return h;
    }
}

误判率一句带过：p ≈ (1 − e^(−kn/m))^k，m 位、k 个哈希、n 个元素；最优哈希个数 k ≈ 0.7·(m/n)。面试一般只要这个公式 + "位数组越满误判越高"的直觉。

追问

  • 追问链：为什么不能删除？→ 位是多 key 共享的，清 0 会连带删掉别的 key 的位 → 误判方向翻转成漏判，语义崩塌。解法是计数布隆过滤器：每位换成 4bit 计数器，add 加一、remove 减一（一句带过）。
  • 追问链：Guava 的 BloomFilter 能直接并发用吗？→ 不能，它内部是普通 long[]，并发 add 会丢位；并发要么按本章 CAS 位图手写，要么分片加锁。Redis 里的 RedisBloom 靠 Redis 单线程把操作串行化——顺口带出"串行化也是一种并发控制"。
  • 追问链：元素数超过设计容量会怎样？→ 误判率随装载率持续上升；要么按业务峰值容量预留位数，要么用可扩容布隆（Scalable Bloom Filter：满了开新层，查询逐层问）。

08高频追问与陷阱

  • 追问链：手写 CHM → 扩容怎么做？→ 简单版锁整表重散列（全局停顿，说得出缺点就行）→ JDK 版 ForwardingNode + 协助迁移（专题 1）。能对比"停顿版 vs 协助版"即满分。
  • 追问链：get 不加锁，会不会读到"写了一半"的数据？→ 不会：引用赋值原子 + volatile happens-before，读到的要么旧值要么完整新值——这题直接连回 第 02 章 happens-before，答"会"就前功尽弃。
  • 陷阱：锁对象选错位置。→ 把锁加在桶头 Node 上：删除/扩容换头后，"锁"跟着换对象，互斥被击穿。手写版用独立锁数组最稳（JDK 靠 ForwardingNode 状态机保证换头安全）。同理，锁数组必须独立于桶数组创建、永不替换。
  • 陷阱：把"容器线程安全"当成"业务原子"。→ CHM 单 key put 原子 ≠ containsKey + put 复合原子（check-then-act 竞态），复合必须用 compute / merge——第 09 章复合操作原子性的考点在本章手写语境下会再问一遍。
  • 追问：你这些结构的一致性强度分层吗？→ 分：单键操作线性一致；size、遍历、迭代器弱一致（近似值、不抛 ConcurrentModificationException）。主动说出"一致性是分层的"是高级岗信号。
  • 追问：什么时候干脆不用并发结构？→ 数据能线程私有就不共享：局部变量 / 线程内累积、最后合并——"不共享是最高级的并发安全"，正是第 15 章词频统计"先局部后合并"的思想。
