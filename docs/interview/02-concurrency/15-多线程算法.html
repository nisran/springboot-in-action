02并行化的基本功

一个算法能不能并行、并行后快不快，取决于四件事：切得开、算得独立、合得回来、匀得均匀。

  • 任务切分（分治）：divide → conquer → combine。先看子问题是否独立：归并排序切两半互不依赖，可以并行；Fibonacci 朴素递归的子问题之间有大量重叠，切了就是重复计算，反而更慢。
  • 合并策略决定整体复杂度：数组归并 O(n)、Map 按 key 逐项 merge、多路取最小用小顶堆——合并做不好，前面省的时间全赔回去。
  • 负载均衡（work stealing）：ForkJoinPool 给每个工作线程一个 deque：自己从队头取任务做，空闲了从别人队尾偷。分治树不均衡（快排 pivot 偏斜、图各层宽度不一）时靠偷任务自动摊平——框架细节在 第 06 章 Fork/Join。
  • 切分阈值：每个任务的调度开销（任务对象 + 入队 + CAS）是微秒级的固定成本，任务计算量必须远大于它，否则"任务开销反超收益"，并行比串行还慢。经验：数组类任务 1k~10k 元素/任务（Arrays.parallelSort 的粒度就是 1<<13 = 8192），最终以基准实测为准。

一眼判断：这个算法能不能并行

模式例子结论
子问题完全独立归并排序两半、map/filter 按分区处理天然并行，分治直接上
链式依赖冒泡排序（相邻比较）、朴素前缀和（后一个依赖前一个的和）难并行，先改算法（前缀和有并行扫描算法）再谈多线程

按阶段推进BFS 的层、流水线阶段阶段内并行 + 阶段间同步（barrier）

Amdahl 定律：加速比 S ≤ 1 / (f + (1−f)/p)，f 是串行部分占比。归并排序里 merge 若只能单线程做，核数再多也封顶——串行段（划分、合并、同步点）才是并行算法设计的胜负手，这句话面试时先说出来。

03专题 1 · 并行归并排序 ⭐

思路

递归二分到阈值以下转串行排序（小段上插入排序/双轴快排的局部性反而更好），段内有序后再两两 merge。用 RecursiveAction（无返回值的 Fork/Join 任务）承载：每个任务负责数组的一个区间 [lo, hi)。

代码

class ParallelMergeSort extends RecursiveAction {    // RecursiveAction：无返回值的 FJ 任务
    private static final int THRESHOLD = 1 << 13;   // 阈值 8192：小于它任务开销反超收益
    private final int[] a, tmp;
    private final int lo, hi;                        // 本任务负责的区间 [lo, hi)

    ParallelMergeSort(int[] a, int[] tmp, int lo, int hi) {
        this.a = a; this.tmp = tmp; this.lo = lo; this.hi = hi;
    }

    @Override
    protected void compute() {
        if (hi - lo <= THRESHOLD) {                  // ⭐ 阈值内转串行
            Arrays.sort(a, lo, hi);                  // 小段直接用现成排序，CPU 缓存友好
            return;
        }
        int mid = (lo + hi) >>> 1;                  // 无符号右移取中点，不溢出
        ParallelMergeSort left  = new ParallelMergeSort(a, tmp, lo, mid);
        ParallelMergeSort right = new ParallelMergeSort(a, tmp, mid, hi);
        left.fork();                                 // ⭐ 规矩①：先 fork 左半（进队列给别人偷）
        right.compute();                             // ⭐ 规矩②：右半当前线程直接算，自己绝不闲着
        left.join();                                 // ⭐ 规矩③：join 放最后，等 fork 出去的那份
        merge(a, tmp, lo, mid, hi);                  // 两半各自有序，最后归并
    }

    private static void merge(int[] a, int[] tmp, int lo, int mid, int hi) {
        System.arraycopy(a, lo, tmp, lo, mid - lo);  // 左半复制到 tmp，右半留在原地
        int i = lo, j = mid;
        for (int k = lo; k < hi; k++) {              // 经典双指针归并
            if (i >= mid)           a[k] = a[j++];   // 左半用尽，取右半
            else if (j >= hi)       a[k] = tmp[i++]; // 右半用尽，取左半
            else if (a[j] < tmp[i]) a[k] = a[j++];   // 取两边较小者（稳定：相等先取左）
            else                     a[k] = tmp[i++];
        }
    }
}

// 启动：共享同一个 tmp 数组，避免每层任务重复分配大数组
int[] a = {5, 3, 8, 1, 9, 2, 7, 6, 0, 4};   // 待排序数据（示意）
ForkJoinPool pool = ForkJoinPool.commonPool();      // 默认并行度 = CPU 核数 - 1
pool.invoke(new ParallelMergeSort(a, new int[a.length], 0, a.length));

fork / join 的规矩（高频追问，错一个就露馅）：① 不要两个都 fork 再两个 join——当前线程 fork 完立刻阻塞等 join，等于把自己变成闲置等待者；正确姿势是"fork 一个、自己算一个、最后 join"。② fork 之后不要马上 join——中间这段是当前线程干活的窗口。③ 等价简写 invokeAll(left, right)，内部就是 fork 一个 + compute 一个 + join。④ 不要在 FJ 任务里做阻塞 IO——worker 被占住又偷不了任务，整个池假死（第 06 章的经典事故）。

性能讨论

  • 为什么快：work stealing 补偷任务。递归左半 fork 进队列后，当前线程继续算右半；如果某个线程先做完，它会从别的线程队列尾部偷大任务——队尾是分治树上游的大粒度任务，偷一次赚得多，负载被持续摊平。理想加速比 O(n log n / p)，实际受内存带宽限制（归并是带宽敏感型）。
  • 与 Arrays.parallelSort 的关系：JDK 8+ 的实现就是这套——commonPool + 粒度 8192（MIN_ARRAY_SORT_GRAN）+ 阈值内转串行。对象数组用并行归并（TimSort 变体，保稳定性），基本类型用并行双轴快排（不用保稳定，快排常数更小）。手写这道题等于把 parallelSort 讲透了。
  • 为什么归并"天然"适合并行：两半完全独立（各自排序互不依赖），merge 只在边界处发生；对比冒泡/选择排序——相邻比较是链式依赖，切开子段后边界还有逆序对，合并代价把收益全吃掉。链式依赖是并行化的天敌。

追问

  • 追问链：为什么归并可以不用并行快排？→ 也能做（partition 后两半独立递归），但 partition 本身是串行段（Amdahl），且分治树随 pivot 偏斜，更依赖 work stealing 兜底；JDK 对基本类型正是并行快排、对象类型并行归并——稳定性和常数各有取舍。
  • 追问链：tmp 数组为什么要外面传进来共享？→ 每层任务各自 new 大数组会把内存和 GC 压力放大；共享一个 tmp 时，各任务的 merge 只读写自己的 [lo, hi) 区间，无重叠即无需同步——"共享但分区"是无锁的常见手法。
  • 追问链：数组只有 1 万个元素还并行吗？→ 直接 Arrays.sort。1 万元素串行排序毫秒级，任何任务调度开销都不值——先问数据量级再谈并行，这是工程判断力。

04专题 2 · 多线程词频统计

思路

大文本按块切分（按行边界对齐，别把单词截断）→ 每个线程在自己的局部 HashMap 里统计（全程不碰任何共享结构）→ 最后合并阶段用 ConcurrentHashMap.merge 把各线程的局部结果归成全局。这就是 "先局部后合并"（map-side combine），和 MapReduce 的 Combiner 是同一个思想。

代码

int cores = Runtime.getRuntime().availableProcessors();
List<String> lines = Files.readAllLines(Path.of("big.log"));  // 示意；超大文件应分块读
int chunk = (lines.size() + cores - 1) / cores;               // 均分 n 块（按行切，不截断单词）
ExecutorService pool = Executors.newFixedThreadPool(cores);
List<Future<Map<String, Integer>>> futures = new ArrayList<>();

for (int i = 0; i < lines.size(); i += chunk) {
    List<String> part = lines.subList(i, Math.min(i + chunk, lines.size()));
    futures.add(pool.submit(() -> {
        Map<String, Integer> local = new HashMap<>();   // ⭐ 线程局部累积：全程零共享、零同步
        for (String line : part)
            for (String w : line.toLowerCase().split("\\W+"))
                if (!w.isEmpty()) local.merge(w, 1, Integer::sum);  // 普通 HashMap 就够
        return local;
    }));
}

// 合并阶段：只在边界发生一次，用 CHM 的复合原子操作逐 key 归并
ConcurrentHashMap<String, Long> global = new ConcurrentHashMap<>();
for (Future<Map<String, Integer>> f : futures)
    for (Map.Entry<String, Integer> e : f.get().entrySet())    // InterruptedException 处理略
        global.merge(e.getKey(), e.getValue().longValue(), Long::sum);  // ⭐ 读旧值+求和+写回，一步原子
pool.shutdown();

如果只需要总词数（不分组），计数器用 LongAdder 而不是 AtomicLong：

LongAdder total = new LongAdder();
total.increment();   // 高竞争下把热点分散到 Cell[]，读时 sum() 汇总
                     // AtomicLong 是单点 CAS，竞争一激烈自旋失败率陡增 —— 详见 05-无锁编程.html

性能讨论：为什么"先局部后合并"赢

  • 对比方案：直接共享一个 CHM，每读一个词就 merge 一次。每次 merge 都要：hash 定位桶 → 桶内链/树遍历 → 可能进桶级 synchronized；而高频词（the / is / and）全部撞在同一个桶，竞争集中、缓存行在核间反复失效。局部 HashMap 没有任何同步指令，合并只在最后做一次 O(总词数)——把几十万次竞争摊薄成几千次。
  • 本质：减少共享写点的数量级。并发结构的优化上限是"缩小临界区"，而线程私有数据的优化是"消灭临界区"——呼应 第 14 章结尾那句"不共享是最高级的并发安全"。
  • CHM.merge 的原子性靠什么？桶头 synchronized 包住"读旧值-计算-写回"的复合操作——这正是 第 09 章复合操作原子性的落点，两个考点在这道题里会合。

答题技巧：先报数字再讲方案。"10GB 文本 ≈ 百亿字符，8 核切成 8 块各 1.25GB；局部 HashMap 只装去重后的词（英文词库量级 10^5~10^6），每块内存几十 MB，可控；合并阶段只需归并 8 份局部表。"——有量级估算的答案自带"真的做过"的说服力，7 年经验尤其要这么答。

追问

  • 追问链：最后要 TopK 高频词呢？→ 每线程局部维护大小为 K 的小顶堆（或直接局部排序截断），最后只合并 n×K 个条目——数据移动量从"全量词表"降到 n×K，还是"先局部后合并"。
  • 追问链：10GB 文件读不进内存怎么办？→ FileChannel 按 position 分块，每块内先找换行符把边界对齐再交给线程；合并阶段不变。切分必须尊重数据的语义边界（这里是"单词不能截断"）。
  • 追问链：流式/无限数据呢？→ 分批局部聚合 + 周期性滚动合并（滑动窗口聚合），思想不变，只是合并不是"最后一次"而是"每个窗口边界"。
  • 追问链：用 parallelStream 一行搞定行不行？→ 功能上可以（parallelStream().collect(groupingBy(..., counting()))），但 commonPool 是全局共享的、切分粒度不可控、还怕流水线里混进阻塞——面试口径："能写，但生产上我自己管线程池和粒度更稳"（详见 第 07 章）。

05专题 3 · 并行 BFS ⭐

思路：层级同步

BFS 按"层"（frontier）展开：同一层的节点互不依赖（最短路性质保证同层节点不会互为前驱），是天然并行单元；而下一层的输入 = 本层全部输出，层与层之间必须同步。整体结构 = 层内 map 并行 + 层间 barrier，两种实现：每层一栅栏（CyclicBarrier）或层内未完成计数归零开门（AtomicInteger）。

实现 A：CyclicBarrier 每层一栅栏

class ParallelBFS {
    private final List<List<Integer>> graph;          // 邻接表
    private final int n;
    private final int threads;                        // 常驻 worker 数
    private final CyclicBarrier barrier;              // ⭐ 循环栅栏：每层复用（cyclic 的含义）
    private final AtomicIntegerArray visited;         // CAS 置位，代替非线程安全的 boolean[]
    private volatile List<Integer> frontier;          // 当前层（全体线程统一读）
    private final ConcurrentLinkedQueue<Integer> next = new ConcurrentLinkedQueue<>();

    ParallelBFS(List<List<Integer>> graph, int threads) {
        this.graph = graph; this.n = graph.size(); this.threads = threads;
        this.barrier = new CyclicBarrier(threads);    // parties = 工作线程数
        this.visited = new AtomicIntegerArray(n);
    }

    void bfs(int src) {                               // 启动：置源点 + 起 N 个 worker（示意）
        visited.set(src, 1);
        frontier = List.of(src);
        for (int i = 0; i < threads; i++)
            new Thread(new Worker(i), "bfs-worker-" + i).start();
    }

    private void await() { try { barrier.await(); } catch (Exception e) { throw new IllegalStateException(e); } }

    class Worker implements Runnable {
        final int id;
        Worker(int id) { this.id = id; }
        public void run() {
            while (!frontier.isEmpty()) {
                List<Integer> layer = frontier;
                // ⭐ 同层节点互不依赖：本线程只扩展按步长分给自己的那一份
                for (int i = id; i < layer.size(); i += threads) {
                    for (int nb : graph.get(layer.get(i))) {
                        if (visited.compareAndSet(nb, 0, 1))  // 恰好一个线程能置 1 成功
                            next.add(nb);                      // 置位成功者负责入队：不重不漏
                    }
                }
                await();                       // 栅栏①：层内全员扩展完毕
                if (id == 0) {                  // 0 号线程统一换层（避免全员同时换）
                    frontier = List.copyOf(next);   // volatile 写发布新层
                    next.clear();
                }
                await();                       // 栅栏②：等换层完成，全员再进下一轮
            }
        }
    }
}

实现 B：AtomicInteger 层内计数归零开门

class LevelCountBFS {
    private final List<List<Integer>> graph;         // 邻接表
    private final int n;
    private volatile List<Integer> frontier;
    private final AtomicIntegerArray visited;

    LevelCountBFS(List<List<Integer>> graph) {
        this.graph = graph; this.n = graph.size();
        this.visited = new AtomicIntegerArray(n);
    }

    // 不用栅栏：本层派一个任务/节点，未完成计数归零 = 本层结束（多线程 BFS 面试题的通行思路）
    void bfsParallel(int src, ExecutorService pool) {
        visited.set(src, 1);
        frontier = List.of(src);
        while (!frontier.isEmpty()) {
            List<Integer> layer = frontier;
            ConcurrentLinkedQueue<Integer> nextQ = new ConcurrentLinkedQueue<>();
            AtomicInteger remaining = new AtomicInteger(layer.size());  // 本层待完成计数

            for (Integer node : layer) {
                pool.submit(() -> {
                    for (int nb : graph.get(node))
                        if (visited.compareAndSet(nb, 0, 1))       // CAS 去重：不重复入队
                            nextQ.add(nb);
                    if (remaining.decrementAndGet() == 0)          // ⭐ 最后一个完成的线程"开门"
                        frontier = List.copyOf(nextQ);             // 发布下一层（volatile 写）
                });
            }
            // ⭐ 层间同步：自旋等新层发布。volatile 写/读构成 happens-before，
            //    看到新 frontier 时，其内容必然完整可见（生产上用 Phaser / CountDownLatch，别忙等）
            while (frontier == layer) Thread.onSpinWait();
        }
    }
}

两方案对比与讨论

CyclicBarrier 每层一栅栏AtomicInteger 计数归零
线程模型N 个常驻 worker 分片扫 frontier每节点一个任务入池，天然适配层宽波动
同步成本每层两次栅栏（扩展完 + 换层完）每任务一次 decrementAndGet + 自旋等待
层很窄时worker 空转等栅栏，浪费明显任务少，天然轻
注意点换层时序：必须二次栅栏等 0 号换完"发布下一层"必须在开门信号可见之前完成

工程上还可直接用 Phaser.arriveAndAwaitAdvance()（每层一个 phase，支持动态注册参与者），语义就是"每层一栅栏"的现代版；CyclicBarrier/Phaser 的对比详见 第 08 章 并发工具类。

为什么 BFS 天然并行、DFS 难并行

  • DFS 的状态是"当前路径"：递归栈走到哪、下一步扩展谁，都依赖路径历史；并行 DFS 要么每条路径复制一份 visited（内存爆炸 + 可能重复搜索同一子树），要么任务间高频通信去重——并行开销吃掉收益。
  • BFS 把"路径状态"显式变成了"层"这个集合：同层节点由最短路性质保证互不为祖先-后代，扩展彼此独立；visited 判定可以 CAS 化。结构上就是 map（同层并行）+ barrier（层间同步），正好对上本章开头的基本功模型——分布式图计算框架 Pregel 的 superstep 就是"层"的全局化版本。

追问

  • 追问链：visited 用 boolean[] 行不行？→ 不行：同层两线程同时发现同一邻居，都读到 false、都入队 → 重复扩展。必须 AtomicIntegerArray.compareAndSet(nb, 0, 1) 保证"恰好一个线程入队成功"。补一句更成熟的：若扩展操作幂等，重复入队只损性能不出错——能分清"正确性必需"与"性能优化"两种 CAS 用途，是亮点。
  • 追问链：前几层只有一两个节点，N 个 worker 全在等？→ 混合策略：层宽小于阈值走串行，超过再切并行——和归并排序的切分阈值是同一个道理：并行化本身有成本，量不够就不切。
  • 追问链：多源 BFS（多起点同时扩散）？→ 初始 frontier 放多个源即可，层级同步模型一字不改——"多源最短路"就是这个变体，能主动指出来说明你理解的是模型而不是模板。

06高频追问与陷阱

  • 追问链：阈值到底定多少？→ 不是拍脑袋：以"任务计算耗时 ≥ 10 倍调度开销"为下限，用 JMH 对不同阈值跑基准；不同负载最优值不同，说"实测调优"比报一个神奇数字可信。
  • 追问链：Fork/Join 会死锁吗？→ 会：任务里 join 一个非自己 fork 的任务、或在 compute 里做长时间阻塞 IO——worker 全被占住、无人可偷，整个 commonPool 假死。规矩：compute 里只做 CPU 计算，join 只 join 自己 fork 的子任务（第 06 章）。
  • 陷阱：parallelStream 一把梭。→ 共享 commonPool（别的框架也在用，互相干扰）、阻塞操作会被全局放大、无序性悄悄改变语义；适合的是纯 CPU、无共享副作用、量够大的小任务——否则老实写线程池（第 07 章有专节）。
  • 陷阱：词频统计把局部 Map 也换成 CHM。→ 局部累积本来零竞争，换并发结构是白白付同步税——"局部数据用普通结构"是本模式的要点，写反了恰恰暴露没理解"先局部后合并"。
  • 亮点：伪共享（false sharing）。→ 多线程写同一缓存行的不同变量（如朴素计数器数组），核间缓存一致性协议让性能塌方；LongAdder 的 Cell 间距 / @Contended 就是解法——主动提一句，链到 第 05 章。
  • 陷阱：把 CyclicBarrier 和 CountDownLatch 用混。→ barrier 是"全员到齐一起放行"且可循环复用（BFS 每层重复用，正合适）；latch 是"计数归零放行"一次性。BFS 若用 latch，每层都要 new 一个——能说出这个差别就顺手复习了 第 08 章。
  • 追问：怎么验证真的并行了？→ 压测吞吐对比（单线程 vs 并行），加线程栈采样（async-profiler / arthas）看 CPU 利用率与线程 park 分布——"并行了但没变快"时，先查串行段和同步开销。

07面试自查清单

  1. 能背出并行化四要素（切分 / 独立子问题 / 合并策略 / work stealing 均衡）+ 切分阈值的成本直觉，并各举一例。
  2. Fork/Join 并行归并能白板写出：RecursiveAction、阈值转串行、fork→compute→join 顺序规矩、共享 tmp。
  3. 知道 Arrays.parallelSort 就是这套实现（commonPool + 粒度 8192），对象/基本类型策略的差异及原因。
  4. 词频统计能写出"分块 → 局部 HashMap → CHM.merge 合并"，并解释为什么比直接共享 CHM 快（热点集中 + 同步税）。
  5. LongAdder vs AtomicLong 的选型与原理张口就来。
  6. 并行 BFS 两种层同步（CyclicBarrier / AtomicInteger 归零开门）能写核心段，知道 visited 必须 CAS 及原因。
  7. 能讲"DFS 难并行、BFS 天然并行"的结构性原因（路径依赖 vs 层独立），能延伸到 Pregel superstep。
  8. Amdahl 定律一句话 + "串行段决定上限"的直觉，知道怎么验证并行收益（基准 + 采样）。
