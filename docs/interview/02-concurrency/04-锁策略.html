02悲观 vs 乐观 ⭐

先给能背的定义（已并入既有笔记口径）

  • 悲观锁（适合多写场景）：假设冲突一定会发生，操作前先独占资源，别的线程只能等。代表：synchronized、ReentrantLock、数据库的 select ... for update。
  • 乐观锁（适合多读场景）：假设冲突大概率不发生，操作时不加锁，提交时才校验"期间有没有人改过"（CAS 或版本号），失败则重试。代表：java.util.concurrent.atomic 原子类（AtomicInteger 等）、数据库的 version 字段。
维度悲观锁乐观锁
核心假设冲突一定发生，先锁再说冲突很少发生，事后校验
加锁时机操作前独占，操作完释放全程不加锁，提交时 CAS / 版本比对
冲突时行为阻塞挂起（进等待队列），让出 CPU失败重试（自旋），不挂起
代表实现synchronized · ReentrantLock · DB for update原子类（CAS）· DB version 字段 · MVCC
适合场景多写、写冲突激烈多读、冲突概率低
主要代价上下文切换 + 唤醒开销高竞争下的重试风暴（见下）

乐观锁在数据库里长什么样

-- 悲观：先独占行锁，事务结束才释放，别的更新全部排队
SELECT balance FROM account WHERE id = ? FOR UPDATE;
UPDATE account SET balance = balance - 100 WHERE id = ?;

-- 乐观：不带锁更新，靠 version 校验（CAS 思想的 SQL 版）
UPDATE account SET balance = balance - 100, version = version + 1
WHERE id = ? AND version = ?;   -- 影响行数 = 0 说明被人改过 -> 读新值重试

乐观锁的隐藏成本：重试风暴

  • CAS 失败 → 自旋重试 → 再失败 → 再重试：竞争激烈时大量线程在空转烧 CPU，吞吐不升反降。写冲突密集的场景，乐观锁可能远差于悲观锁——悲观方案里抢不到的线程直接挂起，CPU 让给别人干活。
  • 数据库侧同理：version 校验失败率一高，应用层重试风暴会放大数据库压力（重试也是一次请求）。
  • 所以口径是"多写用悲观、多读用乐观"，而不是"乐观锁更先进"。选型看冲突概率，不看名字好不好听。

答题技巧：先纠正概念——悲观/乐观不是某把具体的锁，而是并发控制策略；同一把 ReentrantLock 之上可以演化出不同策略。再补一刀加分项：synchronized 策略上是悲观的，但 JVM 的锁升级让它在低竞争时先以 CAS 自旋（轻量级锁）尝试，竞争升级才挂起线程——"悲观策略 + 分级实现"，细节在 第 03 章 锁升级。

03公平 vs 非公平

定义：抢锁前看不看队伍

  • 公平锁（Fair）：获取锁前先检查 AQS 等待队列，有前辈在排队就乖乖排到队尾，严格 FIFO、先来先得。new ReentrantLock(true)。
  • 非公平锁（Nonfair，默认）：锁一释放就先 CAS 试一把，插队成功直接拿走，失败才去排队。new ReentrantLock(false) / synchronized 只能非公平。

二者源码差异只有一行——tryAcquire 里是否先检查等待队列：

// 非公平版 NonfairSync（简化）：锁空闲就直接 CAS 抢，不看队列
final boolean tryAcquire(int acquires) {
    int c = getState();
    if (c == 0 && compareAndSetState(0, acquires)) {   // 直接抢
        setExclusiveOwnerThread(Thread.currentThread());
        return true;
    }
    return false;
}

// 公平版 FairSync（简化）：抢之前多一个"有没有前辈"的检查
final boolean tryAcquire(int acquires) {
    int c = getState();
    if (c == 0 && !hasQueuedPredecessors()              // ⭐ 唯一差异：队列有人就不抢
            && compareAndSetState(0, acquires)) {
        setExclusiveOwnerThread(Thread.currentThread());
        return true;
    }
    return false;
}

为什么非公平吞吐更高

  • 释放锁时要唤醒队头线程：从 unpark 到它真正运行要经过内核调度、上下文恢复，这期间锁是空闲的。非公平锁允许恰好此时到达的新线程直接插队拿锁，锁不空转、省掉一次上下文切换。
  • 代价是可能饥饿：运气差的排队线程可能一直被插队，长时间拿不到锁——排队越久越没有竞争力。
维度公平锁非公平锁（默认）
获取顺序严格 FIFO，按到达顺序可插队，先到不一定先得
吞吐低（每次释放都要走队列唤醒）高（减少上下文切换、锁不空闲等待）
饥饿风险无有（极端时某线程长期抢不到）
适用业务要求严格排队：秒杀按到达顺序放行、公平调度绝大多数场景：Web 请求、缓存更新、任务执行

判断口径：默认都该用非公平，除非业务语义本身就是"排队"（秒杀按到达顺序分配购买资格、审批工单按提交顺序处理）——此时公平性是业务需求，损失吞吐换语义正确。AQS 队列结构本身在 第 03 章 ReentrantLock 展开。

04可重入性 ⭐

定义与实现原理

  • 可重入（Reentrant）：同一线程再次获取自己已持有的锁时直接成功（不死锁），而不是在自己持的锁上等自己。
  • synchronized 与 ReentrantLock 都是可重入的——这是它们与自造轮子锁最关键的区别之一。
  • 实现靠 state 计数 + 持有线程记录：重入一次 state+1，unlock 一次 state-1，减到 0 才真正释放。所以 unlock 次数必须与 lock 次数严格配对。
// synchronized 天生可重入：同步方法互调、递归都不会自己锁死自己
public synchronized void a() { b(); }   // a 已持有 this，b 还要 this -> 直接重入
public synchronized void b() { /* ... */ }

// 递归同理：每次进入 state+1，每次退出 state-1，归零才释放
public synchronized int factorial(int n) {
    return n <= 1 ? 1 : n * factorial(n - 1);
}

反例：不可重入锁会自己锁死自己

// 不可重入锁（示意）：如果 synchronized 不可重入，世界会怎样
class NonReentrantMutex {
    private boolean locked = false;
    public synchronized void lock() throws InterruptedException {
        while (locked) wait();      // 第二次 lock 时：locked=true
        locked = true;              // 等待者恰恰是持锁线程自己 -> 永远醒不来
    }
    public synchronized void unlock() { locked = false; notify(); }
}

// 同一线程连续 lock() 两次：
mutex.lock();    // locked = true
mutex.lock();    // 在等自己释放 -> 死锁（自己等自己）
  • 追问：重入时 AQS 怎么认出"是自己"？——对比当前线程与 exclusiveOwnerThread，相等则 state+1 直接返回（ReentrantLock 的 nonfairTryAcquire 分支）。
  • 追问：重入的价值是什么？——锁的粒度可以按方法设计而不用担心嵌套调用死锁。若不可重入，a() 调 b() 这种最普通的代码结构都得绕开锁，同步方法几乎没法组合。

陷阱：可重入 ≢ 线程安全，更 ≢ 可嵌套释放。lock 两次只 unlock 一次 → state 不归零，锁永远不释放，其他线程全部卡死——这也是"unlock 必须放 finally"的原因之一。

05tryLock 与超时锁

  • tryLock()：立即返回，拿到返回 true，拿不到返回 false——不等待、不阻塞。
  • tryLock(time, unit)：限时等待，超时返回 false，等待期间响应中断（可中断的锁获取，笔记里 ReentrantLock 对比 synchronized 的核心优势之一）。
  • 语义价值：拿到锁不是唯一出路——拿不到就走别的分支或放弃：降级读缓存、返回稍后重试、放弃本次合并写。线程从"无限期等人"变成"自己掌控命运"。

经典用途：破坏"循环等待"来预防死锁

转账要同时拿两把账户锁，两个线程反向转账就可能互相持有对方要的锁（循环等待）。按固定顺序拿锁是首选解法；tryLock 是另一条路：第二把拿不到就放弃并释放已持有的第一把，循环等待根本形不成。

// 任何一把拿不到就整体放弃、稍后重试 —— 两个反向转账线程也不会死锁
boolean transfer(Account from, Account to, long amt) throws InterruptedException {
    if (!from.lock.tryLock(1, TimeUnit.SECONDS)) return false;   // A 都没拿到
    try {
        if (!to.lock.tryLock(1, TimeUnit.SECONDS)) return false; // B 拿不到：放弃
        try {
            from.debit(amt);
            to.credit(amt);
            return true;
        } finally { to.lock.unlock(); }
    } finally {
        from.lock.unlock();   // ⭐ 放弃路径也会执行：把 A 还回去，别人才能推进
    }
}
  • 对照：synchronized 拿不到只能死等（BLOCKED，不可中断、不可超时）——这正是"高竞争场景要不要上 ReentrantLock"的主要判据。
  • 死锁四条件、jstack 排查、活锁（tryLock+重试若退避不当会变活锁）在 第 11 章 并发挑战展开。

加分项：tryLock 无参版本连中断都不响应（试一下就走），有参版本在等待期内响应 interrupt 抛 InterruptedException——"可中断、可超时、可放弃"三个能力是 ReentrantLock 相对 synchronized 的完整功能差集。

06粗粒度 vs 细粒度 ⭐

粒度光谱：从一把全局锁到一条记录

锁保护的范围越大越安全也越慢，越小越快也越容易出事。同一个"扣库存"问题的粒度光谱：

  • 全局静态锁（整个服务一把）→ 实例锁 → 按业务维度拆锁（按 SKU、按用户、按账户） → 数据库行锁（缩小到一行）——数据库"表锁 → 行锁"的演进是同一逻辑。
  • 集合侧的标杆是 ConcurrentHashMap：JDK 7 分段锁（Segment）、JDK 8 桶级 CAS + synchronized，把锁粒度从"整个 Map"缩到"一个桶"——历史一句带过，深讲在 第 09 章 并发容器与 01-java/08 集合框架。
// 粗：全局一把锁 —— 全站所有下单串行，锁竞争的极端
private static final Object GLOBAL = new Object();
void deduct(String skuId, int n) {
    synchronized (GLOBAL) { doDeduct(skuId, n); }
}

// 细：按 SKU 维度拆锁 —— 不同商品互不阻塞，竞争面从"全站"缩到"单个 SKU"
private static final ConcurrentHashMap<String, Object> SKU_LOCKS = new ConcurrentHashMap<>();
void deductFine(String skuId, int n) {
    Object lock = SKU_LOCKS.computeIfAbsent(skuId, k -> new Object());
    synchronized (lock) { doDeduct(skuId, n); }
}

细粒度的代价（面试官等着你说这半句）

  • 管理复杂：锁对象生命周期、内存（Map 里的锁要不要清理）、粒度选错（按 userId 拆还是按 orderId 拆）都会变成设计负担。
  • 死锁概率上升：锁拆得越细，需要同时持有多把锁的操作越多，锁的组合数爆炸——单笔转账要拿 A、B 两把账户锁，拿锁顺序不一致就死锁。粗粒度一把锁反而"天然无死锁"（只有一把锁，循环等待无从谈起）。
  • 口径：先粗后细，按测量数据驱动拆分——先一把锁保正确，压测发现热点在哪一行/哪个业务维度，再沿那个维度拆，同时约定好多锁场景的全局拿锁顺序。

陷阱：细粒度 ≠ 随手加锁。按错误维度拆（例如按"操作类型"而不是按"数据归属"拆）只会制造出更多互相交叉的锁，死锁排查变成噩梦。拆分维度必须是数据本身的隔离维度。

07锁优化手段（JIT / 编码层）

JIT 层：锁粗化与锁消除

  • 锁粗化（Coarsening）：连续的加锁/释放被 JIT 合并成一次——最典型是循环体内反复 synchronized 同一把锁。
  • 锁消除（Elimination）：逃逸分析证明对象不可能被其他线程访问（不逃逸出方法/线程），它上面的锁直接删掉。
// ① 锁粗化：100 次加解锁，中间又没有别的逻辑 -> JIT 合并为一次
for (int i = 0; i < 100; i++) {
    synchronized (lock) { count += i; }
}
// 粗化后等价于：
synchronized (lock) { for (int i = 0; i < 100; i++) { count += i; } }

// ② 锁消除：sb 不逃出方法，StringBuffer 内部的 synchronized 全部被消掉
String concat(String a, String b) {
    StringBuffer sb = new StringBuffer();  // 方法内局部变量、线程封闭
    sb.append(a);                          // append 里的锁 JIT 直接删除
    return sb.append(b).toString();
}

编码层：减小临界区

JIT 帮不了"把不必要的代码关进锁里"——这是工程师自己的事。原则：临界区内只留真正访问共享状态的代码，IO、RPC、大计算全部挪出去。

// 反例：一次几十毫秒的网络 IO 被关在锁里，锁的持有时间放大 1000 倍
synchronized (this) {
    String json = buildPayload();   // 纯计算、无共享 -> 不该在锁内
    String r = http.post(json);     // 网络 IO -> 最不该在锁内
    counter++;                      // 真正需要互斥保护的只有这一行
}

// 正解：锁内只留必须互斥的代码，临界区从几十毫秒缩到纳秒级
String json = buildPayload();
String r = http.post(json);
synchronized (this) { counter++; }

三件事合起来的心智模型：加锁范围要小（减小临界区）、嵌套加锁要顺（避免粗化是 JIT 的事但别反向拆细）、无共享就别加（等逃逸分析救不了跨方法逃逸的对象）。偏向锁/轻量级锁/自适应自旋等 synchronized 内部的锁升级优化归 第 03 章，此处不重复。

08场景题落点

  • 库存超卖：策略题的集大成者——悲观路线（DB for update 行锁 / 分布式锁串行扣减）vs 乐观路线（WHERE stock >= n 条件更新 + 失败重试 / Redis 预扣），按竞争烈度与一致性要求选型，完整推演见 第 13 章 并发票务系统。
  • 多实例部署：JVM 内的锁出了进程就失效——库存拆分、接口防重放这类"跨实例互斥"需要分布式锁（Redis SET NX / Redisson 看门狗 / ZooKeeper 临时顺序节点），展开在 10-microservices 分布式锁。
  • 答题收束句式：策略选型永远回答三个问题——读写比例（定悲观/乐观）、要不要排队（定公平/非公平）、竞争热点在哪个维度（定锁粒度）。把这三个判断说出来，比背十个锁名词管用。

09高频追问与陷阱

  • 追问链：乐观锁 → 高并发写场景还会快吗？→ 不会。CAS 失败率飙升 → 自旋空转烧 CPU、DB version 失败率飙升 → 应用层重试风暴；吞吐可能反低于悲观（阻塞挂起至少让出 CPU）。所以多写用悲观。
  • 追问链：非公平锁 → 饥饿怎么解？→ 换公平锁（损吞吐）；或在业务层限流削峰，降低竞争烈度本身。
  • 追问链：可重入 → state 里存的是什么？→ 重入次数（配 exclusiveOwnerThread 记持有线程）；lock 两次 unlock 一次会怎样 → state 不归零、锁永不释放。
  • 陷阱：tryLock 返回 false 却去 unlock→ IllegalMonitorStateException；unlock 不在 finally → 异常路径锁泄漏，后续线程全部卡死。ReentrantLock 的标配写法是 lock 后紧跟 try-finally。
  • 陷阱：拆了细粒度锁却没定全局拿锁顺序→ 锁组合数变多，A→B 与 B→A 并存即死锁；多锁场景要么统一排序，要么 tryLock 放弃重试（本章第 05 节）。
  • 陷阱：把 CAS 当万能乐观锁→ 单变量、竞争烈度、ABA 三个坑，下一章 第 05 章 无锁编程 逐一展开。
  • 选型对比预备："synchronized 和 ReentrantLock 怎么选"——功能差集（可中断 / 可超时 / 公平 / 多 Condition）在 第 03 章对比表，本章补策略视角：需要 tryLock 这类"拿不到就走"的弹性，才值得为 ReentrantLock 付手动 unlock 的成本。
  • 追问：悲观/乐观锁和 synchronized/CAS 是一一对应吗？→ 不是。悲观/乐观是策略（思想），synchronized/CAS 是实现（手段）；DB 的 select for update / version 条件更新是同一对策略的另一种实现——把"策略 × 实现"分层说清，这道题就答出了体系感。

10面试自查清单

  1. 能用一句话分别定义悲观/乐观锁，说清"多写悲观、多读乐观"的依据（冲突概率 × 失败代价）。
  2. 能主动讲出乐观锁的隐藏成本：高竞争下的重试风暴，以及为什么此时悲观锁反而快。
  3. 公平/非公平的定义落到 AQS 的 tryAcquire（hasQueuedPredecessors），能解释非公平吞吐高的机制（唤醒间隙插队、减少上下文切换）与饥饿代价。
  4. 可重入 = 同线程重复拿自己的锁不死锁；能写出自制不可重入锁"自己等自己"的死锁示例。
  5. 知道 state 计数 + 持有线程记录的实现原理，以及 unlock 次数不配对的后果。
  6. 能用 tryLock(time, unit) 写出"拿不到就放弃并释放已有锁"的死锁预防代码。
  7. 锁粒度题能给"表锁→行锁 / 全局锁→SKU 锁"的完整光谱，并说出细粒度的两大代价（管理复杂、死锁概率上升）。
  8. 能解释锁粗化（循环加锁合并）、锁消除（逃逸分析）、减小临界区三个优化各自解决什么问题。
  9. 场景收尾不慌：超卖引到乐观/悲观选型，跨实例引到分布式锁，并能说出"读写比例 / 要不要排队 / 竞争维度"三问。
