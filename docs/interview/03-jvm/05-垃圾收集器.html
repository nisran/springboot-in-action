面试指纹（版本只需记这三行）：① JDK 8 默认 = Parallel Scavenge + Parallel Old（吞吐量优先）；② JDK 9+ 默认 = G1，CMS 停止维护；③ 问「CMS 为什么被废」= 碎片 + 浮动垃圾 + 并发失败退化为 Serial Old。口诀：Scavenge 结尾 = 新生代，Old 结尾 = 老年代，CMS 单独 = 老年代，G1 全都要。

演进主线（比背表更重要）：Serial → Parallel 解决"单线程慢"；CMS 解决"STW 长"但引入碎片与并发失败；G1 解决"碎片 + 停顿不可控"；ZGC 解决"停顿随堆增长"。每一步都是拿 A 代价换 B 收益——按这条线答，任何"XX 和 YY 的区别"都能现场推导。

03Serial 与 Parallel：吞吐时代的两代

  • Serial（笔记并入）：单线程、Stop The World；适合客户端应用、小内存——没有线程协调开销，小场景反而最快。
  • Parallel（笔记并入）：多线程并行 GC，注重吞吐量（用户代码时间占比），适合后台运算、批处理这类"不关注单次响应、关注总产出"的场景。JDK 8 默认组合是 Parallel Scavenge + Parallel Old。
  • 注意"并行（parallel，多线程 GC）"与"并发（concurrent，GC 与应用同时跑）"是两个维度——CMS/G1/ZGC 的"并发"指后者，这是面试表述准确性的送分点。

04CMS 深挖 ⭐⭐（笔记四阶段并入展开）

CMS（Concurrent Mark Sweep）：老年代收集器，目标是最短停顿——大部分工作与用户线程并发执行。

① 初始标记（STW，短）   —— 只标记 GC Roots 直接关联的对象，速度很快
② 并发标记（并发，长）   —— 从 Roots 直达对象沿引用链遍历，与用户线程同时跑
③ 重新标记（STW，短）   —— 修正并发标记期间用户线程导致的引用变动（增量更新）
④ 并发清除（并发，长）   —— 清理垃圾对象，与用户线程同时跑

停顿 = ① + ③ 两小段；② ④ 虽长但不停止用户线程 —— 这就是"低停顿"的全部秘密

CMS 的三个代价（高频追问）

  • ① CPU 敏感（笔记：对 CPU 资源敏感）：并发阶段默认占走一半核，本就紧张的 CPU 被分流，应用吞吐下降。
  • ② 浮动垃圾 + concurrent mode failure：并发清除阶段用户线程还在产生垃圾（本次收不掉的"浮动垃圾"），所以 CMS 必须预留空间（老年代用到 68%~92% 就要启动，-XX:CMSInitiatingOccupancyFraction）。如果预留不够——并发标记期间对象晋升放不下——触发 concurrent mode failure，退化为 Serial Old 单线程 STW 整理整个老年代（几秒到几十秒），是 CMS 最臭名昭著的事故。
  • ③ 内存碎片（笔记：产生内存碎片）：标记-清除不整理，碎片积累导致"总空间够、连续空间不够"，大对象放不下 → 触发 Full GC。缓解：-XX:+UseCMSCompactAtFullCollection（Full GC 时顺带整理，代价是停顿更长）。

追问：CMS 为什么从来没有成为任何 JDK 的默认收集器 ⭐

事实先摆清：从 1.4 到 8，服务端默认一直是 Parallel 系列；JDK 9 起直接换 G1——CMS 一天默认都没当过。原因一句话：默认的定义是"开箱即用、不调参也稳、行为可预测"，CMS 恰恰每条都不满足。

默认的要求CMS 的现实
不调参也稳必须调 -XX:CMSInitiatingOccupancyFraction 才能跑好：阈值低了易 concurrent mode failure，高了碎片提前耗尽——默认参数下两头都是险
行为可预测失败模式不可预测：预留空间一旦不够，退化 Serial Old 单线程整理整堆，尾延迟方差极大，没人敢把它交给"无人值守"的默认值
能自愈碎片只进不出：标记-清除不整理，长期运行必然积累，靠 Full GC 顺带整理本身又是长停顿——治碎片的药和病同源

但历史地位极高——开路先锋：第一个真正并发的收集器，证明"GC 可以和业务线程并行"，把 STW 从"整个 GC 过程"压缩到"两个标记段"。它暴露的碎片、浮动垃圾、并发失败三大问题，直接催生了 G1（Region 间复制 = 整理，无碎片）、ZGC/Shenandoah（并发整理）——后续每个收集器都在补它的短板。面试指纹：CMS = 用吞吐量换延迟的先驱，死于碎片和不可预测的失败模式，被 G1 接班（9 默认、14 移除）。

美团《9 种 CMS GC 问题》选讲两个生产案例 ⭐

  • 案例一：动态扩容空间震荡（见 第 01 章参数节埋的点）：Xms ≠ Xmx 时，堆在"扩容 → Full GC → 缩容 → 再扩容"里循环，GC 时间曲线周期性震荡——一个 -Xms=-Xmx 就治好。"先怀疑参数与容量，再怀疑玄学"的样板。
  • 案例二：过早晋升（Premature Promotion）：Survivor 太小（或新生代整体太小），对象还没死透就被动态年龄判断提前推进老年代 → 老年代被短命对象灌满 → Old GC 频繁。识别信号：GC 日志里每次 Young GC 的晋升量高、但老年代涨完又跌（说明晋升的对象很快就死了，死错了地方）。治法：调大新生代/Survivor，让短命对象"死在新生代"。

"CMS 都被移除了为什么还问"的标准答法：大量存量系统（JDK 8）仍在跑，且 CMS 的三色标记、并发失败、碎片化是理解 G1/ZGC 的参照系——懂 CMS 才知道 G1 的每个设计在补什么。

05三色标记与并发漏标 ⭐（CMS 与 G1 的分水岭）

并发标记期间用户线程还在改引用，怎么保证不把活对象当垃圾（漏标 = 还在用的对象被回收 = 灾难）？用三色标记抽象来推：

  • 白：未被扫描（垃圾候选）；灰：自己已扫完但成员还没扫完；黑：自己和成员都扫完（确认存活）。
  • 扫描结束后白色 = 垃圾。漏标（活对象被当白）必须同时满足两个条件：
条件① 黑色对象 新增了 指向白色对象的引用（黑不重扫，看不见这条新边）
条件② 灰色对象 原来指向该白色对象的引用 被删除（白失去最后的"被扫到"机会）

// 两种解法 = 破坏其中一个条件：
增量更新（Incremental Update，CMS 采用）：破坏①
  —— 黑→白的新引用记录下来，重新标记阶段把该黑对象降级为灰重扫
原始快照 SATB，Snapshot At The Beginning（G1 采用）：破坏②
  —— 删除的引用记录下来，按"标记开始那一刻的对象图快照"处理：
     快照里活着的，这一轮都算活的（宁可漏杀不可错杀）→ 产生浮动垃圾也认了

追问预埋："CMS 和 G1 的本质区别之一是什么"——就答并发漏标的解决方案不同（增量更新 vs SATB），顺便带出 G1 用 SATB 换来"快照一致性"，代价是浮动垃圾。这是本章分水岭级答案，链 第 04 章可达性分析的钩子在此兑现。

06G1（Garbage First）⭐⭐（笔记 Region 模型并入展开）

核心变化：物理分代 → 逻辑分代

  • G1 之前的收集器：分代是连续物理区域；G1：把堆切成约 2048 个等大 Region（笔记：G1 分区域，region 可以不连续），每个 Region 动态扮演 Eden / Survivor / Old / Humongous（大对象，≥ Region 一半就整个 Region 装，可连续占用多个）四种角色。
  • 回收时不以代为单位、而以 Region 为单位：优先回收"垃圾占比最高"的 Region（Garbage First 名字由来）——用最少工作量换最多空间。

Eden/S0/S1 只是"角色标签"⭐（面试易误答点）

G1 里的 Eden/Survivor 是户口不是地——物理上全是等大 Region，代际只剩逻辑语义：

经典分代（Serial/ParNew/PS）G1
Eden/S0/S1三块固定物理空间，比例 8:1:1动态 Region 集合，每轮数量都变
复制方式from/to 半区交换，两块 Survivor 对半预留没有半区交换：每次 Young GC 现场挑空闲 Region 当新 Survivor，装完存活对象，旧 Eden/Survivor Region 整体释放——顺手完成整理
各占几个固定比例全部动态：Region 总数默认 ~2048（大小取 2 的幂，1–32MB，G1HeapRegionSize）；年轻代占堆 5%~60%（G1NewSizePercent/G1MaxNewSizePercent，停顿模型自适应）；Survivor 只按存活量留几片（个位数~十几片，装不下直接晋升）；Eden = 年轻代 − Survivor

保留的只有年龄语义：每熬一次 Young GC 岁 +1，超过 MaxTenuringThreshold（默认 15）或触发动态年龄判断就晋升 Old——概念没变，变的只是容器。面试指纹：G1 = 分代从"三块地"降级成"三种户口"，半区交换没了，换来回收即整理、无碎片。

三个关键机制

  • RSet（ remembered Set 记忆集）：每个 Region 记一份"谁引用了我"的跨 Region 引用表（卡表实现），Young GC / 并发标记时不用扫整堆就能知道本 Region 被谁引用——空间换时间，解决 Region 化后"跨代引用扫描成本"的问题。
  • 并发标记（SATB）：全局标记跑完后才知道每个 Region 的垃圾比例，为 Mixed GC 做"性价比排序"。
  • 停顿预测模型：-XX:MaxGCPauseMillis=200（默认）是软目标——G1 按历史每个 Region 回收耗时建模，在停顿预算内尽量多装高价值 Region 进 CSet（Collection Set）。设得过小（如 10ms）→ 每次 CSet 只装一点点 → 回收赶不上分配 → 最终退化 Full GC，这是"调参调崩"的经典反面案例（笔记已列该参数）。

Young GC 与 Mixed GC

Young GC（STW，并行）：Eden/Survivor Region 中存活对象 → 复制到新 Survivor/Old Region
                        空出来的 Region 整体回收 —— Region 间复制即"整理"，无碎片问题
Mixed GC（G1 的招牌） ：并发标记后，回收【全部 Young + 部分高垃圾率 Old】Region
                        每次 Mixed 只选 CSet 里的一部分，分多轮完成 —— 停顿可控的原因
退化：并发标记赶不上分配 / Humongous 不断插入 / 晋升失败
      → Full GC 整堆整理（JDK 10 起并行化 JEP 307，仍是秒级灾难，要靠监控提前发现）

三种 STW 回收：Young / Mixed / Full（G1 没有"Major GC"）⭐⭐

术语先纠偏："Major GC"是老术语（≈老年代整堆回收，CMS 语境）；G1 把"回收老年代"拆成并发标记（只统计、不回收）+ Mixed GC（真回收）两步——所以 G1 只有三种 STW 回收：

Young GCMixed GCFull GC
触发Eden Region 满，分配不进来并发标记完成后紧接着，没有独立触发条件兜底：分配赶不上回收 / Humongous 挤爆 / 晋升失败
范围全部年轻代 Region全部年轻代 + 部分高垃圾率 Old Region整堆整理
STW是，并行复制是，并行复制是（JDK 10 起并行化 JEP 307，之前单线程）
时长几 ms~几十 ms（停顿预算内）每轮与 Young 同量级，连续 3~8 轮（G1MixedGCCountTarget=8）秒~几十秒，灾难
收摊条件—可回收垃圾占比 < 5%（G1HeapWastePercent）提前结束—
运作时序：
平时：   Eden 满 → Young GC（几ms）→ 接着分配 → 又满 → Young GC …反复
老年代 ≥ 45%（IHOP）→ 借下一次 Young GC 的 STW 顺带做初始标记
                      → 并发标记（不 STW，给老年代 Region 按"垃圾占比"排队）
标记完成 → Mixed × N 轮（每轮 = Young + 一批 Old Region）
出事：   某一步撑不住 → Full GC（秒级全停）= 调优失败信号

"选择"分三层：① 什么时候干——Young 没得选（Eden 满就干），并发标记由 IHOP（InitiatingHeapOccupancyPercent，默认 45%）决定，JDK 9+ 自适应调整该阈值；② 选谁进 CSet——年轻代 Region 全进，老年代按垃圾占比排序、停顿预算内挑性价比最高的（Garbage First 本义）；③ 多长——不靠设置长短，靠动态调年轻代 Region 数适配 MaxGCPauseMillis 预算（"别手动设 -Xmn"铁律的根因）。

G1 使用两条铁律：① 堆 6GB+、停顿敏感才选 G1（小堆上 Parallel 可能更快）；② 不要手动设置 -Xmn / SurvivorRatio（笔记未提但极重要）——G1 的核心能力就是动态调整年轻代 Region 数来实现停顿目标，手动定死等于废掉它的自适应。

07ZGC 与低延迟路线 ⭐（新热点）

  • 目标：停顿 10ms 以下（实测亚毫秒级），且与堆大小无关——TB 级堆也一样；代价是吞吐量损失约 10% 量级。JDK 11 实验、15 生产可用、17+ 成熟（JDK 21 起分代 ZGC 进一步降开销）。
  • 染色指针（Colored Pointer）：在 64 位指针的地址位里直接存"标记状态"（Marked0/Marked1/Remapped/Finalizable）——对象元信息不再需要额外结构，GC 状态写在指针上。
  • 读屏障（Load Barrier）：应用线程读引用时的一小段检查代码：发现指针"颜色不对"（指向旧地址/未标记），就现场自愈（转发到新地址）。这是 ZGC 能并发移动对象的关键——搬完家不 STW 全局修正引用，谁读到谁修。
  • 并发整理：标记、转移、重定位几乎全部与应用并发 → 停顿只剩极短的根扫描等固定环节，与堆大小解耦。
  • 美团《ZGC 的探索与实践》要点：低延时场景（交易链路、网关）收益显著——P99 延迟大幅平稳；注意点：吞吐换延迟的取舍、单代 ZGC 的对象晋升特征（JDK 21 分代 ZGC 缓解）、超大堆下内存占用略高。7 年经验口径：不是无脑上，是"延迟 SLA 卡得紧、堆又大"时才切。

为什么停顿与堆大小无关（三行动作对照）⭐

一次 GC 三动作：标记（找活对象）→ 转移/整理（搬对象）→ 修正引用
停顿的根：只要在"搬"，就得 STW——业务线程不能看见"搬到一半"的中间状态

CMS：  STW(标记段) + 并发(清除)        → 躲掉了整理 → 碎片死
G1：   STW(标记段) + STW(小批搬)       → 搬是分批的 → 停顿随堆涨
ZGC：  STW(根扫描，固定) + 并发(其余全部) → 停顿 = 常数

并发搬对象的死结：GC 把对象从地址 1 搬到地址 2 时，业务线程手里指着地址 1 的旧引用读谁？解法 = 染色指针 + 读屏障配合的自愈链：

GC 搬走对象，旧址放转发指针（forwarding pointer）
  ↓
业务线程读到旧引用 → 读屏障发现颜色不对（慢路径）
  ↓
沿转发指针找到新家 → 改【自己这一份】引用 + 重新着色 → 返回新地址
  ↓
第一次访问贵，之后全走快路径；GC 收尾 remap 阶段并发遍历对象图补漏

追问热点：三个引用指向旧址，怎么知道"所有指向都转移完了"？——不存在、也不需要全局判定。修复按引用、惰性、各自负责：谁被读，谁的那一份自愈（只改自己 + 重着色）；没被读的由旧址转发指针兜着 + remap 收尾补漏（与读屏障幂等）。正确性锚点只有一条：旧址回收至少推到下一轮周期——转发信息的寿命 > 任何引用的寿命，"读到已回收的旧址"不会发生。

ZGC 里有 Young/Major/Mixed/Full GC 吗？⭐（术语纠偏）

时代GC 种类
JDK 11~20（单代 ZGC）全没有。不分代 → 不存在"只收年轻代"的动作，Minor/Major/Mixed 之分都不成立。只有一种循环：并发标记 → 并发转移，整堆滚动进行；触发不看"Eden 满"，按分配压力自适应启动下一轮
JDK 21+（分代 ZGC，JEP 439）概念回归但换名：Minor cycle（高频，只收年轻代）+ Major cycle（低频，标记+转移全堆）——术语叫 cycle，不再叫 GC

极端兜底不是 Full GC，而是 Allocation Stall（分配停顿）：内存还没腾出来时业务线程短暂等待——GC 本身快，等待有界（毫秒级）；真跟不上才 OOM。单代 ZGC 的日志里看不到 "GC (Allocation Failure)" 这类词汇。

"代价 ~10% 吞吐"的口径：吞吐 = 用户代码运行时间 / 总时间（时间口径）≈ 单位时间处理请求量（产出口径）——同机同压，G1 每秒 10 万 → ZGC ~9 万。损失构成：① 读屏障检查开销（每次引用加载都有，大头）② GC 并发线程抢 CPU ③ 转发表等内存开销。反直觉点：若原来 G1 常打几秒 Full GC，切 ZGC 后积压/超时/重试消失，总吞吐有时反而更好——所以答"典型 10% 左右，看负载特征"，是量级不是定律。

顺带记住同路线的 Shenandoah（Red Hat，用转发指针而非染色指针，思路殊途同归）和 Generational ZGC（JDK 21）——能带出这两个名字，说明你在跟这条线的最新进展。

08怎么选：一张决策表

场景选择理由
小内存 / 客户端 / 边缘Serial协调开销最小，简单即快
后台批处理 / 吞吐优先ParallelSTW 长一次没关系，总吞吐最大
通用在线服务（JDK 8 存量）ParNew + CMS（或直接评估升级）低停顿诉求的老组合，盯 concurrent mode failure
通用在线服务（JDK 9+，堆 6G+）G1（默认）停顿可预测、无碎片，平衡首选
大堆 + 超低延迟 SLA（金融/交易/网关）ZGC停顿与堆大小无关，用 ~10% 吞吐买 P99

答题框架：先问自己三个问题——要吞吐还是要延迟？堆多大？JDK 什么版本？答案基本就定了。把这"三问"说出来再给结论，比直接报名字更像做过决策的人。

09高频追问与陷阱

  • 追问链：G1 和 CMS 的区别（必考）→→ 五点：①Region 化逻辑分代 vs 物理连续分代；②SATB vs 增量更新；③标记-整理（Region 间复制）无碎片 vs 标记-清除有碎片；④停顿可预测（软目标建模）vs 尽力而为；⑤大对象 Humongous 专门处理 vs 直接进老年代。
  • 追问链：JDK 9 为什么默认 G1 →→ 多核大内存时代在线服务都在意延迟；CMS 的碎片与并发失败维护成本高；G1 全场景均衡且自适应 → 再追问：G1 会退化为 Full GC 吗 → 会（分配赶不上回收/Humongous 挤爆），链第 06 节。
  • 追问链：CMS 为什么从来没当过默认 →→ 默认 = 开箱即用可预测；CMS 必须调启动阈值才稳、并发失败退化不可预测（Serial Old 全停）、碎片只进不出 → 但它是并发收集的开路先锋，暴露的三大问题直接催生 G1/ZGC → 再追问：ParNew 为什么被移除 → 唯一搭档是 CMS，CMS 移除即失去存在意义（JDK 14）。
  • 追问链：MaxGCPauseMillis 设 10ms →→ 软目标不是硬承诺 → 每次 CSet 极小 → 回收速率 < 分配速率 → 老年代持续涨 → 退化 Full GC → 一次 10s 的停顿换掉了每次 200ms，完全本末倒置。
  • 追问链：G1 有 Major GC 吗 →→ 没有独立 Major GC（老术语，CMS 语境）；老年代回收 = 并发标记（只排队不回收）+ Mixed GC（真收割）→ 再追问：Mixed 几轮收摊 → 最多 8 轮（G1MixedGCCountTarget），可回收垃圾 <5%（G1HeapWastePercent）提前结束；Full GC 是兜底灾难不是常态。
  • 追问链：G1 里 Survivor 还是俩吗 →→ 不是，没有 S0/S1 半区交换了；Eden/Survivor 只是 Region 的角色标签，每次 Young GC 现场挑空闲 Region 当新 Survivor，按存活量给几片（不是对半），旧 Region 整体释放即整理。
  • 追问链：ZGC 怎么知道地址"所有指向都转移完了" →→ 不存在全局判定，按引用惰性各自负责：谁被读谁自愈（转发指针 → 新地址 + 重着色），没被读的由 remap 收尾补漏；正确性锚点 = 旧址回收推到下一轮周期 → 再追问：单代 ZGC 有 Full GC 吗 → 没有，兜底是 Allocation Stall（有界的毫秒级等待，真跟不上才 OOM）。
  • 追问链：ZGC 的吞吐代价怎么定义 →→ 吞吐 = 用户代码时间占比 ≈ 单位时间请求量；~10% 的构成 = 读屏障开销 + 并发线程抢 CPU + 转发表内存 → 反直觉收尾：原本常打 Full GC 的服务切 ZGC，总吞吐可能反而升。
  • 陷阱：CMS 的"并发"= 没有停顿 →→ 初始标记和重新标记都 STW，只是短；并发失败时更是全停。
  • 陷阱：G1 不需要分代了 →→ 逻辑上仍分代（Eden/Survivor/Old Region 角色），只是不要求物理连续；JDK 21 前 ZGC 才是真正不分代。
  • 场景题：老年代锯齿正常但基线缓涨 →→ GC 能回收但回不到原位：疑似泄漏（对象被 Root 长期引用）或缓存类对象真实变多 → 用第 07 章的 jstat 趋势 + dump 对比法确认。

10面试自查清单

  1. 演进表能默写，且能用"换代价"主线串讲（并行→并发→可预测→与堆无关）。
  2. 版本账本三行指纹：JDK 8 默认 PS+PO、9 起默认 G1、CMS 弃 9 移 14（ParNew 同批移除）；"CMS 为什么没当过默认"能答出"不可预测 + 需调参 + 碎片只进不出"。
  3. CMS 四阶段 + 哪两段 STW；三个代价（CPU 敏感 / 浮动垃圾与 concurrent mode failure 退化 / 碎片）。
  4. 美团两案例能讲成故事：空间震荡（Xms=Xmx）、过早晋升（Survivor 太小，日志识别法）。
  5. 三色标记漏标两条件 + 增量更新 / SATB 分别破坏哪个条件、各自归 CMS / G1。
  6. G1：Region 模型、四种角色（含 Humongous）、RSet 作用、Young/Mixed GC、停顿软目标语义、"不手动设 Xmn"铁律。
  7. G1 进阶：Eden/Survivor 只是 Region 角色标签（无半区交换，年轻代 5%~60% 动态）；三种 STW（Young/Mixed/Full）的触发、时长、收摊条件；"没有 Major GC"术语纠偏；IHOP 默认 45% 且 JDK 9+ 自适应。
  8. ZGC：染色指针 + 读屏障 + 并发整理如何把停顿与堆大小解耦；知道分代 ZGC（21）。
  9. ZGC 进阶：并发搬对象的自愈链（染色指针 → 读屏障 → 转发指针，按引用惰性修复 + remap 补漏，旧址回收推下一轮）；单代无 Minor/Major/Mixed、兜底是 Allocation Stall；吞吐 ~10% 的口径与构成、"延迟换吞吐可能倒挂"。
  10. 选型三问（延迟/堆大小/JDK 版本）+ 决策表能现场走一遍。
