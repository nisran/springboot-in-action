  7. 字符串常量池在堆里还是方法区里？

这一章是整个 JVM 板块的地基：后面 GC 讲的是堆怎么清理，类加载讲的是方法区怎么填，调优排查全是在这几块区域上看指标。答题要带着"区域 → 存什么 → 会出什么事故 → 出了事故看哪个指标"四连的意识，而不是背五个名字。

区域线程存什么会出什么事故
程序计数器私有当前线程执行的字节码指令地址唯一不会 OOM的区域
虚拟机栈私有栈帧（局部变量表、操作数栈、动态链接、返回地址）StackOverflowError；线程过多时 OOM
本地方法栈私有native 方法的栈帧（HotSpot 与虚拟机栈合一实现）同上
堆共享对象实例、数组（GC 主战场）OutOfMemoryError: Java heap space
方法区（元空间）共享类元信息、运行时常量池、JIT 编译后代码缓存OutOfMemoryError: Metaspace
直接内存共享NIO DirectByteBuffer 等堆外缓冲OutOfMemoryError: Direct buffer memory

答题口径：先一句话"线程私有的三块：计数器、虚拟机栈、本地方法栈；共享的两块：堆和方法区"，再主动补"JDK 8 起方法区由元空间在本地内存实现，堆外还有直接内存也归 JVM 管"——这三句说完，这题的层次感就有了。

03程序计数器（PC Register）

  • 是什么：一块很小的内存，记录当前线程执行到的字节码指令地址（字节码解释器工作时就是靠改变这个值来选取下一条要执行的字节码指令）。
  • 为什么必须有：Java 的多线程靠 CPU 轮转切换实现——线程切换后必须能恢复到正确的执行位置，每条线程就需要一个独立的计数器互不影响。它是"线程私有"这个设计的直接原因之一。
  • 执行 native 方法时：计数值为 undefined（native 代码不归字节码解释器管）。
  • 唯一不会 OOM：《JVM 规范》中唯一没有规定任何 OutOfMemoryError 情形的区域——它只存一个地址，大小固定且极小。这题常作为"暖场送分"出现。

04虚拟机栈与栈帧 ⭐

除 native 方法（走本地方法栈）外，所有 Java 方法的调用执行都靠虚拟机栈（笔记原文口径）：每个方法从调用到返回，对应一个栈帧（Stack Frame）的压入与弹出。栈由一个个栈帧组成——栈有多深，取决于调用链有多长。

两种栈事故：SOE vs 栈 OOM

// StackOverflowError：单线程内调用链太深（递归没有出口是经典成因）
private int depth = 0;
public void recurse() { depth++; recurse(); }   // Exception in thread "main"
                                                // java.lang.StackOverflowError
  • StackOverflowError：线程请求的栈深度 > 虚拟机允许的深度。单线程的深递归、方法互相循环调用、超大的单个方法（栈帧装不下）。
  • OutOfMemoryError（栈也能 OOM）：扩展栈容量时申请不到足够内存，或不停创建新线程——每线程一份数，线程本身吃的就是进程内存（unable to create new native thread）。注意后者不是堆的问题，加 -Xmx 反而更糟（堆大了，留给线程栈的进程内存更少）。
  • -Xss（如 -Xss512k）设置单线程栈大小，默认约 1MB。调大 = 单线程能递归更深，但同样进程内存下能创建的线程数变少——栈大小是"深度"和"线程数"之间的预算分配，不是越大越好。

陷阱："StackOverflowError 是 Error 所以 JVM 就崩了"——错，SOE 只杀死当前线程，其他线程照常；同样 OOM 也未必让进程退出（被 catch 或只影响一个请求线程）。"进程到底活没活着"要看具体影响范围，这也是线上"偶发 OOM 但服务还在"的原因。

05堆：对象的家与 GC 主战场

  • 存什么：对象实例与数组（笔记原文）；几乎所有对象实例都在堆分配（逃逸分析的"标量替换"是例外，见 第 03 章）。
  • 分代布局（笔记并入）：新生代 Eden : S0 : S1 = 8 : 1 : 1（-XX:SurvivorRatio=8），新生代外是老年代。为什么这么分：分代假设——绝大多数对象朝生夕死，把"新对象"和"老顽固"分开治理，各自用最划算的算法（完整推理链在 第 04 章）。
  • 对象在哪分配：优先 TLAB（Thread Local Allocation Buffer，线程私有分配缓冲，分配动作免竞争免同步——深入在 第 03 章）；大对象直接进老年代。
  • 对象的一生（先建立主画面）：新对象出生在 Eden（TLAB 就是在 Eden 里划的私有缓冲）→ Minor GC 后幸存的才进 S0/S1（from/to 来回倒，经受考验）→ 年龄 ≥15 晋升老年代（新生代 : 老年代默认 ≈ 1:2）。Survivor 是幸存者中转站，不是出生地——流转细节见 第 04 章。
  • Eden 满了触发 Minor GC；老年代空间不足、担保失败、元空间满等触发 Full GC（触发链完整版在 第 04 章）。

堆参数速记

参数含义生产要点
-Xms / -Xmx初始堆大小 / 最大堆大小通常设成一样大，理由见下面的美团案例
-Xmn新生代大小（堆 − 新生代 = 老年代）G1 下不要手动设（链 第 05 章）
-XX:SurvivorRatio=8Eden 与单个 Survivor 的比例默认 8，即 8:1:1
-XX:MaxTenuringThreshold=15晋升老年代的年龄阈值上限4 位存储上限就是 15（链 第 03 章对象头）

为什么 -Xms = -Xmx（美团 CMS 文案例之一：动态扩容空间震荡）：Xms ≠ Xmx 时堆可动态伸缩——流量高峰堆扩容，流量回落 JVM 又把空闲内存还给操作系统（缩容由 GC 后的空闲率触发）；下一次流量来再扩，扩容缩容都会伴随额外 GC 压力，表现为GC 时间毛刺周期性震荡。设成相等后堆尺寸固定，避免这类自找的抖动。这是"参数为什么这么配"能讲到生产级的一个样板答案。

06方法区与元空间 ⭐

方法区存什么（规范概念）

  • 类的元信息（字段、方法字节码）、运行时常量池（类的符号引用表，类加载后从 class 文件常量池放入）、JIT 编译后的代码缓存。
  • 演进注意：JDK 7 起静态变量、字符串常量池已移到堆；方法区里留下的是类元信息和运行时常量池。很多人背"静态变量在方法区"是 JDK 6 的答案。

永久代 → 元空间（JDK 8）⭐ 高频

方法区是规范里的逻辑概念，永久代（PermGen）/元空间（Metaspace）是HotSpot 的两代实现。JDK 8 彻底移除永久代，改为在本地内存（native memory）上实现元空间。为什么换：

  • 永久代大小难定：永久代在堆内、有 -XX:MaxPermSize 上限，加载类多的应用（动态代理、脚本引擎）频繁 OutOfMemoryError: PermGen space；元空间在本地内存，默认只受进程内存限制（更要主动设 -XX:MaxMetaspaceSize 兜底！）。
  • 为融合铺路：HotSpot 与 JRockit 合并路线中，JRockit 从没有永久代概念，去掉它减少合并阻力。
  • 字符串常量池在 JDK 7 已经先搬进堆（它的回收收益归堆 GC），永久代最后的存在理由也消失了。

两个易混参数：-XX:MetaspaceSize 是首次触发 Full GC 的元空间使用水位（默认很小 ~21M，动态类多的应用会被频繁 Full GC，应调大），不是元空间上限；上限是 -XX:MaxMetaspaceSize。面试能把这两个参数区分开，说明真在生产上看过元空间问题。

07直接内存（堆外内存）

  • 不是运行时数据区的一部分，但 JVM 参数管得到它：NIO 的 ByteBuffer.allocateDirect() 分配堆外缓冲，避免堆内堆外来回复制（零拷贝基础之一，机制链 12-os）。
  • 不受 -Xmx 管辖，但默认上限 ≈ Xmx（-XX:MaxDirectMemorySize 单独设置）。堆外内存泄漏（Netty 池化缓冲未释放、DirectByteBuffer 被静态引用）时 Xmx 调多大都没用——排查手段在 第 07 章（NMT / DirectByteBuffer 计数）。
  • DirecByteBuffer 本身的回收依赖虚引用 + ReferenceQueue（Cleaner 机制）——四种引用的落地案例在 第 04 章。

09高频追问与陷阱

  • 追问链：为什么要分代 →→ 分代假设（对象存活时间两极分化）→ 新生代用复制算法、老年代用标记清除/整理（链 第 04 章）。
  • 追问链：元空间为什么会满 →→ 动态生成类：CGLIB/Spring 代理、Groovy 每个脚本一个类、频繁反射 → 为什么"重启就好了"→ 类加载器泄漏的温床，展开在 第 06 章。
  • 追问链：-Xss 越大越好吗 →→ 单线程递归更深，但进程内存固定下线程数上限变低 → 什么系统会故意调小 → 高线程数服务（早期 Web 容器）。
  • 陷阱：静态变量到底在哪 →→ JDK 7+ 在堆（随 Class 对象），"方法区"是 JDK 6 旧答案。
  • 陷阱：栈溢出只发生在递归 →→ 还有方法互相调用成环、单个方法超大（一次压入的栈帧超过剩余栈空间）、以及深递归序列化/JSON 解析（调用链层叠而非显式递归）。
  • 追问：常量池在堆还是方法区 →→ 分开答：运行时常量池（类符号引用）在元空间；字符串常量池 JDK 7 起在堆——展开在 第 03 章（intern 陷阱）。
  • 场景题：服务启动没多久就 Full GC，之后稳定 →→ 大概率是 MetaspaceSize 默认太小，类加载到 21M 水位触发扩容 Full GC——一个参数的事，但它考的是你分得清元空间两个参数。
