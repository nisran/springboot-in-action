02类的生命周期：七个阶段

加载 ──► 验证 ──► 准备 ──► 解析 ──► 初始化 ──► 使用 ──► 卸载
└────────── 链接(Linking) ──────────┘
        （验证+准备+解析三步合称链接，笔记原文口径）
  • 前五个阶段按顺序开始，但不强制按顺序完成（解析阶段可以滞后到运行期——支持 Java 的动态绑定/晚期绑定）。
  • 类加载器的规则（笔记原文）：按需加载，同一个类只加载一次——"同一个类"的判定是 类加载器实例 + 全限定名 一起，两个不同加载器加载同名类得到的 Class 不相等（这是 Tomcat 隔离的基础）。

03五阶段细拆 ⭐（笔记并入 + 补全）

阶段做什么面试细节点
加载通过全限定名（如 java.lang.String）读取二进制字节流 → 方法区生成类元数据 → 堆中创建该类的 java.lang.Class 对象字节流的来源不限于文件：网络、jar、动态代理生成（这是自定义类加载器的切入点）
验证检查字节流符合 JVM 规范，不危害虚拟机（文件格式、元数据、字节码、符号引用四类验证）-Xverify:none 可关闭加速启动（了解即可，别在生产关）
准备为静态变量分配内存并赋零值（不是代码里的初始值！）⭐ 最爱挖：见下方代码对比
解析把常量池内的符号引用替换为直接引用（笔记原文）符号引用 = 用字面量描述目标；直接引用 = 直接指向目标的指针/偏移量
初始化执行类构造器 <clinit>：静态变量赋代码里的初始值、执行 static 块触发时机有严格规定（下一节）；JVM 保证 clinit 的线程安全
// 准备 vs 初始化：值到底什么时候赋（高频细节题）
public static int a = 100;
// 准备阶段后：a = 0        （零值：int 的零值是 0）
// 初始化阶段后：a = 100    （执行 <clinit> 里的 putstatic）

public static final int B = 100;
// 准备阶段就是 100！static final 的编译期常量走 ConstantValue 属性，
// 准备阶段直接赋予字段码中设定的值 —— 两者的区别就在这里

// 静态代码块也在 clinit 里按源码顺序执行：
static { log.info("initialized"); }   // 与 static 赋值按书写顺序合并成 clinit

陷阱：答"a 在准备阶段就等于 100"是最常见失误。记忆法：准备给零值，初始化给真值；final 常量（编译期常量）例外，准备期直接给真值。

04初始化：触发时机（主动引用 vs 被动引用）

《JVM 规范》规定只有主动引用才触发初始化（六种），被动引用不触发——这是"懒加载"的规范基础：

  • ① new / getstatic / putstatic / invokestatic 访问静态字段或静态方法（new 数组除外）；② 反射调用（Class.forName）；③ 初始化一个类时其父类未初始化，先初始化父类；④ main 所在类；⑤ MethodHandle 相关；⑥ 接口带 default 方法时其实现类初始化先触发接口初始化。
// 三大"被动引用"经典例（都不触发初始化，⭐ 高频判断题）
System.out.println(Sub.HELLO);
// ① 通过子类引用父类静态字段：只初始化 Father，不初始化 Sub
//    （HELLO 定义在 Father 里，对 Sub 的静态解析直接定位到 Father）

Father[] arr = new Father[10];
// ② new 数组：分配数组类型（[LFather;），不初始化 Father

System.out.println(Father.CONSTANT);
// ③ 引用编译期常量：常量在编译期已存入调用方的常量池，
//    运行期与 Father 无任何联系 —— Father 根本不会被加载

clinit 的线程安全（加分点）：JVM 保证一个类的 clinit 在多线程下只被一个线程执行，其余线程阻塞等待——这也是静态内部类单例天然线程安全的底层依据（实例化在 01-java/15 单例模式展开）。注意：如果你的 static 块里造对象，第一个触发初始化的线程要付这个成本（启动慢/首个请求慢的排查点之一）。

05类加载器与双亲委派 ⭐⭐

三层加载器（笔记并入 + JDK 9 更新）

加载器实现加载什么
Bootstrap 启动类加载器C++ 实现（所以没有父类、Java 里拿不到引用，显示为 null）JAVA_HOME/lib 核心库（String、Object…）
Platform/ApplicationJava 实现JDK 9 前叫 Extension（ext 目录）→ JDK 9 起改名 Platform（加载平台模块）；Application 加载 classpath 与模块路径
自定义 ClassLoader继承实现笔记场景：类加密加载时解密、热部署、依赖隔离

双亲委派模型（笔记口径规范化）

WHAT：收到类加载请求，加载器不先自己加载，而是逐层向上委派给父加载器；只有父加载器反馈"我加载不了"（范围里找不到该类），子加载器才尝试自己加载。

// ClassLoader#loadClass 的骨架（双亲委派的源码落点）
protected Class<?> loadClass(String name, boolean resolve) {
    Class<?> c = findLoadedClass(name);            // ① 已加载过直接返回
    if (c == null) {
        try { c = parent.loadClass(name, false); }  // ② 先委派给父亲
        catch (ClassNotFoundException e) { /* 父亲抛了找不到 */ }
        if (c == null) c = findClass(name);         // ③ 父亲不要，我才自己找
    }
    return c;
}

WHY（两个好处，笔记 + 补全）：

  • 安全（防核心 API 被篡改）：自定义的 java.lang.String 会被一路委派到 Bootstrap，由它加载 rt.jar 里正牌的 String——你写的那份根本轮不到加载（笔记原文场景）。
  • 唯一（避免重复加载）：同一个类永远由同一层加载，JVM 中类只存在一份——保证"类加载器 + 类名"唯一确定一个 Class。

06打破双亲委派的三种姿势 ⭐

姿势谁在用原理一句话
① 重写 loadClass / findClassTomcat、热部署框架笔记口径：继承 ClassLoader 重写 loadClass()，先自己加载再委派（顺序反转）
② 线程上下文类加载器（SPI）JDBC、JNDI、JCE父加载器加载的接口需要"逆向"用子加载器加载实现类
③ JDK 9 模块化JPMS类加载委托按模块图走，不再是严格三层链（了解即可）

Tomcat：隔离优先（姿势①的代表）

  • 需求：一个 Tomcat 跑多个 webapp，各自的 Spring 版本可能不同、且同名类互不可见——如果严格双亲委派，第一个加载的 Spring 会污染所有应用。
  • 做法：每个 webapp 一个 WebappClassLoader，加载应用自己的类时先自己找（WEB-INF/classes、lib），找不到再走双亲委派——顺序反转。但核心类库仍委派（防篡改不变）。

SPI：父加载器"逆行"（姿势②，最考理解）

// DriverManager 在 rt.jar（Bootstrap 加载），驱动实现在应用 classpath（App 加载）
// 按双亲委派，Bootstrap 根本"看不见"应用的 mysql Driver —— 死锁式矛盾
ServiceLoader<Driver> loadedDrivers = ServiceLoader.load(Driver.class);
// ServiceLoader.load 内部：
//   ClassLoader cl = Thread.currentThread().getContextClassLoader();
//   —— 线程上下文类加载器：主线程里默认就是 AppClassLoader
//   把"该用谁加载"作为线程属性传下去，父层代码拿着子层加载器用
// 这就是"打破双亲委派"最经典的生产案例：委派链被上下文加载器"抄了近路"

答"怎么打破双亲委派"：先说本质（默认"先委派后自己"的顺序，打破 = 反转或绕开），再给两例：Tomcat 为隔离先自己加载；JDBC SPI 用线程上下文类加载器逆向加载实现。有这两个例子，这题就是满分结构。

07类卸载：三个条件缺一不可

  • 该类所有实例都已被回收；
  • 加载它的 ClassLoader 已被回收；
  • 对应的 Class 对象 没有被任何地方引用（不能通过反射访问）。

Bootstrap 加载的核心类几乎不可能卸载；应用类想卸载，前提是连类加载器一起换掉——这正是热部署的实现原理，也是元空间泄漏的源头：旧 loader 若被任何对象引用着，它加载的全部类都卸不掉，每次热部署净增一批类。排查思路链 第 06 章。

08高频追问与陷阱

  • 追问链：Class.forName vs classLoader.loadClass →→ forName("X") 加载 + 初始化（执行 clinit）；loadClass 只加载不初始化（到链接为止）→ 追问：谁用 loadClass → 框架延迟初始化（如容器注册阶段只拿 Class 信息）。
  • 追问链：静态内部类单例为什么懒加载且线程安全 →→ 被动引用：持有内部类的实例字段不触发外部类初始化；getInstance 触发内部类初始化，clinit 由 JVM 保证单线程执行——类加载机制替你做了双重检查锁的事。
  • 追问：接口有 clinit 吗 →→ 接口不能有 static 块，但接口变量默认 public static final；接口的"初始化"只在其静态变量非常量或 default 方法被实现类用到时发生——知道接口初始化"惰性更强"即可。
  • 追问：一个类可以被打包进两个 jar 让两个加载器各加载一次吗 →→ 可以，JVM 视为两个不同的 Class，instanceof 互相为 false，强转抛 ClassCastException——依赖冲突"同一个类两个版本"诡异异常的根源。
  • 陷阱：准备阶段 static final 就有值 →→ 只对编译期常量（字面量/常量表达式）成立；static final int X = new Random().nextInt() 不是编译期常量，准备期仍是零值。
  • 场景题：SPI 加载不到实现类，怎么排查 →→ ① META-INF/services 文件名/内容写错；② 当前线程上下文类加载器不对（容器线程被改过）；③ 实现类不在 classpath——按这三步走就是实战口径。
