02泄漏 vs 溢出：先辨析再谈治理

内存溢出 OOM内存泄漏 Leak
定义分配内存时空间不够，直接抛 OutOfMemoryError不再使用的对象仍被引用着，GC 回收不掉，占用持续累积
类比水管不够粗（容量问题）水池的排水口被堵了（该流走的流不走）
关系泄漏的终点通常是溢出——泄漏是因，OOM 是果；但溢出不一定是泄漏（也可能真的是容量不够/大对象）
治理方向扩容 / 减小单次占用 / 修泄漏断引用（remove/close/清集合）、限容量的数据结构

答题口径：先一句"泄漏是因、溢出是果"，再补"排查 OOM 第一步是判断属于哪类：泄漏（加内存只延缓）还是容量不足（加内存真有效）"——判断力的展示就在这一句。

03八大泄漏场景 ⭐⭐（每个都要能讲"为什么"）

#场景为什么会泄治理
①静态集合只加不减static Map/List 生命周期 = 类生命周期 = 应用全程；放进去的对象永远可达（GC Root：静态变量）带淘汰的缓存（LRU/Caffeine/TTL）；注册表加注销
②无界缓存本地缓存无容量上限（笔记：本地缓存清理策略缺失），流量大数据全进，最终撑爆maximumSize + expireAfterWrite；超大量放 Redis
③ThreadLocal 忘 remove线程池线程长存 → Entry 的 value 强引用链不断（下一节专讲）try-finally remove（02-concurrency/09主场）
④资源未关闭流 / 连接 / Channel 未 close，底层 fd 与堆外缓冲堆积（不止内存问题，fd 泄漏更早爆）try-with-resources（01-java/07）
⑤监听器/回调未注销注册进事件源的监听器持有外部大对象；事件源长存 → 引用链常在成对 register/unregister；弱引用事件源
⑥无限增长的 Session/上下文笔记原文场景：session、登录态等按用户累积，无过期策略过期时间 + 容量上限 + 淘汰
⑦类加载器泄漏（热部署）旧 ClassLoader 被一个对象引用着 → 它加载的所有 Class 及静态字段卸载不掉 → Metaspace 涨（第 02 章卸载三条件的反面）容器重启前清引用；升级框架版本修已知泄漏
⑧变了的 Hash key对象 put 进 HashSet/HashMap 后修改了参与 hash 的字段 → remove 时 hash 定位不到原槽 → 永远删不掉（"对象自己藏起来了"）可变对象不做 key，或 key 字段不可变

共同规律：所有泄漏 = "长生命周期对象，间接持有了短生命周期对象的引用"。排查任何泄漏都回到这句话：找到那条"不该存在的引用链"（第 07 章 MAT 的 GC Root 链就是干这个的）。

04ThreadLocal 的 JVM 视角（跨章联动）

  • 引用链图与"弱引用救 key 不救 value"的完整推导在 02-concurrency/09 并发容器（主场，含 expungeStaleEntry）；本板块只补 JVM 视角的两句：
  • 为什么 GC 不帮忙：泄漏的 value 沿"线程池 worker → threadLocals → Entry → value"这条强引用链可达——它不是垃圾，是"被错误保活的对象"；GC 只回收不可达对象，无能为力。
  • dump 里长什么样：MAT 里看到大量 ThreadLocal$ThreadLocalMap$Entry 且 value 是大对象、key 为 null——就是它。线上"内存涨、但堆 dump 里全是 Entry"是典型指纹。

05OOM 类型速查 ⭐（六个都要认得）

类型发生区域典型成因第一动作
Java heap space堆泄漏 / 真容量不足 / 大对象（一次查百万行）dump + MAT（第 07 章流程）
GC overhead limit exceeded堆98% 时间在 GC 只回收回 2%（临 OOM 的"放弃信号"，比 OOM 更早出现）同上；通常离 heap space OOM 只差临门一脚
Metaspace元空间动态类爆炸：CGLIB/Spring 代理、Groovy 脚本、反射代理类；类加载器泄漏（场景⑦）jstat -gc 看 M 区；看类加载数（jstat -class）
unable to create new native thread进程内存（栈）线程无限创建：new Thread 失控、线程池配置错误、没有熔断的并发工具jstack 数线程 + 按线程名聚类
Direct buffer memory直接内存NIO/Netty 堆外未释放；MaxDirectMemorySize 到顶NMT（NativeMemoryTracking）/ Netty 泄漏检测
Requested array size exceeds VM limit堆申请的数组超过 VM 上限（如一次 load 2GB 文件进 byte[]）改流式处理，别一次性读

Metaspace"重启就好、几天又满"的解答（高频）：泄漏的是类不是对象——重启清掉全部类加载器所以"好"；运行中动态类不断生成且旧 loader 卸不掉（场景⑦），所以"又满"。能讲出这个循环，就是真的排查过。

06OOM 标准处置（笔记 OOM 节全量并入）

事前：把"黑匣子"提前装好（笔记：提前设计 dump）

# 这两个参数必须在第一次 OOM 前就配上 —— 事后加等于没加
-XX:+HeapDumpOnOutOfMemoryError              # OOM 瞬间自动导出堆快照
-XX:HeapDumpPath=/data/dumps/                # dump 文件落盘目录（注意磁盘容量）
-Xlog:gc*,safepoint:file=/data/logs/gc.log   # GC 日志（JDK 9+ 统一日志语法）

事后四步（笔记：日志复现 → MAT → 定位 → 对症下药）

  1. 收集：dump 文件（自动导出的或 jmap 手动的）+ GC 日志 + OOM 前后的监控曲线；本地能复现最好（笔记：看日志复现）。
  2. 分析：MAT（Eclipse Memory Analyzer，笔记指定工具）打开 dump → Leak Suspects 报告先看自动怀疑点 → Dominator Tree 找"支配内存最大"的对象。
  3. 定位：对可疑对象查 GC Root 引用链（Path to GC Roots，排除弱/软引用）——谁在保活它？答案会指向场景表里的某一条（静态 Map？Entry？未关的流？）。
  4. 对症下药（笔记：代码优化、对症下药）：断引用 / 换有界结构 / 修关闭逻辑 / 必要时才调参数扩容——参数是最后一格。

07高频追问与陷阱

  • 追问链：OOM 加内存行不行 →→ 先分类：泄漏 → 加内存只是推迟 OOM 时间（曲线右移）；容量不足（流量真实增长）→ 有效；大对象（一次性巨查询）→ 无效，会立刻再 OOM。
  • 追问链：Metaspace 满的排查 →→ jstat -class 看类加载数趋势 → 疑动态代理/脚本 → dump 里看 ClassLoader 数量与类名分布 → 治理：缓存代理类、限制脚本生成、修 loader 泄漏。
  • 陷阱：GC 回收了弱引用的 key，所以 ThreadLocal 没有泄漏 →→ key 是弱引用会被回收，value 是强引用仍被 Entry 持有——只清了一半（完整链 02-concurrency/09）。
  • 陷阱：young 代频繁 GC 就是泄漏 →→ 不一定；Young GC 频繁但正常回收、老年代基线不涨，通常只是流量大/新生代小——判据在老年代基线是否缓涨（第 07 章 jstat 判读）。
  • 场景题：堆 dump 里 40% 是某个 Cache 对象，结论？→→ 不一定是泄漏！缓存本来就该占内存——要看它有没有容量上限、命中率是否合理、是否随时间无限涨。"占比大"≠"泄漏"，"只增不减"才是。
  • 追问：堆外泄漏（Direct buffer）怎么查 →→ NMT（-XX:NativeMemoryTracking=summary + jcmd VM.native_memory）看 Commit 趋势；Netty 开 -Dio.netty.leakDetection.level=paranoid；治本：池化 + 规范 release（第 07 章工具节）。
