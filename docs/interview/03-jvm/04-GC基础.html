02判断对象存活 ⭐

引用计数法（笔记并入：反面教材）

  • 规则：被引用 +1，引用失效 -1，计数为 0 即可回收（笔记原文）。实现简单、判定高效，但循环引用永远不为 0——A 引用 B、B 引用 A，谁也死不了。主流 JVM 不用它（Python/部分语言用"循环检测器"补救）。

可达性分析（主流方案）

  • 从 GC Roots 出发向下搜索，能到达的对象存活；到达不了的，判定可回收。循环引用的对象只要从 Roots 够不着，照样回收——根治循环依赖问题。
GC Roots（五种，背全 ⭐）说明
虚拟机栈中引用的对象各线程栈帧的局部变量（方法参数、临时变量）——最重要的 Roots
方法区/元空间中类静态变量引用的对象static 字段（JDK 7+ 静态变量随 Class 在堆，但作为 Roots 的地位不变）
方法区中常量引用的对象字符串常量池等常量引用
本地方法栈 JNI 引用的对象native 代码持有的对象
JVM 内部引用与活跃线程基本类型 Class 对象、常驻异常对象、系统类加载器；正在运行的线程本身

finalize：对象的"一次逃生"（笔记并入）

  • 被判死亡的对象若重写了 finalize() 且未执行过，会被放进 F-Queue 由低优先级线程执行——finalize 里把自己赋给某个引用即可逃生一次。
  • 笔记原文的三条批判照收：不确定什么时候调用（等 GC 心情）、给 GC 添麻烦（可能逃过回收）、JDK 9 起 deprecated。生产结论：资源清理用 try-with-resources，别碰 finalize。

答题口径：先"引用计数有循环引用问题，HotSpot 用可达性分析"，然后主动把 GC Roots 报全——多数人只能报两三种，五种报齐这一题就直接拉开差距。

03四种引用 ⭐⭐（笔记并入 + 场景补全）

引用回收时机实际应用（面试要能报出）
强引用 Strong永不回收：只要强引用在，OOM 也不回收（笔记：最常见的，不会被清理）普通赋值 Object o = new Object()；ArrayList 里放着的都是强引用
软引用 Soft内存不足时才清理（笔记：有用但非必要，避免 OOM）内存敏感缓存（图片缓存、页面缓存）：内存够就留着，快 OOM 了自动让路
弱引用 Weak只要发生 GC 就清理（笔记原话）WeakHashMap（笔记：缓存生命周期很短）；ThreadLocalMap 的 Entry（key 弱引用，链 02-concurrency/09）
虚引用 Phantom不影响对象生命周期，不能 get 到对象（笔记），唯一作用：对象被回收时收到"通知"堆外内存回收：DirectByteBuffer 的 Cleaner 机制（配合引用队列回收 native 内存，链 第 01 章 直接内存）
  • 引用队列（ReferenceQueue，笔记并入）：软/弱/虚引用创建时可关联一个 ReferenceQueue；引用的对象被清理时，该引用本身入队——"对象死了"这件事的通知机制，虚引用清理堆外内存就靠它。
  • 强度排序：强 > 软 > 弱 > 虚。记忆锚点：软 = 内存不足才死（保数据）；弱 = GC 就死（保时效）；虚 = 死时通知（管身后事）。

04三大回收算法（笔记并入，优缺点照收）

算法流程优点缺点（笔记口径）
标记-清除
Mark-Sweep		标记：从 GC Roots 标记所有可达对象；清除：遍历堆回收未标记的效率高、实现直接（笔记：效率高）内存碎片（笔记：内存地址不连续）——碎片多了大对象放不下，提前触发下一次 GC
复制
Copying		内存分两块只用一块；存活对象复制到另一块，整块清空已用区无碎片、分配快（指针碰撞）（笔记：没有碎片、简单高效）内存利用率只有 50%（笔记原文）；存活对象多时复制成本高
标记-整理
Mark-Compact		标记所有可达对象 → 存活对象向一端移动 → 清理边界外内存无碎片 + 内存利用率高移动对象成本高，需要 STW（笔记原文）——存活对象多时最痛

勘误说明：原笔记此处把"复制"算法误写成了"标记-整理"标题（内存分两块/利用率 50% 的是复制），已修正。三个算法名的对应关系按本表背：碎片问题选整理、效率问题选清除、新生代选复制。

为什么没有"最好"的算法：清除怕碎片、复制怕存活多、整理怕移动贵——三条互相矛盾的代价线，催生了分代收集：按对象存活特征分区，各区用各自最划算的算法（下一节）。

05分代收集与堆布局（笔记 Minor GC 全流程并入）

分代假设：对象存活两极分化

  • 绝大多数对象朝生夕死（请求级临时对象）；熬过数次 GC 的对象大概率会活很久（配置、缓存、连接）。把两者混在一起治理，哪种算法都吃亏——分开治理。

Minor GC 完整流程（笔记原文展开）

① 分配：新对象优先在 Eden 区分配（TLAB 内免竞争，见第 03 章）
② 填满：Eden 空间不足 → 触发 Minor GC
③ 标记：对新生代做可达性分析，标记存活对象
④ 复制清除：
     Eden + 正在使用的 Survivor（如 S0）的存活对象 → 复制到另一块
     空的 Survivor（S1）；【存活对象年龄 +1】；直接清空 Eden 和 S0
⑤ 晋升：年龄达到阈值（默认 15）→ 晋升（Promote）到老年代
⑥ 例外：大对象直接进老年代；S1 装不下的存活对象也直接进老年代
  • 为什么 Survivor 是两块：一块用一块空，复制后有干净的目标地；如果只有一块，Eden 存活对象复制进去后自己也碎片化了。8:1:1 是因为新生代存活率通常 < 10%——10% 的 Survivor 空间足以接住，90% 的 Eden 留给分配。
  • 老年代用标记-清除或标记-整理（笔记：对老年代标记清除或标记整理）：存活率高，复制算法代价爆炸。CMS 用清除（避免 STW 整理）、G1 用整理（Region 间复制），差异在 第 05 章。

06晋升老年代：四条规则 ⭐⭐

#规则要点
①年龄达到阈值-XX:MaxTenuringThreshold=15（上限 15 的原因：对象头 4 位年龄字段，链 第 03 章）
②动态年龄判断Survivor 中同龄对象总大小超过 Survivor 一半，该年龄及以上的对象直接晋升——不等熬到 15，防止 Survivor 被"中生代"挤爆
③大对象直接进老年代-XX:PretenureSizeThreshold：大对象（大数组/大字符串）避免在 Eden/Survivor 间反复复制，一步到位
④空间分配担保Minor GC 前检查：老年代可用 < 历次晋升平均大小 → 直接 Full GC 先腾地方（老年代都装不下就别 Y 了，链下一节）

高频陷阱："熬过 15 次 Minor GC 就进老年代"只对了一半——动态年龄判断（同龄超半提前晋升）和大对象直入经常先发生。答"什么时候进老年代"必须四条全报。

07Minor · Major · Full GC

类型回收区域触发速度
Minor / Young GC新生代（Eden + 一个 Survivor）Eden 满快（存活少、复制少），频繁但便宜
Major GC / Old GC老年代老年代空间不足（含 CMS 的并发收集）慢（存活多）
Full GC整堆 + 方法区（元空间）见下六种最慢，STW 最重——一切调优都在少 Full GC

Full GC 的六种触发（背全 ⭐⭐）

  1. 老年代空间不足（晋升放不下 / 大对象直入失败）;
  2. 空间分配担保失败：Minor GC 前检查老年代可用 < 历次晋升平均值；
  3. 元空间不足（类加载到 MetaspaceSize 水位 / 动态类爆炸）；
  4. System.gc() 建议（显式 GC，多数收集器直接 Full GC——CMS 可配 -XX:+ExplicitGCInvokesConcurrent 改并发）；
  5. CMS 的 promotion failed / concurrent mode failure：并发回收期间对象晋升失败 → 退化为 Serial Old 单线程整理（链 第 05 章）；
  6. jmap -histo:live 等命令触发的Full 统计（排查时注意别在生产乱敲，链 第 07 章）。

08高频追问与陷阱

  • 追问链：为什么新生代用复制 →→ 存活率低，复制成本最小且无碎片 → 为什么老年代不用 → 存活率高，复制=全量搬家；用清除（CMS）或整理（G1）。
  • 追问链：可达性分析怎么面对并发修改 →→ GC 标记时应用还在跑，对象引用还在变 → 三色标记 + 漏标两种解法（增量更新/SATB）——这是 第 05 章 CMS vs G1 的核心分叉点，先埋个钩子。
  • 追问：GC Roots 为什么不含"堆里对象引用的对象" →→ 可达性分析的搜索空间就是从 Roots 出发的引用闭包，堆内互相引用只是闭包内部的边——从任何 Root 够不着的子图整体回收（循环引用能死的原因）。
  • 陷阱：软引用缓存 = 绝对安全 →→ 软引用在内存临界时成批死亡可能引发回收风暴（缓存集体失效 → 重建风暴）；大缓存要用容量上限（Caffeine/LRU）而不是只靠软引用。
  • 陷阱："Full GC 就是 Major GC" →→ 多数语境 Full ≈ 整堆 + 元空间；老年代收集器是 CMS 时，"Major/CMS GC"（并发、老年代）与 Full（STW 退化）要分开说，链 第 05 章。
  • 场景题：接口每请求 new 大 list，Full GC 频繁 →→ 优先怀疑过早晋升（大对象直入或 Survivor 太小）→ 看 GC 日志里晋升量与对象年龄分布 → 分页/流式处理减少大对象，链 第 07 章的日志分析法。

09面试自查清单

  1. 引用计数 vs 可达性分析（循环引用）一句话；GC Roots 五种能报全。
  2. finalize 的"一次逃生" + JDK 9 deprecated 的三条批判。
  3. 四种引用的回收时机 + 每种至少一个真实应用（WeakHashMap/ThreadLocal/Cleaner）。
  4. ReferenceQueue 的通知机制与虚引用回收堆外内存的关系。
  5. 三大算法的流程与优缺点表能默写，说得出"分代就是按存活率分算法"。
  6. Minor GC 六步流程；两块 Survivor 与 8:1:1 的原因。
  7. 晋升老年代四条规则（阈值/动态年龄/大对象/担保）一条不落。
  8. Full GC 六种触发能数全，并与第 05 章 CMS 退化场景接得上。
