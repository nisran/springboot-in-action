03jstat 与 GC 趋势判读 ⭐

jstat -gcutil <pid> 1000     # 每秒输出一次各代使用百分比与 GC 次数
  S0     S1     E      O      M     YGC   YGCT   FGC  FGCT   GCT
  0.00  95.2  80.3   61.4  94.1   523  12.30    8   9.87  22.17
# S0/S1: 两块 Survivor  E: Eden  O: 老年代  M: 元空间
# YGC/YGCT: Young 次数/总耗时   FGC/FGCT: Full 次数/总耗时   GCT: GC 总耗时

两条判读铁律（泄漏判定的核心）

  • 健康曲线：老年代锯齿——Full GC / 并发回收后 O 列能跌回原位。锯齿的"牙"高一点没关系，只要基线不涨。
  • 泄漏曲线：老年代阶梯——每次回收后 O 的低点一次比一次高（基线缓涨），最终逼近 100% 稳定 OOM。看到阶梯 → 启动 第 05 节泄漏流程。
  • 加分判读：YGC 次数猛涨但 O 不涨 → 多半是流量大/新生代小；FGC 每次耗时（FGCT/FGC）越来越长 → 老年代对象越来越多或碎片化（CMS）。

04jmap 与 dump：看堆里有什么

# ① 直方图：按类统计对象数与占用（最轻量，先看这个）
jmap -histo <pid> | head -20
#    num   #instances   #bytes  class name
#    1:      1203456   512MB    [B                    ← byte[] 异常大？查大对象来源
#    2:       890123   301MB    java.util.HashMap$Node ← 静态 Map 灌爆？

# ② 完整堆快照（给 MAT 用）
jmap -dump:live,format=b,file=heap.hprof <pid>   # live: 只dump存活对象

生产意识题：线上能直接 jmap dump 吗？⭐dump 需要借安全点（safepoint）暂停所有线程、串行遍历整堆——大堆（几十 G）会停顿几十秒，线上高峰期执行等于主动事故。正确姿势：① 低峰期摘流量后执行；② 优先用 -XX:+HeapDumpOnOutOfMemoryError 提前埋好自动 dump；③ 只要粗略分布先用 -histo（轻得多）。能主动说出风险与替代方案，就是"上过生产"的信号。

MAT 三板斧：Leak Suspects（自动怀疑报告）→ Dominator Tree（谁支配最多内存）→ Path to GC Roots（谁在保活，排除弱/软引用）——链 第 06 章处置四步。

05CPU 100% 排查全流程 ⭐⭐（笔记 top+jstack 并入完整化）

# ① 找到吃 CPU 的【进程】
top                              # 记下 Java 进程 pid，确认 %CPU ≈ 100

# ② 找到进程里吃 CPU 的【线程】
top -Hp <pid>                    # -H 显示线程级，记下最耗 CPU 的线程 pid（如 25390）

# ③ 线程号转 16 进制（jstack 里线程 nid 是 16 进制）
printf "%x\n" 25390              # → 632e

# ④ 拿线程栈，定位到具体代码行
jstack <pid> | grep -A 30 "nid=0x632e"
#    "biz-worker-3" #33 runnable  ← 看 RUNNABLE 的栈顶：
#        at com.xx.OrderService.calcPrice(OrderService.java:87)  ← 就是它

# ⑤ 对症下药（见下方四类原因）

CPU 高的四类原因（笔记四条并入展开）

原因栈上长什么样处置
死循环/低效算法业务栈帧 RUNNABLE 停在同一行改代码（边界条件、正则回溯、HashMap 死循环式 jdk7 bug 已成历史）
频繁 GC最耗 CPU 的是 GC task thread / VM Thread，业务线程多在 BLOCKED/GC 相关转 jstat 判读：泄漏？堆小？大对象？——GC 线程吃 CPU 是"果"，堆的问题才是"因"
死锁jstack 末尾直接打印 Found one Java-level deadlock，点名互相持有的锁按提示修锁顺序 / tryLock 超时（链 02-concurrency/11）
密集运算业务栈正常、确实是计算（序列化、加密、报表）异步化/扩容/优化算法——这是"业务真需要"，不是故障

OS 视角分流（去重约定）：本流程是 JVM 主阵地；us 高走本章，sy/si 高、load 高但 CPU 不高的 OS 层问题（上下文切换、页错误）在 12-os 排查工具。一句"先看 top 里 us 还是 sy"就能体现分流意识。

06内存泄漏排查全流程 ⭐

# ① 确认趋势（是不是泄漏）
jstat -gcutil <pid> 5000        # 老年代基线 30 分钟内缓涨？→ 疑似泄漏
# ② 低峰期抓证据
jmap -dump:live,format=b,file=heap1.hprof <pid>    # 第一份 dump
# （间隔一段时间再抓第二份，对比增长更硬核）
# ③ MAT 分析
#    Leak Suspects → Dominator Tree → 找异常大的支配者
# ④ 找到"谁在保活"
#    右键对象 → Path to GC Roots → exclude weak/soft references
#    → 链头通常是：static 字段 / ThreadLocal Entry / 未关闭的连接 / ClassLoader
# ⑤ 回到代码修引用（对照第 06 章八大场景表对症）
  • 区分泄漏 vs 容量不足（高频追问）：泄漏——回收后基线持续上涨、dump 里同一批对象只增不减；容量不足——锯齿正常但整体水位高、dump 里是"合理的业务对象"（正常缓存/正常请求积压）。前者修引用，后者扩容或降占用。
  • 加分的硬核操作：两份 dump 对比（MAT 的 compare baskets / histo diff）——只涨不跌的类就是嫌疑对象，比单份 dump 有说服力得多。

07Arthas：生产在线诊断

  • 为什么生产爱用：attach 到运行中进程、不重启、开箱即用、开销小——把"重启试试"变成"当场看"。
  • dashboard：一屏总览（线程/内存/GC）——替代 jps+jstat+top 的第一眼。
  • thread -n 3：最耗 CPU 的 3 个线程栈（第 05 节四步的命令级平替）；thread -b：直接找阻塞源头/死锁。
  • profiler start/stop：生成火焰图（async-profiler），CPU 热点一目了然——比单看某个线程更全局。
  • watch 类 方法 '{params,returnObj,throwExp}'：不重启观察线上方法出入参——排查"偶发坏数据"神器。
  • heapdump：等同于 jmap dump（同样注意停顿风险）。

答题时给一个自己的案例最有说服力，例如："一次接口偶发 500ms 毛刺，arthas trace 方法链发现是某个缓存未命中走了全量 DB 查询"——工具 + 场景 + 结论三件套。

08常用参数速查（笔记参数节并入扩展）

类别参数说明
堆-Xms = -Xmx初始 = 最大（笔记列入），避免动态扩缩震荡（链 第 05 章美团案例）
-Xmn / -XX:SurvivorRatio=8新生代大小 / Eden:S 比例（G1 下不要手动设 Xmn）
-XX:MaxTenuringThreshold=15晋升年龄上限
元空间-XX:MetaspaceSize / MaxMetaspaceSize前者是首触 Full GC 的水位，后者才是上限（链 第 01 章）
G1（笔记并入）-XX:MaxGCPauseMillis=200最大 GC 停顿（毫秒）——软目标，设太小反而退化（链 第 05 章）
-XX:G1HeapRegionSize=4mRegion 大小（笔记注解：region 一半要能承受 90% 的对象——避免过多 Humongous）
事故三件套-XX:+HeapDumpOnOutOfMemoryErrorOOM 自动 dump（必须事前配）
-XX:HeapDumpPath=...dump 落盘目录
-Xlog:gc*:file=gc.logGC 日志（JDK 9+ 语法；8 用 -XX:+PrintGCDetails）

09GC 日志判读（一段样例走一遍）

[gc,start] GC(412) Pause Young (Normal)
[gc,heap] GC(412) Eden regions: 612->0(612)      ← Eden 612 个 Region 清空
[gc,heap] GC(412) Old regions: 120->128(512)      ← 老年代 120→128：晋升了 8 个 Region
[gc,heap] GC(412) Humongous regions: 2->2         ← 大对象区域没变
[info] GC(412) Pause Young 210M->96M(1G) 23.5ms   ← 堆 210M→96M，停顿 23.5ms ✓

# 判读三问：
# ① 停顿多少？——23.5ms 对目标 200ms，健康
# ② 每次 Young GC 晋升多少？——8 Region：偏高的话查"过早晋升"（对象没死透就进老年代）
# ③ 老年代整体趋势？——拉长时间轴看基线（第 03 节 jstat 同款判读在日志层的版本）
  • 过早晋升的日志指纹（美团文方法）：每次 Young GC 晋升量大、但老年代涨完很快又跌（晋升进去的对象接着死了）——说明 Survivor 装不下/年龄阈值动态判断提前放行，治法在 第 05 章 CMS 案例。
  • GC 日志是"事后诸葛"里信息密度最高的材料：次数、耗时、各代变化、晋升量全在里面——排查 GC 问题的顺序永远是 jstat 看趋势 → gc 日志看细节 → dump 看对象。

10调优心法（7 年经验的答法）

  1. 先观测后动手：任何参数调整前必须有基线数据（jstat/GC 日志/监控），调完有对比——没有 before/after 的调优是玄学。
  2. 多数"JVM 调优"其实是修代码：一次查百万行、无界缓存、忘 remove、循环里拼大字符串——参数治不了这些。把最常见的真实案例说出来，比背参数表值钱十倍。
  3. 一次只动一处：多参数同改等于不知道谁起作用；改一处、压测、对比、再决定。
  4. 别抄模板：网上"-Xmx4g -XX:+UseG1GC 万金油"式配置不问场景；参数跟着"堆大小 / 延迟诉求 / 收集器"三要素走（链 第 05 章选型三问）。

11高频追问与陷阱

  • 场景题：服务突然变慢，先查什么 →→ 开场分流三连：top 看 CPU（us/sy）→ jstat 看是不是 GC 停顿（FGC 涨没涨）→ 看监控是不是下游/DB 慢。三条路各走一步再深入——展示的是"分诊"意识而不是上来就背 jstack。
  • 场景题：Full GC 频繁五步 →→ ① jstat 确认频率与耗时 → ② GC 日志看触发原因（promotion failed？元空间？System.gc？）→ ③ dump 看老年代里是什么 → ④ 对照六种触发（链 第 04 章）定位 → ⑤ 治理（修泄漏/调新生代/换收集器）。
  • 追问：为什么 dump 要安全点 →→ 遍历堆对象需要一致性视图，所有线程停在安全点才能保证堆结构不被并发修改——顺带解释了 jmap 停顿的本质（第 04 节）。
  • 陷阱：jstack 抓一次就下结论 →→ 单次快照可能正好错过；CPU 问题抓 3~5 次间隔几秒，反复出现在同一栈帧才算实锤。
  • 陷阱：把调优答成背参数 →→ 面试官要的是案例与方法论：观测→定位→改动→验证的闭环（第 10 节四条心法就是答案骨架）。
