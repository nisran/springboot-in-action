02对象创建五步 ⭐⭐

new Object()
   │
   ① 类加载检查：常量池定位符号引用 → 类是否已加载/解析/初始化过？
   │    没加载 → 先走第 02 章的类加载（这是两章的接缝）
   ② 分配内存：从堆中划出一块确定大小的空间
   │    规则A 指针碰撞：堆绝对规整（标记-整理后）→ 移动分界指针即可
   │    规则B 空闲列表：堆碎片化 → 维护"哪里空闲"的列表去匹配
   │    并发安全：TLAB（见下）或 CAS + 失败重试
   ③ 零值初始化：内存全部置零 —— 这就是字段不赋值也有默认值的原因
   ④ 设置对象头：Mark Word（hash/GC年龄/锁标志）+ 类型指针（哪个类的实例）
   ⑤ 执行 <init>：构造函数 + 字段初始化 —— Java 代码视角的"对象诞生"

TLAB：分配的并发安全答案 ⭐

  • 堆是共享的，两个线程同时分配会争抢同一块地址。JDK 默认用 TLAB（Thread Local Allocation Buffer）：Eden 里给每个线程划一小块私有分配缓冲，线程在自己的 TLAB 里分配——纯指针移动、无竞争；TLAB 用完再申请新的一块（申请时才需要同步）。
  • TLAB 装不下的大对象（或绕过场景）用 CAS + 失败重试直接在堆上分配。
  • -XX:+UseTLAB 默认开启；"分配"这个动作的答案链：优先栈上（逃逸分析）→ TLAB → Eden 堆 → 大对象直入老年代。

答题口径：五步报完后主动补一句"其中 ③ 的零值初始化解释了字段默认值、② 的 TLAB 解释了高并发下分配为什么快"——把步骤和"现象"挂钩，比背流程高一个层次。

03内存布局：对象头 · 实例数据 · 对齐填充

普通对象（64 位 JVM，开指针压缩）
┌───────────────────────────────────────┐
│ Mark Word（8B）：hash / GC 年龄 / 锁标志 │  ← 对象头
│ 类型指针 KlassPointer（4B 压缩/8B）      │
├───────────────────────────────────────┤
│ 实例数据：字段值（long/double 对齐排列…） │  ← HotSpot 字段重排优化
├───────────────────────────────────────┤
│ 对齐填充：补齐到 8 字节的整数倍           │
└───────────────────────────────────────┘
数组对象额外多一块 4B 的 length（所以 new int[0] 也有 16B）
new Object() = 8 (MarkWord) + 4 (Klass) + 4 (填充) = 16 字节
  • Mark Word 到底是什么：每个对象自带的 8 字节元数据槽位（64 位 JVM 的一个机器字长，HotSpot 源码里是 oopDesc 的第一个字段 _mark）。JVM 让它分时复用——对象处于不同阶段时，同一块 8 字节被写入不同元数据，靠末 2 位锁标志位判别当前含义。名字由来：Mark 源自 GC 标记用途，Word = 机器字长。为什么要复用？堆里对象以亿计，new Object() 的 16B 里头已占 12B——每种元数据各开一个字段，头开销吃不消。
状态（64 位 JVM）末 2 位Mark Word 里存什么
无锁01identity hashCode(31) + 分代年龄(4)
偏向锁 *01（可偏向位=1）持有线程 ID(54) + epoch(2)——与 hashCode 抢同一片位，调过 identity hashCode 的对象不能再偏向
轻量级锁00指向栈帧 Lock Record 的指针(62)——原 Mark Word 先复制进 Lock Record（Displaced Mark Word），解锁时抄回
重量级锁10指向 C++ ObjectMonitor 的指针(62)
GC 标记中11GC 运行期临时征用：标记位 / 转发指针——名字里的 Mark 就源于此

* 偏向锁 JDK 15 废弃（JEP 374）、JDK 18 代码移除，现代 JVM 只剩 无锁→轻量级→重量级 三级。锁升级主线（各级为什么存在、怎么逐级膨胀）在 02-concurrency/03 锁升级——这里认"它是什么"，那里讲"它怎么变"。

JOL 实测（JDK 21，ClassLayout.parseInstance(o).toPrintable()，同一对象的四个时刻——末 2 位的变化肉眼可见）：

① 刚 new（未调 hashCode）  0x0000000000000001   末2位 01 无锁；age 0，hash 还没算
② 调过 hashCode()         0x0000002a65fe7c01   末2位 01 仍无锁；31 位 hash 写入高位
③ synchronized 持有中     0x000000016f552b00   末2位 00 轻量级锁 → 指向栈上 Lock Record
④ 解锁后                  0x0000002a65fe7c01   末2位 01；hash/age 原样抄回
   —— ③④ 连看 = Displaced Mark Word 机制实证：62 位拿去存指针，原数据先存栈再恢复
  • GC 年龄用 4 位存储 → 上限 15，这就是 -XX:MaxTenuringThreshold 不能超过 15 的底层原因。
  • 验证工具：JOL（Java Object Layout），依赖 org.openjdk.jol:jol-core，一行 ClassLayout.parseInstance(obj).toPrintable() 打印真实布局；JDK 15+ 紧凑对象头实验（JDK 25 默认化）可把对象头压到 8 字节，见 01-java/14 新特性。

04指针压缩（Compressed Oops）

  • 问题：64 位 JVM 里引用是 64 位，对象里的引用字段、Klass 指针都变大一倍，小对象们白白多耗内存。
  • 做法：堆 ≤ 4GB 时，用 32 位"地址偏移"代替 64 位指针（8 字节对齐保证偏移可反推真实地址），-XX:+UseCompressedOops 默认开启。
  • 32GB 临界（高频）：偏移量按 8 字节粒度编址，32 位偏移最多表示 32GB。堆一旦超过 32GB，压缩失效、全部指针变回 64 位——内存不增反降（对象头/引用膨胀吃掉的比多给的堆还多）。实践经验：要么 ≤ 31GB，要么直接跳到 40GB+ 才划算。

陷阱："堆 33GB 比 31GB 能放更多对象"——错，33GB 时指针压缩关闭，实际可用容量反而可能更小。这是 JVM 参数里少见的"非单调"行为，也是这题的价值所在。

05访问定位：句柄池 vs 直接指针

栈帧里的引用怎么找到堆里的对象（Java 侧语义在 01-java/02 面向对象已讲，这里补 JVM 视角的利弊表）：

方式结构优点缺点
句柄池引用 → 句柄（稳定地址）→ 对象本体GC 移对象只改句柄里的指针，引用本身不动多一次寻址开销；句柄池本身占内存
直接指针引用直接指向对象本体（对象头里带类型指针）访问快（省一次跳转）GC 移动对象要更新所有引用（但 GC 本来就要遍历）

HotSpot 用直接指针——访问是最高频操作，用移动成本换访问速度。追问点：G1 这类会整理内存的收集器为什么也敢用直接指针？因为移动发生在 STW 或读屏障保护下，引用更新是收集器自己负责的。

06字符串常量池与 intern ⭐

位置演变（先答对位置再谈其他）

  • JDK 6 及以前：字符串常量池在永久代；JDK 7 起移入堆中（永久代紧张 + 想让堆 GC 顺手回收无引用的池内字符串）。intern 的行为也随之改变。

经典题一：new String("ab") 创建几个对象

String s = new String("ab");
// 答案：1 或 2 个
//  · 堆里 new 的这个对象：一定创建
//  · 池里的 "ab"：如果此前池中没有（首次出现），字面量在类加载的
//    解析/首次使用时入池 —— 也算一个；池里已有就只有 1 个
// 补充：byte[] value 数组（JDK 9 起是 byte[]）不算"new 出的对象"层次里的答案

经典题二：intern 的 JDK 7 变化（区分度题）

String s = new String("a") + new String("b");   // 堆里动态拼出 "ab"（StringBuilder）
// 此刻：池中没有 "ab"（运行期拼接不进池），堆里有一个 s 指向的 "ab"

String interned = s.intern();
System.out.println(s == interned);
// JDK 6：false —— intern 把对象复制一份进永久代，返回永久代里那个
// JDK 7+：true  —— 池中首次出现时，intern 直接把【堆里这个对象的引用】
//                   存入池中并返回它 —— 不再复制，s 与 interned 是同一个

String lit = "ab";        // 此时池里已有（指向 s 那个对象）
System.out.println(lit == s);   // JDK 7+ true；JDK 6 false —— 经典变体
  • intern 语义：池里已有 equals 相等的字符串 → 返回池内那个；没有 → 入池并返回（JDK 7+ 存引用，JDK 6 复制本体）。
  • 编译期折叠："a" + "b" 两个字面量拼接，编译器直接常量折叠成 "ab" 入池——和运行期 new String("a")+new String("b")（StringBuilder.append，不进池）路径完全不同，这是这类题的判断关键。

7 年经验口径：别在生产上用 intern 做大规模去重优化——JDK 7 后池在堆里能被回收，但 StringTable（Hashtable 结构，默认 1009 桶）在大量 intern 下哈希碰撞严重；要做重复字符串压缩优先看 -XX:StringTableSize 或业务级缓存。

07逃逸分析与"栈上分配"

  • 逃逸分析是 JIT 的分析手段：判断对象是否会"逃出"方法/线程（被外部引用、返回、赋给静态字段）。
  • 标量替换（主要落地形式）：对象不逃逸时，JIT 干脆不创建对象，把它的字段拆成独立局部变量（标量）放栈/寄存器——对象从未在堆上存在过，GC 都不用管。HotSpot 实际做的是标量替换，而非真的"在栈上分配完整对象"。
  • -XX:+DoEscapeAnalysis 默认开启（JDK 7+）。
  • 所以"对象一定在堆上吗"的严谨答案：规范层面对象在堆分配；HotSpot 实现上，不逃逸的小对象可能被标量替换优化掉，根本不占堆。典型受益者：临时包装类、循环内小对象。

08高频追问与陷阱

  • 追问链：对象头为什么和锁升级有关 →→ Mark Word 复用：无锁/hashCode → 偏向/线程ID → 轻量级/LockRecord 指针 → 重量级/Monitor 指针（链 02-concurrency/03）。
  • 追问（加分）：对象算过 hashCode 还能偏向吗 →→ 不能：Mark Word 无锁态才放得下 hashCode，一旦调用过 identity hashCode，无法再进入偏向状态（两者抢同一个位置）——把两章知识串起来的加分细节。
  • 追问：为什么必须 8 字节对齐 →→ 指针压缩按 8 字节粒度编址、CPU 按字长取数效率；代价由对齐填充兜底。相邻字段挤在同一缓存行的"伪共享"是另一回事，链 02-concurrency/05 @Contended。
  • 陷阱：new String("ab") 答"2 个"不看条件 →→ 要看池里有没有；严谨答法是"1 个确定 + 1 个条件"。
  • 陷阱：intern 一定省内存 →→ 见上面 StringTable 碰撞与回收语义，大规模 intern 是反模式。
  • 场景题：大量小对象创建导致 GC 压力大，怎么办 →→ 先确认是否可被逃逸分析吃掉（局部小对象别赋给外部）→ 减少包装（int 换 Integer、可变复用 StringBuilder）→ 大促型请求对象考虑对象池（谨慎）。
