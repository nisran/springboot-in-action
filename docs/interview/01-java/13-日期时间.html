日期时间题的特点：题目不深，但特别容易暴露"知其然不知其所以然"。7 年经验的答法：旧 API 的问题要能像数家珍一样列出来（说明被坑过），SimpleDateFormat 线程安全要能讲到"共享 Calendar 状态被并发写坏"这一层，最后落到 JSR-310 的设计哲学——把"机器时间"和"人类时间"分成两条线、全部不可变。

02旧 API 的问题：java.util.Date / Calendar 槽点巡礼

JSR-310（java.time，随 Java 8 引入，作者即是 Joda-Time 的创始人 Stephen Colebourne）不是推倒重来式炫技，而是对旧 API 二十年实战教训的回应。先看旧 API 到底有多别扭：

Date d = new Date(2026, 9, 17);   // 实际是 3926 年 10 月：年份要减 1900，月份 0 起始（9 = 十月）
d.setYear(126);                   // Date 是可变的：状态可被随时篡改，跨线程传递就是隐患
Calendar cal = Calendar.getInstance();
cal.set(2026, Calendar.OCTOBER, 17);  // 月份必须用常量，直接写 10 会变成 11 月
int year = cal.get(Calendar.YEAR);    // 取个字段也要走"字段编号 + get"的模型，臃肿

槽点清单（按面试可背的顺序）

  • 可变：Date、Calendar 都有 setter，对象建完还能改。作为参数传递、放进缓存 / Map 的 key 都可能被污染——和 String 不可变的好处正好反着来（呼应 第 01 章 String 不可变）。
  • 反直觉的数值：年份从 1900 偏移、月份 0 起始，几乎每个老程序员都写出过差一年 / 差一月的 bug。
  • 职责不清：Date 既表示"某一个时刻"（时间戳）又被当作"年月日"用；java.sql.Date / Timestamp 继承自 java.util.Date，继承关系扭曲（父类明明是"时刻"，子类却表示"纯日期"）。
  • 非线程安全：Date/Calendar 本身可变；格式化器 SimpleDateFormat 更是线程不安全（下下节专讲 ⭐）。
  • 时区是二等公民：要靠 TimeZone 在旁边打补丁，处理夏令时（DST）几乎必然出错。
  • API 风格不一致：一半方法废弃、一半功能塞进 Calendar，两者职责重叠。

新旧 API 对照表

旧 API新 API（java.time）说明
java.util.DateInstant机器时间线上的一个点
CalendarLocalDateTime / ZonedDateTime人类视角的日期时间（无 / 带时区）

答题口径：被问"新旧 API 区别"时，别只说"新的好用"。按"设计缺陷 → 新 API 对应改进"配对讲：可变 → 不可变；数值偏移 → 所见即所得；职责混杂 → 机器/人类两条时间线、日期时间拆成独立类型；格式化线程不安全 → Formatter 不可变。这一段讲完，基本不用再答第二问。

03LocalDate / LocalTime / LocalDateTime：人类时间线

Local* 系列表示"日历上的日期时间，不含时区概念"——就像纸质日历和墙上的钟，"2026-10-17 14:30" 本身不对应唯一的物理时刻，得配上时区才能落到时间轴上。生日、入职日期、营业时间这类"人类语义"用它们最合适。

LocalDate date = LocalDate.of(2026, 10, 17);   // 月份 1~12，所见即所得
LocalDate today = LocalDate.now();              // 依赖系统默认时区
date.getYear();                                 // 2026
date.getDayOfWeek();                            // SATURDAY —— 返回枚举，不再是 magic int
date.isLeapYear();                              // true
date.lengthOfMonth();                           // 31

// 所有"修改"都返回新对象，this 不动：
LocalDate nextWeek = date.plusWeeks(1);
LocalDate firstDay = date.withDayOfMonth(1);
LocalDate monday  = date.with(TemporalAdjusters.next(DayOfWeek.MONDAY));  // 日期校正器

LocalTime t = LocalTime.of(14, 30, 0);
LocalDateTime dt = LocalDateTime.of(date, t);
LocalDateTime parsed = LocalDateTime.parse("2026-10-17T14:30:00");  // 默认 ISO 格式
  • 工厂方法三板斧：now() 当前、of(...) 构造、parse(...) 解析——整个 java.time 包风格统一。
  • with / plus / minus 全部返回新实例，链式调用，绝不会改老对象。
  • Month / DayOfWeek 是枚举，彻底告别 Calendar.OCTOBER 这种常量魔法值。
  • 月份天数、闰年这类问题交给 API：date.plusMonths(1) 自动处理 1 月 31 日 → 2 月 28 日的边界（旧 API 要自己擦屁股）。

陷阱：LocalDate.now() / LocalTime.now() 用的是 JVM 默认时区。容器里时区配置不对，半夜跑批的"今天"可能差 8 小时；对确定性敏感的代码显式传 LocalDate.now(ZoneId.of("Asia/Shanghai"))，测试时传 Clock 固定时间。

04Instant 与时间戳：机器时间线

JSR-310 的核心设计：两条时间线分开建模。机器视角（连续的、单调递增的秒数）用 Instant；人类视角（年月日时分秒，有历法规则）用 LocalDateTime 等。两者通过时区互转，语义清晰。

Instant now = Instant.now();            // UTC 时间轴上的一个点（纳秒精度）
now.getEpochSecond();                   // 自 1970-01-01T00:00:00Z 起的秒数
now.toEpochMilli();                     // 等价于 System.currentTimeMillis()

Instant i1 = Instant.ofEpochSecond(1760688000);     // 按 epoch 秒构造
Instant i2 = Instant.parse("2026-10-17T06:00:00Z"); // Z = UTC（Zulu time）

// 与老代码互转（JDK 8+ 桥接方法）：
Date legacy = Date.from(i1);
Instant back = legacy.toInstant();
Date d = new Date();          // d.getTime() 就是 epoch 毫秒
Calendar c = Calendar.getInstance();
Instant fromCal = c.toInstant();
  • Instant = epoch 秒 + 纳秒，与 System.currentTimeMillis() 同源，但它有类型、有行为（plus/minus/compare），不再是裸 long。
  • 怎么选：日志时间戳、接口超时、缓存 TTL、分布式系统传递"物理时刻"→ Instant / epoch 毫秒；页面展示、业务字段（生日、活动开始时间）→ LocalDate / LocalDateTime。
  • 接口契约经验：对外 API 传 epoch 毫秒或 ISO-8601 UTC 字符串（无时区歧义），落到库里再按业务时区转 LocalDateTime——这是 7 年经验能主动讲的实战细节。
  • Instant 不能直接获取年月日（它不知道时区），必须先 atZone(ZoneId)。这是设计使然，不是缺陷。

MySQL 的 DATETIME 无时区、TIMESTAMP 底层按 UTC 存储并在会话时区间换算——和 Instant/LocalDateTime 的关系刚好对应：TIMESTAMP ↔ Instant 思路，DATETIME ↔ LocalDateTime 思路。面试聊到存储层时带上这一句很加分（深入在 06-sql）。

05Duration vs Period：两种"时间量"

DurationPeriod
度量单位秒 + 纳秒（精确物理时长）年 + 月 + 日（日历上的跨度）
适用类型Instant / LocalTime / LocalDateTimeLocalDate
典型输出PT1H30M10S（ISO-8601 时长）P1Y2M3D
语义"过了 24 小时""过了 1 天"（可能因 DST 不是 24 小时）
场景超时、耗时统计、TTL年龄、账期、会员有效期
LocalDateTime start = LocalDateTime.of(2026, 10, 17, 9, 0);
LocalDateTime end   = LocalDateTime.of(2026, 10, 17, 10, 30, 10);
Duration d = Duration.between(start, end);   // PT1H30M10S
d.toMinutes();                                // 90
d.toDays();

LocalDate birth = LocalDate.of(1996, 6, 1);
Period age = Period.between(birth, LocalDate.now());   // P30Y4M16D
age.getYears();                                        // 30 —— 三个字段分别读

// "总共相差多少天"不要用 Period 手算，用 ChronoUnit：
long days = ChronoUnit.DAYS.between(birth, LocalDate.now());
  • 为什么分两个类：日历跨度不是确定时长——"1 个月"可能是 28~31 天，"1 天"在夏令时切换日是 23 或 25 小时。Period 表示前者（跟着日历走），Duration 表示后者（跟着秒表走）。
  • localDate.plus(Period.ofDays(1)) 与 instant.plus(Duration.ofDays(1)) 在 DST 边界会差 1 小时——跨时区业务里这是真实事故来源。
  • 统计类需求（任务耗时、接口 RT）一律 Duration；账期、有效期一律 Period；"差多少天"用 ChronoUnit.DAYS.between()。

陷阱：Period.between(a, b) 的结果是三个独立字段（年、月、日各自算差），不是总天数——P1M2D 换算成天数没有唯一答案，这正是 Period 存在的意义。面试官爱拿"用它算两个日期差几天"钓人。

06DateTimeFormatter：格式化与解析

// 预定义格式（ISO-8601）
DateTimeFormatter iso = DateTimeFormatter.ISO_LOCAL_DATE_TIME;
iso.format(LocalDateTime.now());   // 2026-10-17T14:30:00

// 自定义 pattern —— 推荐定义为 static final，可安全共享
private static final DateTimeFormatter F = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");

F.format(LocalDateTime.now());
LocalDateTime.parse("2026-10-17 14:30:00", F);

DateTimeFormatter chinese = DateTimeFormatter.ofPattern("yyyy年MM月dd日");
LocalDate.parse("2026年10月17日", chinese);

// 带时区格式化（off 即 ZoneOffset）
DateTimeFormatter f = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss Z");
  • 线程安全：DateTimeFormatter 不可变（pattern 解析结果在内部构建成只读结构），可以放心做成 static final 单例共享——这正是它替代 SimpleDateFormat 的根本原因。
  • 双向能力：同一个 formatter 既 format 又 parse；SimpleDateFormat 里 format/parse 共享一个可变 Calendar 的隐患在这里不存在。
  • 解析失败抛 DateTimeParseException（运行时异常），错误信息带失败位置，比旧的 ParseException 好排查。

高频陷阱：yyyy vs YYYY。yyyy 是 calendar year；YYYY 是 week-based year（按 ISO 周算法归属的年份）。跨年周（如 2026-12-29 属于 2027 年第 1 周）用 YYYY 会打出 2027——每年元旦前后总有人在线上踩这个坑。同理 dd 是日、DD 是"年内第几天"。答出这个细节基本能证明真用过。

07时区：ZonedDateTime 与 OffsetDateTime

时区 ≠ UTC 偏移

  • ZoneOffset：纯偏移量，如 +08:00——"此刻比 UTC 快 8 小时"，不含任何规则。
  • ZoneId：IANA 时区，如 Asia/Shanghai——是一套规则集合（历史偏移 + 夏令时规则）。同一 ZoneId 在不同日期可能对应不同偏移（如 Europe/Paris 夏天 +02:00、冬天 +01:00）。
  • 所以存储/传输未来时间要用 ZoneId 语义（ZonedDateTime 或 "时间 + 时区 ID"），只存偏移会在 DST 切换后出错。
ZonedDateTime tokyo = ZonedDateTime.now(ZoneId.of("Asia/Tokyo"));
ZonedDateTime beijing = tokyo.withZoneSameInstant(ZoneId.of("Asia/Shanghai"));
// 同一物理时刻，换墙上的钟——17:00 东京 = 16:00 北京

// 人类时间 ⇄ 机器时间 的桥梁：
LocalDateTime ldt = LocalDateTime.of(2026, 10, 17, 14, 0);
ZonedDateTime zdt = ldt.atZone(ZoneId.of("Asia/Shanghai"));   // 赋予时区 → 落到时间轴
Instant inst = zdt.toInstant();                                // → 机器时间
LocalDateTime back = LocalDateTime.ofInstant(inst, ZoneId.of("Asia/Tokyo"));  // 15:00

OffsetDateTime odt = ldt.atOffset(ZoneOffset.of("+08:00"));    // 只带偏移，无 DST 规则

ZonedDateTime vs OffsetDateTime 怎么选

ZonedDateTimeOffsetDateTime
携带信息时间 + ZoneId（含 DST 规则）时间 + 固定偏移
场景业务展示、跨时区换算、会议时间与系统/API 交互、序列化协议（很多协议只认偏移）
plus 天的语义按当地日历走（保持墙钟时间）按秒平移

答题口径："中国没有夏令时，为什么还要在乎 ZoneId？"——因为跨时区业务（海外用户、跨机房日志对齐）和 IANA 规则库本身会更新（历史修正），Asia/Shanghai 与 GMT+8 看似等价，前者是有规则库支撑的完整时区。能讲出"历史上有过夏令时的地区（如 1986-1991 的中国）规则库照样记录"就更完整。

08SimpleDateFormat 线程不安全 ⭐⭐（必考）

现象

// 常见的"看起来没问题"的写法：
private static final SimpleDateFormat SDF = new SimpleDateFormat("yyyy-MM-dd");

// 多线程并发调用 SDF.parse(...) / SDF.format(...)：
// 轻则解析出 1970 年、日期错乱，重则抛 NumberFormatException、ArrayIndexOutOfBoundsException

根因：内部共享可变状态 Calendar

SimpleDateFormat 继承自 DateFormat，内部持有一个 protected Calendar calendar 字段。parse() 的执行过程是：① cal.clear() 清空 → ② 把解析出的年月日逐个 set 进去 → ③ 再从 calendar 里取结果构建 Date；format() 同样要把 Date set 进这个 calendar 再逐字段读。这三步不是原子的——线程 A 刚 set 了年份，线程 B 一句 clear() 清掉，A 拿到的就是被污染的中间状态。本质：把可变对象当共享资源用却没有任何同步。

三种解法（按推荐度排序）

// ③ 换 DateTimeFormatter（首选）：不可变对象，无共享可变状态，天然线程安全
private static final DateTimeFormatter F = DateTimeFormatter.ofPattern("yyyy-MM-dd");
LocalDate.parse("2026-10-17", F);
LocalDate.now().format(F);

// ① ThreadLocal 包装（遗留代码/还要用 Date 时的过渡方案）
private static final ThreadLocal<SimpleDateFormat> SDF_TL =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
SDF_TL.get().parse("2026-10-17");   // 每线程一份实例，互不干扰

// ② 用局部变量：方法内 new，栈封闭（thread-confined），天然安全
public static Date parse(String s) throws ParseException {
    SimpleDateFormat sdf = new SimpleDateFormat("yyyy-MM-dd");  // 每次新建，有创建开销但简单
    return sdf.parse(s);
}
  • 解法对比：DateTimeFormatter 一步到位且 API 更现代；ThreadLocal 适合"历史代码大量共用 static SDF"的渐进改造，注意线程池场景线程复用不会导致脏数据（每线程独立实例），但要警惕长期不清理可能持有的引用（ThreadLocal 内存泄漏话题在 02 并发板块展开）；局部变量最简单，但高频调用下反复创建 formatter（解析 pattern）有成本。
  • 加分点：阿里巴巴规约明确要求 SimpleDateFormat "定义时尽量使用 static final + ThreadLocal 或 DateUtils 工具类（内部即 ThreadLocal）"；更进一步说明 JDK 21 的虚拟线程下 ThreadLocal 方案成本变高（百万线程各持一份），不可变 formatter 的优势放大——一句带过即可，深入在 02 板块。

答题骨架（三句话拿满）：① 现象——并发 parse/format 结果错乱或抛异常；② 根因——内部共享一个 Calendar，parse 是 clear+set+读 多步非原子操作，并发写坏状态；③ 方案——首选 DateTimeFormatter（不可变），过渡用 ThreadLocal 或改局部变量。追问"为什么 DateTimeFormatter 就安全"答"它和 String 一样是不可变对象，格式化过程中不写任何共享字段"。

09新 API 的不可变设计：一次面向并发的总复盘

怎么做到的

  • 类全部 final：LocalDate、Instant 等不可被继承改写行为（与 String 同款手段）。
  • 字段全部私有 final，无任何 setter；"修改"操作（plus/minus/with）一律返回新实例，原对象永不变化。
  • 线程安全免费获得：不可变对象可以无锁共享——static final DateTimeFormatter、把 LocalDate 当 Map key、跨线程传参数，都不需要考虑同步。这正是 SimpleDateFormat 问题的釜底抽薪式解法。
  • 设计上属于 Effective Java "最小化可变性"条目的教科书实现（见 第 15 章）。

代价与权衡（高级岗要能讲两面）

  • 对象分配变多：每次 with/plus 都 new。缓解：多数日期对象生命周期短（逃逸分析可标量替换）、创建成本低（几个 int 字段）；比起并发 bug 的修复成本，这点开销是划算的。
  • 不适合频繁变更的场景：高频率字段更新（如每 tick 更新时间）应改用可变的累加模型或直接操作 long 时间戳，而不是循环 plus 产生海量中间对象。
  • 与 String 一样，不可变性换来的是：安全性（可作可信 key）、简化推理（值语义）、自由共享。这是 Java 平台一以贯之的品味。

串起来的一句话总结：旧 API 输在"可变 + 线程不安全 + 语义混乱"，新 API 赢在"不可变 + 两条时间线（机器 Instant / 人类 LocalDateTime）+ 类型化时区"。这句能作为整章的收束答案。

10高频追问与陷阱

  • 追问链：SimpleDateFormat 不安全 → 那 JDK 里还有哪些线程不安全的类？→ Calendar、Date（可变但一般不当共享资源）、普通 HashMap、SimpleTimeZone、随机数 java.util.Random（并发性能差而非安全问题）——答出"共性是内部可变状态"即可。
  • 追问链：为什么不用 synchronized 包一层 SDF？→ 能用但串行化后高并发下成为瓶颈；且治标不治本，不可变化才是正解。
  • 陷阱：LocalDateTime.parse("2026-10-17") 会抛异常——默认 ISO 格式要求完整 "yyyy-MM-ddTHH:mm:ss"，纯日期用 LocalDate.parse。
  • 陷阱：格式化 pattern 大小写敏感——mm 是分钟、MM 是月份；YYYY/DD 一节已讲，属于元旦 bug 常客。
  • 追问：LocalDateTime 存库用什么类型？→ JDBC 4.2+ 用 setObject 传 LocalDate/LocalDateTime 即可，MyBatis/Spring Data 都已支持；时间戳语义用 TIMESTAMP（UTC 存储）+ 时区一致的连接参数 serverTimezone，否则差 8 小时是经典事故。
  • 追问：如何生成固定时间做单测？→ 业务代码注入 java.time.Clock，测试用 Clock.fixed(...)——体现可测试性意识，能自然接到第 15 章单元测试话题。
  • 陷阱：Date.toString() 带时区——它按 JVM 默认时区打印，但 Date 本体只是 epoch 毫秒；很多人因此误解"Date 里面存了时区"。

  6. 能区分 ZoneId 与 ZoneOffset，并说明 ZonedDateTime / OffsetDateTime 的选型。
  7. 知道 yyyy 与 YYYY、mm 与 MM 的区别，能举出元旦跨年 bug 的例子。
  8. 能从不可变设计角度解释新 API 为什么线程安全，并说出代价与适用边界。
