01面试怎么考

  1. 泛型是什么？解决了什么问题？没有泛型的世界（JDK 4 之前）怎么写代码？
  2. 泛型类、泛型接口、泛型方法分别怎么声明？泛型方法的类型参数什么时候能省略？
  3. <T extends Number> 是什么意思？多个上界怎么写？
  4. ? extends 和 ? super 的区别？为什么 List<? extends Number> 不能 add？⭐
  5. 什么是 PECS？JDK 里哪些 API 用到了？让你设计 copy(dest, src) 的签名怎么写？⭐
  6. 什么是类型擦除？擦除发生在编译期还是运行期？擦成什么？⭐⭐

  8. 什么是桥方法？没有它，泛型继承的多态为什么会破？
  9. 为什么不能创建泛型数组 new T[]？什么是堆污染（heap pollution）？
  10. 泛型信息被擦除了，Gson / Jackson 是怎么拿到 List<Foo> 里的 Foo 的？

泛型是"语言机制题"的主场：面试官考的不是 API 使用，而是你有没有把编译期/运行期的边界想清楚。7 年经验的打法：所有问题最终都收束到一句话——泛型是编译期的类型检查，运行期没有泛型，围绕这句话组织全部答案。

02泛型类 · 泛型方法 · 泛型接口

泛型 = 把"操作的类型"参数化。没有泛型的年代只能用 Object + 强转：编译期不查错、运行期 ClassCastException 随时炸、读出来必转型。泛型把类型检查前移到编译期，三个收益（对应既有笔记里的提纲：类型安全 / 代码通用 / 减少手动转换）：

  • 编译期类型安全：错误类型根本塞不进去，ClassCastException 在源头消灭；
  • 消除强制转换：取值自动是声明类型，代码干净；
  • 一套代码多种类型复用：集合框架就是最大受益者。
// 泛型类：类型参数跟在类名后
public class Box<T> {
    private T value;
    public void set(T value) { this.value = value; }
    public T get() { return value; }
}

// 泛型接口：实现类要么继续泛型化，要么钉死类型参数
interface Converter<S, T> { T convert(S source); }
class StringToIntConverter implements Converter<String, Integer> {
    public Integer convert(String s) { return Integer.valueOf(s); }
}

// 泛型方法：类型参数跟在返回类型前，作用域仅限本方法（static 方法只能这样用泛型）
public static <K, V> boolean compare(Pair<K, V> p1, Pair<K, V> p2) {
    return p1.getKey().equals(p2.getKey()) &&
           p1.getValue().equals(p2.getValue());
}

// 调用时通常可省略类型参数（目标类型推断）：
compare(new Pair<>("a", 1), new Pair<>("a", 1));      // K, V 被推断为 String/Integer
Main.<String, Integer>compare(p1, p2);                     // 显式写法（歧义时才用）
  • 类型参数命名惯例：T（Type）、E（Element）、K/V（Key/Value）、R（Result）、T/U/V 多参数。
  • 泛型可以有多个类型参数；菱形 <> 从 JDK 7 起用于构造器侧的推断。
  • static 方法不能用类的类型参数（类级 T 属于实例的类信息，static 成员不依赖实例；且擦除后无法区分），要泛型就声明成泛型方法。

03有界类型参数（Bounded Type Parameters）

不加约束的 T 只能当 Object 用；加 上界后，T 就拥有了上界的能力——这是"既泛化又有能力约束"的手段（对应既有笔记里的"向上界定"）：

// 单上界：T 至少是 Number，可以调 Number 的方法
public static <T extends Number> double sum(List<T> list) {
    double s = 0;
    for (T t : list) s += t.doubleValue();   // 没上界这里根本编译不过
    return s;
}

// 多上界：& 连接，第一个可以是类（最多一个），其余必须全是接口
public static <T extends Number & Comparable<T>> T max(List<T> list) {
    T m = list.get(0);
    for (T t : list) if (t.compareTo(m) > 0) m = t;   // 同时拥有两个上界的能力
    return m;
}

// 递归类型约束：Java 没有自类型（self type），用"可与其超类比较"模拟
public static <T extends Comparable<? super T>> void sort(List<T> list) { }
// 这就是 Collections.sort 的真实签名 —— 和 PECS 一起考
  • 通配符也有单上界 ? extends Number 和下界 ? super Integer——但类型参数 T 只有上界，没有下界语法（<T super X> 不存在），下界需求交给通配符。
  • 有界类型参数 vs 有界通配符：前者是"声明一个具体的类型 T"（方法体内可当类型用），后者是"一个未知类型"（只能读写受限），面试常考这个辨析。

04通配符与 PECS ⭐（高频）

泛型不变性是理解一切的前提

泛型不是协变的：List<String> 不是 List<Object> 的子类——否则下面的代码就能把 Integer 塞进 String 列表：

List<String> strs = new ArrayList<>();
// List<Object> objs = strs;      // ❌ 编译错：泛型不变（invariant）
// objs.add(42);                   // 若允许，strs 里就混进了 Integer

Object[] arr = new String[3];      // ✅ 数组是协变的（这是运行期 ArrayStoreException 的根源）
// arr[0] = 42;                    // 编译过、运行时才炸 —— 泛型把这个错误提前到了编译期

为了在"不变"的框架下表达灵活性，JDK 提供了两个方向的有界通配符：

? extends（上界通配符）：只读不写

static double sum(List<? extends Number> src) {
    double s = 0;
    for (Number n : src) s += n.doubleValue();   // ✅ 读出来保证是 Number
    // src.add(1);  src.add(2.0);  src.add(null 只除外)   // ❌ 一律编译错
    return s;
}
  • List<? extends Number> 表示"某种未知的、Number 的子类型"的 List——可能是 List<Integer> 也可能是 List<Double>，编译器不知道是哪种，无论 add 什么都可能破坏类型安全，干脆全禁（除 add(null)）。
  • 读取永远安全：取出的元素至少是 Number。

? super（下界通配符）：只写不读（读只能当 Object）

static void fill(List<? super Integer> dst) {
    dst.add(1);  dst.add(2);                    // ✅ Integer 放进"Integer 或其父类的列表"必然安全
    // Integer x = dst.get(0);                   // ❌ 读出来只能当 Object
    Object o = dst.get(0);                       // ✅
}
  • List<? super Integer> 是"某种 Integer 的父类型"的 List（List<Number>、List<Object>…），往里 add Integer 一定类型安全；但读出来只知道是 Object。

PECS：Producer Extends, Consumer Super ⭐

  • 生产者用 extends：这个参数是给你"读数据"的（生产数据给你用）→ ? extends T；
  • 消费者用 super：这个参数是给你"写数据"的（消费你产出的数据）→ ? super T；
  • 既要读又要写 → 别用通配符，用确切类型。
// JDK 标准答案：Collections.copy 的签名
public static <T> void copy(List<? super T> dest, List<? extends T> src)
//                         ^^^^^^^^^^^^^^^ 消费者（往里写）  ^^^^^^^^^^^^^^ 生产者（从里读）

// 让 copy 支持把 List<Integer> 拷进 List<Number>，非 PECS 写不出来：
List<Number> dest = new ArrayList<>();
List<Integer> src = List.of(1, 2, 3);
Collections.copy(dest, src);        // T 推断为 Integer：dest 是 Integer 的消费者

// 其他 JDK 实例：
boolean addAll(Collection<? extends E> c);                 // 生产者：读 c 灌进来
void sort(Comparator<? super E> c);                          // 消费者：把元素喂给比较器
void forEach(Consumer<? super T> action);                    // 消费者：把元素喂给动作

答题口径：先一句"泛型不变，通配符是给不变性开的两个口子"；再讲 extends 只读 / super 只写及其编译器原因；最后甩出 PECS + Collections.copy 签名。能现场写出 copy 签名的，这题基本满分。追问"为什么 List 不能协变"→ 用上面的 add 反例回答，并对比数组协变的 ArrayStoreException。

05类型擦除（Type Erasure）⭐⭐

是什么、擦成什么

Java 泛型由编译器在编译期实现：做完类型检查后，把类型参数擦除，生成的字节码里没有泛型信息（这是为了兼容 JDK 5 之前的老代码——迁移兼容是当年压倒一切的设计目标）。

源码声明擦除后（字节码层面）
Box<T>（无界）Box，T 的位置变成 Object
Box<T extends Number>（单上界）T 的位置变成 Number
<T extends A & B>（多上界）变成第一个界 A
List<String>就是 List
T[]Object[]
// 证据一：运行期 class 相同
List<String> a = new ArrayList<>();
List<Integer> b = new ArrayList<>();
System.out.println(a.getClass() == b.getClass());   // true —— 都是 ArrayList.class

// 证据二：参数化类型的 Class 不存在
// Class<List<String>> c = List<String>.class;      // ❌ 编译错，根本没有这个 Class 对象

// 证据三：javap -c 反编译可见——编译器在"取值处"插入了 checkcast
// T get()  编译后返回 Object，调用处编译器补一句  checkcast java/lang/String
List<String> list = new ArrayList<>();
String s = list.get(0);     // 字节码：invokeinterface get / checkcast String / astore

// 证据四：擦除后签名相同，无法重载
// void f(List<String> a) {}  void f(List<Integer> b) {}   // ❌ 都擦成 f(List)，编译错

编译器实际做了什么（答题时展开）

  • 编译前检查：所有泛型类型安全检查发生在编译期（调 add 时校验实参类型）；
  • 擦除类型参数：无界 → Object，有界 → 上界（首个界）；
  • 插入强制转换：取值处自动补 checkcast（这就是"不用手写强转"的真相——编译器替你写了）；
  • 合成桥方法：保证擦除后多态仍然成立（§06 专讲）。

为什么 Java 选擦除而 C# 选具化（reification）：JDK 5 引入泛型时，海量的老类库都在用 Object，擦除让新老字节码无缝互操作（迁移兼容优先）。C# 的泛型是运行期真实的 List<int>，代价是与老集合不兼容。追问"以后会改吗"→ Valhalla 项目的具化泛型方向（允许 List<int> 特化布局），提一句即是加分。

06擦除带来的问题与桥方法 ⭐

一系列"不能"（全部源于运行期没有 T）

// ① 不能实例化类型参数
T t = new T();                          // ❌ 运行期不知道 T 是谁

// ② 不能创建泛型数组
T[] arr = new T[10];                    // ❌ 数组需要运行期做协变检查，T 不可得（§07）

// ③ 不能取 T 的 Class 对象 / 静态成员上不能用类类型参数
Class<T> c = T.class;                   // ❌
static T field;                         // ❌ static 不属于实例化的类型

// ④ 不能用于 instanceof 的参数化形式
if (o instanceof List<String>) {}       // ❌ 擦除后无法区分
if (o instanceof List) {}               // ✅ 只能裸类型

// ⑤ 基本类型不能做类型参数
List<int> list;                          // ❌ 擦除后是 Object 引用，int 不是对象 → 只能 List<Integer>（装箱开销）

// ⑥ 泛型类不能继承 Throwable
class MyEx<T> extends Exception {}      // ❌ catch(T e) 无法保证类型安全

// ⑦ 不能重载"擦除后签名相同"的方法
void f(List<String> a) {}
void f(List<Integer> b) {}              // ❌ 都是 f(List)

“不能 new T()” 的标准解法：把运行期类型信息传进来

// 方案一：传 Class<T>，反射 newInstance
public static <T> T create(Class<T> clazz) throws Exception {
    return clazz.getDeclaredConstructor().newInstance();
}

// 方案二：传工厂 / Supplier（推荐，无反射开销）
public static <T> T create(Supplier<T> factory) {
    return factory.get();
}
// 这正是 Spring 泛型注入、JDK 的 Optional.orElseGet(Supplier) 的姿势

桥方法（Bridge Method）：擦除下多态的救火队员 ⭐

class Node<T> {
    private T data;
    public void setData(T data) { System.out.println("Node.setData"); this.data = data; }
}
class StringNode extends Node<String> {
    @Override
    public void setData(String data) { System.out.println("StringNode.setData"); }
}

Node<String> node = new StringNode();
node.setData("hi");     // 期望（且实际）调用 StringNode 的重写 —— 但擦除后怎么分派？

问题：擦除后父类的方法签名是 setData(Object)，而子类写的是 setData(String)——签名都不一样，按 JVM 方法解析规则根本不构成重写，多态会失灵。编译器的解法是给 StringNode 合成一个桥方法：

// javap 可见 StringNode 编译后有两个方法：
public void setData(java.lang.String);          // 你写的
public void setData(java.lang.Object);          // 编译器合成的桥方法（flag: ACC_BRIDGE, SYNTHETIC）
    Code: aload_0 / aload_1 / checkcast String / invokevirtual setData(String) / return
    // 桥方法体内：强制转换参数，再转调真正的 setData(String)

// 分派链：node.setData("hi") → 多态调到 StringNode.setData(Object)（桥方法）→ 转调 setData(String)
  • 桥方法 = 父类擦除后签名 → 子类具体签名的转发垫片，JVM 的方法表多态因此完好。
  • 顺带解释了两个高频现象：① 反射 getDeclaredMethods() 会看到签名怪异的合成方法；② 桥方法里的 checkcast 在参数类型不匹配时抛 ClassCastException——堆污染在"消费端"炸出来的位置就在这。

07泛型数组

为什么 new T[] 被禁止

数组的类型检查是运行期做的（协变 + ArrayStoreException 机制依赖运行期知道组件类型），而擦除让运行期根本不知道 T——两者天然矛盾：

T[] create() { return (T[]) new Object[10]; }   // ⚠ 能编译，但返回的是 Object[] 强转视图

// 危险场景：把 T[] 当真实类型的数组用
String[] arr = factory.create();      // 堆里实际是 Object[]，强转 String[] 通过（编译器视角）
arr[0] = "ok";                        // 运行时 ArrayStoreException / ClassCastException 在某处引爆
// 根因：数组在运行期保留了组件类型并做存储检查，而擦除后的 Object[] 顶不住
  • 泛型集合用 E[]，泛型数组用 Object[]——这是 JDK 自己的取舍：ArrayList<E> 的 elementData 声明为 Object[]，在 get 处强转 E；而 Arrays.asList / toArray(T[] a) 在无参时返回 Object[]。
  • 业务代码正解：用 List<T> 代替 T[]（类型安全交给编译器）；确要数组就用 toArray(new T[0])（传入真实类型的数组，由调用方提供运行期类型）。

堆污染（Heap Pollution）与 @SafeVarargs

// 泛型可变参数：varargs 底层是数组，等价于 List<String>... → List[]（擦除）
@SafeVarargs                            // JDK 7+：向编译器承诺"我只读，不做破坏类型安全的事"
static <T> void printAll(List<T>... lists) {
    for (List<T> l : lists) System.out.println(l);
}

// 堆污染反例：一个"标着 List<String> 实际装了 Integer"的引用逃逸出去
static List<String> polluted() {
    List l = new ArrayList();           // 裸类型，跳过检查
    l.add(42);
    return (List<String>) l;            // ⚠ 编译警告 unchecked，运行期埋雷
}
String s = polluted().get(0);           // ClassCastException —— 在消费端的 checkcast 处爆炸
  • 堆污染定义：变量声明类型与实际引用对象的泛型类型不一致（脏引用进了堆）。它本身不报错，在读出来强转那一刻才炸（往往离案发现场很远）。
  • @SafeVarargs 只能标注 static / final / private 方法（可重写的方法无法保证承诺），提示"我知道 varargs 有泛型数组风险，此处安全"。JDK 9 起也可用于 private 实例方法。

陷阱：toArray() 无参版返回 Object[]，强转 (String[]) list.toArray() 必炸 ClassCastException（运行期还是 Object[]）；必须用 toArray(new String[0])。这是堆污染最常见的一线事故。

08泛型与反射

擦除了，为什么反射还能拿到泛型？

关键：擦除擦的是"对象/数组里的运行期类型"，但写在字段、方法参数、返回值、父类/接口签名里的泛型会被写进 class 文件的 Signature 属性，反射 API 能读到它——泛型元数据保存在"声明处"而非"实例里"。

class Dao {
    List<String> names;                       // 字段签名里有 <String>
}

Field f = Dao.class.getDeclaredField("names");
Type g = f.getGenericType();                  // 不是 getDeclaredType（擦成 List）！
if (g instanceof ParameterizedType pt) {
    System.out.println(pt.getActualTypeArguments()[0]);   // class java.lang.String
}

// 方法签名同理：method.getGenericParameterTypes() / getGenericReturnType()

Super Type Token：匿名子类的魔法

直接 new TypeToken<List<Foo>>() 的泛型拿不到（实例不带泛型），但匿名子类会把参数化父类签名固化到自己的 class 文件里：

List<String> list = new ArrayList<String>() {};   // 注意末尾 {}：匿名子类
ParameterizedType pt = (ParameterizedType) list.getClass().getGenericSuperclass();
System.out.println(pt.getActualTypeArguments()[0]);   // class java.lang.String

// Gson / Jackson / Feign 的套路同源：
TypeToken<List<Foo>> token = new TypeToken<List<Foo>>() {};
List<Foo> foos = gson.fromJson(json, token.getType());   // 没它只能拿到 List，Foo 丢失

// JDK 内置的简化版：TypeReference（Jackson）
List<Foo> foos = mapper.readValue(json, new TypeReference<List<Foo>>() {});
  • 这就是为什么 gson.fromJson(json, List.class) 会得到 List<Object>（元素实际是 Map）——泛型没进 class 文件；必须用 TypeToken 把签名"种"进匿名子类。
  • 实战关联：通用 DAO / MyBatis 泛型 Mapper、Spring 的 ResolvableType（解析容器里 Bean 的泛型层次）都建立在这套机制上；更系统的反射内容见 第 12 章 注解与反射。

答题口径：一句话纠正误区——"擦除不等于元数据全丢，Signature 属性保留了声明处的泛型"；然后给"字段 getGenericType + 匿名子类 TypeToken"两段证据；最后带一句 Gson/Jackson 的实际用法。这一题答好，直接体现"编译期/运行期边界"的功底。

09高频追问与陷阱

  • 追问链：擦除 → 那 List<String> 和 List<Integer> 是同一个类吗→ 是（同一个 ArrayList.class），泛型只活在编译期；追问"能通过反射往 List<Integer> 里塞 String 吗"→ 能，list.getClass().getMethod("add", Object.class).invoke(list, "abc") 绕过编译期检查，取出时才在 checkcast 处炸——堆污染的教科书演示。
  • 追问链：PECS → 为什么 JDK 的 sort 签名是 Comparator<? super T>→ 比较器是消费者（吃元素吐序号），允许传"按父类维度写的比较器"复用逻辑；配合 <T extends Comparable<? super T>> 一起答满分。
  • 追问链：泛型 vs 数组协变 → 为什么数组要协变→ JDK 1.0 没泛型，集合只能收 Object[]，协变让 Object[] 能装任何子类数组——代价是 ArrayStoreException 运行期兜底；泛型出现后"不变 + 通配符"是更安全的替代。
  • 陷阱：原始类型混用：List list = new ArrayList<String>() 能编译（裸类型跳过检查），一堆 unchecked 警告——老代码迁移的常见污染源，团队规范应禁裸类型。
  • 陷阱：静态泛型：class Box<T> { static T x; } 编译错——类的类型参数随实例化确定，static 属于类本身；正解是 static 泛型方法自带 <T>。
  • 陷阱：instanceof 与 Class.cast：List<?> 判断用裸类型 List；拿到 Class<T> 后用 clazz.cast(obj) 代替裸强转，编译器能沿途保住 T。
  • 陷阱：泛型与重载：方法重载看擦除后签名，f(List<String>) 与 f(List<Integer>) 冲突；但返回类型不同的两个方法若只有泛型实参不同也会冲突（擦后同签名）。
  • 场景题口径："设计通用 JSON 反序列化工具"→ TypeToken/Super Type Token；"写通用对象工厂"→ Supplier<T> / Class<T>；"写通用仓库层"→ 泛型 DAO + 反射 getGenericSuperclass 拿实体 Class（MyBatis-Plus 的 BaseMapper 思路）。

10面试自查清单

  1. 能说出泛型三大收益（编译期类型安全 / 免强转 / 复用）并对应 JDK 4 的 Object 写法反例。
  2. 泛型类 / 接口 / 泛型方法声明语法熟练，知道 static 成员不能用类类型参数。
  3. 单上界、多上界（&、类在前）能写，认得 <T extends Comparable<? super T>> 这种签名。
  4. 能解释泛型不变性 + 数组协变的对比，及 extends 只读 / super 只写的编译器原因。
  5. PECS 口诀脱口而出，能默写 Collections.copy(List<? super T>, List<? extends T>) 并举 2 个 JDK 实例。
  6. 类型擦除的规则（无界→Object、有界→上界、多界→首界）+ 四条证据（同 class / 无 List<String>.class / checkcast / 不能重载）。
  7. "不能 new T() / T.class / new T[] / List<int> / instanceof 泛型 / 继承 Throwable"六大限制及各自解法。
  8. 能画/讲桥方法的合成过程（setData(Object) 转发 setData(String)）并说明它保住了多态。
  9. 知道堆污染的成因、炸点（消费端 checkcast）与 @SafeVarargs 的适用范围。
  10. 能解释"擦除了为何反射还能拿泛型"（Signature 属性）+ TypeToken 匿名子类原理。
