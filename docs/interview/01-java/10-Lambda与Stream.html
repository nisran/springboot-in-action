02Lambda 语法与本质 ⭐

一句话定义：Lambda 表达式是函数式接口（Functional Interface）的实例。函数式接口 = 有且只有一个抽象方法（SAM，Single Abstract Method）的接口，@FunctionalInterface 注解只是编译期检查，不加也不影响（如 Runnable、Comparator 早就满足条件）。

// 三种等价写法，右侧两种是语法糖的糖：
Runnable r1 = new Runnable() { public void run() { System.out.println("hi"); } };
Runnable r2 = () -> System.out.println("hi");
Runnable r3 = System.out::println;   // 方法引用（见第 04 节）

本质：不是匿名类的语法糖，而是 invokedynamic

反编译 javap -v 一个含 Lambda 的类，看不到 Outer$1.class 这样的匿名类产物，只看到一条字节码指令：

// javap -v LambdaDemo.class 的关键输出：
public static void main(java.lang.String[]);
  Code:
    invokedynamic #x, 0   // InvokeDynamic #0:run:()Ljava/lang/Runnable;
                      // ↑ 一条动态调用指令，指向 BootstrapMethods 里的引导方法

BootstrapMethods:
  0: #x REF_invokeStatic java/lang/invoke/LambdaMetafactory.metafactory(
         MethodHandles$Lookup, String, MethodType, MethodType, MethodHandle, MethodType)
   // 引导方法：LambdaMetafactory
  • 执行流程：JVM 首次执行到 invokedynamic 时，调用引导方法 LambdaMetafactory.metafactory(...)，由它在运行时动态生成一个实现函数式接口的类（JDK 8 用 ASM 生成内部类；JDK 15+ 改用 Hidden Class），并返回一个调用点（CallSite），此后调用直接绑定到这个轻量类上。
  • 为什么这样设计：把"Lambda 如何实现"的决策从编译期推迟到运行期。编译器只写死"这里是函数式接口实例"，JDK 厂商可以自由演进实现策略（内部类 → hidden class → 未来 VM 原生优化），而无需改任何已编译的代码。若当初绑死匿名类语法糖，就没有这个演进空间。
维度匿名内部类Lambda
编译产物生成 Outer$1.class，编译期固定无独立 class 文件，运行时由 LambdaMetafactory 动态生成
字节码指令new + dup + invokespecial<init>invokedynamic
this 指向匿名类实例自身（Outer.this 才是外部类）外围实例（没有自己的 this，词法作用域）
变量捕获要求 final要求 effectively final（语义相同）
内存/性能每个匿名类一份类元数据无捕获的 Lambda 可全局单例复用（JDK 缓存）

为什么只能捕获 effectively final 变量

已有笔记里的结论 + 原因：Lambda 捕获的是局部变量的副本。局部变量在栈帧里，方法返回栈帧即销毁，而 Lambda 可能在之后才执行（如异步线程、Stream 惰性求值），所以它拿到的必须是拷贝。如果允许原变量后续被修改，拷贝和原值就会不一致，语义不可靠——干脆要求 effectively final（不必显式写 final，只要事实不再赋值即可）。

成员变量没有这个限制：实例存在堆里，Lambda 持有的是外围对象的引用，读写的是同一份内存。这也解释了"Lambda 里改成员变量编译通过、改局部变量编译失败"的经典疑问。

答题口径："Lambda 是函数式接口的实例，编译成 invokedynamic 指令，运行时由 LambdaMetafactory 生成实现类，不是匿名类的语法糖。区别体现在：没有独立 class 文件、this 语义不同、实现策略可演进。"能说出 metafactory 和 hidden class 演进，就是高级岗水准。

03四大函数式接口 ⭐

java.util.function 包有几十个接口，但万变不离四个原型，其余都是它们的" arity 扩展 + 原始类型特化"：

接口抽象方法语义典型场景
Function<T,R>R apply(T t)输入 T 映射输出 Rmap 的入参、转换器
Predicate<T>boolean test(T t)断言真假filter 的入参、校验规则
Consumer<T>void accept(T t)消费不返回forEach 的入参、回调
Supplier<T>T get()无输入只产出工厂、懒加载、orElseGet 的入参
Function<String, Integer> len = String::length;
Integer n = len.apply("hello");                       // 5
Function<Integer, Integer> square = x -> x * x;
System.out.println(len.andThen(square).apply("ab")); // 2 -> 4，compose 则先执行参数那个

Predicate<String> isEmpty = String::isEmpty;
System.out.println(isEmpty.negate().test("abc"));    // true，还有 and / or 默认组合方法

Consumer<String> printer = System.out::println;
printer.andThen(s -> log.info("printed {}", s)).accept("hi");  // 顺序执行两个消费

Supplier<List<String>> factory = ArrayList::new;      // 工厂：延迟到 get() 才创建
List<String> list = factory.get();
  • 扩展家族：BiFunction<T,U,R>（两个入参）、UnaryOperator<T>（同型映射，Function 特化）、BiConsumer、BooleanSupplier 等。
  • 原始类型特化：IntFunction、ToIntFunction、IntPredicate、IntSupplier… 存在的意义是避免装箱拆箱——IntStream 全家桶就是靠它们做到无装箱数值计算的。
  • JDK 8 接口的 default / static 方法不计入 SAM 计数，equals 等来自 Object 的签名也不计入。

记忆口诀：Function 有进有出、Predicate 有进出布尔、Consumer 有进无出、Supplier 无进有出。再追问就往"特化避免装箱"和"默认组合方法（andThen/compose/negate）"上引。

04方法引用四种

方法引用是 Lambda 的极简写法：当 Lambda 体只是"转发调用一个已存在方法"时，可以直接用 :: 引用它。底层与 Lambda 完全相同（同样走 invokedynamic + LambdaMetafactory）。

类型写法等价 Lambda
静态方法引用Integer::parseInts -> Integer.parseInt(s)
特定对象的实例方法System.out::printlns -> System.out.println(s)
类的实例方法（第一个参数当接收者）String::toUpperCasestr -> str.toUpperCase()
构造器引用ArrayList::new、int[]::new() -> new ArrayList<>()
// 第三种最容易懵：String::toUpperCase 用在 map 里，流中的每个元素就是"接收者"
Stream.of("a", "b").map(String::toUpperCase).forEach(System.out::println);  // A B

// 构造器引用配合 toArray 极常用：
List<String> src = List.of("a", "b");
ArrayList<String> copy = src.stream().collect(Collectors.toCollection(ArrayList::new));
String[] arr = src.stream().toArray(String[]::new);

易错：String::toUpperCase 和 str::toUpperCase（局部变量 str）是两种不同引用——前者是"类 + 实例方法"（参数做接收者），后者是"对象 + 实例方法"（固定接收者）。面试口述时说清"接收者是谁"就不会被绕晕。

05Stream 的创建

来源API说明
集合collection.stream() / parallelStream()最常用；Collection 接口默认方法
数组Arrays.stream(arr)int[] 会得到 IntStream（无装箱）
静态工厂Stream.of(...) / Stream.empty()少量元素
无限流Stream.iterate(seed, f) / Stream.generate(sup)必须配 limit 等短路操作截断；iterate 三参重载可带条件（JDK 9+）
数值区间IntStream.range(0, n) / rangeClosed替代 for 循环，无装箱
文件Files.lines(path)惰性按行读，必须放 try-with-resources 关闭
其他Pattern.compile(re).splitAsStream(s)、Stream.concat、Random.ints()按需取用
// 无限流典型用法：生成前 10 个斐波那契数
Stream.iterate(new int[]{0, 1}, a -> new int[]{a[1], a[0] + a[1]})
      .limit(10)
      .map(a -> a[0])
      .forEach(System.out::println);

流是一次性的：每个 Stream 只能被一个终端操作消费，重复使用抛 IllegalStateException: stream has already been operated upon or closed。流不是数据结构，是"数据源上的操作管道"。

06中间操作 vs 终端操作 ⭐

分类的黄金标准：返回 Stream 的是中间操作（可以继续链），返回其他类型或 void 的是终端操作（管道到此结束）。更重要的是语义差异：中间操作是惰性的，只记录描述（什么 filter、什么 map），不触发计算；终端操作才驱动整个管道跑起来。

类别方法说明
中间（惰性）filter(Predicate)过滤，无状态
map(Function) / mapToXxx一对一映射，无状态
flatMap(Function)一对多拍平（map 的元素是流时用它），无状态
distinct()去重，有状态（要记住见过的元素）
sorted()排序，有状态（必须拿到全部元素才能排）
peek(Consumer)窥探每个元素（调试用），无状态
limit(n) / skip(n)截断/跳过，有状态 + 短路（limit 见 limit 的并发版见 09 节）
终端（触发）forEach / forEachOrdered逐个消费；后者保证遇遇顺序（并行流代价大）
collect(Collector)归约成集合/聚合结果，最常用
reduce(identity, BinaryOperator)累积归约成单个值
count / min / max聚合（内部就是 reduce）
findAny / findFirst / anyMatch / allMatch / noneMatch / toArray查找与匹配，前五者短路
  • 有状态 vs 无状态：无状态中间操作可以逐元素流水线处理；有状态（sorted/distinct/limit）需要缓存元素甚至等全量到齐，并行流下代价更高、可能多轮数据搬运。
  • findAny vs findFirst：串行流下行为基本一致；并行流下 findAny 允许返回任意一个（哪个线程先命中就返回谁，性能更好），findFirst 必须返回遇到顺序中的第一个（要协调，约束更强）。

答题口径："返回 Stream 的是中间操作，惰性只记账；终端操作触发遍历，把整条管道融合成一次遍历执行（loop fusion），中间不会生成中间集合。"最后这句 loop fusion 是拉开差距的关键。

07惰性求值与短路

惰性求值：没有终端操作，一行都不会执行

List<String> names = List.of("tom", "jerry", "spike");

names.stream()
     .peek(s -> System.out.println("peek: " + s))   // 什么都不会打印！
     .filter(s -> s.length() > 2);

names.stream()
     .peek(s -> System.out.println("peek: " + s))   // 打印 3 行
     .filter(s -> s.length() > 2)
     .count();                                        // count 是终端操作，驱动执行

执行时也不是"先 filter 完所有元素，再 map 所有元素"，而是逐元素垂直执行：元素一个个穿过整条管道，filter 拦下的元素根本不会走到后面的 map。所以链式写法的"表观多次遍历"实际是一次遍历，中间零临时集合。

短路操作：满足条件立即收工

int firstEven = IntStream.range(0, 1_000_000)
        .peek(i -> System.out.println("check " + i))
        .filter(i -> i % 2 == 0)
        .findFirst()
        .orElse(-1);
// 只打印 check 0 就返回了：filter 放行第一个元素后，findFirst 短路终止整个管道
  • 终端短路：findAny / findFirst / anyMatch / allMatch / noneMatch——拿到结果就通知所有环节停止拉取元素。
  • 中间短路：limit(n)（这也是无限流能安全使用的原因）；skip 在串行下也具有"跳过即丢弃"的短路语义。
  • 无限流 + limit 是惰性/短路最经典的组合考点：Stream.iterate 本身不产生任何数据，全靠管道按需拉取。

陷阱：把副作用放进 peek 用于生产逻辑是反模式（peek 的设计意图是调试）；更别指望"没写终端操作的 peek 会执行"。副作用应放到 forEach / collect 里。

08Collector 收集器

Collectors 工具类是终端操作 collect 的弹药库。Collector 内部是五个协同组件：supplier（建容器）/ accumulator（累加）/ combiner（并行合并）/ finisher（最终转换）/ characteristics（特征位）——能说出这个结构就是源码级回答。

常用收集器速查

需求API备注
收 List / SettoList() / toSet() / toCollection(ArrayList::new)toList 返回的 List 不要依赖可变性（JDK 16+ 返回的实现不可变）
收 MaptoMap(k, v)key 冲突抛 IllegalStateException；value 为 null 抛 NPE——要传第三个参数 merge 函数
拼接字符串joining(", ") / joining(sep, prefix, suffix)底层 StringBuilder
分组groupingBy(classifier)返回 Map<K, List<T>>；可传下游收集器做多级加工
分区partitioningBy(predicate)groupingBy 的布尔特例，key 只有 true/false 两组
聚合counting() / summingInt / averagingDouble / maxBy常作为 groupingBy 的下游
再加工mapping(fn, downstream) / reducing(...) / collectingAndThen(c, fn)下游套下游，组合出复杂统计

groupingBy 分组统计（高频手写题）

record Employee(String name, String dept, int salary) {}
List<Employee> emps = List.of(
    new Employee("tom", "dev", 20000),
    new Employee("jerry", "dev", 25000),
    new Employee("spike", "ops", 18000));

// 1. 基础分组：部门 -> 人员列表
Map<String, List<Employee>> byDept = emps.stream()
        .collect(Collectors.groupingBy(Employee::dept));

// 2. 分组统计人数：部门 -> 人数
Map<String, Long> countByDept = emps.stream()
        .collect(Collectors.groupingBy(Employee::dept, Collectors.counting()));

// 3. 分组 + 下游 mapping 拿名单
Map<String, List<String>> namesByDept = emps.stream()
        .collect(Collectors.groupingBy(Employee::dept,
                 Collectors.mapping(Employee::name, Collectors.toList())));

// 4. 多级分组：部门 -> 薪资档 -> 人数（下游再嵌 groupingBy）
Map<String, Map<String, Long>> deep = emps.stream()
        .collect(Collectors.groupingBy(Employee::dept,
                 Collectors.groupingBy(e -> e.salary() > 20000 ? "high" : "low",
                         Collectors.counting())));

// 5. joining 拼名字
String all = emps.stream().map(Employee::name)
        .collect(Collectors.joining(", ", "[", "]"));   // [tom, jerry, spike]

toMap 两大坑：① key 重复直接抛异常，业务上几乎总要显式传 merge 函数 (a, b) -> b（后者覆盖）或 (a, b) -> a；② value 为 null 时 NPE（内部用 HashMap.merge，null 不合法）。真实事故高发点，7 年经验应主动提。

09并行流陷阱 ⭐

底层机制

  • parallelStream() / parallel() 把管道标记为并行，终端操作触发时：数据源用 Spliterator 递归二分拆分任务，提交到 ForkJoinPool.commonPool() 执行（工作窃取调度）。
  • commonPool 的默认并行度 = CPU 核数 − 1（至少 1），主调用线程自己也会参与计算；可用 -Djava.util.concurrent.ForkJoinPool.commonParallelism=N 调整，或提交到自定义池。
  • 拆分是否高效取决于数据源：ArrayList / 数组 / IntStream.range 支持随机访问，拆得又快又匀；LinkedList、迭代器包装的流拆分差，并行可能比串行还慢。

陷阱一：共享可变状态（经典翻车题）

List<Integer> result = new ArrayList<>();          // 反例：线程不安全的容器 + 并行 add
IntStream.range(0, 10_000).parallel().forEach(result::add);
System.out.println(result.size());                 // 可能 < 10000，还可能抛 ArrayIndexOutOfBoundsException
// 原因：ArrayList 非线程安全，并行扩容/add 丢数据、索引越界

// 正解一：让 Stream 帮你并发安全地收集（内部按线程分桶再合并）
List<Integer> ok = IntStream.range(0, 10_000).parallel()
        .boxed().collect(Collectors.toList());

// 正解二：真要手动累积就用并发容器
ConcurrentMap<String, Long> m = stream.parallel()
        .collect(Collectors.toConcurrentMap(...));

陷阱二：IO 密集任务拖死全局 commonPool

// 反例：慢 IO 跑在 commonPool 里，会把这台 JVM 上所有并行流/ForkJoinTask 饿死
files.parallelStream().forEach(f -> callSlowHttpApi(f));   // 每个任务耗时 2s

// 正解：IO 密集就别用并行流；确需并行，提交到自定义线程池
ForkJoinPool ioPool = new ForkJoinPool(32);        // 按并发度设线程数
try {
    ioPool.submit(() ->
        files.parallelStream().forEach(f -> callSlowHttpApi(f))
    ).get();
} finally {
    ioPool.shutdown();
}
// 原理：并行流用"提交它的线程所在/绑定的 ForkJoinPool"，在 ioPool 的任务里创建并行流，就跑在 ioPool 上

该不该用并行流的判断口径（四问）

  1. 数据量够大吗？几万以下，拆分与调度的开销可能吞掉收益。
  2. 单个元素的计算够重吗？CPU 密集（加密、解析、复杂计算）适合；纯轻量过滤不适合。
  3. 无共享可变状态吗？有就先重构，或用并发安全的 collect。
  4. 数据源可高效拆分吗？ArrayList/数组可以，LinkedList / iterator 流不行。

答题口径："并行流底层是 Spliterator 拆分 + ForkJoinPool.commonPool，默认并行度 CPU−1。我的实战原则：CPU 密集 + 大数据量 + 无共享状态 + 数据源可拆分才用；IO 密集一律不用并行流（会饿死全局 commonPool，影响整台 JVM），要用就自定义 ForkJoinPool 提交。"并发的线程池、ForkJoin 工作窃取细节见 02 并发编程板块。

10Optional 正确用法

设计意图：为"返回值可能缺失"提供一个显式类型，把"可能为 null"从口口相传的约定变成方法签名的一部分，逼调用方处理缺失分支。

推荐姿势

// 生产者：可能查不到就返回 Optional，别返回 null
Optional<User> findUser(String id) { ... }

// 消费者：链式处理，几乎不需要 isPresent
String city = findUser(id)
        .map(User::getAddress)          // 值存在才映射，不存在则整个链保持 empty
        .map(Address::getCity)
        .filter(c -> !c.isEmpty())
        .orElse("unknown");             // 缺省值

findUser(id).ifPresentOrElse(
        u -> log.info("found {}", u),   // JDK 9+
        () -> log.warn("not found"));

User u = findUser(id).orElseThrow(
        () -> new BusinessException("用户不存在"));   // 取值并显式抛业务异常

orElse vs orElseGet（高频追问）

Optional<User> empty = Optional.empty();
User a = empty.orElse(loadFromDb());      // ❌ 无论是否缺失，loadFromDb() 都会执行（急切求值）
User b = empty.orElseGet(() -> loadFromDb()); // ✅ 只有缺失才执行（懒加载，Supplier）
// 缺省值是常量用 orElse，需要计算/查库用 orElseGet

反模式清单

  • 不做字段：Optional 不是免序列化友好的轻量对象，字段多一层包装徒增内存，且字段可为 null 本身就矛盾。
  • 不做方法参数：调用方多写一层包装，签名可读性变差；参数校验用 Objects.requireNonNull 更直接。
  • 不包集合：Optional<List<T>> 不如直接返回空集合 Collections.emptyList()。
  • 不裸调 get()：等价于把 NPE 换成 NoSuchElementException，应使用 orElseThrow 带语义异常。
  • 不用 isPresent + get 组合：那就退化回了 if (x != null)，换汤不换药。

一句话总结：Optional 是"返回值可能缺失"的领域专用类型，只出现在返回值位置，配合 map/filter/orElseXxx 链式消费。它不是消灭 null 的银弹——参数与字段里的 null 仍靠规约与断言。

11高频追问与陷阱

  • 追问链：Lambda 本质 → 为什么编译器不直接生成匿名类？→ 匿名类每个都生成一份 class 文件、加载开销大且 this 语义混乱；invokedynamic 把实现策略留给运行期，JDK 8→15 从内部类演进到 hidden class 就是受益于此。
  • 追问链：Stream 惰性 → 那多写几个中间操作会不会多跑几趟？→ 不会，终端操作触发时融合成一次遍历；但有状态操作（sorted）会破坏纯流式处理，需要缓存全量。
  • 陷阱：forEach 里的 return 不是 break：forEach 的 lambda 是普通函数调用，return 只结束当前元素的处理（相当于 continue）；要"找到即停"用 filter + findAny，要完整控制流用普通 for。
  • 陷阱：并行流 + forEach 输出乱序：forEach 不保证顺序，需要顺序用 forEachOrdered（代价：失去并行自由度）。
  • 陷阱：Stream<Integer> 做数值求和：装箱严重，应转 IntStream（mapToInt）再 sum。
  • 陷阱：无限流忘了 limit：Stream.generate 不配 limit/skip，终端操作会永远跑下去（或 OOM）。
  • 场景题口径："你们项目里 Stream 用在哪、踩过什么坑？"——准备一个真实例子：如 toMap 未传 merge 函数上线后抛 IllegalStateException、并行流调外部接口拖慢整机的排查经历。
