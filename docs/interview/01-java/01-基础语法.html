02从 .java 到运行：JDK / JRE / JVM 与字节码

关系一句话：JDK ⊃ JRE ⊃ JVM。JVM 只负责执行字节码；JRE = JVM + 核心类库；JDK = JRE + 编译器 javac + 工具链（javap、jdb、jconsole 等）。

执行链路

.java ──javac 前端编译──> .class（字节码）──类加载──> JVM
                                        ├─ 解释器逐条执行
                                        └─ JIT 热点代码编译为机器码（存入 CodeCache）
  • 为什么有中间字节码层：一次编译到处运行（不绑定特定 CPU 指令集）；相比 JS / Python 纯解释执行效率更高；字节码是 JVM 生态的基石（Kotlin、Scala、Groovy 都编译成 .class）；安全和反射等动态能力也建立在这层之上。
  • JIT（Just-In-Time）：运行期把频繁执行的热点代码（方法调用计数 / 回边计数超过阈值）编译成机器码缓存，用次数换速度。
  • 分层编译（Tiered Compilation）：HotSpot 实际是 C1（client，编译快、优化浅）和 C2（server，编译慢、优化深）两级 JIT 配合——C1 先快速出机器码保住启动速度，热点再升级 C2 深度优化（内联、逃逸分析、锁消除）。JDK 8 起默认开启。
  • AOT（Ahead-Of-Time）：执行前静态编译成机器码（GraalVM Native Image）。启动快、内存省、难反编译；代价是反射、动态代理、运行时类加载等动态特性受限——这正是 Spring 3 对 Native 支持做了大量改造的原因。

亲手看一眼字节码（javap，加分动作）

// Demo.java
public class Demo {
    public static int add(int a, int b) { return a + b; }
    public static void main(String[] args) { System.out.println(add(1, 2)); }
}

$ javac Demo.java && javap -c Demo
public static int add(int, int);
    Code:
       0: iload_0        // 取局部变量表第 0 个 int（a）压栈
       1: iload_1        // 取 b 压栈
       2: iadd           // 栈顶两个 int 相加，结果回栈
       3: ireturn        // 返回栈顶 int
// 每个 .class 头 4 字节是魔数 0xCAFEBABE——"为什么 Java 图标是咖啡"的标准冷知识
  • 字节码是基于栈的指令集（操作数先进栈再运算），不是物理 CPU 那种基于寄存器的指令集——所以同一份 .class 才能不绑定具体 CPU 架构。
  • javap 常用参数：-c 反汇编、-v 常量池/版本号/行号表全量、-l 行号表与局部变量表。面试聊"你看过字节码吗"，拿 add 方法这三条指令开讲最稳。

答题口径：先说三层包含关系，再主动展开"字节码 + 解释/JIT 混合执行"，能顺带提一句 AOT 和 GraalVM 就是加分项。类加载与 JIT 细节在 03-jvm 板块深入。

  • 追问链：.class 一定能跨版本运行吗？→ 不能。每个 JDK 编译出的 .class 带 major version（JDK 8 = 52，JDK 17 = 61），高版本 JVM 能加载低版本字节码，反之报 UnsupportedClassVersionError——这就是"用 JDK 17 跑 JDK 11 编译的包没问题，反过来必炸"的原理。
  • 追问链：解释执行既然慢，为什么不全部 JIT？→ 冷代码编译不划算（编译本身耗 CPU/内存），且很多代码一生只执行几次。分层编译的本质是"按热度分级投资"。

03数据类型全景：8 种基本类型 + 引用类型

类型大小默认值包装类缓存范围

存储位置（高频追问点）

  • 基本类型局部变量：存在栈帧的局部变量表里，方法结束随栈帧弹出。
  • 基本类型成员变量：随对象在堆里（static 的在方法区/元空间的类信息中）。
  • 包装类型 / 引用类型：对象本体在堆，变量里存的是引用。

易错："基本类型存在栈上"这句话不严谨——只有局部变量在栈上，成员变量跟着对象进堆。面试官就爱挖这个半对不对的表述。

基本类型 vs 包装类型怎么选

  • 局部变量、循环计数用基本类型：无装箱开销、不会 NPE。
  • 实体字段 / RPC / DAO / 泛型与集合只能用包装类型（List<int> 不存在），数据库可能为 null 的列必须用包装类型，否则 0 和 null 语义混淆。
  • 比较：基本类型用 ==，包装类型一律 equals()。
  • 追问链：char 2 字节能存"𠀀"这种生僻字/emoji 吗？→ 存不了。char 是 UTF-16 代码单元，BMP 内字符（常用汉字"中""国"）一个 char 够；增补区字符（emoji 😀、生僻字）要两个 char 组成代理对（surrogate pair），所以 "😀".length() == 2——数"字符个数"应该用 codePointCount。详见本章 char 与编码一节。
  • 追问链：boolean 到底占几个字节？→ JVM 规范没定义 boolean 的独立指令，压栈操作按 int（4 字节）处理；单个 boolean 字段在对象里通常占 1 字节（再补齐到 8 的倍数）。标准答案就一句："规范未定，实现上栈按 int、堆里按 1 字节算"。

04自动装箱拆箱与缓存池 ⭐

装箱 = Integer.valueOf(int)，拆箱 = intValue()，编译期自动插入（语法糖）。经典陷阱题：

Integer a = 127, b = 127;
Integer c = 128, d = 128;
System.out.println(a == b);   // true  —— 127 在缓存池内，valueOf 返回同一个对象
System.out.println(c == d);   // false —— 128 超出缓存，各自 new 了新对象
System.out.println(c.equals(d)); // true —— 值比较，包装类型永远用 equals
  • 缓存实现在 Integer.valueOf() 里的静态内部类 IntegerCache，默认 [-128, 127]；-XX:AutoBoxCacheMax=<size> 可调上限，下限 -128 不可改。
  • Byte/Short/Integer/Long 缓存 [-128,127]，Character 缓存 [0,127]，Boolean 返回 TRUE/FALSE 单例；Float/Double 没有缓存。
  • 若一边是基本类型，== 会先拆箱再比值：c == 128 为 true——陷阱只在两边都是包装类型时出现。

IntegerCache 源码（能默写核心三行就够）

private static class IntegerCache {
    static final int low = -128;          // 下限写死
    static final int high;                // 上限可在 JVM 启动时调
    static final Integer[] cache;         // 静态数组，类加载时全部预先建好
    static {
        int h = 127;
        String integerCacheHighPropValue =
            VM.getSavedProperty("java.lang.Integer.IntegerCache.high");
        // ... 解析 -XX:AutoBoxCacheMax，上限还可以把 high 压到不小于 127
        cache = new Integer[(high - low) + 1];
        int j = low;
        for (int k = 0; k < cache.length; k++)
            cache[k] = new Integer(j++);
    }
}
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];   // 命中直接返回缓存对象
    return new Integer(i);            // 未命中才 new（JDK 9 后 new Integer 已 @Deprecated）
}

拆箱 NPE：藏得最深的一类线上事故

Integer count = null;
int n = count + 1;                      // 拆箱 NPE——好懂，但少见

int flag = flagConfig ? 1 : count;      // 三元运算符：两臂类型不一致
// 编译器把 int 臂 1 装箱、Integer 臂拆箱"统一类型"→ 实际调 count.intValue() → NPE
// 修复：cond ? 1 : count == null ? 0 : count，或两臂都用 Integer（统一成装箱不拆箱）

原理：JLS 规定三元运算符若一臂是基本类型、另一臂是包装类型，结果类型按"数值提升"走基本类型——于是包装臂被迫拆箱。这是阿里规约"三元表达式注意拆箱 NPE"条目的根源。

实战关联：阿里巴巴规约强制"POJO 属性必须用包装类型"，RPC 方法返回值/参数用包装类型；同时提醒所有包装类型之间相等比较必须用 equals——这两条就是从这道题长出来的。

  • 追问链：为什么下限 -128 不能调？→ 协议约定俗成 + 实现简单（负索引偏移 i + 128 恒非负）；上调上限只放宽"命中区间"，不影响任何既有语义，所以 JVM 敢开放它。
  • 追问链：装箱发生在方法重载时怎么选？→ 重载解析三步：① 先找不需要装箱/变长参数就能匹配的（int → foo(int)）；② 找允许装箱/拆箱的（foo(Integer)）；③ 才考虑 varargs（foo(int...)）。所以 foo(1) 在 foo(int) 和 foo(Integer) 同时存在时永远选前者，装箱只是兜底——同理 remove(int index) 和 remove(Object o) 的经典冲突（见 第 08 章）。

05Java 只有值传递 ⭐

结论先行：Java 是严格的值传递（pass by value），没有引用传递。传递引用类型时，拷贝的是"引用的值"（即地址值的副本），不是对象本身。

static void change(StringBuilder sb, int x) {
    sb.append("!");        // 生效：副本引用指向同一个对象，改的是堆里那个对象
    sb = new StringBuilder("new");  // 不影响外面：只改了副本引用的指向
    x = 99;                // 不生效：基本类型拷贝的是值
}

StringBuilder buf = new StringBuilder("hi");
int n = 1;
change(buf, n);
System.out.println(buf + " " + n);   // hi! 1

记忆骨架

  • 基本类型 → 拷贝值；引用类型 → 拷贝地址值。
  • 方法内对参数重新赋值（改指向）不影响调用方；通过参数修改对象内部状态会影响调用方。
  • 所以 String / Integer 这类不可变对象在方法里"改不了"：看起来是改值，实际只能改指向。

经典反例：为什么"swap 两个 Integer"永远失败

static void swap(Integer a, Integer b) {
    Integer tmp = a; a = b; b = tmp;   // 只交换了两个"引用副本"的指向，堆对象纹丝不动
}
Integer x = 1, y = 2;
swap(x, y);
System.out.println(x + "," + y);       // 还是 1,2

// 想真的换出去，只能走"可变载体"：数组 / AtomicReference / 自定义 Holder
static void swap(int[] pair) { int t = pair[0]; pair[0] = pair[1]; pair[1] = t; }

追问预判："那 C++ 的引用传递和 Java 有什么区别？"——C++ 的 int& r = x 是变量的别名，对 r 赋值直接改 x；Java 永远拿到的是副本，做不到这件事。

  • 追问链：String 参数在方法里"改"了，为什么外面看不到？→ 两层原因叠加：① 值传递——改的是副本引用；② String 不可变——concat/replace 全是新对象，连"改内部"这条路都不存在。两个知识点经常被串成一道题考。
  • 追问链：为什么说"数组当出参"不违反值传递？→ 传进去的是数组引用的副本，但两个引用指向同一个堆上数组，arr[0] = x 改的是共享对象的内容——"改指向不可见，改内容可见"口诀的直接应用。

06类型转换与浮点精度

自动提升与强制转换

  • 隐式 widening：byte → short → int → long → float → double（注意 int → float 可丢精度——float 尾数只有 24 位，装不下全部 int）。
  • 强制 narrowing 要显式写 (int)，可能截断；byte b = (byte)(byte1 + byte2) 这种编译期提升坑要会讲。
int big = 130;
byte b = (byte) big;          // 截断：只留低 8 位 → -126（130 = 0b10000010，符号位 1）
System.out.println(b);        // -126，不是 130 也不是 3

char c = 'A';
int n = c + 1;                // char 参与算术先提升为 int → 66；写回 char 要强转
System.out.println((char) n); // 'B'
byte b1 = 10;
b1 += 1;                      // ✅ 复合赋值自带隐式强转，编译通过
b1 = b1 + 1;                  // ❌ b1+1 提升为 int，赋回 byte 报错——复合赋值反而"更宽松"

浮点数为什么不准

IEEE 754 用 V = (-1)^S × M × 2^E（符号位 + 尾数 + 阶码）表示。二进制下 0.1、0.2 这类十进制小数是无限循环二进制小数，尾数位数有限必然截断，误差就进来了。

System.out.println(0.1 + 0.2);            // 0.30000000000000004
System.out.println(0.1 + 0.2 == 0.3);     // false
System.out.println(1.0 / 3 * 3 == 1);     // false；double 能精确表示的只有"分母是 2 的幂"类小数

// 金额计算的正解：
BigDecimal a = new BigDecimal("0.1");     // ⭐ 用 String 构造，别用 double 构造
BigDecimal r = a.add(new BigDecimal("0.2"));
System.out.println(r);                     // 0.3 精确
System.out.println(r.compareTo(new BigDecimal("0.3")) == 0);  // true（equals 会连 scale 一起比）

BigDecimal 四个陷阱：① new BigDecimal(0.1) 把 double 的误差原样带进来（打印就是 0.1000000000000000055511151231257827…），必须用字符串构造或 BigDecimal.valueOf()（内部先 Double.toString）；② equals 比较 scale（0.10 ≠ 0.1），比大小用 compareTo；③ divide 除不尽且不指定 scale/舍入模式直接抛 ArithmeticException——必须写 divide(b, 2, RoundingMode.HALF_UP)；④ 它也不可变，setScale/add 返回的是新对象，"调完方法不接返回值"等于白调。

  • 追问链：为什么金额不用 long 存"分"？→ 其实这是比 BigDecimal 更稳的方案（long 9.2×10^18 分 = 92 亿亿元，永不溢出、无舍入误差）；BigDecimal 的价值在"小数位数本身是业务需求"的场景（利率、汇率），两者都要会说。面试加分答法：内部记"分"用 long，对外展示时再转 BigDecimal 格式化。

07String 不可变性 ⭐⭐（必考）

怎么实现的

public final class String {          // final 类：不能被继承改写行为
    private final byte[] value;       // JDK 9+：byte[] + coder（LATIN1/UTF16）；JDK 8 是 char[]
    private int hash;                 // 缓存 hashCode，因为内容不会变
    // 没有 setter，所有"修改"方法都返回新对象：replace/substring/concat/trim/toUpperCase…
}

为什么设计成不可变（答题骨架，4 条）

  1. 字符串常量池的前提：同一份字面量可以放心共享一个对象，省内存。若 String 可变，一处修改、所有引用全遭殃。
  2. 线程安全：不可变对象天然线程安全，不需要任何同步，可以自由跨线程传递。
  3. hashCode 可以缓存：String 是 HashMap 最常用的 key，hash 算一次就存字段，后续 O(1) 取用；key 可变的话 HashMap 直接废掉。
  4. 安全性：类加载器按类名字符串加载、文件路径、网络参数——不可变保证传入后不会被中途篡改。

常量池与 intern

String s1 = "abc";                 // 字面量 → 字符串常量池（JDK 7 起位于堆中）
String s2 = "abc";
System.out.println(s1 == s2);       // true，池中同一个对象

String s3 = new String("abc");      // 堆里 new 一个新对象；"abc" 字面量若不存在还会先进池
System.out.println(s1 == s3);       // false
System.out.println(s1 == s3.intern()); // true，intern() 返回池中那份

// 编译期常量折叠：
String s4 = "ab" + "c";             // 编译期直接折叠成 "ab c"→"abc"
System.out.println(s1 == s4);       // true
String ab = "ab";
String s5 = ab + "c";               // 运行期拼接（JDK 8：StringBuilder；JDK 9+：invokedynamic），产生新对象
System.out.println(s1 == s5);       // false
final String fab = "ab";
String s6 = fab + "c";              // fab 是编译期常量（final + 字面量初始化）→ 常量传播后仍折叠
System.out.println(s1 == s6);       // true

"new String("abc") 创建几个对象"的标准答案：最多 2 个——池中字面量 "abc"（若首次出现）+ 堆中 new 出来的对象。追问 new String("ab") + "c" 时注意 StringBuilder 参与，此时答案是"堆上 2~3 个 + 池中 'ab'"级别的讨论题——先给"最多 2 个"的口径再展开，别一上来就抠细节。

intern()：一个方法横跨 JDK 6/7 的版本差异

String s = new String("a") + new String("b");  // 堆上新对象 "ab"，池中没有 "ab" 字面量
String i = s.intern();
System.out.println(i == s);        // JDK 7+：true —— intern 发现池里没有，
                                   //   把堆上这个对象的引用登记进常量池（JDK 7 起）
                                   // JDK 6：false —— 常量池在永久代，intern 会"复制"一份进去，
                                   //   池里那份和堆里 s 不是同一个对象
  • 变化的根因：JDK 7 把字符串常量池从永久代挪到了堆，池里存"堆对象的引用"成为可能，intern 从"复制"变"登记"。这一问能同时考常量池位置 + 版本演进，高级岗常拿它区分背诵党和理解党。
  • 实战口径：业务代码别手写 intern()。它适合"海量重复短字符串去重"的特定场景（如缓存 key），滥用会让我们自己管理池压力——且 intern 是 native 方法、旧版本有性能争议。
  • 同类需求生产上更常用 G1 的字符串去重（JDK 8u20+，-XX:+UseStringDeduplication）：GC 时自动把 value 数组相同的 String 底层共享，对业务透明。

JDK 9 把 char[] value 改成 byte[] + coder 标记（Compact Strings）：纯 Latin-1 字符串内存减半，中文等多数字符仍走 UTF-16。这一句能体现你跟过新版本演进。

反射改 String 的下场：JDK 8 时代反射改 value 字段能"全局污染"（同字面量全 JVM 生效），JDK 9 模块系统把 java.lang 封死后，setAccessible(true) 直接抛 InaccessibleObjectException——面试聊"反射能改 String 吗"，按"能→有害→新版已封死"三段答。

为什么循环里不能用 String +

// 反例：每次 + 都 new StringBuilder + new String，n 轮产生 ~2n 个临时对象
String s = "";
for (int i = 0; i < 10000; i++) s += i;

// 正解：循环外建一个 builder，内部 char[] 扩容 amortized O(1)
StringBuilder sb = new StringBuilder(64);   // 能预估容量就给初始容量，避免扩容拷贝
for (int i = 0; i < 10000; i++) sb.append(i);
  • StringBuilder 底层是 char[]（JDK 9 后 byte[]），默认容量 16，扩容为 (旧容量 × 2) + 2，Arrays.copyOf 拷贝。
  • 单行 a + b + c 编译器本身就会转成 StringBuilder / invokedynamic（JDK 9+ StringConcatFactory），单行拼接不必手写 builder。
  • JDK 9+ 拼接底层从固定 StringBuilder 改为 invokedynamic 调 StringConcatFactory，可按策略生成更优字节码——高级岗加分点。

09char 与编码：UTF-16、代码点与乱码根因 ⭐

char 是 UTF-16 代码单元，不是"一个字符"

  • Java 源码层的 char 固定 2 字节，取值 [0, 65535]，本质是 UTF-16 的一个代码单元（code unit）。
  • Unicode 字符分两段：BMP（基本多文种平面）内一个代码点 = 1 个 char；增补平面（emoji、古文字、部分生僻汉字）一个代码点 = 2 个 char（代理对：高代理 0xD800-0xDBFF + 低代理 0xDC00-0xDFFF）。
  • 所以「一个汉字占几字节」在 Java 里要反问编码：JVM 内 String 按名字是 UTF-16（JDK 9 后纯 ASCII 内部存 LATIN1），落盘/上网则看所选编码——UTF-8 常用汉字 3 字节、GBK 2 字节、UTF-16 4 字节（含 BOM 讨论）。
String s1 = "中";
System.out.println(s1.length());              // 1 —— BMP 字符，1 个 char
System.out.println(s1.getBytes("UTF-8").length);   // 3 —— 落盘 UTF-8 编码
System.out.println(s1.getBytes("GBK").length);     // 2

String s2 = "😀";                              // U+1F600，增补平面
System.out.println(s2.length());              // 2 —— 代理对，2 个 char
System.out.println(s2.codePointCount(0, s2.length()));  // 1 —— 才是"人眼数出来的字符数"
System.out.println(s2.charAt(0));             // 打出乱码 '?'：半个代理对不是合法字符

// 遍历"字符"的正确姿势（按代码点）：
s2.codePoints().forEach(cp -> System.out.println(new String(Character.toChars(cp))));

乱码的根因：编码与解码不对称

  • 乱码从来不是"数据坏了"，而是用编码 A 编码的字节被拿编码 B 去解码。经典组合："UTF-8 字节流按 ISO-8859-1 解码"（每个字节变一个怪字符，可逆，能救回来）；"GBK 字节按 UTF-8 解码"（大量非法序列被替换成 �，不可逆，救不回来）。
  • 方向记法：byte[] ← 编码 → String。new String(bytes, charset) 是解码（字节→字符串），str.getBytes(charset) 是编码（字符串→字节）。两端 charset 不一致 = 乱码。
  • 为什么 ISO-8859-1 当"中间转码跳板"：它和字节是一一映射的（单字节全区间），任何字节流按它解码都不丢信息，所以老系统"存不动中文"时常用 latin1 落库再转回来。

面试组合拳：为什么读写文件/网络必须显式指定 charset？——因为 new String(bytes)、getBytes() 无参版本用的是平台默认编码（file.encoding，Linux 容器里常是 ANSI_X3.4-1968 即纯 ASCII），本地好好的代码进容器就乱码。JDK 18 起（JEP 400）默认编码统一为 UTF-8，但老项目仍要显式写。这也是 StandardCharsets.UTF_8 被规约要求 everywhere 的原因。

  • 追问链：char 能存 emoji 吗？→ 不能。char 只有 16 位，emoji 在增补平面（码点 > 0xFFFF），一个 emoji 要两个 char（代理对）或直接用 int 码点表示——Character.toChars(0x1F600) 返回 length 2 的 char[]。
  • 追问链：String.length() 返回什么？→ 代码单元数不是字符数。带 emoji 的字符串截取子串还可能把代理对拦腰截断，产出"半个字符"的非法 String——文本截断要按 code point 或用 BreakIterator。

10运算与溢出陷阱 ⭐

整型溢出：静默回绕，不是异常

int max = Integer.MAX_VALUE;      // 2147483647 = 0x7FFFFFFF
System.out.println(max + 1);      // -2147483648 —— 补码回绕，不抛任何异常
System.out.println(max * 2);      // -2

// 经典事故：先按 int 乘再转 long，溢出已经发生
int seconds = 1_000_000;
long millis = seconds * 1000;          // 1_000_000_000 没超 int，侥幸对
long nanos  = seconds * 1_000_000;     // 先 int 溢出再 widening → 错值！
long ok     = seconds * 1_000_000L;    // ✅ 让一边先变 long，全程 long 运算
long safe   = Math.multiplyExact(seconds, 1_000_000L);  // JDK 8+ Math.*Exact 全家桶：溢出直接抛 ArithmeticException
  • 为什么静默：JVM 设计追求指令确定性——每条算术指令耗时固定、不依赖检查分支，溢出检查交给需要的人显式调 Math.addExact / subtractExact / multiplyExact（JDK 8+）。
  • 业务口诀："可能大"的中间量先升 long，金额量根本不用浮点；分页计算 (pageNo-1) * pageSize 在 pageNo 极大时就是这个坑。

位运算与移位：三个必考细节

int neg = -8;
System.out.println(neg >> 1);    // -4  —— 算术右移，高位补符号位（负数还是负数）
System.out.println(neg >>> 1);   // 2147483644 —— 逻辑右移，高位补 0（负数变巨正数）
System.out.println(neg >>> 0);   // -8；>>> 会先把操作数提升 int/long

System.out.println(-1 >> 1);     // -1 —— 负数算术右移永远不"趋近 0"，除 2 口诀只对正数严格成立
System.out.println(1 << 35);     // 32 —— 移位数对 32 取模（int）；long 对 64 取模，1L<<64==1L 自身
  • >>> 是 Java 补齐 C 缺口的发明：C/C++ 对无符号右移没区分，Java 没有 unsigned int，就用 >>> 显式表达"补 0"。HashMap.hash() 的 h ^ (h >>> 16) 正是用它取高位参与扰动（第 08 章细讲）。
  • 追问链：自增 i++ 是原子操作吗？→ 不是。i++ 编译成"读-改-写"三条字节码（getfield/iload → iadd → putfield），多线程下丢失更新；i++ 的正确并发替代是 AtomicInteger.incrementAndGet()（CAS）或锁——本质成因与修法见 02-concurrency 无锁编程。
  • 追问链：1/0 和 1/0.0 的区别？→ 整数除 0 抛 ArithmeticException；浮点除 0 得 Infinity/NaN（IEEE 754 定义了这些特殊值），Double.isNaN/isInfinite 检查。0.0/0.0 == Double.NaN 是 false（NaN 与任何比较都假），判 NaN 必须 isNaN。

11高频追问与陷阱

  • 追问链：String 不可变 → 那我想改怎么办？→ StringBuilder / 想共享就 intern；再追"反射能改 value 吗"→ JDK 9 前可以暴力改 value 字段（有隐患），JDK 12+ 后模块系统封锁 String.value，反射修改直接失败。
  • 追问链：Integer 缓存 → 为什么是 -128 到 127？→ JVM 规范建议的最小区间，命中率高、内存可控；设计上是对"小整数高频使用"的权衡，可调上限体现了这一点。
  • 追问链：char 能存汉字吗？→ 常用汉字能（BMP 内，一个 char），生僻字/emoji 不能（增补平面要代理对两个 char）；进一步追"String.length() 返回什么"答"代码单元数，不是字符数"。
  • 追问链：为什么读写文件必须指定编码？→ 无参 API 用平台默认编码（JDK 17- 是 file.encoding，容器里常退化为 ASCII），本地/线上环境不一致就乱码；JDK 18+ 默认 UTF-8 但显式 StandardCharsets.UTF_8 仍是规约。
  • 追问链：BigDecimal 还有什么坑？→ 除不尽不传 scale 抛 ArithmeticException、equals 比 scale、不可变方法要接返回值；再深问"金额为什么不用 double"回到 IEEE 754。
  • 陷阱：整型先算后转 long——int * int 先溢出再 widening；同类坑：两个 Integer 用 ==、a += b 的隐式强转。
  • 陷阱：-1 >> 1 还是 -1——负数算术右移不趋近 0；"右移一位等于除 2"口诀只对正数成立。
  • 陷阱：字符串拼接混入 null——"v=" + null 得到 "v=null" 字符串（不是 NPE），悄悄把 null 写进日志/落库；真正的 NPE 在 null.toString() 或拆箱场景。
  • 陷阱：Integer == null 拆箱 NPE：三元运算符 cond ? 1 : wrappedNull 会因类型统一自动拆箱，NPE 藏得极深（阿里规约专门有条目）。
  • 陷阱：str.equals("abc") 顺序反了 NPE → 常量放前面 "abc".equals(str) 或 Objects.equals。
  • 陷阱：switch 传 null 的 Integer 也会拆箱 NPE。
