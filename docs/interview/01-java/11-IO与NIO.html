02IO 体系：字节流 vs 字符流

Java IO 按数据单位分两族、按方向各四基类（全是抽象类，全部实现 Closeable）：

输入输出单位适用
字节流InputStreamOutputStreambyte（0~255）一切数据：图片/视频/exe/压缩包；网络传输的底层单位
字符流ReaderWriterchar（16 bit）文本：需要按字符处理、涉及编码解码时
  • 字符流的本质 = 字节流 + 编码解码器：任何 Reader/Writer 内部都包着一个流 + Charset。InputStreamReader / OutputStreamWriter 就是字节流与字符流之间的桥梁。
  • 编码陷阱（笔记要点）：FileReader / FileWriter 使用平台默认编码，跨环境（开发机 UTF-8、容器 UTF-8、生产 GBK）读写文本会乱码——显式指定更安全。字符集：ASCII（英文 1 字节）、GBK（中文 2 字节）、Unicode（字符集标准）；互联网通用编码 UTF-8（变长 1~4 字节，中文 3 字节）。

常用具体流速查（按包装层次记）

层次字节流字符流用途
节点流（直连数据源）FileInputStream / FileOutputStreamFileReader / FileWriter文件
ByteArrayInputStream / ByteArrayOutputStreamCharArrayReader / StringReader内存数组/字符串（不需要关闭）
PipedInputStream / PipedOutputStreamPipedReader / PipedWriter线程间管道通信
Socket 的流—网络
处理流（包装增强）BufferedInputStream / BufferedOutputStreamBufferedReader / BufferedWriter缓冲（readLine 在 Reader 侧）
DataInputStream / DataOutputStream—基本类型读写
ObjectInputStream / ObjectOutputStream—对象序列化（见第 04 节）
转换/打印PrintStream（System.out）PrintWriter、InputStreamReader / OutputStreamWriter桥接与格式化输出

标准写法：显式编码 + try-with-resources

// try-with-resources：实现 Closeable 的资源自动 close（编译期生成 finally close）
try (InputStream in = new FileInputStream("a.txt");
     OutputStream out = new FileOutputStream("b.txt")) {
    byte[] buf = new byte[8192];
    int n;
    while ((n = in.read(buf)) != -1) {     // read 返回实际读到字节数，-1 表示 EOF
        out.write(buf, 0, n);
    }
}

// 文本读写：InputStreamReader 显式指定字符集，别让平台默认编码决定行为
try (BufferedReader reader = new BufferedReader(
        new InputStreamReader(new FileInputStream("a.txt"), StandardCharsets.UTF_8))) {
    String line;
    while ((line = reader.readLine()) != null) { ... }
}
// JDK 11+ 更省事：Files.readString(path, StandardCharsets.UTF_8) / new FileReader(file, charset)

衍生族谱记法：字节流节点流（File/Socket/ByteArray）→ 过滤流层层包装（Buffered/Data/Object/Print）；字符流同理（FileReader → BufferedReader，PrintWriter）。System.in 本身就是 InputStream，System.out 是 PrintStream——打印流只做输出方便格式化。

03缓冲流与装饰器模式 ⭐

装饰器模式在 IO 里的体现

装饰器（Decorator）：不改变原对象、不改其类层次，通过包装给对象叠加职责。Java IO 的过滤流全部继承基类并持有基类引用——这就是教科书级的装饰器：

// BufferedInputStream 的类骨架（简化）：
public class FilterInputStream extends InputStream {     // 装饰器基类
    protected volatile InputStream in;                   // 持有被装饰者
    ...
}
public class BufferedInputStream extends FilterInputStream {
    protected volatile byte[] buf;                       // 默认 8192（8KB）
    ...
}

// 使用：一层层洋葱式包装，读写接口不变、能力叠加
InputStream in = new BufferedInputStream(                // 第 2 层：加缓冲
                 new FileInputStream("data.bin"));       // 第 1 层：真正干活（节点流）
DataInputStream din = new DataInputStream(in);           // 第 3 层：加基本类型读写
din.readInt();
  • 为什么缓冲流快：无缓冲时每个 read() 都是一次系统调用（用户态/内核态切换，微秒级）；BufferedInputStream 先一次性读满 8KB 缓冲，后续 read 从内存数组里拿——把 N 次 syscall 合并成 N/8192 次。缓冲区默认 8KB，构造器可传自定义大小。
  • 适配器模式：InputStreamReader / OutputStreamWriter 是字节流 ↔ 字符流之间的适配器（接口形状转换 + 编解码）。
  • 其他：NIO 里还能见到工厂（Channels/ByteBuffer 工厂方法）、观察者（Selector 的事件注册与就绪通知，也被称作 NIO 的核心设计）。
  • 典型考题："设计模式里装饰器和代理的区别"——装饰器强调同接口叠加职责、多层包装、调用者明知；代理强调控制访问，增强对调用者透明（见第 12 章动态代理）。

陷阱：包装了缓冲流之后又直接读写节点流，或 BufferedWriter 不 flush()/不 close 就退出进程——缓冲区里的尾部数据会丢。close() 会级联触发内层流的 flush + close。

04序列化：Serializable、serialVersionUID、transient

序列化：把对象转成字节流，用于网络传输、中间件缓存、落库；反序列化是其逆过程。Java 原生方案：实现标记接口 java.io.Serializable，用 ObjectOutputStream.writeObject() / ObjectInputStream.readObject()（笔记要点）。

serialVersionUID：版本指纹

public class User implements Serializable {
    private static final long serialVersionUID = 1L;   // 强烈建议显式声明
    private String name;
    private transient String password;                  // 不参与序列化
    // 反序列化后 password == null
}
  • 反序列化时 JVM 会比对字节流里的 serialVersionUID 与当前类的：不一致直接抛 java.io.InvalidClassException——这是"两端类版本不一致就报错"的机制。
  • 不显式声明会怎样：编译器按类结构（字段/方法/接口等）自动计算一个，一旦类有任何结构性改动（加个字段），指纹就变，旧数据全部反序列化失败。显式声明后，兼容性由开发者自己掌控：新增字段反序列化时为默认值，删掉的字段被忽略。
  • transient：标记的字段不参与序列化（敏感信息密码、缓存字段、不可序列化的派生值）。
  • 静态变量不序列化：static 属于类不属于实例，序列化的是对象状态。
  • 父类未实现 Serializable 时，父类字段不参与（且父类必须有无参构造器供反序列化链路初始化）。

ArrayList 的 writeObject 优化（源码级加分点）

// ArrayList 实现 Serializable，但 elementData 数组容量往往大于实际元素个数：
// 若直接默认序列化，会把尾部一堆 null 也写进字节流，浪费空间。
// 所以它提供了私有的 writeObject/readObject：
private void writeObject(java.io.ObjectOutputStream s) throws IOException {
    int expectedModCount = modCount;
    s.defaultWriteObject();                 // 序列化元数据（含 size 字段）
    s.writeInt(size);                       // 只写"有效元素个数"
    for (int i = 0; i < size; i++) {
        s.writeObject(elementData[i]);      // 只写前 size 个非 null 元素
    }
    ...
}
// 教训：序列化协议可以定制——提供私有 writeObject/readObject 即可接管默认行为
  • 同类机制：readResolve() 可以在反序列化后替换返回对象——单例/枚举防反序列化破坏靠它（枚举天然免疫，反序列化返回同一个实例）。
  • 替代方案：实际项目多用 JSON（Jackson）、Protobuf（跨语言、体积小）；Java 原生序列化因体积大、性能差、且存在反序列化漏洞（构造恶意字节流触发任意类构造/gadget 链），在安全审计里是重点扣分项。

答题口径："serialVersionUID 是类的版本指纹，显式声明是为了让兼容性由开发者控制；不一致抛 InvalidClassException。transient 和 static 不序列化。另外我知道 ArrayList 覆写了私有 writeObject 只写 size 个元素避免序列化冗余容量——序列化行为是可定制的。"最后一句是 7 年经验的分水岭。

05NIO 三大组件：Buffer · Channel · Selector ⭐

先立认知：一次 IO = 等待就绪 + 数据拷贝

（笔记要点）一次读取要两步：① 等待数据就绪（从网络/磁盘进内核缓冲区，慢）；② 拷贝数据（内核缓冲区进用户态，快）。三种 IO 模型就差在怎么处理第 ① 步：

BIO（阻塞）NIO（同步非阻塞 + 多路复用）AIO（异步）
等待数据就绪线程一直阻塞死等不傻等：注册到 Selector，就绪才处理发起后立刻返回，内核完成后回调
拷贝数据自己拷自己拷（就绪后同步 read/write）内核直接拷到你给的缓冲区
线程模型一连接一线程一个线程管多连接回调 / Future
Java 支持java.iojava.nio（JDK 1.4+）AsynchronousChannel（JDK 7+，Linux 上实际用 epoll 模拟，Netty 未采用）

Buffer：NIO 的数据容器

ByteBuffer buf = ByteBuffer.allocate(1024);   // 三个指针：capacity >= limit >= position
// 写模式：position 指向下一个写入位
channel.read(buf);        // 数据进 buffer
// 写转读的关键一步：
buf.flip();               // limit = position; position = 0 —— 切为读模式
while (buf.hasRemaining()) {
    channel2.write(buf);  // 从 position 读到 limit
}
buf.clear();              // 归位为写模式（内容不清，只是指针重置）
  • flip 是必考点：写完不 flip 就读，读到的是未定义区域；clear 之后旧数据还在，只是逻辑上可覆盖。
  • Heap Buffer（allocate，堆内 byte[]）vs Direct Buffer（allocateDirect，堆外，见第 07 节）。
  • Buffer 不是线程安全的。

Channel：双向通道

  • Stream 是单向的（Input/Output 分家），Channel 双向，可同时读写，可异步，必须配合 Buffer 使用（不提供字节级 API）。
  • 常用：FileChannel（文件，唯一不能配 Selector 的——文件始终"就绪"）、SocketChannel / ServerSocketChannel（TCP）、DatagramChannel（UDP）。

Selector：一个线程管多连接

// 骨架：Reactor 事件循环的雏形（笔记要点：Selector 是"事件复用器"，
// 在一个阻塞点上同时等待很多通道的就绪事件，而不是每个通道各自阻塞或轮询）
Selector selector = Selector.open();
ServerSocketChannel server = ServerSocketChannel.open();
server.bind(new InetSocketAddress(8080));
server.configureBlocking(false);                       // 注册 Selector 的 Channel 必须非阻塞
server.register(selector, SelectionKey.OP_ACCEPT);     // 关注"连接到达"事件

while (true) {
    selector.select();                                 // 唯一的阻塞点：等任一通道就绪
    Set<SelectionKey> keys = selector.selectedKeys();   // 就绪事件集合
    for (SelectionKey key : keys) {
        if (key.isAcceptable()) { /* accept 新连接，注册 OP_READ */ }
        if (key.isReadable())   { /* 从该 Channel 非阻塞 read 到 Buffer */ }
        if (key.isWritable())   { /* 缓冲区可写时写出（一般不常驻注册 OP_WRITE） */ }
    }
}
// 四种事件：OP_ACCEPT / OP_CONNECT / OP_READ / OP_WRITE
  • 为什么省线程：BIO 里 1 万个连接 = 1 万个线程各自阻塞在 read；NIO 里 1 万个 Channel 注册到 1 个 Selector，只有真正有数据的连接才会被 select() 返回——线程数与连接数解耦，这是 Netty 用少量 EventLoop 撑起海量连接的根本原因。
  • Selector 在 Linux 上的底层就是 IO 多路复用（select/poll/epoll）的封装；epoll 为什么高效（红黑树 + 就绪链表、回调而非遍历）在 12-os 板块展开。

答题口径："NIO 三大组件：Buffer 是数据容器（capacity/position/limit 状态机，flip 切读写）；Channel 是双向通道，必须非阻塞地配 Buffer；Selector 是事件复用器，把'每连接一线程各自阻塞'变成'一个阻塞点等所有连接'，底层是 epoll。所以 NIO 的准确定义是同步非阻塞 + IO 多路复用——就绪通知是异步的，数据拷贝仍要自己同步做，这就是它和 AIO 的分界。"

06mmap 内存映射：FileChannel.map

和传统 read 的区别

  • 传统 read：磁盘 → 内核 page cache → 拷贝到用户态缓冲区 → JVM 堆内 byte[]。两次拷贝、一次 syscall。
  • mmap：FileChannel.map() 把文件区域映射进虚拟地址空间，用户态和内核共享同一份 page cache——省掉"内核 → 用户态"那次拷贝，首次访问触发缺页中断由内核把数据加载进 page cache，之后读文件 = 读内存。
try (FileChannel ch = FileChannel.open(Path.of("big.data"), StandardOpenOption.READ)) {
    MappedByteBuffer mbb = ch.map(FileChannel.MapMode.READ_ONLY, 0, ch.size());
    // 读文件就像读内存：不需要 ch.read(buf)，也没有"拷贝到堆"这一步
    while (mbb.hasRemaining()) {
        byte b = mbb.get();
    }
    // MapMode.READ_WRITE 下对 mbb 的修改最终会写回文件（由 OS 按脏页刷盘策略决定时机）
}
  • 适用场景：大文件的随机读写与修改、进程间共享内存；对顺序读提升有限。中间件实战：RocketMQ 的 CommitLog、Kafka 的索引文件都基于 mmap——把磁盘文件当内存数组操作。
  • 代价与注意：映射大小受 int 偏移限制（单次最多约 2GB，大文件要分段映射）；释放不可控（依赖 GC 回收 MappedByteBuffer 时经 Cleaner unmmap，显式释放要反射/Unsafe，长期持有会占用虚拟地址与 page cache）；修改写回时机由操作系统决定，崩溃前可能丢。
  • FileChannel.transferTo()/transferFrom()（sendfile 零拷贝）与 mmap 的对比、零拷贝完整原理（Kafka 为什么快）归 12-os 板块，此处记住结论：mmap 少一次拷贝、适合随机读写；transferTo 连用户态都不经过、适合整块转发。

07直接内存：DirectByteBuffer

  • 是什么：JVM 堆外（native）内存，由 ByteBuffer.allocateDirect() 分配（返回 DirectByteBuffer）。
  • 为什么 IO 场景快：向 socket/文件写堆内数据时，GC 可能移动对象导致地址变化，JVM 无法保证内核能稳定持有这块地址，所以会先把堆内数据拷贝到一块堆外临时内存再交给内核——堆外缓冲天生地址稳定，省掉这次拷贝，socket 读写尤其受益。
  • 与 GC 的关系（一句带过）：直接内存不受堆 GC 直接管理，靠引用队列 + Cleaner（本质 Cleaner 是 PhantomReference 机制）在 DirectByteBuffer 被回收时释放 native 内存——回收滞后，分配过快会 OutOfMemoryError: Direct buffer memory，受 -XX:MaxDirectMemorySize 限制。GC 与堆外内存的完整分析在 03-jvm 板块。
  • 谁在重度使用：NIO 框架（Netty 的 PooledDirectByteBuf 池化堆外内存 + 引用计数手动释放，就是为规避"等 GC 才释放"的滞后）；RPC 框架序列化缓冲也常用堆外。
  • 选型口径：频繁 socket 读写、大块数据、复用缓冲 → direct；小数据、频繁创建用完即弃 → heap buffer 更省事（堆外分配/释放本身也不便宜，Netty 靠池化摊薄）。

排查经验：线上"堆很健康但进程 RSS 涨、最终 OOM（direct memory）"——先查 MaxDirectMemorySize、Netty 池化配置和有没有忘了 release 的 ByteBuf；用 NMT（NativeMemoryTracking）看 committed 分布。这是直接内存最高频的实战问法。

08高频追问与陷阱

  • 追问链：装饰器 → IO 里还有别的模式吗→ 适配器（InputStreamReader 桥接字节/字符）、工厂（NIO 的 open/allocate 静态工厂）、观察者（Selector 事件通知）、门面（java.nio.file.Files 简化 API）。
  • 追问链：NIO 为什么快 → 是所有场景都快吗→ 只在"连接多且活跃度不高或需要高并发吞吐"时优势明显；连接少而活跃时事件循环的开销反而多余。文件 IO 场景 FileChannel 没有 Selector 加持，优势来自缓冲和零拷贝。
  • 追问链：序列化 → 单例被序列化破坏怎么办→ 提供 readResolve() 返回既有实例；或直接用枚举（JVM 层面保证）。
  • 陷阱：read() 返回 0 与 -1：非阻塞 Channel 的 read 返回 0 表示"暂时没数据"（正常），返回 -1 才是流结束——NIO 编程里把 0 当 EOF 是经典 bug。
  • 陷阱：写 Buffer 忘 flip：读写模式切换全靠 flip/clear/rewind，指针状态错误读到脏数据。
  • 陷阱：ObjectOutputStream 写到的类没实现 Serializable：运行时 NotSerializableException，编译期不查。
  • 陷阱：FileInputStream 重复打开未关闭：Linux 上表现 fd 泄漏（Too many open files）——用 try-with-resources 是纪律。
  • 场景题口径："设计一个日志/文件采集模块"——主动提 mmap 大文件读取、direct buffer 网络发送、BufferedOutputStream 批量刷盘三个工具的取舍。
