02创建对象的方式：静态工厂 vs 构造器

Effective Java 条目 1：考虑用静态工厂方法代替构造器。注意这不是 GoF 的"工厂方法模式"，就是一个普通的 public static 方法返回实例。

// JDK 里到处是教科书案例：
public static Boolean valueOf(boolean b)            // 返回缓存单例，不 new
public static Integer valueOf(int i)                // 命中 IntegerCache 就不 new
LocalDate.of(2026, 10, 17)                          // 比 new LocalDate(...) 可读（虽然它构造器是私有）
List.of("a", "b")                                   // 返回不可变集合，具体实现类由 JDK 决定
BigInteger.probablePrime(bits, rnd)                 // 名字说明了一切： probable（可能是素数）

五大优势（背诵骨架）

  1. 有名字，可读性强：probablePrime(100, rnd) vs new BigInteger(...)，语义差一条街；同名不同参的构造器没法区分，静态工厂可以起不同名字（ofSeconds / ofMinutes）。
  2. 不必每次都创建新对象：可以缓存（Boolean/Integer）、可以做成享元，也能顺势实现单例/实例受控（instance-controlled）。
  3. 可以返回原类型的子类：调用方只面向接口 List，JDK 按数据量返回 List12 或 ListN；EnumSet.of() 按枚举数量在 RegularEnumSet / JumboEnumSet 之间挑——实现细节完全私有。
  4. 返回类型可以随入参变化：同样的方法签名，不同参数返回不同实现类。
  5. 返回的类在编写时可以不存在：服务提供者框架（JDBC SPI：DriverManager → Connection），面向接口 + 反射加载实现——这条能顺势聊到框架是怎么解耦的。

两个代价

  • 类没有 public/protected 构造器就不能被子类化——但这反而是鼓励组合的推力。
  • 静态工厂和其他静态方法"长得没区别"，所以要靠命名约定：from / of / valueOf / instance / getInstance / create / newInstance / getType / newType。看到这些名字就要想到"这是个工厂"。

答题口径：被问"new 之外还有哪些创建对象的方式"先给全景（静态工厂 / 反射 Class.newInstance / clone / 反序列化 / Unsafe.allocateInstance），再重点讲静态工厂五大优势——全景证明知识面，展开证明熟练度。

03单例的枚举写法 ⭐

public enum Router {
    INSTANCE;                                              // 唯一实例，JVM 保证

    private final Map<String, Endpoint> routes = new ConcurrentHashMap<>();

    public void register(String path, Endpoint ep) { routes.put(path, ep); }
    public Endpoint route(String path) { return routes.get(path); }
}

// 使用：天然线程安全，无锁、无双重检查
Router.INSTANCE.route("/order/create");

为什么 Effective Java 条目 3 说它是"最佳单例"

  • 线程安全免费：枚举实例在类加载的初始化阶段由 JVM 创建，JVM 类加载机制保证唯一性与初始化的线程安全——不需要 volatile + 双重检查锁（DCL 细节在 02 并发板块）。
  • 防反射攻击：反射 Constructor.newInstance() 内部对枚举有专门检查，直接抛 IllegalArgumentException: Cannot reflectively create enum objects——普通私有构造器单例可以靠 setAccessible(true) 破防。
  • 防反序列化破坏：枚举的序列化机制特殊（按 name 定位，valueOf 返回同一实例），readResolve 都不用写；普通单例反序列化会凭空造出第二个实例。
  • 一行声明 + 无缝带状态和方法，可读性也是几种写法里最好的。

几种单例写法横向对比

写法线程安全懒加载防反射防反序列化备注
饿汉（static final 直接 new）✔△ 类初始化级✘✘简单；类初始化时创建
懒汉 + synchronized 方法✔✔ 实例访问级✘✘每次调用都锁，性能差
DCL（volatile）⭐✔✔ 实例访问级✘✘面试最爱；必须讲 volatile 防指令重排
静态内部类 Holder✔✔ 实例访问级✘✘借类加载惰性初始化，优雅
枚举✔△ 类初始化级（同饿汉）✔✔Effective Java 首选

"懒加载"这一列有两个粒度，必须先拆开：类初始化级＝实例在单例类自己的 <clinit> 里创建，该类首次被主动使用就 new（饿汉、枚举）；实例访问级＝实例字段延迟到 getInstance()（或另一个只在 getInstance() 里被碰到的 Holder 类）里才创建，因此可以先用该类的其他静态方法而不创建实例（懒汉、DCL、Holder）。所以"枚举是懒加载"只对了一半——它确实"不用不创建"，但并不比饿汉更懒。

枚举单例到底算不算"懒汉"？（口径校正）⭐

懒汉式的标志是代码里自己写 if (instance == null) 控制创建时机；枚举没有一行检查代码，它的"晚创建"完全来自 JVM 的类初始化时机——是"白捡的懒"，不是懒汉模式。三种写法的差别看代码最清楚：

// 饿汉：实例住在自己类的 <clinit> 里 —— 调 helper() 也会顺手把它创建出来
class Eager {
    private static final Eager INSTANCE = new Eager();
    static void helper() { }          // 只想用工具方法，实例已被创建
}

// Holder：实例住在 H 里 —— 只有 getInstance() 会碰到 H，真正的实例级懒加载
class Holder {
    private static final class H { static final Holder INSTANCE = new Holder(); }
    static Holder getInstance() { return H.INSTANCE; }
    static void helper() { }          // 不碰 H，实例不会创建
}

// 枚举：INSTANCE 就是枚举类自己的 <clinit> —— 与饿汉同一粒度
enum Router { INSTANCE }              // 谁主动使用 Router，谁就创建它

结论：枚举的"懒"= 类初始化级，和饿汉式同一粒度；真正更细的懒只有 Holder。Effective Java 推荐枚举的理由从来不是"更懒"，而是免费线程安全 + 防反射 + 防反序列化 + 代码最少——这三条护城河才是答题重点。

哪些操作会提前把它创建出来

  • 经典 switch：javac 为 switch (router) 生成的合成 SwitchMap 类会调 Router.values()——哪怕分支里根本没碰 INSTANCE，类初始化照样发生。"我只写了个 switch，单例怎么已经建好了"就是它（JDK 21 的 pattern switch 走 invokedynamic，机制不同，但同样要拿到枚举常量）。
  • Router.values() / Router.valueOf("INSTANCE") / EnumSet.allOf(Router.class) / Class.getEnumConstants()：都会触发类初始化。
  • 框架把枚举常量注册进字典/容器（枚举扫描、字典翻译）同理。
  • 反之，Router.class、Class.forName(name, false, loader)、编译期常量（static final int）的引用不会触发初始化——"类加载"和"类初始化"是两件事，这也是"到底加载时创建还是使用时创建"这个争论的根源。

两个真坑：① 枚举构造器里别做重活（建连接池、读配置、发远程调用）——构造抛异常会让类进入 erroneous 状态，之后每次访问都是 NoClassDefFoundError 且无法恢复；② 多 ClassLoader 环境（Tomcat webapp、OSGi、热部署）单例不再单例——"JVM 保证唯一"只保证每个类加载器内唯一，跨类加载器会各有一份，要靠容器或外部存储兜底。

陷阱："懒汉 DCL 为什么必须 volatile"是这道题的标准追问——new 分三步（分配内存 → 初始化 → 引用赋值），重排后别的线程可能拿到"已赋值未初始化"的半成品对象。另外别把 Spring 的单例 Bean 和这里混淆：Spring 是容器托管的单例（每容器一个），不防反射、不防反序列化，是另一种粒度。

04Builder 模式：多参数创建的救星

Effective Java 条目 2。痛点：参数一多，两种传统写法都疼——重叠构造器（telescoping）：2 参、3 参、5 参构造器叠罗汉，调用方读不懂 new Order(1, "SKU001", 2, null, null, false) 里每个位子是什么；JavaBeans（set 链）：可读但构造过程中对象处于半初始化状态，且没法做不可变、没法校验"必填组合"。

OrderCreateRequest req = new OrderCreateRequest.Builder(uid, "SKU001")   // 必填进构造器
        .quantity(2)                    // 可选参数链式设置，参数名自解释
        .couponCode("DOUBLE11")
        .build();                       // build 时做最终校验，产出不可变对象

public class OrderCreateRequest {
    private final long userId;          // 全 final —— 产物不可变
    private final String sku;
    private final int quantity;
    private final String couponCode;

    private OrderCreateRequest(Builder b) {
        this.userId = b.userId; this.sku = b.sku;
        this.quantity = b.quantity; this.couponCode = b.couponCode;
    }
    public static final class Builder {
        private final long userId;      // 必填：非 final 字段的区别一目了然
        private final String sku;
        private int quantity = 1;       // 可选：给默认值
        private String couponCode;
        public Builder(long userId, String sku) {
            this.userId = Objects.requireNonNull(userId);
            this.sku = Objects.requireNonNull(sku);
        }
        public Builder quantity(int v) { this.quantity = v; return this; }
        public Builder couponCode(String v) { this.couponCode = v; return this; }
        public OrderCreateRequest build() { return new OrderCreateRequest(this); }
    }
}
  • Builder 是"安全 + 可读 + 不可变"三者兼得的方案；代价是样板代码，所以生产里几乎都配 Lombok @Builder（或 Records + 手写紧凑校验）。
  • JDK / 框架里认脸：StringBuilder、Stream.Builder、HttpRequest.newBuilder()（JDK 11 HTTP Client）、OkHttp、ProtoBuf——builder 在"多参数构造 + 可变构建过程"场景是通用语言。
  • 与 record 搭配：字段少于 4~5 个直接用 record + 紧凑构造器校验；参数多、有可选值、构建过程分步才上 builder。

Lombok @Builder 的坑（实战题）：@Builder 会生成"全参私有构造器"，把默认无参构造器挤掉——MyBatis / Jackson 反序列化时直接报错。修法是 @Builder + @NoArgsConstructor + @AllArgsConstructor 三件套。踩过并修过这个坑，说出来就是 7 年的成色。

05避免浮点精确计算 & 最小化可变性

金额永远不要用 double（Effective Java 条目 60）

float/double 是二进制浮点（IEEE 754），无法精确表示 0.1 这类十进制小数，误差会在加减乘除和比较里累积——钱丢在精度里是最不可原谅的线上事故。两条正解（细节与陷阱在 第 01 章浮点精度）：

// ① BigDecimal，务必用字符串构造；比大小用 compareTo 不用 equals（equals 连 scale 一起比）
new BigDecimal("19.90").add(new BigDecimal("0.10"));

// ② 高并发支付系统更常见的做法：放大为 long 的"分"，整数运算，性能好一个数量级
long priceCents = 1990;
long total = priceCents * 3;              // 展示时再除以 100 格式化

最小化可变性（Effective Java 条目 17）

  • 手段：类声明 final（或所有构造器私有）、字段全部 final、不提供 setter、构造时初始化完所有字段、可变成员防御性拷贝（返回 new Date(d.getTime())、入参 List.copyOf(items)）。
  • 好处：不可变对象天然线程安全、可自由共享、hashCode 可缓存、当 Map key 可靠——String / LocalDate / record 全是这条条目的落地（呼应 第 13 章不可变设计）。
  • 代价：每个不同的值都要一个新对象。频繁变更的场景用 builder 一次性构建，或用可变的 companion 类在内部攒、对外仍暴露不可变视图。
  • 面试一句话："能不可变就不可变，需要变才可变，变了谁负责说清楚"——record 让这条从"纪律"变成了"默认"。

06组合优于继承 ⭐（Effective Java 条目 18）

核心论点：继承打破了封装。子类正确运行依赖父类的实现细节（self-use 自用性），父类下个版本换实现，子类无感知地坏掉——这不是理论风险，JDK 自己都踩过（HashSet 之于 AbstractCollection）。

经典反例：InstrumentedHashSet

public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) { addCount++; return super.add(e); }

    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);     // 父类 addAll 内部逐个回调 this.add → addCount 被加了两次！
    }
}

Set<Integer> s = new InstrumentedHashSet<>();
s.addAll(List.of(1, 2, 3));         // 期望 addCount=3，实际 6

组合 + 转发（装饰器思想）

public class InstrumentedSet<E> {          // has-a，不是 is-a
    private final Set<E> s;                 // 持有任意 Set 实现，行为自己全权负责
    private int addCount = 0;

    public InstrumentedSet(Set<E> s) { this.s = s; }

    public boolean add(E e) { addCount++; return s.add(e); }
    public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        for (E e : c) s.add(e);             // 不依赖 s 的内部实现，怎么改都不会重复计数
        return true;
    }
    public int getAddCount() { return addCount; }
}
  • 组合版不依赖被包装类的任何实现细节，还能按需注入不同实现（HashSet / TreeSet / 不可变 Set），这就是 Collections.unmodifiableList() / synchronizedList() 的写法（转发包装类 forwarder）。
  • 什么时候才用继承：确凿的 is-a 关系 + 父类是为继承而设计的（文档写明自用性，或本身就是抽象骨架如 AbstractList）。跨包继承普通具体类，基本都该改成组合。
  • 追问链预判：→ "那接口 default 方法算继承吗" → 接口是规范的多实现，风险小得多；→ "包装类层级太深怎么办" → 这正是组合的缺点（不适配回调/对象身份），JDK 也因此给了 List 接口直接实现类的建议。

答题口径：先给结论"默认组合，继承是特例"，再讲 HashSet 双重计数的例子（这个例子讲顺了，这条就是送分题），最后补一句实战："我们团队 Review 里看到 override 具体类方法，默认会问一句能不能改成组合/装饰器。"

07异常最佳实践回顾（一分钟版）

  • 只用于异常情况，不做流程控制：异常构造成本高（填栈），用异常跳出循环/找元素是反模式——"peek 异常"写接口慢一半就是这么来的。
  • 不吞异常：catch (Exception e) {} 空块是头号大罪；至少记日志带上下文，保留异常链 new BizException("订单状态非法", e)，否则现场全丢。
  • 捕获要具体：先 catch 子类后父类；抓 Exception 兜底的位置要放在边界层（RPC handler / 定时任务外层），不是随处都抓。
  • try-with-resources 关资源：实现 AutoCloseable 的资源（流、连接、锁）别手动 finally close——漏关、覆盖原始异常都是坑。
  • 受检 vs 非受检：可恢复且调用方能处理的用受检；编程错误/不可恢复用 RuntimeException（现代框架趋势是后者 + 全局异常处理）。

细节（异常表、finally 执行顺序、栈轨迹丢失场景）在 第 07 章 异常处理，本章只保留答题时的"口头禅"版本。

08阿里巴巴 Java 开发手册高频条款

条款（分级）内容为什么 / 底层原因
POJO 属性用包装类型（强制）POJO / RPC 参数返回值用包装类，局部变量用基本类型DB 可空列映射 null 而非 0；0 和 null 语义不同——"查询失败返回 0" 会被当成"查到 0 元"（呼应 第 01 章拆箱 NPE）
equals 常量在前（强制）"PAID".equals(status)，或 Objects.equals变量为 null 时不会 NPE；写反了 status.equals("PAID") 就埋雷
禁 Executors 创建线程池（强制）⭐用 new ThreadPoolExecutor(...) 显式 seven 参数newFixedThreadPool/newScheduledThreadPool 队列是无界 LinkedBlockingQueue（Integer.MAX_VALUE），任务堆积 → OOM；newCachedThreadPool 最大线程数 Integer.MAX_VALUE，线程爆炸 → OOM。原理与参数怎么配见 02 Java 并发编程
禁魔法值（强制）状态码 "PAID"、阈值 3 这种裸值不许直接写常量类 / 枚举，一改全改；可搜索可维护
循环内字符串拼接（强制）用 StringBuilder（能预估容量更佳）String + 每轮产生临时对象（原理在 第 01 章）
foreach 里增删元素（强制）用 Iterator.remove() 或 removeIf()fail-fast 机制：modCount 变了抛 ConcurrentModificationException
rollbackFor（推荐）@Transactional(rollbackFor = Exception.class)Spring 默认只回滚 RuntimeException/Error，受检异常吞掉不回滚（深入在 04-spring）

怎么在面试里用：不要说"我读过阿里手册"，要说条款 + 原因 + 团队落地方式："我们把手册做成了 Sonar/IDE 检查规则，违规合并请求直接卡住"——从"读过"升级成"工程化落地过"。

09JUnit 5 单测基础

核心注解速查

注解作用备注
@Test标记测试方法方法可包私有（JUnit 5 不再强制 public）
@BeforeEach / @AfterEach每个测试方法前后各跑一次替代 JUnit 4 的 @Before/@After；造干净的被测对象
@BeforeAll / @AfterAll整个测试类前后各跑一次必须 static（除非 @TestInstance(PER_CLASS)）；放重资源的建与销
@ParameterizedTest参数化测试配 @ValueSource / @CsvSource / @MethodSource
@Nested内嵌分组测试类按场景分组，共享外层状态
@DisplayName / @Disabled显示名 / 跳过报告可读性

一个完整的测试类（AAA 结构）

@DisplayName("折扣计算器")
class DiscountCalculatorTest {

    private DiscountCalculator calc;

    @BeforeEach
    void setUp() {                       // Arrange 前置：每个用例拿到全新被测对象
        calc = new DiscountCalculator();
    }

    @Test
    @DisplayName("VIP 用户享 8 折")
    void vipUserGets20PercentOff() {
        // Act
        BigDecimal result = calc.apply(new BigDecimal("100"), UserType.VIP);
        // Assert
        assertEquals(new BigDecimal("80.00"), result);
    }

    @Test
    @DisplayName("负数价格抛参数异常")
    void negativePriceThrows() {
        IllegalArgumentException ex = assertThrows(IllegalArgumentException.class,
                () -> calc.apply(new BigDecimal("-1"), UserType.NORMAL));
        assertTrue(ex.getMessage().contains("price"));
    }

    @Test
    void multiAssertionsTogether() {     // assertAll：一组断言都执行，不会第一个失败就跳过后面的
        assertAll("订单折扣",
            () -> assertEquals(new BigDecimal("80.00"), calc.apply(new BigDecimal("100"), UserType.VIP)),
            () -> assertEquals(new BigDecimal("100.00"), calc.apply(new BigDecimal("100"), UserType.NORMAL)));
    }
}

参数化测试：一行一个用例，消灭复制粘贴

@ParameterizedTest(name = "[{index}] {0} 下单 {1} 元 → {2}")
@CsvSource({
    "NORMAL, 100, 100.00",
    "VIP,    100,  80.00",
    "SVIP,   100,  60.00"
})
void applyDiscountByUserType(UserType type, String price, String expected) {
    assertEquals(new BigDecimal(expected), calc.apply(new BigDecimal(price), type));
}

// 复杂对象用 @MethodSource 指向一个返回 Stream 的静态工厂方法
@ParameterizedTest
@MethodSource("edgeCases")
void edgeCases(OrderCase c) { assertEquals(c.expected, calc.apply(c.price, c.type)); }
static Stream<OrderCase> edgeCases() {
    return Stream.of(new OrderCase("0", NORMAL, "0.00"),
                     new OrderCase("0.01", SVIP, "0.01"));
}
  • 断言够用的场景用 JUnit 自带；真实项目里更常见 AssertJ（流式断言 assertThat(list).hasSize(3).contains(x)）+ Mockito（when/verify 隔离依赖）——面试提一句生态即可。
  • 测试方法论口径：优先测边界和异常分支（null、0、负数、极大值、并发冲突），AAA 结构，方法名即文档（中文 @DisplayName 也行）；不测私有方法——私有方法复杂到想单测，说明类该拆了。

107 年工程师怎么聊"代码质量"

面试场景题："给你一个陌生项目 / 你怎么保证团队的代码质量？"——按这六维答，每一维都能带一句自己团队的落法：

  1. 可读性：命名说清意图（为什么存在而不是做什么）；方法一屏读完；圈复杂度 >10 就拆（Sonar 有阈值）；注释解释 why 而不是翻译 what。
  2. 结构与边界：分层清晰、依赖单向（api → service → dao），模块边界稳定；越界依赖是 Review 重点。
  3. 重复与抽象：DRY，但警惕过度抽象——重复的成本是线性罚，错误抽象的成本是复利罚（Sandi Metz），两次重复忍、第三次再抽象（三次法则）。
  4. 测试：核心链路（资金、状态流转）单测是底线；看变更覆盖率（diff coverage）比看全量覆盖率诚实；"覆盖率 100% 但没有断言"的测试比没测试更危险。
  5. 自动化门禁：CI 上 SonarQube / CheckStyle / 依赖漏洞扫描（OWASP），Blocker 不清零不许合；规范靠工具不靠自觉——把阿里手册配成规则就是例子。
  6. 可持续演进：技术债有台账、有还款窗口（每次大需求顺带重构相关模块）；Review 文化卡的是设计问题（边界、异常处理、并发安全），风格问题交给格式化工具。

高分答法示例："我评估陌生项目分两步：先跑工具拿数据——Sonar 热点、依赖树里的老版本和安全漏洞、构建时长、测试覆盖与变更覆盖；再抽核心模块读代码——异常怎么处理、并发怎么保护、边界是否清晰。数据告诉我风险在哪，读码告诉我团队习惯是什么。最后给结论时会区分'必须马上修'和'记账排期'，不追求一次性完美。"——有方法、有数据、有优先级，这是高级岗要的味道。

11高频追问与陷阱

  • 追问链：静态工厂 vs 工厂方法模式？→ 前者是"类里的一个静态方法"（编码习惯），后者是 GoF 创建模式（父类定接口、子类决定实例化谁）；静态工厂 + 接口 + 函数式 Supplier（如 Supplier<Cache> 注入）很多时候替代了工厂模式。
  • 追问链：枚举单例是懒加载吗？→ 严格说不是"懒汉"：它是"类初始化级延迟"——枚举类首次被主动使用（读 INSTANCE、values()、经典 switch、EnumSet.allOf…）时由 JVM 在 <clinit> 里创建，与饿汉式同一粒度，并不比饿汉更懒；真正的实例级懒加载是 Holder（实例住在另一个只在 getInstance() 里被碰到的类）。答"是"会被追"那和饿汉有什么区别"，答"不是"又漏了类加载时机——先把两种粒度拆开再答，最稳。
  • 陷阱：Builder 会稀释不可变吗？→ 不会，Builder 只是构建期的可变中间态，build 出来的对象全 final；但如果 Builder 被复用（build 后继续改再 build），产物之间互不影响，别共享 Builder。
  • 追问：防御性拷贝 vs 不可变对象？→ 不可变是"根治"（字段不可变就无漏可防）；防御性拷贝是"兜底"（字段只能可变时，进出口各拷一次：构造入参 List.copyOf、getter 返回副本或不可变视图）。EnumMap/Map key 那些坑都源于此。
  • 追问：单测覆盖率多少算够？→ 没有圣数。我的口径：核心链路 70%+ 且必须覆盖异常分支；全量覆盖率作趋势看（不降），变更覆盖率作门禁卡。
  • 陷阱：BigDecimal.equals 的 scale 陷阱——new BigDecimal("1.0").equals(new BigDecimal("1.00")) 是 false，比大小永远 compareTo（第 01 章讲过，最后再提醒一次，因为真的高频）。
  • 追问：私有方法怎么测？→ 不测私有测公开行为；真想测说明职责该拆成新类了——这个回答本身就是设计品味的展示。

12面试自查清单

  1. 静态工厂五大优势 + 两个代价 + 命名约定，能配 JDK 真实例子讲。
  2. 枚举单例三大护城河（类加载线程安全 / 防反射 / 防反序列化）脱口而出，并知道 DCL 为什么要 volatile。
  3. 能写出 Builder 的骨架，说清它相对重叠构造器和 JavaBeans 的优势，会讲 Lombok @Builder 的坑。
  4. InstrumentedHashSet 双重计数例子能白板写出来，组合/转发版能口述。
  5. 金额计算两套方案（BigDecimal 字符串构造 / long 分）及各自适用场景。
  6. 阿里手册 7 条高频条款都能说"条款 + 原因 + 团队怎么落地"。
  7. JUnit 5：注解语义（尤其 @BeforeAll 要 static）、能写参数化测试、知道 AssertJ/Mockito 的位置。
  8. 聊代码质量有六维框架 + 工具门禁 + 一段自己的评估方法。

如果只记 10 条（全章压缩版，面试前最后一遍）：

  1. 创建对象优先静态工厂：有名字、可缓存、可返回子类、可做实例受控。
  2. 单例用枚举；懒加载 DCL 必须 volatile。
  3. 多参数构建用 Builder，产物不可变；Lombok @Builder 记得补无参构造。
  4. 金额禁 double：BigDecimal 字符串构造 + compareTo，或 long 分。
  5. 能不可变就不可变（record）；可变字段进出口防御性拷贝。
  6. 默认组合，继承仅限 is-a 且父类为继承而设计；HashSet 例子常备。
  7. 异常：不吞、具体捕、带 cause、try-with-resources、不做流程控制。
  8. POJO 用包装类型、equals 常量在前、禁魔法值、foreach 不增删。
  9. 线程池禁 Executors 快捷方法——手动 new ThreadPoolExecutor 并说得清七个参数。
  10. 单测测边界与异常，AAA + 参数化；覆盖率看趋势与变更覆盖，质量靠门禁不靠自觉。
