02Collection 体系总览

Java 集合有两棵树：Collection（存单个元素）和 Map（存键值对），Map 不继承 Collection。先把体系图背下来，选型题才有骨架：

Iterable

   │   ├─ LinkedList    双向链表（节点 = prev + item + next），线程不安全
   │   └─ Vector        底层数组，方法级 synchronized，线程安全（遗留，基本弃用）

03ArrayList vs LinkedList ⭐

ArrayList：动态数组

  • 默认容量 10，但是懒初始化：无参构造只是把 elementData 指向共享的空数组 DEFAULTCAPACITY_EMPTY_ELEMENTDATA，首次 add 才真正分配长度 10 的数组——所以 new ArrayList<>() 本身不占 10 个槽的内存。
  • 扩容 1.5 倍：newCapacity = oldCapacity + (oldCapacity >> 1)，再 Arrays.copyOf 整体拷贝。均摊下来 add 是 O(1)；能预估大小就 new ArrayList<>(n) 一次到位，避免多次拷贝。
  • 随机访问 get(i)/set(i) O(1)；中段插删要 System.arraycopy 移动后续元素，O(n)。
// JDK 8 ArrayList 扩容核心
private void grow(int minCapacity) {
    int oldCapacity = elementData.length;
    int newCapacity = oldCapacity + (oldCapacity >> 1);   // 1.5 倍：10 → 15 → 22 → 33 …
    if (newCapacity - minCapacity < 0)
        newCapacity = minCapacity;                          // 一次 addAll 大集合时直接给够
    elementData = Arrays.copyOf(elementData, newCapacity);  // 新数组 + 整体拷贝
}

LinkedList：双向链表 + 双端队列

  • 节点 Node<E> { E item; Node<E> next; Node<E> prev; }，同时实现了 List 和 Deque，可当队列/栈用。
  • 头尾插删 O(1)；随机访问 O(n)——get(i) 内部会按 i < (size >> 1) 决定从头还是从尾遍历，但这只是减半常数，量级没变。
  • 每个节点多两个引用 + 节点对象头，内存开销大且地址不连续（缓存不友好）——"删中间元素"也要先 O(n) 定位，所以实际工程里 LinkedList 几乎全面输给 ArrayList。

陷阱：" LinkedList 插入删除快" 是半对答案——只对已定位到节点的插删成立；按下标操作仍要先 O(n) 遍历。高级岗标准答案：默认 ArrayList；要队列/栈用 ArrayDeque；LinkedList 在真实项目里基本没有胜出场景，说出这句反而是加分。

LinkedList 的真实使用场景：理论上有，实际都被替代了

说"没有胜出场景"要能兜住追问——它不是一无是处，而是每个理论适配的场景都有更优解。把这张表讲出来，比一句"不用"有说服力得多：

它理论上适合的场景为什么成立实际被谁替代
频繁头尾增删的队列 / 栈 / 双端头尾插删 O(1)，且同时实现了 Deque 接口ArrayDeque（JDK 6）——循环数组、无锁、缓存友好，两端同样 O(1)
迭代中频繁删"当前元素"ListIterator 定位后 remove 是改两个指针 O(1)，无数组搬移ArrayList.removeIf——批量标记 + 一次压缩，整体 O(n) 反而更快
超大列表避免扩容拷贝尖刺ArrayList 扩容要整体 copy + 申请一大块连续内存；链表每次只做小分配，单次操作耗时稳定（延迟敏感场景看重这点）预估容量 new ArrayList<>(n) 一次到位；真有稳定延迟要求换分块结构
同一结构既要 List 又要 Deque它是 JDK 里唯一同时实现 List 和 Deque 的通用类真到这步通常说明该自己封装或换专门结构了

口径升级："LinkedList 头尾 O(1) 所以适合做队列/栈"是 JDK 6 之前（没有 ArrayDeque 时代）的答案，背它会显得停留在老教材。现代口径："它的理论场景都有更好的替代——栈/队列归 ArrayDeque、列表归 ArrayList、批量删除归 removeIf，所以真实项目里我基本不用它；唯一不可替代点是 List + Deque 双接口，但那属于设计该改的信号。"

04Queue、Deque 与 Stack ⭐

Queue 的两套 API：抛异常 vs 返回特殊值 ⭐

语义抛异常版返回特殊值版满 / 空时的行为差异
入队add(e)offer(e)容量受限队列已满：add 抛 IllegalStateException / offer 返回 false
出队remove()poll()队空：remove 抛 NoSuchElementException / poll 返回 null
看队头element()peek()队空：element 抛异常 / peek 返回 null
  • 追问升级：BlockingQueue 在此之上又加两套——阻塞版 put()/take()（满了/空了就挂起）和超时版 offer(e, time, unit)/poll(time, unit)。两套 + 阻塞两套 = "立即失败、立即返回、一直等、等一会"四种失败策略，能说全这四种是加分项（阻塞队列本体在 02-concurrency 展开）。
  • 实践口径：业务代码统一用 offer/poll/peek，让"失败"成为可判断的返回值，而不是拿异常做流程控制。

Deque：双端队列，一个结构两种用法

  • Deque = Double Ended Queue，两头都能进出：addFirst/addLast、pollFirst/pollLast、peekFirst/peekLast。
  • 它内嵌了栈语义和队列语义：push/pop/peek 就是 addFirst/removeFirst/peekFirst；offer/poll/peek 就是 addLast/pollFirst/peekFirst——"用 Deque 当栈或队列"只是同一结构的两种视角，接口只是把用法收窄。
  • 首选实现 ArrayDeque：底层循环数组，两端插删 O(1)；无容量上限，满了翻倍。
// JDK 8 ArrayDeque：循环数组 + head/tail 两个指针
transient Object[] elements;    // 长度恒为 2 的幂（默认 16；传初始大小会向上取到 2 的幂）
transient int head;             // 指向第一个元素
transient int tail;             // 指向最后一个元素的下一格

public void addFirst(E e) {
    if (e == null) throw new NullPointerException();            // 禁 null：poll/peek 用 null 表示"空"
    elements[head = (head - 1) & (elements.length - 1)] = e;    // head 左移一格，与掩码 & 实现环绕
    if (head == tail) doubleCapacity();                         // 两指针相遇即满，容量翻倍
}
  • 环绕示例：head=0 时 (0 - 1) & 15 = 15，"向左出界"自动绕回数组尾——这就是"循环数组"的由来；& (length - 1) 能替代取模的前提同样是长度为 2 的幂（与 HashMap 的取模优化同源）。
  • 新版 JDK 的 ArrayDeque 改用取模实现、初始容量留一个空槽，实现细节有变，但"循环数组 + 双指针 + 禁 null"的骨架没变，面试按 JDK 8 口径答即可。
  • 为什么禁止 null：poll()/peek() 约定用返回 null 表示"没有元素"，如果允许存 null 就无法区分"取到了 null"和"队列为空"——LinkedList 当队列用时也应遵守这个约定。

Stack 为什么被弃用：继承 Vector 的反面教材 ⭐

Stack（遗留，别用）Deque + ArrayDeque（官方推荐）
锁继承 Vector，所有方法 synchronized，整表一把锁无锁
封装暴露 get(i)/insertElementAt 等任意位置 API，破坏 LIFO 语义只有双端操作，语义纯粹
null允许（Vector 允许）禁止（null 是"空"的哨兵）
迭代顺序从栈底到栈顶，与操作直觉相反从头到尾，即从栈顶往下
  • Stack 是"为了复用而继承"的经典事故：想要 Vector 的数组能力，结果把不该公开的能力（随机访问、任意位置插删）全暴露了出来——组合优于继承的活教材，Javadoc 明确建议改用 Deque。这个升华比背 API 更值钱。

实战使用场景：栈 / 队列 / 双端各管一摊

// 栈：撤销/重做、括号匹配、非递归 DFS、最近访问历史（浏览器后退）
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1);        // = addFirst，栈顶进
stack.pop();          // = removeFirst，栈顶出（空则抛 NoSuchElementException）
stack.peek();         // = peekFirst（空返回 null）

// 队列：BFS 层序遍历、进程内任务按序缓冲、批处理流水
Queue<Integer> queue = new ArrayDeque<>();
queue.offer(1);       // 尾进
queue.poll();         // 头出（空返回 null）

// 双端：滑动窗口最大值用"单调双端队列"——头弹出窗口外的、尾弹出比新元素小的
Deque<Integer> dq = new ArrayDeque<>();
dq.peekFirst(); dq.pollFirst(); dq.pollLast(); dq.offerLast(v);
  • 栈场景：方法调用栈、表达式求值（编译器）、括号与标签配对（HTML/JSON 解析）、撤销栈、DFS 非递归化、单调栈（"下一个更大元素"类题，归 05-dsa）。
  • 队列场景：BFS、日志/事件按序消费、生产者-消费者的进程内版（并发与背压上 BlockingQueue）。
  • 双端场景：滑动窗口最大值；ForkJoinPool 的工作窃取（owning 线程从一端取、窃取者从另一端偷——双端队列天然支持）。

陷阱：ArrayDeque 是无界的——new ArrayDeque<>() 没有容量上限，构造传的只是初始数组大小。要做有界队列/背压，用 ArrayBlockingQueue（02-concurrency）。

答题口径："Stack 和 LinkedList（当栈/队列用）都过时了，现代写法一律 Deque 接口 + ArrayDeque 实现——循环数组、两端 O(1)、无锁、连续内存缓存友好。"一句话把"为什么"说完，再补 Queue 两套 API 的行为差异。

05PriorityQueue 与堆 ⭐

底层：数组表示的二叉小顶堆

  • PriorityQueue 既不是链表也不是树对象图，就是一个 Object[] queue 按完全二叉树的层序存放的小顶堆：下标 n 的元素，parent = (n - 1) >>> 1，左孩子 2n + 1，右孩子 2n + 2。
  • 堆性质：每个父节点 ≤ 它的孩子（小顶）；因此 queue[0] 永远是当前最小值，peek O(1)；但数组整体不是有序的——这是"迭代乱序"问题的根源（见下文陷阱）。
  • 基本约束：默认初始容量 11；无界（自动扩容）；不允许 null；元素必须实现 Comparable 或构造时传 Comparator，否则运行时 ClassCastException——首个元素不参与比较，第二次 offer 才炸，报错时机是个细节考点。
  • 线程不安全——并发场景换 PriorityBlockingQueue（02-concurrency）。

offer / poll：上浮 siftUp 与下沉 siftDown

// offer 的核心：新元素放尾部，一路与父节点比较，小则上浮 —— 最多走树高 O(log n)
private void siftUpComparable(int k, E x) {
    Comparable<? super E> key = (Comparable<? super E>) x;
    while (k > 0) {
        int parent = (k - 1) >>> 1;          // 父节点下标
        Object e = queue[parent];
        if (key.compareTo((E) e) >= 0)        // 不比父亲小 → 堆性质已满足，停
            break;
        queue[k] = e;                         // 父亲下来占自己的位
        k = parent;                           // 自己升到父亲的位置
    }
    queue[k] = key;                           // 落定
}

// poll 对称：取走 queue[0]，用尾元素补位，siftDown 与"较小的孩子"交换下沉 —— O(log n)
// peek 只读 queue[0]，O(1)
  • 建堆是 O(n) 不是 O(n log n)：构造器 PriorityQueue(Collection) 走 heapify——从最后一个非叶节点（(size >>> 1) - 1）倒序逐个 siftDown。绝大多数节点在底层、下沉高度小，按高度加权和正好是 O(n)。逐个 offer 才是 O(n log n)。这是算法面经典追问。

扩容：与 ArrayList 不一样的"两段式" ⭐

private void grow(int minCapacity) {
    int oldCapacity = queue.length;
    int newCapacity = oldCapacity + ((oldCapacity < 64) ?
                                     (oldCapacity + 2) :    // 容量 < 64：约翻倍（+ 自身 + 2）
                                     (oldCapacity >> 1));   // 达到 64 后：1.5 倍
    queue = Arrays.copyOf(queue, newCapacity);
}
  • 细节对比题：ArrayList 从 10 起步恒定 1.5 倍；PriorityQueue 从 11 起步、64 之前翻倍、64 之后 1.5 倍——小堆翻倍减少扩容次数，大堆 1.5 倍省内存，两段式在时间与空间之间切换。

两个必考陷阱

  • 迭代顺序 ≠ 优先级顺序：iterator 按底层数组下标遍历，只保证"父 ≤ 子"，不保证全局有序。要按优先级消费必须逐个 poll()（或 Arrays.sort(toArray())）——"for 循环打印 PriorityQueue 发现不是有序的"是真实高频困惑。
  • remove(Object) / contains 是 O(n)：堆只为"取最值"而生，不服务于任意查找与删除。频繁"修改优先级 / 删中间元素"的调度场景，要么自己维护"元素 → 下标"映射做 IndexedHeap，要么换 TreeSet。

实战场景：哪些业务在用堆 ⭐⭐

场景怎么用堆复杂度
Top-K：求最大的 K 个维护 K 大小的小顶堆（堆顶 = 当前 K 个里最小的，是最先被挤出去的门槛）；新元素比堆顶大才进O(n log k)，优于全排序 O(n log n)
Top-K：求最小的 K 个反过来用大顶堆：new PriorityQueue<>(k, Comparator.reverseOrder())——"求大用小堆、求小用大堆"是反直觉考点O(n log k)
合并 K 个有序链表/日志段各链的头节点进小顶堆，poll 出全局最小、再补对应链的下一个——多路归并，外部排序、ES/Lucene 段合并的雏形O(N log k)
延时/定时任务调度按触发时间排序的堆：Timer 的 TaskQueue、ScheduledThreadPoolExecutor 的 DelayedWorkQueue 都是小顶堆（变体），取最早到期任务入队/取最早 O(log n)
线程池按优先级消费new ThreadPoolExecutor(..., new PriorityBlockingQueue<>(n, cmp))，任务实现 Comparable 按优先级排队O(log n)
图算法Dijkstra / Prim 按距离、权重取最小节点（配懒删除）O((V+E) log V)
流式中位数 / 分位数对顶堆：大顶堆放较小一半 + 小顶堆放较大一半，两堆大小差 ≤ 1插入 O(log n)，查中位数 O(1)
// Top-K 模板：流式数据里维护"最大的 K 个"（热点商品、慢接口 Top10、热搜榜）
Queue<Integer> heap = new PriorityQueue<>(k);            // 小顶堆
for (int x : nums) {
    if (heap.size() < k) {
        heap.offer(x);
    } else if (x > heap.peek()) {        // 只比"K 个里最小的"（门槛）大才有资格进
        heap.poll();
        heap.offer(x);
    }
}
// 业务化：把元素换成记录、传 Comparator.comparingLong(Record::getCost) 即可套用

答题骨架："底层是数组小顶堆，offer/poll 上浮下沉 O(log n)，peek O(1)，remove/contains O(n)；迭代不有序，按优先级出必须 poll；不允许 null，线程不安全。求最大 K 用小顶堆——堆顶是门槛；延时任务调度（Timer、ScheduledThreadPoolExecutor）底层就是同款堆。"场景能报出 3 个以上，这题就稳了。

hash 扰动函数：为什么不是直接用 hashCode

static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
  • 定位桶用的是低几位（hash & (n-1) 只取低位）。若直接用原始 hashCode，高位不参与运算——很多类的 hashCode 高位差异大、低位相似，冲突会集中。
  • 高 16 位异或到低 16 位：让高位也影响桶定位，近似"花小代价混合各位信息"，显著降低小容量下的冲突率。用异或而不是与/或，是因为与会偏 0、或会偏 1，异或分布均匀。
  • 注意 key == null 返回 hash 0，所以 HashMap 允许一个 null key，固定落在 0 号桶。

put 流程（putVal 逐步拆解）⭐⭐

final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab; Node<K,V> p; int n, i;
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length;                    // ① 表空：懒初始化，首次 put 建表
    if ((p = tab[i = (n - 1) & hash]) == null)
        tab[i] = newNode(hash, key, value, null);       // ② 桶空：直接放新节点
    else {
        Node<K,V> e; K k;
        if (p.hash == hash &&
            ((k = p.key) == key || (key != null && key.equals(k))))
            e = p;                                      // ③ 头节点就是目标 key：记录待覆盖
        else if (p instanceof TreeNode)
            e = ((TreeNode<K,V>)p).putTreeVal(this, tab, hash, key, value);  // ④ 红黑树插入
        else {
            for (int binCount = 0; ; ++binCount) {      // ⑤ 沿链表找：JDK 8 尾插
                if ((e = p.next) == null) {
                    p.next = newNode(hash, key, value, null);   // 挂到链尾
                    if (binCount >= TREEIFY_THRESHOLD - 1)      // ⑥ 链长达到 8
                        treeifyBin(tab, hash);                  //    尝试树化（容量<64 先扩容）
                    break;
                }
                if (e.hash == hash &&
                    ((k = e.key) == key || (key != null && key.equals(k))))
                    break;                               // 链上命中目标 key
                p = e;
            }
        }
        if (e != null) {                                 // key 已存在：覆盖并返回 oldValue
            V oldValue = e.value;
            if (!onlyIfAbsent || oldValue == null) e.value = value;
            afterNodeAccess(e);                          // LinkedHashMap 访问回调
            return oldValue;
        }
    }
    ++modCount;
    if (++size > threshold)                             // ⑦ 超过阈值：扩容
        resize();
    afterNodeInsertion(evict);                           // LinkedHashMap 删老回调（LRU 用）
    return null;                                         // 全新 key 才走到这
}

答题骨架（背这 7 步）：①表空先 resize 建表 → ②(n-1) & hash 定位桶、桶空直插 → ③头节点 key 相同（hash 相等 + == 或 equals）则覆盖 → ④红黑树走 putTreeVal → ⑤否则链表尾插遍历 → ⑥链长到 8 调 treeifyBin（容量不足 64 优先扩容） → ⑦++size > threshold 再 resize。补一句"modCount++ 供迭代器 fail-fast 检查"就是源码级完成度。

容量为什么必须是 2 的幂 ⭐

  • 取模优化：hash % n 等价于 hash & (n - 1) 的前提是 n 是 2 的幂。位运算比除法快，且此时 n-1 是全 1 的掩码（如 n=16 → 0b1111），每一位都能用上，散列更均匀；若 n 不是 2 的幂，掩码有 0 位，某些桶永远分不到元素。
  • 扩容定位 O(1)：容量翻倍意味着掩码多出一位高位。旧表迁移时不需要重算 hash，只看 e.hash & oldCap：该位是 0 → 留在原下标 j；是 1 → 落到 j + oldCap。一条链最多拆成两条，迁移成本大幅下降。
  • 构造时传入的容量不是 2 的幂也无所谓：tableSizeFor(n) 向上取最近的 2 的幂（new HashMap<>(17) 实际 32）。
// JDK 8 resize() 迁移核心：不重算 hash，按新增那一位拆两条链
do {
    if ((e.hash & oldCap) == 0) {        // 新增位是 0：留在原下标 j
        ...
    } else {                              // 新增位是 1：落到 j + oldCap
        ...
    }
} while ((e = next) != null);

负载因子与扩容

  • threshold = capacity × loadFactor（默认 16 × 0.75 = 12）：size 超过它就扩容，新容量 = 旧容量 << 1（翻倍）。
  • 为什么是 0.75：空间与时间的折中——太大则冲突率高（查询变慢），太小则频繁扩容（浪费内存、拷贝多）。0.75 配合容量 2 的幂，还能让阈值保持整数。源码注释里还给了泊松分布依据：负载 0.5 期望下，单个桶链长达到 8 的概率约 0.00000006。
  • 构造器传初始容量是实战优化：已知要放 n 个元素时给 (int) (n / 0.75f) + 1（Guava Maps.newHashMapWithExpectedSize 同理），避免反复扩容拷贝——大 Map 场景（本地缓存预载）收益明显。

树化与退化：8 和 6 的算术 ⭐

  • 树化两个条件同时满足：链长 ≥ 8（TREEIFY_THRESHOLD）且 table 容量 ≥ 64（MIN_TREEIFY_CAPACITY）；容量不足时 treeifyBin 会优先扩容——早期冲突大概率靠扩容摊薄就能解决，红黑树节点内存是普通 Node 的两倍，是最后手段。
  • 为什么是 8：理想散列下桶内链长服从泊松分布（参数约 0.5），链长到 8 的概率约千万分之六——正常情况几乎不会树化，树化本身是哈希劣化 / 碰撞攻击的兜底信号，阈值 8 就是"到这基本不是运气问题"的统计边界。
  • 退化阈值 6（UNTREEIFY_THRESHOLD）：扩容拆树时，拆出的链长 ≤ 6 就变回链表。取 6 而不是 8 是留 2 的缓冲带，避免链长在 7~8 之间反复增删导致树 ⇄ 链来回转换的结构抖动。

get 流程与比较顺序（第二问必到）

// getNode 的三分支，与 put 对称：
① (n - 1) & hash 定位桶，桶空 → null
② 头节点匹配（first.hash == hash && (== || equals)）→ 直接返回
③ 头节点是 TreeNode → getTreeNode（O(log n)）
   否则沿链表逐个比对 → 命中返回，链尾未中返回 null
  • 比较顺序是三层短路：先比 hash（int，不等直接下一个），再 ==（同一引用直接命中），最后 equals（才是真正的对象比较）——"先 hash 后 equals"不只是定位问题，还是桶内比对的短路优化。追问"为什么还要比 hash"就答这个：hash 不等 equals 必不等，省掉昂贵调用。
  • 所以一个 key 能被 get 到，要求入桶时的 hashCode 与查询时的 hashCode 完全一致——可变 key 的"丢失"本质就是这两次 hash 对不上。

equals / hashCode 与桶定位 ⭐

  • hashCode（经扰动）决定落在哪个桶，== / equals 决定桶内是不是同一个 key。put 与 get 各用一次这套定位，两边必须完全一致。
  • 约定（Object 规范）：equals相等 ⇒ hashCode 必须相等；反之不要求（hash 相等只说明同桶，可能是冲突）。因此重写 equals 必须同时重写 hashCode。
  • 只重写 equals 的经典事故：两个"相等"对象因 hashCode 不同落进不同的桶——map.get(obj2) 返回 null、set.contains(obj2) 为 false，明明 equals 说它们相等。HashMap 还会因此"越存越多"（去重失效）。
  • 好的 hashCode 要分布均匀且稳定：把参与 equals 的字段都掺进来（Objects.hash(...)），不可变对象最好缓存 hash（String 就这么干，HashMap 的 key 选不可变对象也是这个原因——key 入桶后再被改内容，hash 对不上就"丢"了）。

追问预判："key 是可变对象会怎样？"——入桶后修改参与 hash 的字段，对象的 hashCode 变了但节点还在旧桶，get 按新 hash 去找自然找不到，这个 entry 就像"丢失"了（除非改回原值）。所以 Map/Set 的 key 必须不可变（String、Integer、不可变 DTO）。

07JDK 7 死循环与 JDK 8 改动 ⭐⭐

死循环怎么形成的（头插法 + 并发扩容）

JDK 7 的 transfer（扩容迁移）用头插法——为了"新插入的数据更热、放链头更快被找到"，但这个顺序反转在并发下能成环：

// JDK 7 HashMap.transfer()：头插法
while (null != e) {
    Entry<K,V> next = e.next;   // ① 先记住下一个
    e.next = newTable[i];       // ② 头插：e 指向新桶当前头
    newTable[i] = e;            // ③ e 成为新桶头
    e = next;                   // ④ 继续处理下一个
}

推演（桶内链 A → B，扩容后仍落在同桶，头插反转为 B → A）：

  1. 线程 1 执行完 ①（记下 e=A, next=B）后挂起；
  2. 线程 2 独自完成整个扩容：新表里变成 B → A（头插把顺序倒了）；
  3. 线程 1 恢复，拿着旧的引用继续：把 A 头插进新表（A.next = B，即 A → B），再把 B 头插（B.next = A）——A.next = B 且 B.next = A，环形链表形成；
  4. 之后任何一次 get 落到这个桶且没命中，遍历就出不去：CPU 100%，死循环（不是死锁，没有锁）。

为什么需要它：HashMap 并发三宗罪

  • JDK 7 并发扩容死循环（§07）；并发 put 数据覆盖丢失；size 失真。Hashtable 的解法是整表一把锁——读读互斥、读写互斥，并发度等于 1，早已淘汰。

key / value 为什么都不允许 null ⭐

核心是二义性无法消解：get(key) 返回 null，分不清"key 不存在"还是"value 就是 null"。HashMap 单线程可以用 containsKey 补判——两次调用之间状态不可能变；并发下 containsKey 和 get 之间别的线程可能已写入/删除，这个补判不再可靠，二义性彻底无法消除，所以从 API 上直接禁止。

答题口径：先给两个版本的"结构 + 锁粒度 + 并发度"三句话对比，再补 size 的 LongAdder 思想和 null 二义性——这三层下来基本到追问天花板。追问"get 要加锁吗"：不用，Node 的 val 和 next 都是 volatile，保证可见性与happens-before。并发容器全景（BlockingQueue、CopyOnWrite 写时复制的并发细节）见 02-concurrency 板块。

09TreeMap 与红黑树

红黑树是什么（先答数据结构，再答 Java 实现）

  • 一颗自平衡二叉搜索树，靠 5 条性质维持"最长路径 ≤ 2 × 最短路径"：节点非红即黑；根黑；叶（NIL）黑；红节点的孩子必黑（无连续红）；任一节点到其所有叶子的黑高相等。
  • 增删查稳定 O(log n)——不像 AVL 那样严格平衡（AVL 查询略快但插删旋转多），红黑树是"查询与修改的折中"，所以被 TreeMap、HashMap 树化、JDK 的排序实现大量采用。
  • 平衡手段：变色 + 左右旋转（插删后从事发点向上修复）。

TreeMap 要点

  • 底层就是一颗红黑树（Entry 有 left/right/parent/color），key 必须可比较：构造时传 Comparator，否则 key 必须实现 Comparable，两者都没有抛 ClassCastException。
  • 不允许 null key（无法比较；value 可以 null）。
  • 插入/删除/查找 O(log n)，遍历严格按比较序——这是它与 HashMap 的本质差异，也是"要排序选它"的原因。
  • 招牌 API（范围查询场景的答案）：firstKey / lastKey / floorKey / ceilingKey / subMap / headMap / tailMap / navigableKeySet。
  • 实战：时间戳索引（floorKey 找"不晚于 t 的最近版本"）、区间命中、排行榜取 TopN 前缀。

具体开发里什么时候真的用它（7 年经验口径）

先纠一个常见答法：TreeMap 不是缓存，也不能简化成"要排序就选它"。它的定位是有序索引——只有当你要问"比某个值小的最近一个是谁 / 谁落在这个区间里 / 按比较序扫一段"时，它才是正确答案；如果只是想在输出时排个序，List.sort() 更快更省内存。下面这些是我在项目里真用过的场景，也是被问"你用过吗"时能接住的答案：

答题口径（一句话立住）："TreeMap 我当有序索引用，不当容器用——配置按生效时间做版本索引取 floorEntry、费率按档位下界取档、号段/排班用前驱后继判重叠、一致性哈希用 ceilingEntry 找顺时针第一个节点。并发场景直接换 ConcurrentSkipListMap，纯排序输出用 List.sort()。" 这段话答完，"为什么不用 HashMap"和"为什么不自己排个序"两个追问都会被提前关掉。

追问预判 · 一致性哈希："为什么不用 hash % N？"——N 一变几乎全部 key 都要重新映射，缓存/分片集体失效；环上扩缩容只影响相邻一段（约 1/N 的数据）。再追"节点性能不均怎么办"——按权重分配虚拟节点数量；追"环上元素怎么遍历"——ceilingEntry 找不到时回绕 firstEntry，这是环状语义的代码体现。

追问预判："红黑树和跳表怎么选？"——Redis 的 ZSet 用跳表（实现简单、范围遍历天然顺序、并发实现更容易），Java 生态（TreeMap、ConcurrentSkipListMap——跳表版并发 Map）两者都有。答"复杂度都是 O(log n)，选型看实现复杂度与并发友好度"即可。红黑树的插入删除细节在 05-dsa 板块展开。

10LinkedHashMap 与 LRU

结构：HashMap + 一条双向链表

  • 在 HashMap 的散列骨架上，给每个 Entry 加 before/after 两个引用，串成一条贯穿全表的双向链表——迭代顺序不再由桶位置决定，而由这条链决定。
  • accessOrder 构造参数（默认 false）：false = 插入序（FIFO）；true = 访问序——get/put 命中的节点会被移到链尾（借助 HashMap 留的 afterNodeAccess 回调实现，自己没写多少代码）。
  • 链头 = 最老/最久未用，链尾 = 最新/最近使用——这正是 LRU 的形态。

三行核心实现 LRU 容器

class LRUCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    LRUCache(int capacity) {
        super(16, 0.75f, true);            // accessOrder = true：访问即挪到链尾
        this.capacity = capacity;
    }
    @Override
    protected boolean removeEldestEntry(Map.Entry<K,V> eldest) {
        return size() > capacity;          // 每次 put 后回调：true 则删链头（最久未用）
    }
}
  • 原理链：访问序维护（afterNodeAccess）+ 插入后钩子（afterNodeInsertion → removeEldestEntry）= O(1) 的 LRU 驱逐。
  • 局限：非线程安全；并发版要么 Collections.synchronizedMap 包装（锁整表），要么手写"ConcurrentHashMap + 双向链表 + 段锁/reentrant 锁"，工业级实现参考 Caffeine（W-TinyLFU，比朴素 LRU 抗扫描污染）。

面试分工：LinkedHashMap 的 accessOrder / removeEldestEntry 机制是本章考点；"手写 LRU（双向链表 + HashMap）"是算法题，完整实现与变体（O(1) get/put、带 TTL）在 05-dsa 板块。被问手写时主动说一句"生产上我直接用 Caffeine"能带出实战感。

11fail-fast 与 fail-safe ⭐

fail-fast：modCount 机制

  • ArrayList/HashMap 等的结构性修改（增删、扩容，set 不算）都会 modCount++；迭代器创建时记下 expectedModCount = modCount，每次 next()/remove() 先比对，不一致立刻抛 ConcurrentModificationException（CME）。
  • 设计意图：快速失败暴露"迭代中被改"的错误用法（单线程误用或多线程修改），而不是默默给出错乱结果。CME 是"尽量发现"的检测，不保证一定抛——它不拦截并发修改本身。
  • 增强 for 是迭代器语法糖，所以在增强 for 里调 list.remove() 走的是集合的方法（只改 modCount 不改 expectedModCount），下一次 next() 必炸：
List<String> list = new ArrayList<>(List.of("a", "b", "c"));
for (String s : list) {
    if ("b".equals(s)) list.remove(s);     // 💥 ConcurrentModificationException
}

// 正解一：迭代器自己的 remove（内部同步 expectedModCount = modCount）
for (Iterator<String> it = list.iterator(); it.hasNext(); ) {
    if ("b".equals(it.next())) it.remove();
}

// 正解二（最推荐）：JDK 8 removeIf，内部批量标记 + 一次性压缩
list.removeIf(s -> "b".equals(s));

// 正解三：下标倒序删（正序删会漏判后移元素）
for (int i = list.size() - 1; i >= 0; i--) {
    if (cond.test(list.get(i))) list.remove(i);
}

// 正解四：并发场景直接换 CopyOnWriteArrayList（§12）

经典深坑：删"倒数第二个元素"时增强 for 不抛异常但也没删干净后续判断——删除后 size 变小，游标恰好和 size 相等，hasNext() 返回 false 直接退出检查。这解释了"CME 时有时无"，能说清这个特例是源码级理解。另注意 forEach（Lambda 版）内部同样比对 modCount，一样会炸。

fail-safe：弱一致迭代

  • 并发容器（ConcurrentHashMap、CopyOnWriteArrayList 等）的迭代器不抛 CME：创建时直接/快照式遍历，不保证看到迭代开始后的修改（弱一致性，weakly consistent）。
  • COW 系是"快照强一致"（拿到的是创建时刻的副本）；CHM 是"尽量走最新但容忍并发变化"。代价都不是数据损坏，而是读到的可能是旧值——最终一致。

12CopyOnWrite 容器

// CopyOnWriteArrayList.add 核心逻辑
public boolean add(E e) {
    synchronized (lock) {                        // 写：全局锁（JDK 8 是锁对象，JDK 11+ 是 ReentrantLock）
        Object[] es = getArray();
        es = Arrays.copyOf(es, es.length + 1);   // 复制整个底层数组
        es[es.length - 1] = e;
        setArray(es);                            // volatile 写，整体替换引用
        return true;
    }
}
// 读：无锁，直接 getArray()[i]，永远拿到某个完整版本的快照
  • 读写分离：读永远不加锁（数组引用 volatile，读到的是某一刻的完整快照）；写锁住后复制新数组改完再原子换引用——旧数组仍在被读方使用，所以读方零干扰。
  • 适用：读多写极少、数据量不大、能容忍读到旧值——白名单/黑名单配置、事件监听器列表（Listener 注册基本不变、触发极频繁）。
  • 不适用：写频繁或大列表——每次写 O(n) 复制 + 等量内存垃圾，GC 压力大；迭代器不支持 remove；只是最终一致。
  • 家族：CopyOnWriteArraySet（基于 COWAL 去重）。

答题口径：一句原理（写时复制、读无锁快照）+ 一句适用（读多写少配置类）+ 一句代价（写 O(n) 复制、内存翻倍、弱一致）。追问"为什么读不用加锁"：数组引用是 volatile 的，且数组一旦发布不再修改，读到的一定是完整版本——不变性替代了锁。

15高频追问与陷阱

  • 追问链：HashMap → 为什么容量 2 的幂 → 那指定 17 会怎样→ tableSizeFor 向上取 32；再追"阈值什么时候生效"→ 构造时先存 threshold，首次 put 才建表并重算 threshold = newCap × 0.75。
  • 追问链：put → 如果两个 key hash 相同但 equals 不同→ 同一个桶里链着（正常冲突）；如果 hash 相同且 equals 相同 → 覆盖旧 value 返回 oldValue。hash 相同是冲突、equals 相同才是同一个 key，这两个概念要拆开说。
  • 追问链：树化 → 为什么先看容量 64→ 小表冲突大概率是"桶太少"而不是"hash 太坏"，扩容摊薄成本远低于红黑树节点（内存双倍、维护复杂）；64 = 4 × 16，给了 2 次翻倍机会。
  • 追问链：CHM → get 为什么不加锁→ Node.val/next 为 volatile，读到的引用链要么是完整旧版本要么是完整新版本；再追"正在扩容时 get"→ 碰到 ForwardingNode 会转发到新表继续找。
  • 追问链：fail-fast → 单线程也会抛 CME 吗→ 会（迭代中自己调集合的 add/remove 就是），fail-fast 不只防多线程，本质防"迭代中被结构性修改"。
  • 陷阱：HashSet add 重复元素的返回值——底层 map.put 返回旧 value 非 null 时 add 返回 false，add 失败不是异常而是布尔。
  • 陷阱：Arrays.asList 返回的 List——定长视图，add/remove 抛 UnsupportedOperationException，set 可以；new ArrayList<>(Arrays.asList(...)) 或 List.of(...)（同样不可变）按需选。
  • 陷阱：subMap/subList 是视图——修改视图直接影响原表；原表结构性修改后视图操作抛 CME。
  • 陷阱：HashMap 遍历时删除——同 fail-fast 规则，正解 entrySet 迭代器 remove / removeIf。
  • 场景题口径："几万级 QPS 的本地缓存用什么"→ Caffeine（W-TinyLFU），说得出它与朴素 LRU 的差异（抗扫描污染）就是亮点。
  • 追问链：PriorityQueue 迭代 → 为什么遍历不是有序的→ 底层是堆数组，只保证父 ≤ 子，不保证左右子树之间有序；要按优先级消费必须逐个 poll（或 Arrays.sort(toArray())）。
  • 追问链：Top-K → 数据量内存放不下呢→ 堆只留 K 个元素，天然适合流式/超大数据；再追"多机"→ 各机先出本地 Top-K 再合并（分治 + 多路归并，MapReduce 思想）。
  • 追问链：ArrayDeque → 为什么不允许 null→ poll/peek 约定用返回 null 表示"没有元素"，允许存 null 就无法区分"取到了 null"和"队列为空"；同理 PriorityQueue 也禁 null。
  • 陷阱：Stack 的 get(i)/insertElementAt——继承 Vector 暴露了任意位置访问，破坏 LIFO 语义，是"组合优于继承"的官方教材；现代代码一律 Deque + ArrayDeque。
  • 陷阱：PriorityQueue 是无界的——初始容量只是数组初值不是上限，塞多了是 OOM 不是"拒绝入队"；要有界/背压用 ArrayBlockingQueue（02-concurrency）。
