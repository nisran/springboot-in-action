02抽象类 vs 接口：怎么选 ⭐⭐（必考）

技术约束对比表

维度抽象类（abstract class）接口（interface）
继承机制extends，单继承implements，多实现
成员变量任意：可变实例字段、protected、静态块初始化只能 public static final 常量（无实例状态）
方法抽象 + 具体方法 + static + final 方法都行抽象方法 + default/static（JDK 8）+ private（JDK 9）
构造器有（供 super() 链初始化自身字段）无
初始化块静态块、实例块都可以都不行（无状态可言）
语义is-a：身份的一部分，模板骨架can-do：能力契约，可插拔
演化代价新增抽象方法 → 所有子类必须改（源码不兼容）新增 default 方法可做到二进制兼容

选型口径（按这个顺序说）

  1. 语义优先：is-a 且要共享状态（字段）、受保护方法、部分实现 → 抽象类（模板方法模式）；can-do 的能力横切面（Comparable、AutoCloseable、Serializable）→ 接口，一个类可以同时具备多种能力。
  2. 默认接口：抽象类占用唯一的继承名额且耦合实现层；接口面向使用方编程（面向接口编程、依赖注入的基础），扩展时新增实现零侵入。
  3. 框架实证（背两个例子）：List（契约）与 AbstractList（骨架实现）的分工——JDK 同时给出两者，骨架类替你实现通用方法；HttpServlet 的 service → doGet/doPost 是模板方法；Spring 的 JdbcTemplate 把"资源获取/异常翻译"固定，把 SQL 与回调留给子类/ Lambda。

一句话口径："模板骨架用抽象类，能力契约用接口；不确定就先定义接口，需要共享字段/受保护方法/公共实现时再补一个抽象类实现它——List + AbstractList 就是这个双层结构。"最后这句双层结构是高级岗的区分点。

陷阱：① 抽象类可以有构造器但不能实例化——构造器是给子类 super() 链用的；② abstract 与 final 不能同时修饰类（一个要被继承、一个禁止被继承，自相矛盾，编译错误）；③ 抽象类可以没有抽象方法（用途：纯"禁止 new"的基类），有抽象方法的类必须是抽象类。

03接口方法演化：default / static / private

JDK 8 之前：接口 = 纯契约

只有 public abstract 方法和 public static final 常量。致命问题：接口一旦发布就没法加方法——JDK 8 要给 Collection 加 stream()，全世界所有实现类都得跟着实现？于是 default 方法诞生。

default 方法：带实现的接口方法

interface PaymentChannel {
    void pay(BigDecimal amount);

    // JDK 8：default 方法，老实现类无需改动即可获得新能力
    default String describe() {
        return "channel: " + name();
    }
    default boolean supportsRefund() { return false; }
    String name();
}
  • 定位：接口演化的"向后兼容补丁"，不是"多继承工具"——别把它当 trait 用来堆逻辑。
  • 菱形冲突：实现两个接口存在同名同签名 default → 编译错误，必须重写，可用 InterfaceName.super.method() 指定沿用哪边：
class Alipay implements Pay, Refundable {
    @Override
    public String receipt() {
        return Pay.super.receipt() + " | " + Refundable.super.receipt();
    }
}
  • 规则细节：类中继承的方法（含抽象类里的具体方法）优先于接口 default；default 方法不能覆盖 Object 的方法（equals/hashCode/toString 的语义属于值本身，不该由接口统一实现，编译器直接禁止）。

同名方法裁决四步（类优先原则的完整版）⭐

类继承树与接口树同时有同名方法时，编译器按固定优先级裁决（亲爹压后爹，离得近压离得远，平级冲突法庭拒绝裁决）：

优先级胜者说明
1自己重写的方法实现类自己写的永远最优先
2超类方法（具体/抽象都算）父类有同名方法 → 接口 default 出局；父类是抽象方法也会"挡住" default，逼实现类自己实现（经典冷知识）
3更具体的接口 defaultIB extends IA 且都实现了 hi() → 实现 IB 的类拿 IB 的版本（离得近压离得远）
4父接口 default兜底
interface IA { default String hi() { return "IA"; } }
interface IB extends IA { default String hi() { return "IB"; } }   // 更具体
class Base { public String hi() { return "Base"; } }               // 超类方法

class C1 extends Base implements IA, IB {}
new C1().hi();                       // "Base" —— 类优先压过两个接口

class C2 implements IA, IB {}        // 不冲突！IB 重写的就是 IA 的那个 default（同源覆盖）
new C2().hi();                       // "IB" —— 最具体者胜

interface IC extends IA {}
interface ID extends IA {}           // 两条路都指向【同一个】IA.hi —— 菱形同源，也不冲突
class C3 implements IC, ID {}        // ✅ 编译通过，用 IA 的实现

interface IE { default String hi() { return "IE"; } }   // 与 IA 平级且互不相干
class C4 implements IA, IE {}        // ❌ 编译错误：IA 与 IE 的 default 互不相关
                                     //    "class C4 inherits unrelated defaults"
class C5 implements IA, IE {
    @Override public String hi() { return IA.super.hi() + "|" + IE.super.hi(); }  // 唯一解：重写+点名
}
  • 为什么类优先：Java 8 加 default 的目标是"给存量类补新能力而不破坏它们"——若接口 default 能悄悄压过类里已有的方法，加一个接口就会改变无数既有类的行为，向后兼容直接破产。"类是亲爹，接口是干爹"。
  • 验证方式（面试可提）：javac 与 IDE 都会直接报冲突；用 javap -c 看编译产物，冲突类根本不会生成字节码。

static 方法：挂在接口上的工具/工厂

interface Point {
    static Point of(int x, int y) {          // 工厂方法：调用 Point.of(...)
        return new SimplePoint(x, y);
    }
}
// JDK 8 风向标：Comparator.naturalOrder()、List.of()、Optional.of()
// 取代了 "Collections 工具类 + 私有构造器" 的旧模式

private 方法（JDK 9）：default 之间的复用

interface Validator {
    default String validateName(String s)  { return check(s, 20); }
    default String validatePhone(String s) { return check(s, 11); }

    private String check(String s, int max) {   // JDK 9：私有方法，供 default 复用
        return (s == null || s.length() > max) ? "invalid" : "ok";
    }
    private static String trim(String s) { ... } // 也可以是 private static
}

兼容性三档：源码兼容（调用方不用改能重新编译）、二进制兼容（已编译的 class 不重编也能链接运行）、行为兼容（语义不变）。default 方法解决的是二进制兼容——这也是"为什么接口能有方法体了"的官方动机。接口依然没有实例状态，default 只能操作方法参数和静态常量。

04函数式接口与 @FunctionalInterface

定义：SAM —— Single Abstract Method

  • 有且仅有一个抽象方法的接口就是函数式接口，可以用 Lambda / 方法引用赋值。
  • 计数规则：default、static、private 方法不计入；Object 的 public 方法（equals 等）也不计入——Comparator 虽然声明了 equals，仍是函数式接口。
  • @FunctionalInterface：非必需，但编译器校验（多了抽象方法立刻报错），必须写——相当于函数式接口版的"契约声明"。
@FunctionalInterface
interface Printer {
    void print(String msg);

    default Printer andThen(Printer next) {      // default 不影响 SAM 判定
        return msg -> { print(msg); next.print(msg); };
    }
}

JDK 内置函数式接口（四大天王 + 特化）

接口抽象方法语义代表场景
Function<T,R>R apply(T)入 → 出（转换）map、computeIfAbsent
Consumer<T>void accept(T)消费不返回forEach、peek
Supplier<T>T get()无入有出（生产/惰性）orElseGet、懒加载
Predicate<T>boolean test(T)断言filter、removeIf
衍生BiFunction / UnaryOperator / IntFunction / ToLongFunction …双参/同型/原始类型特化避免装箱开销

答题口径：函数式接口是 Lambda 的类型载体——Lambda 本身没有类型，写 (a, b) -> ... 时编译器从目标上下文（变量声明/参数/返回值）推断它是哪个 SAM。自定义函数式接口的典型时机：业务回调语义需要命名（如 RetryPolicy、ShardingHandler）。深入见 第 10 章。

05record：不可变数据载体 ⭐（JDK 16 转正）

一行换五件套

// JDK 14 预览、16 转正（JEP 395）："数据的透明载体"
public record Point(int x, int y) {}

// 编译器自动生成：
// ① 全参规范构造器 Point(int x, int y)
// ② 访问器 x() / y()        —— 注意不是 getX()！
// ③ equals()：基于全部组件的值比较（不是引用）
// ④ hashCode()：基于全部组件
// ⑤ toString()：Point[x=1, y=2] —— 天然适合日志

紧凑构造器：参数校验与规范化

public record Range(int low, int high) {
    public Range {                                        // 紧凑构造器：不写参数列表
        if (low > high) throw new IllegalArgumentException("low > high");
        low = Math.max(low, 0);                           // 规范化后赋回参数（无需 this.low = low）
    }
}

// 静态工厂惯用法：语义化构造
public record Money(long cents, String currency) {
    public static Money ofCny(long yuan) { return new Money(yuan * 100, "CNY"); }
    public static Money zero()           { return new Money(0, "CNY"); }
}

规则与限制

  • 组件（字段）隐式 private final；类隐式 final（不能被继承），隐式继承 java.lang.Record（不能再 extends 别的类），可以实现接口。
  • 不能再声明可变实例字段（静态字段、静态方法、实例方法随意加）；不能再手动写规范构造器以外的"全字段构造"混淆语义。
  • JDK 16 起支持局部 record：方法体内临时建一个中间结果类型，比 double[] 和 Pair 更有表达力。
  • 浅不可变：组件是可变对象（List、Date）时，引用不变但内容可改——防御性写法 List.copyOf(items) 存进去。
  • 生态注意：访问器是 x() 不符合 JavaBean 规范，Jackson 需 2.12+、Spring 需 2.6+ 才友好支持 record 反序列化（构造器绑定）。

record vs Lombok @Data（高频对比题）

维度recordLombok @Data / @Value
层次语言级（编译器 + JLS 语义）注解处理器改字节码（编译期织入）
可变性强制不可变（无 setter）@Data 全家桶默认可变（getter/setter）
equals/hashCode按组件语义生成，规格稳定按字段生成（exclude/include 可配）
新特性协同与解构模式匹配（JDK 21）、sealed 天然配合无此能力
工具链耦合无（JDK 自带）依赖 Lombok 版本，IDE/升级常踩坑
适用值对象、DTO、多返回值、Map 的 key需要可变 POJO / JPA 实体（实体需要无参构造与 setter）

答题口径："新的值对象/DTO 一律 record——不可变、equals/hashCode/toString 白送、还接得住模式匹配；Lombok 留给 JPA 实体这类必须可变的场景，别再用 @Data 生成'伪值对象'（可变 + equals 全字段，放进 HashSet 就埋雷，呼应第 03 章可变 key 的坑）。"

06sealed：受控继承 ⭐（JDK 17 转正）

动机：在 final（全封）与开放（全开）之间加一档

过去只有两个极端：final 谁都不能继承；不加 final 任何人随便继承。sealed 让作者声明"谁可以继承我"——把继承从"默认开放"变成"白名单许可"。

// JDK 17 转正（JEP 409）
public sealed interface PaymentResult permits Paid, Declined, Pending {}
//                       ↑ sealed 类/接口    ↑ 显式列出全部许可类型

public record Paid(String txnId, BigDecimal amount) implements PaymentResult {}
public record Declined(String reason)                 implements PaymentResult {}
public record Pending(String txnId, Duration eta)     implements PaymentResult {}

规则（三条硬约束）

  • 每个 permitted 子类型必须直接 extends / implements 该 sealed 类型，且必须三选一标注：final（到此为止）/ sealed（继续受控下放）/ non-sealed（重新开放给任何人）。
  • sealed 类型必须有子类：permits 列表不能为空（或省略 permits 要求子类同文件）；permitted 类型必须同模块，或未命名模块时同包。
  • sealed 不能与 final 同用（final 已经全封了，没有 permits 可言）；sealed 与 record 是绝配——record 天生 final。

核心收益：穷尽性（exhaustiveness）

static String render(PaymentResult r) {
    return switch (r) {
        case Paid p     -> "✅ " + p.txnId() + " " + p.amount();
        case Declined d -> "❌ " + d.reason();
        case Pending p  -> "⏳ " + p.txnId();
    };  // ✅ 无需 default：编译器知道 permitted 集合已全覆盖
        // 将来新增 Delayed implements PaymentResult → 这里【直接编译错误】
}
  • switch 模式匹配（JDK 21 转正，JEP 441）下，编译器按 permits 集合做穷尽性检查：新增子类型时所有漏改的 switch 全部编译报错——把"漏处理一个分支"从运行期事故变成编译期错误。
  • 反射可查：Class.getPermittedSubclasses()——框架（如 Jackson、验证器）可据此做序列化/校验。
  • 典型建模：领域状态机（订单状态、支付结果）、结果类型（模拟函数式语言的 Option/Result）、消息协议的封闭指令集。

陷阱：① 加了 default 分支会毁掉穷尽性检查——编译器认为已全覆盖，新增子类型不再报错，等于白用 sealed；② permitted 子类必须能被 sealed 类型"看到"（访问权限），跨包放错位置直接编译错误；③ sealed 管的是编译期封闭，不是运行时校验，别和安全验证混为一谈。

07三件套协同：sealed × record × 模式匹配 = 代数数据类型

函数式的"sum + product"落到 Java

  • record = product 类型（积：一个值由多个字段的组合构成，且仅此组合）。
  • sealed = sum 类型（和：一个值是有限集合中的恰好一种）。
  • 两者组合就是代数数据类型（ADT）——Scala/Rust/Haskell 里 enum 的表达力，Java 17/21 终于补齐。

实战示例：模拟 Result 类型

public sealed interface Result<T> permits Ok, Err {}
public record Ok<T>(T value)              implements Result<T> {}
public record Err<T>(int code, String msg) implements Result<T> {}

static <T> String log(Result<T> r) {
    return switch (r) {
        case Ok(T value)      -> "ok: " + value;              // JDK 21 record 解构模式
        case Err(int code, String msg) -> "err[" + code + "] " + msg;
    };
}
  • JDK 21 的 record patterns（JEP 440）直接把组件解构成变量，嵌套 record 也能一层层拆。
  • 对比旧写法：继承体系 + if-else + 强转 + 手写校验 → 现在"类型即文档、分支即穷尽、编译器当测试"。
  • 业务里最先落地的位置：支付/工单的状态流转、消息队列的事件类型定义、对外 API 的错误码分类——把一堆魔法字符串换成一目了然的类型树。

三个特性各自版本线：record 16（JEP 395）、sealed 17（JEP 409）、模式匹配 instanceof 16（JEP 394）、switch 模式匹配 21（JEP 441）、record 解构 21（JEP 440）。JDK 17/21 两个 LTS 是面试讲新特性的主线，完整时间轴见 第 14 章；用它们做低耦合设计的例子见 07-LLD 板块。

08高频追问与陷阱

  • 追问链：抽象类 vs 接口 → 接口能定义 main 方法吗？→ 可以，static 方法允许（JDK 8+），interface I { public static void main(String[] a){...} } 合法——考你对 static 接口方法的掌握。
  • 追问链：default 方法 → 类优先原则？→ 裁决顺序：自己重写 > 超类方法（具体/抽象都赢，抽象的会"挡住" default 逼你实现）> 更具体的接口 default > 父接口 default；菱形同源（两条继承路指向同一个 default）不算冲突，两个平级 default 才冲突——编译器拒绝裁决直接报错，实现类必须重写，体内用 X.super.m() 点名调用。加分点：default 不能覆盖 Object 的方法（toString/equals/hashCode，实测编译错误）；接口 static 方法不传给实现类。
  • 追问链：接口为什么不能有实例字段？→ 接口是契约不是实现，多实现下"接口状态"归属矛盾（两个接口同名字段听谁的）；JDK 团队刻意保持"无状态"边界。
  • 追问链：record → 能不能继承抽象类？→ 不能（已隐式继承 Record）；可实现接口。能不能实现抽象类里的抽象逻辑？→ 只能通过接口侧。JPA 实体为什么不用 record？→ 实体需要可变 + 无参构造 + 代理增强。
  • 追问链：record 两个组件相同的实例 equals 相等吗？→ 相等（全组件值比较）——所以 record 当 HashMap 的 key 完美契合第 03 章"key 必须不可变"的要求。
  • 陷阱：sealed 的 permits 子类忘了标 final/sealed/non-sealed→ 编译错误；子类与 sealed 类不同包（未命名模块）→ 编译错误。
  • 陷阱：@FunctionalInterface 注解的接口又加了第二个抽象方法→ 编译错误；但加 default/static/private/Object 方法不算——考 SAM 计数规则。
  • 陷阱：default 方法里修改"常量"字段→ 接口字段是 public static final，改不了；想在 default 里存状态是设计错误，请改用抽象类。
  • 追问链：有 default 之后抽象类还有存在价值吗？→ 有：① 状态——抽象类能有实例字段/构造器维护中间状态，default 只能靠"接口常量 + 纯函数"；② protected 成员与模板方法——对子类暴露受控扩展点；③ 单继承的代价换来强约束。一句话："default 是能力共享，抽象类是骨架与状态共享。"
  • 追问链：sealed 和 enum 什么关系？→ enum 是"有限实例集合"（每个常量是单例），sealed 是"有限类型集合"（每个子类型可携带不同字段与行为）；需要"每种状态带各自数据"时 enum 就捉急了（得靠构造器传参硬塞），sealed + record 是"万能枚举"。
  • 追问：接口初始化什么时候发生？→ 访问接口的非常量字段/触发其 <clinit> 才初始化；实现类初始化不会连带初始化接口（与类父子不同）——冷门但真实的 JLS 行为，答出来就是区分度。

09面试自查清单

  1. 能按"约束表 + 语义口径 + 框架实证（List/AbstractList、HttpServlet）"三层回答抽象类 vs 接口怎么选。
  2. 能解释 default 方法的动机（二进制兼容、Collection.stream()）、菱形冲突规则与 X.super.m() 消歧。
  3. 知道接口 static 方法（工厂/工具）和 private 方法（default 复用）各自的定位。
  4. 能给出函数式接口的 SAM 判定规则（default/static/private/Object 方法不计入）并写 @FunctionalInterface。
  5. 能列出 record 自动生成的五件套，会用紧凑构造器做校验，知道 record 浅不可变 + List.copyOf 防御。
  6. 能对比 record 与 Lombok @Data（层次、可变性、协同、工具链），给出选型建议。
  7. 能写出 sealed interface + permits 的完整例子，说出三条硬约束和 non-sealed 的语义。
  8. 能解释穷尽性：sealed + switch 模式匹配如何把"漏分支"从运行期事故变成编译期错误，以及 default 分支为什么会毁掉它。
  9. 能说清 sealed（sum）+ record（product）= ADT，举一个状态机或 Result 类型的业务例子。
  10. 能按四步裁决表讲同名方法冲突（含"抽象超类挡 default"冷知识），并写出 X.super.m() 消歧代码。
  11. 能回答"default 之后抽象类还有何价值"（状态/protected/模板骨架）与 sealed vs enum（实例集合 vs 类型集合）。
