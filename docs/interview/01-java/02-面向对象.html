02类与对象：OOP 三特征与对象内存布局

三大特征一句话版（开场题）

  • 封装：私有化字段 private + 暴露受控方法，把"怎么做的"藏起来只留"做什么"——变化的防火墙。
  • 继承：子类复用/扩展父类，is-a 关系（细节在第 03 章）。
  • 多态：父类引用指向子类实例，运行期决定实际调谁的方法（底层在第 03 章展开）。
  • 为什么 OOP：易维护（改一处不扩散）、易复用（组合 + 继承）、易扩展（多态 + 接口注入新实现，对修改关闭、对扩展开放）。

开场题的深水区：三特征各自的追问点

特征带来什么失去什么 / 风险面试官下一句
封装降低耦合、可精确控制读写权限、内部实现可自由演进过度封装成"贫血模型"（只有 getter/setter 没有行为）封装只是 private 字段吗？——行为封装（把不变式锁在方法里）才是灵魂
继承代码复用、建立 is-a 分型白盒复用：子类依赖父类实现细节，父类一改子类就碎（脆弱基类）组合优于继承怎么讲？→ 第 15 章
多态扩展新实现不动调用方（开闭原则的发动机）字段与 static 方法没有多态（静态绑定）多态的三个前提？——继承/实现 + 重写 + 父类引用指向子类对象，底层虚分派见 第 03 章

答题口径：别只背"封装继承多态"三个词。每个特征补一句"代价/边界"（封装 ≠ 藏字段、继承是白盒复用、多态只覆盖实例方法），再各带一个追问的接法——这一段答完，面试官通常就会顺势进入内存布局或初始化顺序的深水区。

类与对象在内存里是什么

  • 类：被类加载器加载后，类元数据（字段/方法描述、字节码）进入元空间（JDK 8+，替代永久代），同时在堆里创建一个 java.lang.Class 实例作为访问入口。
  • 对象：堆中的一块内存 = 对象头（Mark Word + 类型指针 klass pointer）+ 实例字段（含父类字段）+ 对齐填充。引用变量存的是这块内存的地址。
  • 类型指针就是"对象找到自己类元数据"的钩子，getClass()、instanceof、虚方法分派都依赖它。

对象头与锁状态（无锁 → 偏向锁 → 轻量级锁 → 重量级锁）在 02-concurrency 板块的 synchronized 原理里展开；类加载的七个阶段见 03-jvm 板块。

Mark Word 细看（64 位 HotSpot）：一个 8 字节字段的四种身份

64 位 JVM 上对象头的 Mark Word 占 8 字节，JVM 复用同一块比特位存"当前最需要的信息"，锁状态不同、布局就不同（这是 synchronized 锁升级能原地发生的物理基础）：

锁标志（biased + lock）状态Mark Word 比特布局（64 位）
0 01无锁unused:25 | hashCode:31 | unused:1 | 分代年龄:4 | 0 01
1 01偏向锁线程 ID:54 | Epoch:2 | unused:1 | 分代年龄:4 | 1 01
— 00轻量级锁指向栈中 Lock Record 的指针:62 | 00
— 10重量级锁指向 ObjectMonitor 的指针:62 | 10
— 11GC 标记标记整理算法下的转发指针等 | 11
  • 两个必考推论：① hashCode 占 31 位，偏向模式里线程 ID 要占 54 位——两者放不下，所以调用过 identityHashCode() 的对象无法进入偏向状态（只好直接轻量级起跳）；② 分代年龄只有 4 位 → 最大 15，这正是 MaxTenuringThreshold 上限 15 的由来（晋升细节见 03-jvm 板块）。
  • 布局验证工具：JOL（Java Object Layout）——ClassLayout.parseInstance(obj).toPrintable() 直接打出每个字段偏移；加 -XX:MarkSweep... 不必，默认输出即含对象头 12 字节（开启压缩指针时 Mark Word 8 + klass 4）+ 实例数据 + 对齐填充到 8 的倍数。
  • 锁标志怎么变化、偏向怎么撤销、为什么 JDK 15 起默认废弃偏向锁——这些锁策略属于 02-concurrency 锁升级一节，本章只认布局不展开。

对象实例 vs 对象引用：气球与绳子（JavaGuide 经典问法）

User u1 = new User("alan");   // 右边在堆里"吹气球"，左边在栈局部变量表里"拴绳子"
User u2 = u1;                 // 又拴了一根绳子到同一个气球——没有新对象，引用拷贝而已
u1 == u2                      // true：两根绳子系着同一个气球
u2.setName("bob");
u1.getName()                  // "bob"：从任何一根绳子过去改的都是同一个气球
  • 引用本身只是个地址值：局部变量时在栈帧的局部变量表；作为字段时随宿主对象在堆里。
  • 追问接法："那 Java 参数是值传递还是引用传递？"——永远是值传递（传引用的拷贝），完整论证在 第 01 章值传递一节。

对象相等 vs 引用相等

User a = new User("alan");
User b = new User("alan");
a == b        // false：引用相等——比较的是"是不是同一个气球"
a.equals(b)   // true（若 User 重写了 equals）：对象相等——比较的是"内容是否一致"
  • 不重写 equals 时继承自 Object 的版本就是 ==。equals/hashCode 契约、重写规则与散列冲突是 第 03 章 Object 常用方法的主场，包装类型的 == 缓存陷阱见 第 01 章。

引用怎么找到对象：句柄 vs 直接指针（HotSpot 用后者）

方案引用里存什么优点缺点
句柄（中间表）句柄池里条目的地址对象被 GC 移动时，只需改句柄表，引用本身不动多一次跳转，访问慢
直接指针（HotSpot）对象地址本身访问快（一次直达）GC 移动对象（复制/整理）时要改所有指向它的引用
  • HotSpot 选直接指针：对象访问是最高频操作，用 GC 时多改几个引用换日常访问零跳转——"停顿时间换吞吐"思路的又一例。
  • 追问接法："GC 移动对象时引用怎么改？"→ 利用 OopMap / 安全点记录的引用位置精确修正（细节归 03-jvm）；顺带一句：对象引用是 4 还是 8 字节取决于压缩指针（-XX:+UseCompressedOops，堆 < 32GB 默认开），这也是"堆超 32G 性能反而可能掉"的经典解释。

对象拷贝三兄弟：引用拷贝 / 浅拷贝 / 深拷贝 ⭐

class Address { String city; Address(String c){ city = c; } }
class Person implements Cloneable {
    String name; Address addr;
    Person(String n, Address a) { name = n; addr = a; }
    @Override protected Person clone() throws CloneNotSupportedException {
        return (Person) super.clone();          // 浅拷贝：只复制第一层
    }
}

Person p  = new Person("alan", new Address("HZ"));
Person q  = p;                                  // ① 引用拷贝：q 和 p 是同一个对象
Person s  = p.clone();                          // ② 浅拷贝：新 Person，但 addr 指向同一个 Address
q  == p        // true
s  == p        // false —— 拷贝出了新对象
s.addr == p.addr   // true  ← 浅拷贝的铁证：引用字段仍然共享
// ③ 深拷贝：s.addr 是 new Address("HZ")，两棵完全独立的对象图
//    s.addr == p.addr → false，改 s.addr.city 不影响 p
引用拷贝浅拷贝（super.clone）深拷贝
新对象？否是（第一层）是（整棵对象图）
引用类型字段同一对象仍指向原对象（共享）递归复制，各自独立
改一个影响另一个？全影响改引用字段内部状态会互相影响互不影响
  • clone 机制三层：① Object.clone() 是 protected native——子类不重写为 public 就调不到，且不重写返回的是 Object 要强转；② Cloneable 是标记接口（无方法），只用于给 Object.clone "授权"，没实现就调用抛 CloneNotSupportedException；③ super.clone() 做的是逐字段位复制——这就是它只能是浅拷贝的原因。
  • String/包装类的迷惑项：浅拷贝复制的是引用，但 String 等不可变类型"改不了内容"，所以浅拷贝里它们表现如深拷贝——只有可变引用类型（Date、集合、数组、自定义可变类）才暴露浅拷问题。
  • 深拷贝三种实现：① 递归重写 clone（每层可变类都实现 Cloneable，样板代码多）；② 拷贝构造器 / 静态工厂（new Person(this)，最清晰可控，推荐）；③ 序列化-反序列化一轮（对象图整体复制，写法最省但性能最差，且要求全图 Serializable）。
  • clone 的坑：final 字段改不了引用（深拷贝时没法给 final 引用字段换新对象，只能拷构造器能救）；克隆不走构造器，不变式校验会被绕过——这正是"防御性拷贝别用 clone"的理由，实战见 第 05 章防御性拷贝。

答题口径：先给"新不新对象、引用字段独不独立"两个判定维度，再用 s.addr == p.addr 一行代码证明浅拷；追问实现方式时报"递归 clone / 拷贝构造器 / 序列化"三件套，最后主动补一句 clone 不走构造器会绕过校验——分层级收尾。

03构造器与 this

构造器的规则清单

  • 没有返回值类型（连 void 都没有），与类同名；不写时编译器生成默认无参构造器（一旦手写任何构造器，默认的就不给了）。
  • 可以被重载；不能被继承，因此不能被重写；不允许 abstract / static / final / synchronized 修饰。
  • 同一个构造器里 this(...) 与 super(...) 都必须是第一条语句，所以只能二选一；链式 this(...) 最终一定走到某个调用 super(...) 的构造器（默认插入无参 super()）。
  • private 构造器 = 禁止外部 new：工具类（如 java.util.Objects）、单例、枚举之外控制实例数（如 IntegerCache 那种受控实例）。

this 的四个面孔

public class User {
    private String name;
    private int age;

    public User() { this("anonymous"); }        // 1. this()：构造器链，必须第一行

    public User(String name) {
        this.name = name;                        // 2. 区分成员与参数（最常见）
    }

    public User grow() {
        this.age++;                              // 3. 当前对象引用
        return this;                             //    链式调用的基础：user.grow().save()
    }

    class Label {
        void print() {
            System.out.println(User.this.name);  // 4. 内部类里限定外部实例：Outer.this
        }
    }
}
  • 底层视角：实例方法的字节码里，this 就是隐式的第 0 个参数（aload_0）——所以 static 方法没有 this、不能引用实例成员。
  • 接口/抽象的价值：返回 this 支撑 Builder 链式 API（StringBuilder.append、Lombok @Accessors(chain=true)）。

new 的时候，对象是哪一刻"创建"的：先毛坯后装修

常见误解是"构造器创建对象"。真实时序是先分配、后装修——构造器一行代码没跑，对象就已经存在了，构造器只负责初始化：

new Child()
① 分配堆内存：对象头 + 全部字段（含继承来的）先置默认值 0/null/false   ← 对象此刻已存在，this 已可用
② 执行 <init>：super() 链 → 字段赋值 / 实例块（按源码顺序）→ 构造器体
③ 最外层构造器体结束 = <init> 完成，new 表达式返回引用
  • 并发 new 天生安全：每次 new 分配各自的内存（HotSpot 靠 TLAB 线程私有分配缓冲，分配动作基本无锁），各线程装修各自的对象互不干扰——要防的不是并发 new，而是下面"装修没完就交钥匙"的 this 逃逸。
  • 这个时序顺带解释了 第 03 章"父类构造器调可重写方法 → NPE"反例的根因：父类构造器执行时，子类字段还停在第 ① 步的默认值。

this 逃逸（构造器泄漏）：在构造器里把 this 注册进监听器、缓存、或启动新线程——对象可能还没构造完就被其他线程看见，读到半初始化字段。这就是"不在构造器里调用可被重写的方法"的根因（第 03 章给 NPE 反例），也是并发里"不安全发布"的典型。口径：构造器只做字段赋值，注册/启动动作挪到 start() 方法。

this 逃逸可运行示例：构造未完，watcher 先到

class Server extends Thread {
    private final String name;                       // blank final：构造器末尾才赋值
    Server() {
        new Thread(this::watch, "watcher").start();  // ❌ this 在这里就逃逸了
        try { Thread.sleep(10); } catch (InterruptedException ignored) { }
        this.name = "server";                        // 赋值发生在 watcher 启动之后
    }
    private void watch() { System.out.println("watcher sees: " + name); }
    @Override public void run() { }
    public static void main(String[] args) { new Server(); }
}
// 大概率输出：watcher sees: null
// 根因：start() 与 name 赋值之间没有任何 happens-before，
// watcher 线程完全可能读到尚未初始化的字段（甚至因重排序看到"乱序"状态）
  • 即便把赋值挪到 start() 之前也一样危险：缺少同步屏障时，另一个线程看到的写入顺序可能被打乱。修复不是调顺序，而是别在构造器里发布 this——先构造完，再由调用方（或工厂方法）负责注册/启动。
  • 构造器里调用可被重写的方法是 this 逃逸的"近亲"：父类构造器执行时子类字段还是默认值，重写方法一碰就 NPE——完整反例与规则（只调 private/final/static 方法）在 第 03 章 super 与构造器链。
  • 两个小追问的答案：构造器互相调用不能成环（this() 递归循环直接编译错）；构造器不能加 synchronized——对象和监视器还没就绪，锁它没有意义，需要原子初始化该用静态工厂 + <clinit> 锁（见下节 Holder 单例）。

04static：类级语义与存储真相 ⭐

一份、随类走、先于对象存在

  • static 变量：全类只有一份，所有实例共享；生命周期 = 类的生命周期（类卸载才回收，一般活到进程结束）。
  • static 方法：属于类，无 this，只能直接访问静态成员；用引用调静态方法是合法但误导的写法（编译器按声明类型解析，警告点）。
  • static 块：类初始化时执行一次，多个按文本顺序执行（详见初始化顺序节）。

三种变量横向对比（JavaGuide 高频表）

维度静态变量实例变量局部变量
归属类（Class 对象）对象方法调用（栈帧）
存储（JDK 8+）随堆中 Class 对象随对象在堆栈帧局部变量表
生命周期类卸载（通常进程结束）对象被 GC方法返回即失效
默认值有（0/null/false）有无——未显式初始化就使用是编译错
线程可见全类共享（并发要自己保护）对象内共享线程私有，天然安全
修饰权限可用 private/protected/public 修饰不能用访问修饰符（作用域即方法体）

"局部变量不初始化不能编过、成员变量却默认有值"常被追问为什么：成员变量随对象/类分配内存时 JVM 统一清零（第 03 节时序的第 ① 步），零成本顺手做了；局部变量在栈上复用槽位，强制清零每次方法调用都要付钱，JVM 选择把责任交给编译器检查。

存哪里：速答版与深挖版

  • 速答版：方法区（逻辑概念）——静态变量属于类信息的一部分。辨析（规范 vs 实现）："方法区"是 JVM 规范定义的逻辑区域，好比接口；HotSpot 先后用永久代（JDK 7-，堆内）→ 元空间（JDK 8+，本地内存）落实它，好比两代实现——三者不是并列的三块内存，"元空间"只是当前实现的名字。
  • 深挖版（JDK 8+ HotSpot）：永久代被移除，类元数据进元空间（本地内存）；而静态变量实际存放在堆中的 java.lang.Class 对象里（Class 对象本身就是堆里一个普通对象）。字符串常量池 JDK 7 起也移到了堆。
  • static final 编译期常量（基本类型/字符串字面量初始化）：进 class 文件的运行时常量池，访问不触发类初始化（经典陷阱，见追问节）。

static 方法"重写"其实是隐藏（hiding）

class Parent {
    static void who() { System.out.println("Parent"); }
    void hi()         { System.out.println("Parent hi"); }
}
class Child extends Parent {
    static void who() { System.out.println("Child"); }   // 隐藏，不是重写！
    @Override void hi() { System.out.println("Child hi"); }
}

Parent p = new Child();
p.who();   // Parent  ← static 按编译期类型静态绑定
p.hi();    // Child   ← 实例方法运行期动态绑定（多态）

答题口径："static 方法可以被继承、可以被同名同签名地再声明，但那是隐藏不是重写——它不参与多态，调用由编译期类型决定；同理字段也没有多态。"能把 hiding 和 override 区分清楚，这道题就赢了。

05final 的三种语义

修饰对象语义典型例子 / 目的
final class不能被继承String、Integer：实现安全（不可变类的封闭）、防子类破坏约定
final method不能被子类重写（可重载）模板方法里锁死的不变骨架；JIT 内联更友好
final 变量只能赋值一次（常量/只读引用）常量、不可变引用、Lambda 捕获前提

final 变量的三层细节

  • 基本类型：值不可变。引用类型：引用不可变，对象本身可变——final List<String> list 不能再指向别的 List，但照样能 add()。final ≠ 不可变，完整不可变见 第 05 章。
  • 空白 final（blank final）：声明时不赋值，构造器每条路径必须赋一次——适合"每个实例一个定值"的场景（天然线程安全：构造器写 final 字段有禁止重排序的语义保证，JMM final 字段规则）。
  • static final 编译期常量：编译期直接宏替换（常量折叠）进调用方字节码——改了这个常量只重编译定义类不重编译使用方，运行期还是旧值，跨模块发布的经典生产事故。
  • 等效 final（effectively final）：JDK 8 起 Lambda / 匿名类捕获的局部变量只要求"从未重新赋值"，不必显式写 final。
final List<String> names = new ArrayList<>();
names.add("alan");        // ✅ 合法：改的是对象内容
// names = new ArrayList<>();  // ❌ 编译错误：引用不可再指向别处

06类初始化顺序 ⭐⭐（必考）

骨架一句话：静态先于实例、父类先于子类、字段/块按文本顺序、构造器体最后。静态部分只在类初始化时执行一次，实例部分每 new 一次执行一轮。

完整可运行验证代码

class Parent {
    static String ps = log("1. 父类静态字段");
    static { System.out.println("2. 父类静态代码块"); }
    String pf = log("5. 父类实例字段");
    { System.out.println("6. 父类实例代码块"); }
    Parent() { System.out.println("7. 父类构造器体"); }
    static String log(String m) { System.out.println(m); return m; }
}

public class Child extends Parent {
    static String cs = log("3. 子类静态字段");
    static { System.out.println("4. 子类静态代码块"); }
    String cf = log("8. 子类实例字段");
    { System.out.println("9. 子类实例代码块"); }
    Child() { System.out.println("10. 子类构造器体"); }

    public static void main(String[] args) {
        System.out.println("--- 第一次 new ---");
        new Child();
        System.out.println("--- 第二次 new ---");
        new Child();
    }
}

输出（背下来）

1. 父类静态字段      ┐
2. 父类静态代码块    │ 类初始化 <clinit>：只在首次主动使用时执行一次
3. 子类静态字段      │ 父类先行，再子类
4. 子类静态代码块    ┘
--- 第一次 new ---
5. 父类实例字段      ┐
6. 父类实例代码块    │ 实例初始化 <init>：每 new 一轮
7. 父类构造器体      │ 字段与实例块按【文本顺序】内联进构造器
8. 子类实例字段      │ （位于 super() 之后、构造器体之前）
9. 子类实例代码块    │
10. 子类构造器体     ┘
--- 第二次 new ---
5. 父类实例字段 … 10. 子类构造器体        ← 静态部分不再执行

字节码视角：两个魔法方法

  • <clinit>()：javac 把所有静态字段初始化 + 静态块按文本顺序拼成的一个方法，在类加载的初始化阶段由 JVM 调用，且 JVM 保证加锁执行、只执行一次——这就是静态内部类单例线程安全的根源。
  • <init>()：每个构造器对应一个；实例字段初始化和实例块的代码被复制内联到每个构造器的 super() 调用之后。所以"实例块在所有构造器前执行"更精确的说法是"实例块被织入每个构造器"。

答题口径：先背顺序（父静态 → 子静态 → 父实例+构造 → 子实例+构造），再补一句"静态块对应 <clinit>，类加载初始化阶段只跑一次且加锁；实例字段和实例块会被编译器织进每个构造器，位于 super() 之后"。能说到 <clinit>/<init> 基本就是这题的满分线，类加载七阶段细节链到 03-jvm。

什么会触发类初始化（主动使用）

  • new 实例、读写非编译期常量的静态字段、调用静态方法、反射（Class.forName）、初始化子类连带父类、启动类（main 所在类）。
  • 不触发：访问 static final 编译期常量（常量池宏替换）；通过子类名访问父类定义的静态字段（只初始化父类，见追问节）；定义类数组。

07初始化块：静态块与实例块

静态初始化块实例初始化块
执行时机类初始化，仅一次每次 new，随构造器执行
能访问仅静态成员静态 + 实例成员（含 this）
多个块按文本顺序按文本顺序
典型用途加载配置/驱动、初始化复杂静态表多构造器公共逻辑去重、匿名类"构造逻辑"

实例块的独门用途：给匿名类"装构造器"

// 匿名类没有构造器（没有类名就没法写构造方法），实例块就是它的"构造器"：
Runnable task = new Runnable() {
    private final long start;          // 匿名类的字段
    {                                   // 实例初始化块 = 它唯一的"构造逻辑"
        start = System.currentTimeMillis();
        System.out.println("task created at " + start);
    }
    @Override public void run() {
        System.out.println("elapsed: " + (System.currentTimeMillis() - start));
    }
};
  • 普通类里实例块的价值：多个重载构造器的公共初始化逻辑只写一遍（JDK 8 前没有"构造器委托到 this()"习惯时的主流写法，现在多推荐 this() 链）。
  • 静态块经典场景：Class.forName 注册 JDBC 驱动的旧代码、单例的饿汉变体、构建静态查表（如敏感词 DFA）。

陷阱：静态块只能保证顺序，不能保证"别的类已就绪"——静态块里如果依赖另一个类的静态状态，而对方又依赖你（循环初始化），可能读到 null/0。另外静态块抛异常会导致 ExceptionInInitializerError，类直接不可用，后续访问全部 NoClassDefFoundError——排查时别被第二现场的错误骗了。

08内部类四种形态

种类声明位置持外部引用编译产物典型场景
静态嵌套类
static class		成员位置（static）否Outer$InnerHashMap.Node、Builder、Holder 单例
成员内部类成员位置是（Outer.this）Outer$Inner集合与它的 Iterator、事件源与适配器
局部内部类方法体内是（若在实例方法中）Outer$1Inner方法内一次性辅助类（少见）
匿名内部类表达式位置是Outer$1（编号）回调、Comparator、JDK 8 前监听器

为什么 HashMap.Node 是 static 的（高频追问）

  • 嵌套类如果不加 static，每个实例都会隐式持有外部类实例的引用（this$0）——纯粹为了"存数据"的 Node 根本不需要访问 HashMap 的实例成员，白白拖着宿主对象，妨碍 GC（外部大对象本可回收却被 Node 引着）。
  • 规则：不需要访问外部实例成员的嵌套类，一律加 static（Effective Java Item 24）。这也是"内存泄漏排查"场景的高频考点。

成员内部类怎么读外部 private 字段（加分点）

  • 早期实现：编译器合成 this$0 字段 + 静态 access$xxx 桥接方法"绕过"private。
  • JDK 11 起 nestmates（JEP 181）：同一嵌套结构算一个"巢"，JVM 层面直接允许互访私有成员，不再生成合成方法——反射 getDeclaredMethods 结果因此变干净。

静态内部类单例（Holder 模式）

public class Singleton {
    private Singleton() {}
    private static class Holder {                       // 外部类加载时不加载 Holder
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
  • 线程安全：靠 <clinit> 的加锁 + 只执行一次（JVM 保证，不加 synchronized）。
  • 懒加载：只有首次调 getInstance() 触发 Holder 类初始化才 new——比饿汉懒、比双重检查锁简洁，标准答案之一。

09匿名内部类：Lambda 的前身

语法与三个限制

// 形式：new 父类构造器(实参) { 类体 }  /  new 接口() { 实现体 }
List<String> list = new ArrayList<>();
list.sort(new Comparator<String>() {          // 匿名实现 Comparator
    @Override
    public int compare(String a, String b) {
        return b.length() - a.length();       // 按长度降序
    }
});

// JDK 8+ 等价 Lambda（语法糖层面之外的差异见下表）：
list.sort((a, b) -> b.length() - a.length());
  • 没有名字（编译产物是 Outer$1.class），没有构造器（用实例初始化块模拟），只能继承一个父类或实现一个接口。
  • 匿名类里的 this 指向匿名类实例自己；外部实例要 Outer.this。
  • 捕获的局部变量必须 final / effectively final。

为什么捕获的局部变量必须 effectively final ⭐

int counter = 0;
Runnable task = () -> System.out.println(counter);  // ✅ 读，合法
// counter++;  // 若放开：Local variable counter defined in an enclosing scope must be final

int[] box = {0};
Runnable incr = () -> box[0]++;   // ✅ "曲线救国"——数组引用没变，改的是数组内容
  • 根因是生命周期错位：局部变量活在栈帧，方法一返回栈帧就弹出；而 Lambda/匿名类对象可能活得比方法久（被缓存、提交到线程池）。所以编译器捕获的不是变量而是值拷贝——把值复制进 Lambda 对象的合成字段（匿名类里能看到 val$counter）。
  • 既然是拷贝，原变量再改也同步不到副本里——两个"变量"从此是两份独立数据。Java 干脆禁止捕获后再赋值，避免"看起来是一个变量、实际各改各的"的认知陷阱（语言设计的诚实原则：做不到共享，就别假装共享）。
  • 对比：成员变量/静态变量不需要 final——它们在堆里，Lambda 捕获的是引用，改的是同一份。
  • int[] box 是常见的绕过写法，但并发下非原子（box[0]++ 丢更新）；真要跨线程计数用 AtomicInteger——链 02-concurrency 无锁编程。

答题口径："局部变量在栈上会随方法结束销毁，Lambda 可能活得更久，所以捕获的是值拷贝；拷贝后两边独立，Java 禁止捕获后再修改以免误导；成员变量不拷贝引用，故无需 final。"——四个要点按顺序说完整就是满分。

匿名类 vs Lambda（不是简单语法糖）

维度匿名内部类Lambda
编译产物独立 class 文件不生成类，编译为 invokedynamic 指令
运行机制普通对象创建首次调用时 LambdaMetafactory 动态生成/映射实现类
this 语义匿名类实例外部实例（词法 this）
变量遮蔽可定义与外部同名的成员变量（遮蔽）不能遮蔽外部局部变量
适用范围任意接口/抽象类（可加状态字段）仅函数式接口（无状态）

答题口径：匿名类是"声明同时实例化"的一次性类，Lambda 出现前的回调全靠它；两者最本质的差异是实现机制（独立 class vs invokedynamic）和 this 指向。深入展开在 第 10 章 Lambda 与 Stream。

泄漏陷阱：匿名类持外部引用——Android 里 Handler/Runnable 匿名类拖住 Activity；服务端里注册到全局事件总线的匿名监听器忘记反注册，拖住整个大对象图。排查手段：heap dump 看 this$0 引用链。

10高频追问与陷阱

  • 追问链：初始化顺序 → 局部变量放块里行吗？→ 不能，静态块/实例块都在类/实例层面，方法内声明的"块"只有 {} 普通代码块（属于方法作用域，按位置顺序执行，不参与初始化语义）。
  • 追问链：通过子类名访问父类静态字段，子类会初始化吗？→ 不会。Child.PS（PS 声明在 Parent）编译期直接优化为 Parent.PS，只触发 Parent 的 <clinit>——和"3. 子类静态字段"输出对不上的经典题眼。
  • 追问链：静态块加锁 → 那多线程同时第一次用这个类会怎样？→ 一个线程执行 <clinit>，其余阻塞等待；这也是"静态块死锁"的来源（两个类互相依赖、两个线程各自持有一个类的初始化锁）。
  • 追问链：构造器是创建对象的那一步吗→ 不是，先分配后装修：内存分配与字段默认值先于 <init>（第 03 节时序图）；那多线程同时 new 会怎样 → TLAB 各自分配，天生安全；什么时候才真出事 → this 逸出，或"全局只许 new 一次"的单例首次并发。
  • 陷阱：final 字段在构造器里"被重写方法"读到 null→ 父类构造器调用被子类重写的方法，此时子类 final 字段尚未赋值——完整反例在第 03 章构造器链一节。
  • 陷阱：static final 引用对象 ≠ 编译期常量→ 只有基本类型和 String 字面量才会宏替换；static final List 的访问仍会触发类初始化。
  • 陷阱：接口里也可以有初始化…吗→ 接口不能有初始化块和构造器，但接口的初始化（<clinit>）会初始化其中的字段常量；初始化实现类不会触发初始化其接口（初始化接口的只有访问其字段等少数路径）。
  • 追问：内部类的 class 文件名？反射能拿到匿名类名字吗？→ Outer$Inner / Outer$1；匿名类 getClass().getName() 形如 Outer$1，日志里见到别慌。
