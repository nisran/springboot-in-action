02内置注解与元注解 ⭐

常用内置注解

注解作用保留策略
@Override编译期检查覆写签名是否正确（父类/接口确有该方法）SOURCE
@Deprecated标记过时，调用处编译警告RUNTIME
@SuppressWarnings压制指定类型警告（unchecked、rawtypes…）SOURCE
@FunctionalInterface编译期校验"有且只有一个抽象方法"RUNTIME
@SafeVarargs声明泛型可变参数不做堆污染检查（只能用于 final/static/private 方法）RUNTIME

元注解（用来注解"注解"的注解）

元注解控制什么常用取值
@Target注解能贴在哪些位置TYPE / METHOD / FIELD / PARAMETER / CONSTRUCTOR / ANNOTATION_TYPE …
@Retention注解保留到哪个阶段（核心）SOURCE / CLASS / RUNTIME
@Documented是否进入 javadoc—
@Inherited子类是否可继承父类的注解（只对类有效，方法/字段不继承）—
@Repeatable同一位置可重复标注（JDK 8+，配合容器注解）—

保留策略三档（高频）

策略保留到哪能否反射读取典型代表
SOURCE只存在于源码，编译后丢弃否@Override、@SuppressWarnings；Lombok（编译期注解处理器改 AST 生成代码）
CLASS（默认值）编进 class 文件，运行时 JVM 不加载否字节码增强工具（如一些 APT/字节码分析框架）
RUNTIME运行时可通过反射读取是Spring 全家桶：@Component/@Autowired/@Transactional；MyBatis @Select；JUnit @Test

答题口径："自定义注解要被运行时读到必须 @Retention(RUNTIME)，否则反射拿不到——这是新手写注解框架最常见的第一坑。Lombok 是 SOURCE 级，编译期改字节码所以没有反射开销。"一句话区分"编译期注解处理"和"运行时反射处理"两条技术路线，就是加分点。

注解本质：编译后注解是继承了 java.lang.annotation.Annotation 接口的特殊接口，注解成员是接口方法，取值存在编译期生成的常量池/运行时结构里——所以"注解不继承类、不能有未加 default 的成员缺省"。

03自定义注解

@Target(ElementType.METHOD)                 // 只能贴方法
@Retention(RetentionPolicy.RUNTIME)        // 运行时可通过反射读取
public @interface Log {
    String value() default "";             // 成员：以"无参方法"形式声明
    boolean required() default true;       // 必须给默认值或使用时必须显式赋值
}

// 使用：value 可省略名字直接写
@Log("查询用户")
public User findUser(Long id) { ... }

// 反射读取：
Method m = clazz.getMethod("findUser", Long.class);
if (m.isAnnotationPresent(Log.class)) {
    Log log = m.getAnnotation(Log.class);
    System.out.println(log.value());       // 查询用户
}
  • 成员类型限制：基本类型、String、Class、枚举、注解、以及它们的一维数组——不能是 Integer 包装类以外的对象、不能是二维数组。
  • 成员名叫 value 时使用处可省略 value=；只有一个成员时强烈建议就叫 value。
  • 注解不能显式继承（没有 extends）；注解本身只是"贴标签"，所有行为都由处理方（反射处理器 / 编译器插件）赋予——这句是"注解是元数据而非逻辑"的正确理解。

04反射 API 全景

反射：运行时动态获取类信息、操作类成员（字段/方法/构造器）的能力（笔记定义）。入口都是 java.lang.Class 对象——每个已加载的类在方法区/元空间有且只有一份 Class。

获取 Class 的三种方式（+ 初始化差异，笔记要点补深）

Class<?> clazz1 = Class.forName("com.example.Person");  // 全限定名，会触发类初始化（静态块执行）
Class<?> clazz2 = Person.class;                       // 类字面量，加载但不初始化
Class<?> clazz3 = personInstance.getClass();          // 运行时对象的实际类型（多态下是子类）
// 第 4 种：ClassLoader.loadClass("com.example.Person") —— 也不初始化，可控制加载器
方式触发类加载触发初始化（static 块）场景
Class.forName是是按名字动态加载（JDBC 老式 Class.forName 加载驱动）
X.class / loadClass是否只要类型信息、不想执行静态代码
obj.getClass()（类已加载）否拿到运行时真实类型

操作字段 / 方法 / 构造器

Class<?> clazz = Person.class;

// 创建实例（JDK 9+ 推荐；clazz.newInstance() 已废弃——绕不过检查异常）
Object obj = clazz.getDeclaredConstructor().newInstance();

// 字段
Field field = clazz.getDeclaredField("name");  // getDeclaredXxx：含 private，不含继承
field.setAccessible(true);                     // 突破 private 限制（见第 06 节）
field.set(obj, "张三");
// getField/getMethod：只返回 public，含继承自父类/接口的

// 方法
Method method = clazz.getMethod("getName");    // 公有方法
Object result = method.invoke(obj);            // 反射调用
// 私有方法：getDeclaredMethod + setAccessible(true)

// 元数据（笔记要点）：注解、泛型、接口、父类
clazz.getAnnotation(MyAnno.class);
clazz.getGenericSuperclass();                  // 泛型父类（TypeToken/超类型 token 靠它）
clazz.getInterfaces();
clazz.getSuperclass();
API 家族getXxx（public + 继承）getDeclaredXxx（本类全部 + private）
字段getField(s)getDeclaredField(s)
方法getMethod(s)getDeclaredMethod(s)
构造器getConstructor(s)getDeclaredConstructor(s)

为什么框架离不开它（笔记场景清单）

  • Spring：DI 依赖注入——反射创建对象并注入依赖；AOP——反射生成代理对象，在目标方法前后插入切面逻辑（日志、事务）；注解驱动——@Component 自动扫描、@RequestMapping 路由注册。
  • ORM（MyBatis/Hibernate）：查询结果集按属性名反射赋值到实体；@Select/@Table 注解映射。
  • JUnit：扫描 @Test 方法反射调用；序列化框架：反射读写字段。
  • 优点：灵活、动态、通用性强（一份代码处理所有类）；缺点：性能开销、破坏封装、绕过编译期检查（错误推迟到运行时）、代码可读性差。

05反射的性能与开销 ⭐

为什么慢（四个原因）

  1. 方法查找：getMethod 要按名字遍历方法数组做字符串匹配，还要检查访问权限（每次 invoke 都过 AccessibleObject 的安全检查）。
  2. 装箱与数组分配：参数打包成 Object[]（可变参数数组每次分配），基本类型来回装箱拆箱。
  3. JIT 难以优化：调用目标运行时才确定，JIT 无法像普通虚调用那样内联（inline）、无法做激进的去虚化/逃逸分析优化——这是差距的根本来源。
  4. 无法利用编译期绑定：普通调用在编译期就完成了符号解析与静态绑定检查，反射全部推迟到运行时。

缓解手段（框架都在做）

  • 缓存元数据：Method/Field 对象查一次存 Map（Spring 的 ReflectionUtils、BeanUtils 内部都有缓存）；JDK 自己也会缓存 root Copy。
  • 提前 setAccessible(true)：跳过每次 invoke 的访问安全检查。
  • MethodHandles（JDK 7+）：更接近字节码 invokedynamic 语义的方法句柄，JIT 友好，配合 LambdaMetafactory 甚至能把反射调用变成像 Lambda 一样的直接调用——"把反射转成 Lambda"是现代框架的高阶优化。

量级口径：冷调用（未 JIT 优化）反射比直接调用慢 10~100 倍；热点调用经 JIT 优化后差距收窄到约 2~3 倍。回答时给"冷热两档 + 原因是 JIT 无法内联"比背一个固定数字可信得多。

06setAccessible 与模块封装 ⭐

  • 作用：AccessibleObject.setAccessible(true) 让反射绕过 Java 语言访问检查，直接读写 private 成员/调私有方法（笔记：突破 private 限制）。它只跳过"语言级检查"，不改变成员本身的访问属性。
  • 代价：破坏封装（绕过类设计者的约束）、可能破坏不可变对象（改 String.value 这类 hack）、与 SecurityManager 安全策略冲突。
  • JDK 9 模块化的变化：模块系统对未显式 open 的包实施强封装——对这类包里的私有成员调 setAccessible(true) 会抛 InaccessibleObjectException。这就是升级 JDK 17 后 Spring/Hibernate/日志增强框架报错的原因，常见解法是启动参数逐个开洞：
--add-opens java.base/java.lang=ALL-UNNAMED
--add-opens java.base/java.util=ALL-UNNAMED
# 含义：让 java.base 模块向未命名模块（普通 classpath 应用）开放这些包的深反射

面试高频踩分点："你项目升级 JDK 17 遇到过什么坑？"标准素材就是 InaccessibleObjectException——根因是 JPMS 强封装，方案是 --add-opens 或升级框架版本（新版本改用 MethodHandles/var handles 合规访问）。能把这个经历讲完整，模块化这块就过关了。

07注解 + 反射实战：手写迷你框架 ⭐

三十行迷你 @Test Runner

// 1. 自定义注解（RUNTIME 保留 + 只贴方法）
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface MyTest { }

// 2. 运行器：扫描类里带 @MyTest 的方法，反射调用并统计结果
public class MyTestRunner {
    public static void main(String[] args) throws Exception {
        Class<?> clazz = CalculatorTest.class;
        Object instance = clazz.getDeclaredConstructor().newInstance();  // 反射建实例
        int passed = 0, failed = 0;
        for (Method m : clazz.getDeclaredMethods()) {                    // 遍历方法
            if (m.isAnnotationPresent(MyTest.class)) {                   // 找注解
                try {
                    m.invoke(instance);                                  // 反射调用
                    passed++;
                } catch (InvocationTargetException e) {
                    System.out.println("FAIL: " + m.getName()
                            + " -> " + e.getCause());                    // 真实异常在 cause 里
                    failed++;
                }
            }
        }
        System.out.println("passed=" + passed + ", failed=" + failed);
    }
}
// 这就是 JUnit 的雏形：注解打标 → 反射扫描 → invoke 执行 → 异常断言结果

简化版 @Autowired（迷你依赖注入思路）

@Target(ElementType.FIELD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Inject { }

public class MiniContainer {
    private final Map<Class<?>, Object> beans = new HashMap<>();

    public <T> T getBean(Class<T> clazz) throws Exception {
        Object bean = beans.get(clazz);
        if (bean == null) {
            bean = clazz.getDeclaredConstructor().newInstance();     // ① 反射实例化
            beans.put(clazz, bean);
            for (Field f : clazz.getDeclaredFields()) {               // ② 扫描字段
                if (f.isAnnotationPresent(Inject.class)) {           //    找 @Inject
                    f.setAccessible(true);                            //    突破 private
                    f.set(bean, getBean(f.getType()));                // ③ 递归注入依赖
                }
            }
        }
        return (T) bean;
    }
}
// Spring 的主干就是这条链的工业化版本：
// @Component 扫描建 BeanDefinition → 反射实例化 → @Autowired 递归注入 → AOP 代理增强

面试答法：被问"手写迷你框架"时先讲三步范式（打标记 → 扫描 → 反射执行/注入），再主动指出这个玩具版的缺口：没有循环依赖处理、没有单例/原型作用域、没有按名字匹配、性能上应缓存 Field/Method——把不足讲出来比代码本身更加分。

08JDK 动态代理 vs CGLIB ⭐⭐

JDK 动态代理：运行时生成接口的实现类

（笔记要点）JDK 动态代理是 Java 提供的在运行时动态生成代理类和代理对象的技术：程序运行时，JVM 通过反射机制生成目标接口的代理实现类并代替目标类。前提：目标类必须实现接口。

  • InvocationHandler：实现此接口来增强目标类，核心方法 Object invoke(Object proxy, Method method, Object[] args)。
  • Proxy：核心工具类（方法都是静态的），核心方法 static Object newProxyInstance(ClassLoader loader, Class<?>[] interfaces, InvocationHandler h)——生成的代理类实现了目标接口，拥有目标接口的方法。
// 1. 业务接口
interface UserService {
    void addUser(String name);
}
// 2. 业务实现
class UserServiceImpl implements UserService {
    @Override
    public void addUser(String name) {
        System.out.println("添加用户: " + name);
    }
}
// 3. 用 InvocationHandler 的 invoke 来增强
class LogHandler implements InvocationHandler {
    private Object target;                          // 持有目标对象（被代理者）
    public LogHandler(Object target) {
        this.target = target;
    }
    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // 【前置增强】在调用真实方法前执行
        System.out.println("[日志] 开始执行方法: " + method.getName() + ", 参数: " + Arrays.toString(args));

        // 调用目标对象(target)的原始方法
        Object result = method.invoke(target, args);

        // 【后置增强】在调用真实方法后执行
        System.out.println("[日志] 方法执行结束: " + method.getName() + ", 结果: " + result);
        return result;
    }
}
// 4. 客户端
class Client {
    public static void main(String[] args) {
        // 创建目标对象
        UserService target = new UserServiceImpl();

        // 创建调用处理器，并传入目标对象
        InvocationHandler handler = new LogHandler(target);

        // 使用 Proxy 动态创建代理对象
        UserService proxy = (UserService) Proxy.newProxyInstance(
                target.getClass().getClassLoader(), // 1. 类加载器：与目标同加载器
                target.getClass().getInterfaces(),  // 2. 代理类要实现的接口数组
                handler                             // 3. 调用处理器：方法调用全部转发给它
        );

        // 调用代理对象的方法
        proxy.addUser("张三");
    }
}

原理：代理类长什么样

  • newProxyInstance 运行时生成形如 $Proxy0 extends Proxy implements UserService 的类：继承 Proxy 是为了拿到 InvocationHandler 字段，所以 JDK 代理只能走接口（Java 单继承的名额已被 Proxy 占用）。
  • 代理类的方法体只是把调用转发成 h.invoke(this, method, args)；你的 invoke 里再 method.invoke(target, args) 反射调真实对象——增强逻辑就插在两者之间。
  • 生成方式 JDK 8 是 sun.misc.ProxyGenerator（可用 -Dsun.misc.ProxyGenerator.saveGeneratedFiles=true 导出 class 反编译验证），JDK 17 后改为 jdk.internal.reflect；代理类有 WeakCache 缓存，同一组接口只生成一次。
  • equals/hashCode/toString 也会被拦截进 invoke——在 invoke 里对这些方法处理不当会产生诡异递归（拿 proxy 再调 equals）。

CGLIB：运行时生成子类

CGLIB（Code Generation Library）是基于 ASM 字节码生成库的代理方案：运行时动态生成目标类的子类，重写父类方法并织入增强逻辑。不需要目标类实现接口。

class UserService {                        // 没有实现任何接口
    public void addUser(String name) { System.out.println("添加用户: " + name); }
}

Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(UserService.class);           // 代理类继承目标类
enhancer.setCallback((MethodInterceptor) (obj, method, args, methodProxy) -> {
    System.out.println("[日志] 前置: " + method.getName());
    Object result = methodProxy.invokeSuper(obj, args);  // 调用父类（原始）实现
    System.out.println("[日志] 后置");
    return result;
});
UserService proxy = (UserService) enhancer.create(); // 生成并返回代理子类实例
proxy.addUser("张三");
  • 核心组件：Enhancer（生成器）+ MethodInterceptor（拦截器，intercept(Object obj, Method method, Object[] args, MethodProxy methodProxy)）。
  • 限制（笔记要点）：生成子类要调 super()，所以目标类必须有无参构造器（有参构造的类要额外配置）；final 类不能被继承、final/private/static 方法不能被覆写，代理不了。

两种代理怎么选（口径）

维度JDK 动态代理CGLIB
代理方式接口 + java.lang.reflect.Proxy继承目标类（ASM 生成子类）
前提目标类实现接口类和方法非 final，能调 super()
依赖JDK 原生第三方库（Spring 内置 repackaged 版）
性能JDK 8 起优化很好，与 CGLIB 差距很小生成慢一点、首次调用有 FastClass 机制
典型用户MyBatis Mapper、RPC 客户端 stubSpring 默认（Boot 2.x+）、无接口 Bean
  • Spring 的规则：目标实现了接口默认走 JDK 代理，没实现接口走 CGLIB；可用 proxyTargetClass=true 强制 CGLIB。Spring Boot 2.x 起默认就强制 CGLIB——避免 JDK 代理"注入类型必须是接口"导致的 NoSuchBeanDefinitionException 系列问题，统一行为。
  • 实战坑：注解打在实现类方法上时，JDK 代理拿不到（代理的是接口）；CGLIB 代理下自调用（this.method()）不走代理——@Transactional 失效的经典场景，本质是 this 不是代理对象（详见 04-spring 板块）。

答题口径："JDK 动态代理运行时生成实现接口的 $Proxy 类，方法调用统一转发给 InvocationHandler.invoke，受单继承限制只能代理接口；CGLIB 用 ASM 生成子类，MethodInterceptor.intercept 里 invokeSuper，final 类/方法不行。选型上：有接口用 JDK，没接口用 CGLIB；Spring Boot 2.x 默认统一 CGLIB 是为了避免接口注入的坑。另外自调用失效问题我是从 AOP 这条线排查过的。"

09SPI 机制：ServiceLoader 与打破双亲委派

SPI（Service Provider Interface）：接口定义在框架/规范方，实现由第三方提供，运行时按约定发现并加载——"面向接口 + 可插拔"的发现机制。与 API 的区别：API 是"实现方提供接口给你调"，SPI 是"你定义接口，实现方来填"（如 JDBC：java.sql 是 JDK 的，Driver 实现是 MySQL/Oracle 各自的）。

使用三步

// 1. 定义接口
public interface PayService { void pay(String order); }

// 2. 实现方在自己的 jar 里建文件：META-INF/services/com.example.PayService
//    文件内容是实现类的全限定名（一行一个）：
//    com.alipay.AlipayPayService

// 3. 使用方统一发现，不依赖任何具体实现
ServiceLoader<PayService> loaders = ServiceLoader.load(PayService.class);
for (PayService pay : loaders) {       // 懒加载：迭代到才实例化
    pay.pay("order-123");
}
  • 实现类必须有无参公共构造器（ServiceLoader 反射实例化）；找不到实现、类不在 classpath 只在迭代时抛 ServiceConfigurationError。
  • JDK 内置 SPI 到处都是：JDBC（java.sql.Driver）、字符集 Charset、DateFormatProvider、spring 的 spring.factories / AutoConfiguration.imports（Spring Boot 自动装配是 SPI 思想的加强版，允许按 key 取多个实现 + 条件装配）。

为什么说 SPI 打破了双亲委派 ⭐

  • 矛盾：ServiceLoader / DriverManager 在 java.base 里，由启动类加载器（Bootstrap）加载；而第三方实现 jar 在应用 classpath，按双亲委派，Bootstrap 加载器是"看不见"应用类的（它只认 JDK 核心）。
  • 解法：线程上下文类加载器（TCCL, Thread Context Class Loader）——ServiceLoader.load() 默认用 Thread.currentThread().getContextClassLoader()（应用类加载器）去加载实现类，相当于父层加载器"借"子层加载器干活，在加载这一环上打破了双亲委派的单向性。
  • 类加载器层次与双亲委派的完整分析（含 JDBC DriverManager 源码链路）见 03-jvm 板块。
  • 缺点与演进：ServiceLoader 全量串行、无依赖注入、无法按条件选择实现——这正是 Spring 的 spring.factories、Dubbo 自研 SPI（按 key + 自适应扩展）要解决的问题。

10高频追问与陷阱

  • 追问链：注解怎么生效 → 编译期和运行时两条路→ SOURCE 级走 APT/编译器插件（Lombok 改 AST）；RUNTIME 级靠反射读取。回答任何"注解框架原理"先分这两条路。
  • 追问链：动态代理 → Spring AOP 和它什么关系→ Spring AOP 底层就是这两种动态代理的封装（JdkDynamicAopProxy / CglibAopProxy），AspectJ 是编译/类加载期织入，功能更强（能织入字段/构造器）。
  • 追问链：代理对象的 Class 名字 → 怎么看到生成的类→ JDK 代理 $Proxy0（-Dsun.misc.ProxyGenerator.saveGeneratedFiles=true 导出）、CGLIB（DebuggingClassWriter 指定输出目录）——能说出"我反编译看过"非常加分。
  • 陷阱：method.invoke 的异常被包了一层：真实业务异常在 InvocationTargetException.getCause() 里，直接 catch Exception 打印会看不到真实堆栈。
  • 陷阱：反射拿不到注解，先查 @Retention：默认 CLASS 级，反射不可见，必须显式 RUNTIME。
  • 陷阱：CGLIB 代理 final 方法静默失效：不报错，直接走父类原方法，增强没生效——排查 AOP 失效时记得查 final。
  • 陷阱：ServiceLoader 迭代完不换线程复用：ServiceLoader 非线程安全，多线程下各自 load 新实例。
  • 场景题口径："设计一个通用的接口耗时日志组件"——答：RUNTIME 注解打标 + 动态代理增强 + InvocationHandler 里计时与上报，再补一句"Spring 里我会直接用 AOP + 自定义切点"，展示从手写轮子到工程化选择的层次感。
