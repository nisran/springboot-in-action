02封装与四种访问修饰符

封装 = 把数据与操作绑定在类里，隐藏内部表示，只暴露最小接口。它买到的三样东西：① 不变式（invariant）只在一处维护——外部拿不到内部字段就破坏不了约束（金额非负、状态机合法流转）；② 内部实现可自由重构，调用方无感；③ 误用面缩小——构造器校验过的对象，后续状态不会被随手改坏。

修饰符本类同包其他包的子类其他包非子类典型用途
private✓✗✗✗内部字段与实现细节（默认选择）
default（不写）✓✓✗✗包内协作 API（"朋友圈"可见）
protected✓✓✓✗专门留给子类的扩展点（模板方法）
public✓✓✓✓对外契约，越少越好

三个常被追问的细节

  • 顶层类只有两档：public 或 default；private / protected 只有成员（嵌套类、字段、方法）能用。一个 .java 文件最多一个 public 顶层类，且必须与文件名同名。
  • protected 隐含包访问：它覆盖了 default 的全部范围，再叠加"其他包子类"。很多人只知道"子类可见"，漏了"同包非子类也可见"——表格题就埋在这里。
  • 跨包子类访问 protected 的姿势限制：在子类代码里，只能通过子类自身（及其更下层子类）的引用访问继承来的 protected 成员；不能拿父类引用或"别的子类实例"去访问（JLS 6.6.2）。
  • 局部变量不能加访问修饰符——它的作用域天然限于方法块内。

包私有在工业界的真实用法（一行代码讲出场景感）

  • JDK 大量用包私有控制内部 API：java.lang 里 AbstractStringBuilder 是包私有——StringBuilder/StringBuffer 共享它的实现，但不对外暴露；Integer.IntegerCache 同样是包私有静态类。
  • Spring 源码模式：org.springframework.beans.factory.support（实现层）与 org.springframework.beans.factory.config（API 层）分包，default 权限的实现类外部根本 import 不到——包就是它的"模块边界"（无 JPMS 时代的土法模块化）。
  • 实战建议：一个功能的"内部协作类"收进子包用 default 权限，public 只留给真正对外的门面接口——比"全部 public 再靠文档提醒"可靠得多。

答题口径：先甩范围表（四个修饰符按可见性递增排一遍），主动补"protected 含包访问"和"顶层类只有两档"两个细节，最后加一句——封装的粒度不只是类：包（default 权限的生效边界）和模块是更大尺度的封装，一句话把话题引到 06 章，显示知识是成体系的。

03手写不可变类：五条规则 ⭐⭐

这是本章的白板必考题。先给能背的口诀，再给标准代码：

① 类 final · ② 字段 final · ③ 不提供 setter · ④ 构造器对可变入参防御性拷贝 · ⑤ getter 对可变字段返回副本

public final class Card {                              // ① 类 final：杜绝子类覆盖方法破坏规则
    private final String cardNo;                        // ② 字段 private final
    private final int[] pins;                           //    可变类型是防御性拷贝的主战场
    private final Date issuedAt;

    public Card(String cardNo, int[] pins, Date issuedAt) {
        this.cardNo = cardNo;                           // String 不可变，直接存
        this.pins = pins.clone();                       // ④ 构造器：可变入参先拷贝再入字段
        this.issuedAt = new Date(issuedAt.getTime());   //    Date 可变，同样拷贝
    }

    // ③ 不提供任何 setter / 修改状态的方法

    public String getCardNo() { return cardNo; }        // 不可变字段可直接返回

    public int[] getPins() {                            // ⑤ getter：可变字段返回副本
        return pins.clone();
    }

    public Date getIssuedAt() {
        return new Date(issuedAt.getTime());
    }
}

逐条说"为什么"（面试官会抠这里）

  • ① 类为什么要 final：不可变是靠"纪律"维持的约定，不是 JVM 强制的。只要允许继承，子类就能覆盖 getter 把内部引用漏出去、甚至记录窃取入参。String、Integer、LocalDate 全是 final 类，不是巧合。
  • ② 字段为什么要 final：编译器保证引用不再被重新赋值；同时 final 字段在 JMM 里有特殊的内存语义（第 07 节展开），是不可变对象能免同步共享的底层依据之一。
  • ③④⑤ 是一组：④ 保证"进来的脏数据带不进来"，⑤ 保证"干净数据漏不出去"，③ 保证中间没有任何修改通道。
  • 什么字段不用拷：String、包装类、其他不可变类的引用直接存即可——拷贝只针对可变类型（数组、Date、可变集合、StringBuilder）。

record 帮你做了一半：record（JDK 16 转正）隐式 final 类、final 字段、无 setter、无 extends——①②③ 自动满足；但官方定义它是"浅不可变"（shallowly immutable）：accessor 不做防御性拷贝。可变组件仍要自己在紧凑构造器里拷：

public record Card(String cardNo, List<String> tags) {
    public Card {                       // 紧凑构造器：补上防御性拷贝
        tags = List.copyOf(tags);       // 拷成真不可变集合 + 拒绝 null，一箭双雕
    }
}

JDK 里的现成样板（答题时点名）

String、Integer 等包装类、BigDecimal、LocalDate / LocalDateTime（新日期时间 API 全面不可变，就是用来替代可变的 Date）、Optional、List.of(...) 的产物。

04String 为什么天然满足

第 01 章从"常量池 / 线程安全 / hash 缓存 / 安全"四个角度讲了 String 为什么要不可变；这里反过来，用五条规则核验它 怎么做到的：

public final class String {          // ① final 类：String、JDK 里所有不可变类都是 final
    private final byte[] value;       // ② private final 字段（JDK 9+ byte[] + coder，为什么见下方 JEP 254 小节；JDK 8 是 char[]）
    private int hash;                 //    hash 缓存：内容永不变，所以敢缓存一次终身使用
    // ③ 无任何 setter
    // ④⑤ substring / replace / concat / trim 全部返回新对象，value 数组引用从不外泄
}
  • 注意一个微妙点：value 本身是可变的数组，但 String 从不把它的引用交给任何人——所有读取都靠内部遍历/复制完成。"字段是可变类型"不致命，"引用泄漏"才致命，这是手写不可变类时最容易被追问的一句话。
  • 想改 String 只能生成新对象；反射暴力改 value 在 JDK 12+ 已被模块系统彻底封锁（01 章追问链讲过）。

底层存储：JDK 9 为什么把 char[] 改成 byte[]（JEP 254）

JDK 9 之前 value 是 char[]，而 char 是 UTF-16 代码单元、固定 2 字节。各类堆 dump 统计里 String 常占堆的 1/4 ~ 1/2，其中绝大多数只含 Latin-1 字符（ASCII / 西文——JSON key、URL、英文日志），1 字节就够却被迫占 2 字节，一半内存白白浪费。JDK 9（JEP 254 Compact Strings）改为整串二选一的自适应存储：

private final byte[] value;   // 真正存字符
private final byte coder;     // 整串一个标记：0 = LATIN1（1 字节/字符），1 = UTF16（2 字节/代码单元）

"abc"   → coder = LATIN1，value = [61 62 63]                 // 3 字节，省一半
"abc们" → coder = UTF16， value = [00 61 00 62 00 63 4E EC]   // 8 字节：a/b/c 也被撑到 2 字节
"😀"    → coder = UTF16， value = [D8 3D DE 00]               // 4 字节 = 一对代理项（2 个代码单元）
  • coder 是整串级别、一票否决制：构造时扫一遍，任何一个字符 > 0xFF，整串放弃压缩、按 UTF-16 存——不存在"a 用 1 字节、们 用 2 字节"的逐字符混合编码。"abc们" 理想 5 字节实际 8 字节，这 3 字节浪费是被主动接受的（统计上真正的混合串占比很小）。
  • 为什么不逐字符变长（比如干脆用 UTF-8）：charAt(i) 必须保持 O(1)——地址 = 基址 + i × unitSize，unitSize 必须是整串常量；变长编码会让随机访问退化成 O(n)，而 String 的 length / hashCode / indexOf 全建立在常数时间随机访问上。这也是 JEP 254 拒绝 UTF-8 方案的同一理由。
  • 没有"3 字节"形态：UTF-16 每个代码单元固定 2 字节；增补字符（emoji、𠮷）= 代理对 = 两个代码单元 = 4 字节，所以 "😀".length() == 2，codePointCount() 才返回真实字符数。"汉字 UTF-8 占 3 字节"是 getBytes() 序列化时的概念，与堆内存储是两码事。

收益与代价：主收益是内存——Latin-1 串直接减半，堆压力与 GC 频率下降、CPU 缓存局部性变好，性能是间接受益；StringBuilder / StringBuffer 同步做了相同改造。代价：纯中文串毫无收益、还多一次构造探测；Latin-1 与 UTF-16 串拼接要 inflate（膨胀拷贝）；可用 -XX:-CompactStrings 关闭（实践中几乎不用）。验证手段：javap -p java.lang.String 看 byte[] value 字段，或用 JOL 对比对象大小。

05不可变的层次：浅 vs 深 ⭐

"不可变"不是一个开关，是一条光谱。面试官问"字段全 final 就不可变了吗"，考的就是下面这张表：

层次含义线程安全？例子
浅不可变
shallowly immutable		对象自身字段引用不可变（final），但字段指向的对象可能可变不保证record、final List<可变对象> 字段
深不可变
deeply immutable		整棵对象图封闭在不可变类型中（基本类型 + String + 其他深不可变对象）天然线程安全String、Integer、LocalDate、装着不可变元素的 List.of
final class Team {                                            // 类 final、字段 final，看着很"不可变"
    private final List<Member> members;
    Team(List<Member> members) { this.members = members; }     // ❌ 连浅拷贝都没有
    List<Member> getMembers() { return members; }              // ❌ 引用直接外泄
}

// 外部一改，Team 的"不可变"瞬间破防：
team.getMembers().add(new Member("混进来的人"));    // 集合本身可变：结构被改
team.getMembers().get(0).rename("改名");            // 元素可变：即使集合只读，状态照样变

只读 ≠ 不可变：unmodifiableList vs List.of

Collections.unmodifiableList(list)List.of(...) / List.copyOf(list)
本质包装原集合的只读视图（JDK 9+ 会在能确认时返回原不可变集合）拷贝出的真不可变集合
原集合变化视图跟着变不受影响
修改操作抛 UnsupportedOperationException抛 UnsupportedOperationException
null 元素取决于底层集合直接拒绝（NPE）
距离"深不可变"还差两层：底层会变、元素会变还差一层：元素本身也得不可变

答题口径：unmodifiable 的语义是"别人不能通过我这个引用改"，List.of 的语义是"这个集合真的不会变"。要变成深不可变还差最后一步：容器装的元素本身也不可变。三连问（unmodifiable / List.of / Arrays.asList）几乎必出，差异要能张口就来。

06防御性拷贝 ⭐

定义：在信任边界上（构造入参、getter 返回、反序列化、跨线程/跨服务传递）用"复制数据"代替"共享引用"。它是五条规则里 ④⑤ 的正式名字，也是封装的最后一道防线。先看破防现场：

// ❌ 反例：以为 private final 就安全了
public final class Schedule {
    private final Date start;
    public Schedule(Date start) { this.start = start; }      // 存的是调用方的引用
    public Date getStart() { return start; }                  // 又把同一个引用交了出去
}

Date d = new Date();
Schedule s = new Schedule(d);
d.setTime(0);                    // 事后改 d —— s 内部状态被穿透
s.getStart().setTime(0);         // getter 泄漏的引用也能改 —— 双向裸奔

// ✅ 修复：进拷一次、出拷一次
public Schedule(Date start) { this.start = new Date(start.getTime()); }
public Date getStart() { return new Date(start.getTime()); }

三条实战守则（Effective Java 的沉淀）

  • 进出都拷：构造器 / setter 对可变入参拷贝一份再存；getter 对可变字段每次返回副本。不可变类里"进"只需拷一次（拷完即私有状态），"出"看成本。
  • 别用 clone() 做防御性拷贝：非 final 类的 clone() 可能被恶意子类覆盖，返回带后门的副本。用 new Date(d.getTime())、Arrays.copyOf、List.copyOf 这类构造式拷贝。数组用 clone() 反而是安全的（数组 clone 不走用户代码）。
  • 拷贝要"先拷后用"（TOCTOU）：多线程下若先把入参存字段、再异步拷贝，拷贝窗口期调用方仍能改它。构造器第一步就拷贝，拷完再校验。

代价与优化：防御性拷贝每次 O(n)，大集合高频读的场景会疼。更好的姿势是构造期一次 List.copyOf 换成真不可变集合，之后 getter 直接返回它本身（它自己已经改不了），把 N 次拷贝摊销成 1 次。另注意 Arrays.asList 是数组的视图（可 set 不可 add），不是拷贝。

07不可变与线程安全 · 实战权衡

为什么"不可变对象天然线程安全"

  • 状态在构造完成后只读，没有可争用的共享可变状态——线程安全问题的根被拔掉，不需要任何锁与同步。
  • 加分层（7 年经验该说的）：JMM 对 final 字段有专门规则（JLS 17.5）——只要 this 没有在构造器中逸出，即使对象经由数据竞争（无同步）发布，其他线程看到的 final 字段也是正确构造后的值。这是不可变对象"免同步自由共享"的底层依据，普通可变字段没有这层保证。
  • 连锁红利：静态常量自由共享；HashMap 的 key 安全（key 状态不变，hash 定位永不失效）；"快照"式读取天然一致。
  • 前提是深不可变：final StringBuilder 照样被并发 append 打爆——final 锁的是引用，不是对象状态。线程安全视角的展开见 02-concurrency 板块。

实战权衡：不可变值对象 + 可变实体

完全不可变在业务系统里成本很高：每次变更都新建整条对象链（GC 压力大），有生命周期的领域实体（JPA Entity 要被框架填充/脏检查）天然不适合。工业界的常见分层：

不可变值对象可变实体
内容Money、各种 ID、DTO / VO、领域事件、配置快照聚合根、Entity（订单、用户）
生命周期创建即定型，跨线程 / 跨服务随便传单线程事务内演进，边界清晰
并发策略零同步自由共享乐观锁 / 数据库事务保护
  • 原子替换模式：用 volatile 引用指向一个不可变配置对象，切换配置时整体换新引用，而不是在旧对象里逐字段改——并发板块的经典手法（类似 CopyOnWriteArrayList 的思想）。
  • 复杂不可变对象的构造用 Builder 分步组装，最后 build() 一次性定型。

7 年经验答法：被问"你们业务里都用不可变吗"，别背教条。答分层：钱、ID、时间、事件这类事实型数据天然不可变；聚合根实体可变但边界收敛在事务内；最好带一个真实收益案例（配置快照原子切换、线程安全的本地缓存 key、事件对象跨线程无锁传递），比把五条规则再背一遍值钱得多。

08高频追问与陷阱

  • 追问链：手写不可变类 → 字段是 Date 怎么办 → 双向防御性拷贝；更漂亮的答案：换成 LocalDateTime / Instant——新日期 API 本身不可变，直接消灭拷贝问题。
  • 追问链：List.of 之后还能 add 吗 → 抛 UnsupportedOperationException；那 Arrays.asList 呢 → 可 set 不可 add（数组的视图）；和 unmodifiableList 呢 → 视图 vs 拷贝。三个连问是标准套餐。
  • 陷阱：final 引用 ≠ 不可变对象：final 只锁"引用指向"，不锁"对象内部状态"。final List 换不了列表，照样能往里 add。
  • 陷阱：getter 返回内部数组/集合 是封装最常见的漏洞，也是很多安全 CVE 的入口（内部结构泄露可被探测和篡改）。
  • 陷阱：不可变类实现 Serializable 要小心：readObject 相当于第二个构造器，可变字段必须在里面重新拷贝，否则反序列化路径绕过构造器攻破防御性拷贝。
  • 追问：record 算不可变类吗 → 算浅不可变（final 类 + final 字段 + 无 setter），在紧凑构造器里补 List.copyOf 等拷贝可以逼近深不可变。
  • 追问：不可变了还要 clone 吗 → 不需要，复制它没有意义，直接共享引用就是最优解——这也是 JDK 不可变类不实现 Cloneable 的原因。
  • 追问链：String 底层为什么是 byte[] + coder → JEP 254 省内存（大多数串只含 Latin-1）；"abc们" 混着怎么存 → 整串一票否决、全按 UTF-16；那 3、4 字节字符呢 → UTF-16 没有 3 字节形态，4 字节 = 代理对两个代码单元；为什么不用 UTF-8 → 变长破坏 charAt 的 O(1)。完整展开见第 04 节。
  • 追问：为什么密码建议用 char[] 而不是 String？→ 不可变让 String 的清除变被动：① 字面量会进常量池，生命周期无法控制；② 用完只能等 GC，堆 dump 里长期可见明文；③ toString/日志容易顺手泄漏。char[] 用完可主动 Arrays.fill(pwd, '\0') 覆写。同一个思路的延伸：敏感字段 toString 脱敏、日志脱敏（第 03 章）。
  • 追问：Cloneable 深拷贝三坑还记得吗？→ 不调 super.clone 类型错、浅拷贝共享引用数组、Cloneable 是空标记接口却改变 Object.clone 行为（接口的非常规用法）；加上"克隆不走构造器绕过不变式校验"共四坑——展开在 第 02 章对象拷贝三兄弟。

  1. 四种访问修饰符范围表能秒画，含"protected 隐含包访问"和"顶层类只有两档"两个细节。
  2. 手写不可变类五条规则能直接上白板，代码里体现双向防御性拷贝。
  3. 能说清浅不可变 vs 深不可变，并现场给出"final List 装可变元素"的破防反例。
  4. unmodifiableList / List.of / Arrays.asList 三者差异能连着讲。
  5. 知道 record 是浅不可变，会用紧凑构造器补防御性拷贝。
  6. 能讲 final 字段的 JMM 特殊语义（安全发布）与"构造期间 this 逸出"为什么破坏它。
  7. 有"不可变值对象 + 可变实体"分层的实战表达，能举一个真实收益案例。

  10. 说得出密码用 char[] 的三条理由与包私有在 JDK/Spring 里的实例。
