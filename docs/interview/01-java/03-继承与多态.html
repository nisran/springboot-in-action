02继承的本质与"组合优先"

继承是什么

  • Java 单继承（一个 extends）+ 多接口实现；所有类隐式继承 Object，形成一棵继承树。
  • 子类获得父类的字段和方法（private 字段也被继承，只是不可直接访问——要靠父类暴露的方法）；构造器不被继承。
  • 继承表达 is-a：能满足"子类是父类的一种、且能无差别替换父类"（里氏替换原则 LSP）才用继承。

为什么"组合优先于继承"（Effective Java Item 18）

继承会破坏封装：子类依赖父类的实现细节（哪些方法内部调用了哪些方法——"自用性 self-use"），父类升级一改，子类悄悄坏掉。经典反例：

// 想统计 add 被调用了几次：
public class InstrumentedHashSet<E> extends HashSet<E> {
    private int addCount = 0;

    @Override public boolean add(E e) {
        addCount++;
        return super.add(e);
    }
    @Override public boolean addAll(Collection<? extends E> c) {
        addCount += c.size();
        return super.addAll(c);        // HashSet.addAll 内部自用的是 add()
    }                                   // → c 里每个元素 addCount 被加了两遍！
}
  • 父类 addAll 的实现细节（内部循环调 add）是子类不该依赖的"实现自由度"；HashSet 一旦改为批量插入，子类直接失准。
  • 正解：组合 + 觔托（forwarding）——把 HashSet 作为字段持有，实现 Set 接口并把调用转发过去，再自由叠加计数（装饰器思路，见 07-LLD 设计模式）。
  • JDK 反面教材也能佐证：Stack extends Vector、Properties extends Hashtable——把"能力"做成了"继承"，暴露了一堆不该有的方法。

答题口径："业务代码里 90% 想写 extends 的冲动其实是'想复用实现'，此时用组合+委托；继承只在真实 is-a、且父类为继承而设计（模板方法、文档写明自用性）时使用。"这句能把话题引到你熟悉的模板方法/装饰器上，主动权在手。

03super 与构造器链

构造器链规则

  • 每个构造器要么显式调 this(...)（本类链），要么显式/隐式调 super(...)（父类链），二者必有其一且必须第一行——对象一定是从 Object 顶端一路构造下来的。
  • 不写时编译器默认插入 super()（无参）；父类只有带参构造器、子类构造器又不显式调用时，直接编译错误——日常报错高频来源。
  • super.method() / super.field：以静态方式调用父类版本（编译期定死目标，不走虚分派），可以在实现里"调一层父类"。
  • 不存在 super.super.xxx——跳级访问不合法。

经典陷阱：构造器里调用可被重写的方法 ⭐

class Parent {
    Parent() {
        overrideMe();                       // 多态！实际跑的是子类版本
    }
    void overrideMe() { }
}

class Child extends Parent {
    private final String name;
    Child() { name = "child"; }             // 父类构造器执行时，这行还没跑到
    @Override void overrideMe() {
        System.out.println(name.length()); // NPE：final 字段竟是 null
    }
}
  • 顺序是：Parent 构造器 → 其中调用的 overrideMe 动态分派到 Child 版本 → 此时 Child 的字段还没初始化（第 02 章的初始化顺序：父类构造先于子类实例字段）。
  • 同理，构造器里别启动线程、别注册监听器（this 逃逸）。
  • 规则（Effective Java Item 19）：构造器里只调 private / final / static 方法；Cloneable 和反序列化（readObject）同理。
  • 模板方法模式里故意暴露 hook() 给子类，是有意为之的例外——但必须文档化"构造期会被调用"。

04重写规则：两同两小一大

口诀规则说明 / 边界
两同方法名相同—
参数列表相同参数类型、个数、顺序一致（与参数名无关）
两小返回类型 ≤ 父类相同或是其子类型（协变返回，JDK 5+）
抛出异常 ≤ 父类checked 异常更窄或不抛；RuntimeException 不受限
一大访问权限 ≥ 父类protected 可放宽为 public，不能收紧
  • 前置条件：实例方法，且父类方法不是 static / private / final（private 天然不可见谈不上重写；static 是隐藏，见第 02 章）。
  • 参数列表不同 = 重载（overload），是另一件事：编译期静态绑定、可改变返回类型。
  • @Override 注解必须写：拼错方法名/参数时编译器当场报错，否则"以为重写了其实新增了一个方法"，bug 藏得极深。
class Parent {
    protected Number compute(int x) throws Exception { return 0; }
}
class Child extends Parent {
    @Override
    public Integer compute(int x) {          // 权限放大 ✅ 返回收窄（协变）✅ 异常更少 ✅
        return x * 2;
    }
}

重载决议三步：编译器怎么选"最具体的" ⭐

  • 阶段 ①：不用装箱和变长参数就能匹配的（int → f(int)）；阶段 ②：允许装箱/拆箱（f(Integer)）；阶段 ③：变长参数（f(int...)）。上一阶段有候选就不再看下一阶段。
  • "最具体"= 对任意调用实参组合，A 能赋给 B 的形参类型则 A 更具体——父子都匹配时选子类形参版本。
static void f(Object o) { System.out.println("Object"); }
static void f(String s) { System.out.println("String"); }
static void f(int... v) { System.out.println("varargs"); }

f("hi");     // String —— 不装箱直接匹配 String，且比 Object 更具体
f(42);       // Object —— int→String 不匹配；int→Object 不行，但 int→装箱 Integer→Object 可以（阶段②）
f((Object) null);  // Object；f(null) 则选 String（null 可赋给两者，取更具体的 String）
f();         // varargs —— 前两阶段无候选，阶段③兜底

经典生产坑：List.remove(int index) 与 remove(Object o)——List<Integer> list; list.remove(1) 删的是下标 1 不是元素 1（阶段①精确匹配 int）。要按元素删必须 remove(Integer.valueOf(1))。这是第 08 章的高频题，根因在重载决议。

易混：重载（overload）与重写（override）。重载：同类（或父子）中同名不同参，编译期按静态类型选目标；重写：父子间同签名，运行期按实际对象类型选目标。一句话——"重载看左边，重写看右边（运行时对象）"。对返回值的要求是标配追问：重载的判定与返回值无关——两个方法仅返回值不同直接编译错误（调用点 f(); 不接收返回值，编译器无法裁决）；重写的返回值必须相同或协变收窄（仅限引用类型），基本类型 / void 必须严格相同（协变与桥方法展开见第 08 节）。

05多态底层：静态绑定与动态绑定

多态三要素：继承/实现 + 重写 + 父类引用指向子类对象。运行期同一个调用，实际执行哪个方法由对象的实际类型决定。

五种调用指令（字节码视角，加分项）

指令场景绑定
invokestatic静态方法编译期静态绑定
invokespecial构造器、private 方法、super.method()编译期静态绑定
invokevirtual普通实例方法运行期虚分派（vtable）
invokeinterface接口方法运行期虚分派（itable）
invokedynamicLambda、字符串拼接（JDK 9+）运行期引导决定
  • 虚方法表（vtable）：每个类一张方法表，子类表复制父类表，重写的方法占用同一个槽位（覆盖）。invokevirtual 运行期经对象头类型指针找到实际类的 vtable，按槽位取出目标——这就是动态绑定的实现。
  • final / private / static 方法不占虚分派路径（static 用 invokestatic，private 用 invokespecial），所以"final 利于内联"的优化说法从这来。

invokevirtual 运行五步（把 vtable 讲穿）

Shape s = new Circle();
s.area();          // 字节码：invokevirtual #4  // Method Shape.area:()D

① 拿到栈顶对象引用，取对象头的类型指针（klass pointer）→ 实际类型 Circle
② 首次遇到该调用点：解析常量池 #4 → 确认方法名/描述符 area()D，缓存进内联缓存
   （没有解析记录时还要做一次"链接"：访问权限检查、惰性加载）
③ 在 Circle 的 vtable 里，沿 area()D 对应的固定槽位取方法入口
   （javac 编译子类时已保证重写方法与父类同槽位——虚方法表布局在类加载期生成）
④ 校验通过后调用；JIT 热身后若发现调用点单态（mono，只见过一种类型），
   直接内联 + 去虚化，运行期判断退化为一次类型守卫
⑤ 双态（bimorphic）也可分支内联；多态+不可预测则走真·vtable 查表
  • 这一段的价值：把"运行期按实际类型找方法"从口号落到槽位 + 类型指针 + 内联缓存三个实体上。面试官追问"虚分派到底慢在哪"时，能答到"主要是一层间接寻址 + 阻碍内联，JIT 单态去虚化后开销几乎归零"就是高级岗口径。
  • 接口方法走 itable（接口方法表），实现类更多、布局更复杂，历史口径"接口调用比类调用略慢"由此来——现代 JIT 优化后差距基本抹平，答题时别说死。

字段没有多态（必考陷阱）⭐

class P { int x = 1; int get() { return 1; } }
class C extends P { int x = 2; int get() { return 2; } }

P p = new C();
System.out.println(p.x);      // 1 —— 字段按【编译期类型】P 解析，无多态
System.out.println(p.get());  // 2 —— 方法走虚分派，按实际类型 C
((C) p).x;                    // 2 —— 强转后按 C 找字段
  • 字段访问在编译期就定死了（getfield 指令带符号引用，不做虚分派）；"同名字段遮蔽"只是两层独立存储，子类里还能用 super.x 访问父类那份。
  • 追问延伸：static 方法也按编译期类型（第 02 章的 hiding 例子），三者可以串成一个考点。

06Object 方法：equals · hashCode · toString ⭐⭐（必考）

== vs equals

==equals
基本类型比值不能用（不是对象）
引用类型比引用（同一对象？）默认等同 ==；重写后按"内容/逻辑"判等
  • Object.equals 的默认实现就是 this == obj——重写是为了给值语义（id 相同即同一用户）。
  • 包装类型/字符串一律 equals（Integer 缓存陷阱见 第 01 章）；判空安全用 Objects.equals(a, b)。

equals 五大契约 + hashCode 两大约束

  • equals：自反（x.equals(x) 真）、对称、传递、一致（多次调用结果不变）、x.equals(null) 为 false。
  • hashCode：一致性（同对象多次调用一致）；equals 相等 ⇒ hashCode 必须相等；hashCode 相等不要求 equals（哈希碰撞允许）。

核心反例：只重写 equals，HashMap 取不到值 ⭐⭐

class Key {
    final int id;
    Key(int id) { this.id = id; }

    @Override
    public boolean equals(Object o) {
        return (o instanceof Key k) && k.id == id;   // 重写了 equals
    }
    // ❌ 没重写 hashCode：用 Object 的身份哈希（近似内存地址）
}

Map<Key, String> map = new HashMap<>();
map.put(new Key(42), "payload");

map.get(new Key(42));            // null！
map.containsKey(new Key(42));    // false

为什么（HashMap 查找两步走）：

  1. 第一步 hash(key) & (n-1) 算桶下标——两个"逻辑相等"的 Key 身份 hashCode 不同 → 落在不同的桶；
  2. 第二步才在桶内链表/红黑树上用 equals 精确比对——桶都不对，equals 根本没机会执行；
  3. 于是"存进去的 Entry 永远查不到"，HashSet 的 contains 同理为 false，去重也失效。

答题口径："equals 和 hashCode 是同一逻辑身份的两种表达——equals 是完整判等，hashCode 是它的粗粒度摘要（先分桶再精查的索引结构）。HashMap/HashSet/Hashtable 及一切哈希容器都依赖'相等对象必落同桶'这一前提，只改 equals 等于把索引和内容改拧了。"能顺着讲出 HashMap 的两步查找，这题就是满分。

标准写法（7 年经验模板）

@Override
public boolean equals(Object o) {
    if (this == o) return true;                      // 快路径：同一引用
    if (!(o instanceof Order that)) return false;    // 类型检查（JDK 16 模式匹配）
    return id == that.id && Objects.equals(buyer, that.buyer);
}

@Override
public int hashCode() {
    return Objects.hash(id, buyer);     // 参与字段必须与 equals 完全一致
    // 热点路径优化：return 31 * id + Objects.hashCode(buyer);
}
  • 公式 31 * h + fieldHash：31 是奇素数——偶数乘法丢低位信息；31*i == (i << 5) - i 可被 JIT 优化成移位减法。
  • long 用 Long.hashCode(l)（异或高低 32 位），double 先 Double.doubleToLongBits；数组用 Arrays.hashCode。
  • Objects.hash(...) 内部 varargs 会建 Object[]，超热点对象（每秒百万次 equals 的缓存 key）手写三目式。

继承体系下 instanceof vs getClass 之争

  • 用 instanceof 判等 + 子类加字段：Point 与 ColorPoint，p.equals(cp) 真、cp.equals(p) 假 → 破坏对称性（Effective Java Item 10 经典推演）。
  • 三选一口径：① getClass() == o.getClass()（严格：不同类永不等，牺牲"父类引用能等于子类对象"）；② instanceof 且不再被继承（类标 final 或用组合）；③ record / Lombok 自动按全字段生成（本质是①）。
  • 实战推荐：DTO/值对象直接 record（第 04 章），equals/hashCode 全字段自动生成，天然规避此争论。

JDK 真实事故：java.sql.Timestamp extends java.util.Date——同一毫秒时刻的 date 与 ts：date.equals(ts) 为 true（Date 只比毫秒，看不到纳秒），而 ts.equals(date) 恒 false（Timestamp 的 equals 要求参数 instanceof Timestamp）——同一对对象、方向一换结果翻转，对称性破产。官方 javadoc 直言"equals 不是对称的，不建议 Timestamp 与 Date 混用"；一个 Map 里两类混放，contains 结果飘忽。这是"instanceof 宽松判等必须配 final 类"的最佳实证，也被列入 Effective Java Item 10 的反面教材。

// getClass() 严格版（层次结构会扩展、子类不该等于父类时用它）：
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;   // 精确同类
    return id == ((Order) o).id;
}
// 取舍口径：类会被第三方继承 → getClass()；类是 final / 内部实现类 → instanceof 也安全；
// record 直接全字段生成，两难不存在。

toString

  • 默认 类名@十六进制身份哈希，日志里全是它等于没打印——POJO 必须重写。
  • 自动方案：record、Lombok @ToString、IDE 生成；注意敏感字段脱敏（手机号、身份证、密码）——高级岗的实战加分点，顺手提日志安全。
  • 注意 toString 里的开销：超大集合对象打日志会触发整棵对象图的字符串化，影响性能。

可变 key 的坑：把对象放进 HashMap 后修改参与 hashCode 的字段 → 桶下标变了，旧位置的 Entry 从此查不到、删不掉（直到扩容 rehash 才"诈尸"），本质是内存泄漏。阿里规约因此要求：作为 key 的对象及其字段必须不可变（String、Integer、Long 是最稳的 key）。

07instanceof 与 JDK 16 模式匹配

基本规则

  • obj instanceof T：运行期判断 obj 的实际类型是否与 T 兼容（本身或子类/实现）。
  • null instanceof 任何类型 永远是 false——instanceof 天然判空安全。
  • 编译期"恒假拦截"：编译器能证明"声明类型的对象永远不可能是 T"时，instanceof 直接编译错误（Integer i; i instanceof String → "不兼容的类型"）。根因是类单继承：两个无交集的类不可能有共同对象——哪怕都不是 final（ArrayList a; a instanceof LinkedList 也报错）；final 类没实现的接口同理（Integer instanceof Cloneable 报错）。放行：T 是声明类型的子类（Object o; o instanceof String）；声明类型是接口或非 final 类（可能有子类实现/继承 T）；恒真也放行（String s; s instanceof Object）——只拦恒假，不拦恒真。Java 17+ sealed 更进一步：目标类型不在 permits 名单内直接报错。
  • 兄弟方法：Class.isInstance(obj)（反射版）、Class.isAssignableFrom(cls)（类型间关系）、o.getClass() == T.class（精确类型相等，equals 严格版用它）。

三个"兄弟方法"的方向陷阱 ⭐

// 1) Class.isInstance(obj)：反射版 instanceof——类型是运行期变量时只能用它
Class<?> type = Class.forName("java.lang.Integer");
type.isInstance(42);                    // true；类型不是字面量时 instanceof 写不出来

// 2) Class.isAssignableFrom(cls)：类型对类型，【父在左、子在右】
Number.class.isAssignableFrom(Integer.class);   // true  —— Number 能装下 Integer
Integer.class.isAssignableFrom(Number.class);   // false —— 方向反了必错
// 助记：读作"左边的引用类型能否指向右边的实例"（和赋值语句 Number n = new Integer(1) 同向）

// 3) o.getClass() == T.class：只认精确类型，不认子类
Number n = 100;
n instanceof Integer;           // true  —— instanceof 认子类
n.getClass() == Integer.class;  // true  —— 恰好是精确类型时为真
n.getClass() == Number.class;   // false —— getClass() 永不返回父类
  • 选型口径：编译期已知类型写 instanceof（有恒假拦截保护）；类型是运行期变量才用 isInstance；框架里判断继承关系用 isAssignableFrom（Spring 的 ClassUtils.isAssignableValue 内核就是它）；equals 严格版用 getClass ==。
  • isInstance 之所以不享受恒假拦截：类型是变量，编译器无从证明"无交集"，只能运行期老老实实返回 false——呼应上文"恒假拦截"的边界：编译期就注定答案的拦下，运行期才知道答案的放行。

JDK 16：instanceof 模式匹配（JEP 394）

// 老写法：判型 + 强转，三行两步
if (obj instanceof String) {
    String s = (String) obj;
    return s.isBlank();
}

// JDK 16+：模式变量，一步到位
if (obj instanceof String s && s.isBlank()) {
    return s.length();
}
// 作用域是"流敏感"的：只在条件成立的分支里有效，甚至
if (!(obj instanceof String s)) return null;
return s.trim();          // 这里 s 依然可用（else 语义的反向推断）
  • 模式变量的作用域由数据流分析决定（flow scoping），比普通变量声明更精细。
  • 配合 JDK 21 的 switch 模式匹配（case Integer i ->）基本消灭"判型强转"样板代码，完整演进见 第 14 章。

08协变返回类型与桥方法

协变返回（covariant return type，JDK 5 引入）：重写方法可以返回父类方法返回类型的子类型——"两小"之一。

abstract class Shape {
    abstract Shape copy();                 // 返回 Shape
}
class Circle extends Shape {
    @Override
    Circle copy() {                        // ✅ 返回收窄为 Circle（协变）
        return new Circle();
    }
}

// 典型应用：clone() 的正规重写
class Point implements Cloneable {
    @Override
    public Point clone() {                 // Object.clone() 返回 Object，这里收窄
        try { return (Point) super.clone(); }
        catch (CloneNotSupportedException e) { throw new AssertionError(e); }
    }
}

底层：编译器悄悄生成的桥方法（bridge method）

  • JVM 层面方法签名包含返回类型，但虚分派要求父子签名严格一致。协变返回怎么兼容？javac 在子类里合成一个 Shape copy() 的桥方法，内部调用你写的 Circle copy()（ACC_BRIDGE | ACC_SYNTHETIC 标记）。
  • 泛型擦除的协变同理：Comparator<String> 的 compare(String,String) 编译后签名是 compare(Object,Object)，桥方法负责转发——反编译 Comparator 匿名类就能看到两个 compare。
  • 实战关联：注解扫描/反射遍历方法时看到重复方法名，别懵，用 Method.isBridge() 过滤（Spring、MyBatis 源码里都有这处理）。
$ javap -v Circle | grep -A4 "copy"
  public Circle copy();              // 你写的版本：返回 Circle
    Code: ... areturn

  public Shape copy();               // 桥方法：签名与父类一致（虚分派槽位对齐）
    flags: ACC_PUBLIC, ACC_BRIDGE, ACC_SYNTHETIC
    Code:
       0: aload_0
       1: invokevirtual #x  // Method copy:()LCircle;   ← 转调真身
       4: areturn

协变只针对返回类型；参数类型必须严格相同——参数"更窄"那就是重载，不是重写（且会因 @Override 报错）。协变数组是另一回事（数组协变 + 堆污染，见 第 09 章泛型）。

09高频追问与陷阱

  • 追问链：重写 equals → 为什么用 31 做乘数？→ 奇素数（冲突分布均匀 + 不丢低位）、(i<<5)-i 移位优化；String 的 hash 就是这个公式（第 01 章呼应）。
  • 追问链：hashCode 相等 equals 一定相等吗？→ 不一定（碰撞）；反问回去"equals 相等 hashCode 呢？"→ 必须相等，契约所在。
  • 追问链：两个 equals 相等的对象 hash 不同会怎样？→ HashMap 双桶分裂：put/get 各自定位到不同桶，取不到；HashSet 去重失效；该 Entry 成为"孤儿数据"。
  • 陷阱：重写 equals 参数写成 MyClass o 而非 Object o→ 那是重载不是重写，List.contains 会走 Object 版本直接判地址，永远 false；@Override 能当场拦住。
  • 陷阱：子类重写后抛了更宽的 checked 异常→ 编译错误（"两小"）；但抛 RuntimeException 不受限——子类"偷偷"抛 unchecked 异常是合法却阴险的操作。
  • 陷阱：private/final/static 方法 + @Override→ private 不能被重写；final 重写编译错误；static 上写 @Override 直接编译错误（它只是隐藏）。
  • 追问：多态对 static 方法和字段为什么不生效？→ static 走 invokestatic、字段走 getfield，都是编译期静态绑定；只有 invokevirtual/invokeinterface 的实例方法进 vtable 动态分派。
  • 追问：虚分派有性能损耗吗？日常要不要为性能把方法都写成 final？→ 有但很小：一层间接寻址 + 阻碍内联。现代 JIT 对单态调用点做"去虚化"（类型守卫 + 内联）后开销基本归零；盲目 final 不可测且影响子类设计，Profile-Guided 的 JIT 比人猜得准——答"先测量再优化"是高级岗口径。
  • 追问：Timestamp 的 equals 事故说明什么设计原则？→ 继承体系里"加字段的子类"与 instanceof 宽松判等天然冲突；要么 final 类（String/Integer 都这么干），要么 getClass 严格版，要么放弃继承用组合——和"组合优先"是同一件事在判等问题上的投影。
  • 追问：为什么 JDK 5 允许协变返回？泛型擦除下怎么实现的？→ 为了链式 API 不强转；编译器桥方法保签名兼容。
