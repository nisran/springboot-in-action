异常题的特点是"每道都有标准答案，但答到字节码和工程实践才算高级"。7 年经验的打法：结论先行 → 机制（源码/字节码）→ 工程实践（我们项目里怎么分层的）。本章已把 Java/java 基础.md 的异常一节全部并入并补深。

02异常体系结构 ⭐

Throwable 是 JVM 层面一切异常的根（类比 Object 在对象体系中的位置），只有它的子类才能被 throw / 被 catch：

Throwable                              // 一切异常的根
├── Error                              // JVM 自身错误：程序无法/不应该处理
│   ├── OutOfMemoryError               //   堆/元空间耗尽
│   ├── StackOverflowError             //   递归过深、栈溢出
│   └── NoClassDefFoundError           //   编译期存在、运行期缺失（链接失败）
└── Exception                          // 程序级异常
    ├── RuntimeException（及子类）      //   unchecked：NPE、IllegalArgument…
    │   └── NullPointerException / ClassCastException / IndexOutOfBoundsException / ...
    └── 其他子类 = checked             //   IOException、SQLException、ClassNotFoundException…
  • Error：JVM 层面的严重故障，程序无法 / 不应该处理——catch 了也基本无力回天（OOM 时可能连异常对象的内存都分配不出来）。语法上能 catch Error/Throwable，但工程上不该。
  • Exception：程序级异常，又分两支——RuntimeException 家族（unchecked）与其他（checked）。
  • SOE vs OOM 排查分工（一句话版）：StackOverflowError 看线程栈——递归无出口/循环调用（日志通常能直接看到重复栈帧）；OutOfMemoryError 看堆/元空间/直接内存四类来源，要 heap dump（-XX:+HeapDumpOnOutOfMemoryError）区分泄漏还是配置不足——展开在 03-jvm 板块。把两种 Error 的排查路径分开答，是这题的深度标志。

口诀（判别一切异常的归属）：RuntimeException 及其子类 + 所有 Error 都是 unchecked；其余 Exception 子类都是 checked。注意 unchecked 不等于 Exception——Error 也是 unchecked，这个细节常被拿来挖。

03checked vs unchecked ⭐⭐

维度CheckedUnchecked（RuntimeException）
检查时机编译期运行时
强制性必须 try-catch 或 throws，否则编译不通过不强制
继承自Exception（但不是 RuntimeException 子类）RuntimeException
设计意图期望调用者能恢复的外部资源问题（IO、DB、网络）程序 bug，调用者通常无法合理恢复
示例IOException、SQLException、ClassNotFoundExceptionNPE、ClassCastException、IllegalArgumentException
处理哲学强制暴露，减少遗忘（编译器替你记着）故意宽松，避免样板代码淹没业务逻辑

高频延伸：checked 的争议与业界选择（高级岗加分）

  • checked 的初衷是"可恢复就强制处理"，但实践中大量调用者根本无法恢复，只能一层层往上 throws 或者写出 catch (IOException e) {} 这种吞异常的烂代码——强制变成了污染。
  • 后来的语言用脚投票：C#、Kotlin、Scala 都砍掉了 checked 异常；Spring 把 JDBC 整族 checked 的 SQLException 翻译成 unchecked 的 DataAccessException 层级，就是"框架替你消灭 checked 样板"的标杆案例。
  • 主流业务的务实口径：自定义业务异常继承 RuntimeException，少一堆 throws 样板；真正"调用方必须处理的罕见情况"才考虑 checked（如 InterruptedException，catch 后要恢复中断标记）。

易混点：InterruptedException 是 checked，且 catch 后规范做法是 Thread.currentThread().interrupt() 恢复中断位，否则中断信号被吞——这是并发面试的固定追问（细节在 02-concurrency）。

04try-catch-finally 执行顺序 ⭐⭐（经典陷阱）

三组必背实验

// 实验 1：try 和 finally 都 return
static int test() {
    try { return 1; }
    finally { return 2; }     // 方法返回 2 —— finally 的 return 覆盖了 try 的
}

// 实验 2：finally 只是打印，不影响返回
try { return "A"; }
finally { System.out.println("B"); }   // 打印 B，返回 "A"

// 实验 3：try 抛异常 + finally return
try { throw new RuntimeException("x"); }
finally { return "y"; }                // 异常被吞！方法正常返回 "y"

执行规则

  • return 之前 finally 必跑：return 表达式的值先算好压入操作数栈 / 存入局部变量槽，然后跳去执行 finally，finally 里能读到变量但改不了"已经算好的返回值"（基本类型）；引用类型虽然引用改不了，但可以通过引用改对象内部状态。
  • finally 里有 return → 吞掉 try 的返回值和异常；finally 里抛新异常 / System.exit() → 同样覆盖/吞掉原异常，调试时坑极大。
  • 结论（一句话口径）：finally 里只做资源释放，绝不要 return / throw。

反编译级解释（把 finally return 讲到底）

javac 编译 finally 的方式是：把 finally 代码块的字节码复制内联到每一个"出口"之前（正常 return 前、每个能到达的 catch/handler 前）。对实验 1 javap -c 看到的关键逻辑（简化）：

static int test();
 0: iconst_1            // try 里算好返回值 1
 1: istore_0            // 存入局部变量槽 0（返回值先落槽，这是"finally 改不了它"的原因）
 2: iconst_2            // —— finally 逻辑被内联在 return 出口前 ——
 3: istore_0            // 同一个槽位被 2 覆盖：这就是"finally 的 return 赢了"的真相
 4: iload_0             // 加载槽 0 里的最终值
 5: ireturn             // 返回 2
  • try 抛异常时同理：异常先被抛出流程挂起（记入异常表 handler），执行完内联的 finally 后，finally 里的 ireturn 让方法以正常返回结束，挂起的异常对象被直接丢弃——实验 3 的"吞异常"在字节码层面就是这一步。
  • finally 里只是 println（实验 2）时，内联的代码不改返回值槽，所以打印 B、返回 A。

finally 不执行的例外：System.exit()（JVM 直接终止）、JVM 崩溃 / 断电、守护线程随 JVM 退出被杀、finally 自身死循环/抛异常中断。回答"finally 一定执行吗"要主动补这几个例外，否则会被追着问。

05throw vs throws · final / finally / finalize

throw vs throws

维度throwthrows
位置方法体内部，是一条语句方法签名上，是一种声明
作用抛出一个具体的异常实例声明此方法可能抛出的异常类型（给调用者看）
个数一次只能抛一个可声明多个，逗号分隔
后续执行抛出后方法立即中断方法照常执行，只是告诉调用者要处理/继续上抛

重写追问点：子类重写方法时，throws 的 checked 异常可以缩小（甚至不抛），但不能扩大——否则调用方按父类签名写的 catch 就接不住了。unchecked 异常不受此限制。

final / finally / finalize（送分题，但必背）

  • final：修饰符——类不可继承、方法不可重写、变量不可重新赋值（引用不可变 ≠ 对象不可变，见 第 05 章）。
  • finally：try 的配套块，保证资源清理逻辑执行。
  • finalize()：Object 的方法，GC 回收前调用一次（最多一次），JDK 9 起已 deprecated，JDK 18 起 forRemoval——执行时机不确定、性能差、可能复活对象，替代方案是 try-with-resources / Cleaner。答案末尾加一句"早不用了"就是满分答法。

06try-with-resources（Java 7+，推荐写法）

// 资源必须实现 AutoCloseable（JDK 7+）
try (InputStream in = new FileInputStream("a.txt");
     OutputStream out = new FileOutputStream("b.txt")) {
    out.write(in.readAllBytes());
}   // 自动 close：多个资源按声明【逆序】关闭（先 out 后 in，符合栈式依赖）
  • 解决了传统 try-finally 的两个痛点：嵌套丑（多资源层层 try）和异常被 close 的异常覆盖（旧写法里 finally 中 close 抛异常会把 try 里的原始异常顶掉）。
  • close 的异常不会覆盖主异常——Suppressed exceptions：编译器把代码展开成嵌套 try——外层 catch 捕获主异常；close 再抛异常时，用 Throwable.addSuppressed()（JDK 7 引入）把 close 异常附在主异常身上而不是替换它，getSuppressed() 可取回完整列表。这正是第 01 节高频题"finally 异常覆盖"的官方解法。
  • JDK 9 增强：资源变量在 try 外已声明且 effectively final 时，可简写 try (in) { ... }。
  • 自定义资源类实现 AutoCloseable 的 close() 建议幂等（重复调用无害）。
// 手动演示 suppressed：面试能写出这个就是"原理级"掌握
Exception primary = new IOException("主异常");
try (AutoCloseable bad = () -> { throw new IllegalStateException("close 也炸了"); }) {
    throw primary;
} catch (Exception e) {
    System.out.println(e.getMessage());          // 主异常：主异常
    for (Throwable s : e.getSuppressed())        // 附加异常：close 也炸了
        System.out.println(s.getMessage());
}

07异常链（cause / 异常翻译）

底层异常被 catch 后不要直接吞掉，要包成上层语义的异常、把原异常作为 cause 传出去——保留完整现场，方便定位根因：

try {
    dao.query();
} catch (SQLException e) {
    throw new BizException("查询用户失败", e);   // e 作为 cause 挂在新异常上
}
// 通过 e.getCause() 可以一级级拿回根因；
// printStackTrace() 会打印 "Caused by: ..." 链，完整现场一目了然
  • 这就是异常翻译（exception translation）：下层技术异常（SQL/IO/RPC）在层边界翻译成上层业务/领域异常，但 cause 全程携带。
  • 最常见的反模式：throw new BizException("查询用户失败")——只留一句话，原始堆栈全丢，线上排查等于盲人摸象；以及 log.error("失败", e) 之后又原样 throw e，同一条栈打两遍污染日志。
  • 注意与 suppressed 的区分：cause 是我捕获后包装的历史异常（人为构造的链），suppressed 是 try-with-resources 里 close 附带的次要异常（编译器构造的链）——两个都考"多异常共存"。

09自定义异常设计（错误码 + 业务语义）

业务系统的标准做法：错误码枚举 + 业务异常基类 + cause 全保留：

/** 错误码：业务语义的单一事实来源，编号分段（A=业务 B=系统）方便治理 */
public enum ErrorCode {
    USER_NOT_FOUND("A0010", "用户不存在"),
    INSUFFICIENT_BALANCE("A0020", "余额不足"),
    SYSTEM_ERROR("B0001", "系统内部错误");

    final String code;
    final String defaultMessage;
    ErrorCode(String code, String msg) { this.code = code; this.defaultMessage = msg; }
}

/** 业务异常：unchecked + 错误码 + 带 cause 的构造器 */
public class BizException extends RuntimeException {
    private final ErrorCode errorCode;

    public BizException(ErrorCode ec) { super(ec.defaultMessage); this.errorCode = ec; }

    public BizException(ErrorCode ec, Throwable cause) {   // ⭐ 必须提供带 cause 的构造器
        super(ec.defaultMessage, cause);
        this.errorCode = ec;
    }

    public ErrorCode getErrorCode() { return errorCode; }   // 上游用它判定分支，而不是解析 message
}

// 使用：底层技术异常翻译成业务语义，cause 保留完整现场
try {
    return userDao.findById(id);
} catch (DataAccessException e) {
    throw new BizException(ErrorCode.SYSTEM_ERROR, e);
}
  • 继承 Exception 还是 RuntimeException：继承 Exception 则是 checked（老式分层架构用），多数现代项目选 RuntimeException——少一堆 throws 样板（与第 03 节的业界口径一致）。
  • 命名规范：XxxException；提供错误码字段，上游用错误码判定分支而不是 getMessage() 字符串匹配（message 是给人看的，会改文案）。
  • 业务异常和系统异常分开：业务异常（参数错、状态不满足）→ 让上游改参数/换流程，可预期可处理；系统异常（NPE、DB 挂了）→ 只记录 + 报警，绝不该被业务代码 catch 吃掉。两类异常的错误码前缀分开，监控大盘才能分开报警。
  • 落点一句话：Web 层最外层用 Spring 的 @ControllerAdvice + @ExceptionHandler 统一把 BizException 翻译成带错误码的响应、系统异常兜底 500 + 告警——细节在 04-spring 板块。

10最佳实践与反模式

该做的 ✅

  • 早 throw、晚 catch：参数不合法在入口立刻抛（fail-fast），统一在最外层（Controller / 切面 / 全局处理器）兜底。
  • 只捕获你能处理的异常：不知道怎么处理就原样往上抛，别硬接。
  • finally / try-with-resources 只做资源释放，不 return、不 throw 业务异常；多资源一律 try-with-resources。
  • 日志要带上下文（业务主键、参数），且把异常对象作为最后一个参数传给 logger：log.error("查询用户失败, userId={}", userId, e)——框架会打印完整堆栈，而不是只留 e.getMessage()。
  • 包异常时保留 cause；上层处理要区分业务/系统两类。

不该做的 ❌

  • catch (Exception e) {} 空 catch 吞异常——故障静默扩散的万恶之源。
  • 用异常做流程控制：异常构造要 fillInStackTrace()（native 深拷贝栈帧），展开成本高且可读性差；也别在循环里反复 try-catch 同一段。
  • 捕获顶层 Throwable / Error 兜底业务——OOM 也被你吃了。
  • 丢 cause 的包装（见第 07 节反模式）；捕获后只打 message 不打栈。

深挖加分点：JVM 有 -XX:-OmitStackTraceInFastThrow 优化——同一位置的热点异常抛多了，会改抛没有堆栈的预分配单例异常省开销。所以生产上偶见"NPE 但栈是空的"，解法是重启 JVM 或加参数关掉优化。能讲这个的候选人凤毛麟角。

11高频追问与陷阱

  • 追问链：OOM 是 Error，catch 得住吗 → 语法上能 catch Throwable，工程上不该（多数 OOM 无法恢复）；唯一常见"可救"的是 StackOverflowError（收敛递归深度后可继续），但也不建议依赖。
  • 追问链：finally 里的异常会覆盖 try 里的异常，怎么避免 → try-with-resources + suppressed（第 06 节），或 finally 里 close 时再包一层 try-catch 记日志——前者是标准答案。
  • 追问：ClassNotFoundException vs NoClassDefFoundError ⭐ → 前者 checked，来自显式加载（Class.forName() / 反射），类名写错/依赖缺失，调用方预期处理；后者是 Error，编译期存在、运行期初始化/链接失败（jar 冲突、静态初始化块抛异常）——一对高频混耗题。
  • 追问：多个 catch 的顺序 → 子类必须在前，父类在后，否则子类 catch 永远不可达，直接编译错误；JDK 7+ 可用多类型合并 catch (IOException | SQLException e)（e 隐式 final）。
  • 追问：catch 里 return，finally 还执行吗 → 执行（catch 的 return 同样先落槽再走 finally）；只有 finally 也 return 才会覆盖。
  • 陷阱：try 块里 return 的值已算好——finally 里改基本类型局部变量不影响返回值；改对象内部状态会影响（值已拷贝的是引用）。
  • 追问：异常与事务 → Spring 声明式事务默认只对 RuntimeException 回滚，checked 异常默认不回滚（@RollbackFor 可调）——异常分流的又一个工程落点，细节在 04-spring。
  • 追问：超高频抛出的异常怎么消除构造开销？→ 构造大头是 fillInStackTrace()（native，抓整条栈）。两条路：① 子类覆盖 fillInStackTrace() 返回 this（无栈异常，JDK 内部如 ClassCastException 快路径就是这么干的）；② 生产上更常见的是把"高频路径的异常提示"改成返回值/Optional/错误码，异常只留给真异常。
