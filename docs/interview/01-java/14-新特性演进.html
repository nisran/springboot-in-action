02版本全景：发布节奏与 LTS

2018 年起 Java 改为每 6 个月发一版（3 月 / 9 月），每 2 年一个 LTS。面试只需要记牢 LTS 骨架：

版本年份定位面试聊点（每版 2~3 个）
8 (LTS)2014函数式转折点Lambda / Stream / 新日期时间 / 接口 default
92017模块化JPMS 模块系统 / 接口私有方法 / Compact Strings（String char[]→byte[]，详见 05 章）
102018.3语法减负var 局部变量类型推断
11 (LTS)2018.9首个新节奏 LTSHTTP Client / String 增强 / 单文件运行
12~142019~2020预览孵化期switch 表达式（14 转正）
15~162020~2021数据载体成型文本块（15）/ record、instanceof 模式（16）
17 (LTS)2021生态分水岭sealed 转正；Spring Boot 3 最低版本
21 (LTS)2023并发新时代虚拟线程 / 模式匹配 for switch / 记录模式 / 分代 ZGC
25 (LTS)2025最新 LTS虚拟线程 pinning 修复、紧凑对象头等持续优化

记法：LTS 链 "8 → 11 → 17 → 21 → 25"。中间小版本的意义是"新特性以预览形式快速试错，转正后再进 LTS"——所以聊特性时要能说清它是哪个版本转正的（如 record 16、sealed 17、switch 模式 21），这是体现熟练度的细节。

03Java 8 ⭐⭐：现代 Java 的起点

Lambda 与函数式接口：行为参数化

痛点：把"一段行为"当参数传，过去只能写匿名内部类——四五行为了一行逻辑，且冗余的语法淹没了意图（著名的垂直问题）。

// 排序逻辑从"传入一个对象"变成"传入一个行为"，且只保留意图本身：
list.sort(Comparator.comparing(User::getAge).thenComparing(User::getName));

Runnable r = () -> System.out.println("go");          // @FunctionalInterface 单抽象方法才能用 Lambda

// 四大内置函数式接口（背下来，面试常考搭配）：
// Predicate<T>   boolean test(T t)        —— 断言：filter 的参数
// Function<T,R>  R apply(T t)             —— 转换：map 的参数
// Consumer<T>    void accept(T t)         —— 消费：forEach 的参数
// Supplier<T>    T get()                  —— 供给：懒加载 / 工厂
  • Lambda 的本质：函数式接口的实例（编译期生成 invokedynamic 指令 + LambdaMetafactory 运行期生成，而非匿名内部类——后者每次都生成 class 文件，这是追问点）。机制详解在 第 10 章。
  • 方法引用 Class::method 是 Lambda 的进一步简化，四类形式要认得。

Stream：声明式的集合处理

痛点：命令式循环 + 中间状态变量，样板代码多且难并行。Stream 把"怎么做（循环）"换成"做什么（算子）"：source → 中间操作（惰性）→ 终端操作（触发），如 filter / map / flatMap / collect(groupingBy)。深入（惰性求值、短路、并行流坑）同样在 第 10 章，本章不重复。

接口的 default / static 方法：接口演进

痛点：接口一旦发布，加一个抽象方法 = 破坏全世界所有实现类。Java 8 要给 Collection 加 stream()，靠的就是 default 方法给存量实现类兜底。

public interface PaymentChannel {
    String channelCode();

    default boolean supportsRefund() {        // 默认实现，老实现类不改造也能编译通过
        return true;
    }
    static PaymentChannel of(String code) {   // 接口静态方法：工厂逻辑收进接口本身
        return ChannelRegistry.find(code);
    }
}
  • 多实现冲突规则（高频追问）：① 类里的方法永远优先于接口 default；② 两个接口都有同名 default 时，编译器强制你重写，需要的话用 X.super.m() 指定调谁。
  • 新日期时间 API 也是 8 的大件，已在 第 13 章完整覆盖。

04Java 9~11：模块化 · var · HTTP Client

Java 9：JPMS 模块系统

痛点：classpath 是一锅粥——JAR 缺失 / 冲突只有运行期才炸（NoClassDefFoundError），JDK 内部 API 被随意反射（sun.misc.Unsafe 一堆黑魔法），无法按模块裁剪运行时。

module com.order.service {
    requires java.sql;                 // 显式依赖，启动期校验，缺了直接起不来（错误左移）
    requires transitive java.logging;  // 传递依赖：用我的模块的人自动可见
    exports com.order.service.api;     // 只导出 api 包，内部实现对外不可见（强封装）
}
  • 业务系统一般不写 module-info（Spring 生态按普通 classpath 跑，称 automatic module / unnamed module），但模块化带来的JDK 内部强封装影响所有人：JDK 16 起（JEP 396/403）默认拒绝反射访问 JDK 内部，这正是很多老项目从 8 升 11/17 时报 InaccessibleObjectException、要加 --add-opens java.base/java.lang=ALL-UNNAMED 的原因——升级实战故事的标配素材。
  • 另一个红利是 jlink：按模块裁剪出几十 MB 的自定义运行时（配合 jpackage 做 CLI 工具分发）。
  • 接口私有方法（9 正式）：default 方法多了之后抽公共私有逻辑，接口的演进能力补完。
  • 顺带：List.of() / Set.of() / Map.of() 集合工厂，一行造不可变集合。

Java 10：var 局部变量类型推断

var users = new ArrayList<User>();              // 右边信息足够时，左边不啰嗦
var map = new HashMap<String, List<Order>>();  // 泛型钻石的样板代码消失
for (var entry : map.entrySet()) { ... }
  • var 仍是静态类型：编译期推断出确定类型，不是 JS 的 var、也不是动态类型——推断完就是 ArrayList<User>，之后不能再赋别的类型。
  • 限制（追问高频）：只能用于局部变量（要有初始化器）；不能用于字段、方法参数、返回值、catch 参数；var a = null 不行（推不出来）；var 是保留类型名不是关键字，老代码里叫 var 的变量名仍合法。
  • 使用品味：右边类型显而易见才用（new 表达式、工厂方法），var x = service.process() 这种右边看不出类型的，写了降低可读性。

Java 11：HTTP Client / String 增强 / 单文件运行

HttpClient client = HttpClient.newHttpClient();            // 内建 HTTP/2、同步异步双模
HttpRequest req = HttpRequest.newBuilder(URI.create("https://api.example.com/orders"))
        .header("Accept", "application/json").build();
HttpResponse<String> resp = client.send(req, HttpResponse.BodyHandlers.ofString());

// 异步：返回 CompletableFuture，天然融入响应式/回调编排
client.sendAsync(req, HttpResponse.BodyHandlers.ofString())
      .thenApply(HttpResponse::body)
      .thenAccept(body -> log.info("{}", body));

// String 增强：isBlank / strip（懂 Unicode 空格，trim 不懂）/ lines / repeat
"  hi  ".strip();
"a,b,c".lines().count();
"-".repeat(20);

// 单文件运行：脚本化的第一步，不用先 javac
$ java Hello.java
  • 痛点：HttpURLConnection API 古老（2011 年前的设计）、回调式读流难用，多数人被迫引 Apache HttpClient / OkHttp；JDK 11 把现代化客户端标准化，小工具 / SDK 可以零依赖。
  • 11 还悄悄删了 Nashorn（JS 引擎）、JEE 模块（java.xml.bind 等）——升级时 NoClassDefFoundError: javax/xml/bind 也是常见坑，答"升级踩坑"时用得上。

05Java 12~16：switch 表达式 · 文本块 · record

switch 表达式（12 预览，14 转正）

痛点：老 switch 的 fall-through 忘 break 是万 bug 之源；switch 只是语句不能直接"求值"；case 齐不齐编译器不管。

// 箭头语法：无 fall-through、一个 case 多值、switch 成了"表达式"能直接返回值
int days = switch (month) {
    case JAN, MAR, MAY, JUL, AUG, OCT, DEC -> 31;
    case FEB -> 28;
    default -> 30;
};
// 复杂分支用 yield 返回：
String label = switch (status) {
    case PAID -> "已支付";
    case REFUNDING -> {
        log.info("refund in progress");
        yield "退款中";                   // 块里用 yield 而不是 return
    }
    default -> "未知";
};
  • 对枚举 switch 时，穷尽了所有枚举值可以省 default——编译器帮你检查漏分支，这是后续"模式匹配 + sealed"路线的第一步。

文本块（13 预览，15 转正）

String json = """
        {
          "orderId": "%s",
          "amount": %d
        }
        """.formatted(orderId, amount);
// 三引号：换行、缩进原样保留；公共缩进自动剥离（incidental indent）
// 行尾 \\ 续行拼一行；\\s 保留尾随空格 —— 写 JSON / SQL / HTML 模板不再手拼 \n
String sql = """
        select id, amount from t_order
        where user_id = ? and status = ?
        """;

record（14 预览，16 转正）：不可变数据载体

// 一行 = 构造器 + 全只读访问器 + equals/hashCode/toString（按字段值）
public record OrderResponse(Long orderId, BigDecimal amount, String status) {}

// 紧凑构造器：做参数校验 / 规范化的位置，不用重写整个构造器
public record Money(BigDecimal amount, String currency) {
    public Money {                              // 无参数列表，编译器仍帮你赋值
        Objects.requireNonNull(currency);
        amount = amount.setScale(2, RoundingMode.HALF_UP);
    }
    public boolean isZero() { return amount.signum() == 0; }  // 可以加普通方法 / 静态工厂
}
  • 解决什么：Java 写纯数据类要 IDE 生成上百行（getter/equals/hashCode/toString），Lombok 是社区补丁，record 是语言级答案——而且语义更强：值语义（两个字段相同的 record equals 为 true），天然适合当 Map key、DTO、多返回值。
  • 限制（必考）：隐式 final 不能被继承（也不能继承别的类，只能实现接口）；字段全部 final，没有 setter——它是不可变载体，不是 JavaBean；组件可以可变（字段是 List 时不防御拷贝，需要自己在紧凑构造器里 List.copyOf()）。
  • record vs Lombok @Data：@Data 生成 setter（可变）、生成的是"逐字段 equals"但类仍是普通类；record 不可变 + 值语义 + 可解构（配合记录模式）。DTO / 值对象优先 record，需要可变 JavaBean（部分 ORM / 老框架绑定）才用 Lombok。

16 还有 instanceof 模式匹配：if (obj instanceof String s && !s.isBlank()) 判断 + 转型 + 绑定变量一步完成，告别"先 instanceof 再强转"两行。它是后面 switch 模式匹配的前置语法。

06Java 17 LTS：sealed 转正与生态分水岭

sealed（17 转正）：受控继承

痛点：接口/抽象类的继承要么全开（谁都能 implements，分支永远写不全）要么全关（final）。sealed 把"谁能实现我"写进类型声明，介于两者之间。

public sealed interface Payment permits AliPay, WeChatPay, BankCard {}  // 白名单：只有这三个
public record AliPay(String tradeNo)      implements Payment {}   // 子类必须 final / sealed / non-sealed 三选一
public record WeChatPay(String openId)    implements Payment {}
public record BankCard(String cardNo)     implements Payment {}
  • 它的价值要靠组合兑现：sealed 限定了实现集合 → 编译器知道 switch 覆盖了所有情况 → 穷尽性检查（漏 case 直接编译错误，新增实现时所有 switch 自动报错提醒）——这是 Java 版"代数数据类型"的最后一块拼图（下一节展开）。
  • 子类必须与父类同模块（或同包），且必是 final / sealed / non-sealed 之一——继承关系在编译期完全可见。
  • 17 是生态分水岭：Spring Boot 3 / Spring 6 最低要求 17，这条几乎是"要不要升级"的决策开关。所以国内大量公司停在 11 的直接原因消失，17→21 成为当前主流升级路径。

07Java 21 LTS ⭐：虚拟线程 / 模式匹配 / 分代 ZGC

虚拟线程（JDK 19 预览，21 转正）—— 本章只做入口

// 三种创建方式：
Thread t = Thread.ofVirtual().name("v-", 0).start(runnable);   // 直接建
Runnable r = Thread.ofVirtual().unstarted(() -> handle(req));

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {  // 每任务一线程，来一百万个也不慌
    IntStream.range(0, 100_000).forEach(i -> executor.submit(() -> {
        var data = httpClient.send(...);   // 阻塞在 IO 上时，虚拟线程被"卸载"，载体线程去跑别的
        return db.query(data);
    }));
}
  • 一句话是什么：JVM 调度的轻量线程（非 OS 线程），由 JDK 自己把虚拟线程挂载到少量平台线程（载体线程）上；阻塞调用（HTTP、JDBC）会被 JVM 拦截，把载体线程让出去。
  • 解决什么：线程 = 资源的旧模型下，IO 密集服务想扛高并发只能"每连接一线程（内存撑不住）"或"回调/响应式（难写难调）"。虚拟线程让你用同步阻塞的写法拿到异步的吞吐——"每请求一线程"模型复活。
  • 适合：IO 密集（Web、网关、爬虫、调外部接口）。不适合：CPU 密集（虚拟线程不提升计算吞吐，线程数再多核还是那几个）。
  • 注意：不要池化虚拟线程；synchronized 块内阻塞会 pin 载体线程（JDK 21 已知问题，24 才修复）；ThreadLocal 滥用在百万线程下内存翻车——这些深入机制全部在 02 并发板块 · 第 10 章虚拟线程展开（原理 mount/unmount、M:N 调度、pin 演进、迁移清单共 10 节）。

模式匹配 for switch + 记录模式（21 转正）

String describe(Object obj) {
    return switch (obj) {
        case Integer i when i > 0 -> "正整数 " + i;   // 类型模式 + when 守卫
        case Integer i      -> "非正整数";
        case String s       -> "字符串: " + s;         // 自带绑定，无强转
        case Point(int x, int y) -> "点(%d,%d)".formatted(x, y);  // 记录模式：直接解构 record
        case null           -> "空";                   // null 也能接住（旧 switch 直接 NPE）
        default             -> "其他";
    };
}
public record Point(int x, int y) {}
  • 对比 JDK 16 的 instanceof 模式：if 版只能"一个类型一个 if"，switch 版可以穷尽、可以解构嵌套（case Line(Point a, Point b) 一路拆到底）、编译器查穷尽性。
  • 记录模式 = record 的"反操作"：构造时聚合，解构时拆开——数据和类型配对成完整闭环。

分代 ZGC（JDK 21 转正，JEP 439）

  • ZGC 此前不分代（所有对象一个堆），优点是停顿 <1ms，缺点是为维持低停顿整体 CPU 开销偏高；分代 ZGC 引入分代假设（朝生夕死对象占多数），年轻代独立回收，吞吐开销显著降低。
  • 用法：-XX:+UseZGC -XX:+ZGenerational（JDK 23 起分代成为默认、JDK 24 移除开关方向不变）。面试口径：大堆（几十 GB）+ 低延迟（P99 不抖）的服务，21 时代首选分代 ZGC；一般吞吐型应用 G1 仍然够用。GC 深入在 03 JVM 板块。

21 一句话总结（可直接背）："21 是并发模型换代 + 数据建模范式成型双重意义的 LTS：虚拟线程把 IO 密集服务的吞吐天花板抬高一个数量级，sealed+record+模式匹配让业务建模有了函数式的表达力，分代 ZGC 补齐了低延迟 GC 的吞吐短板。"

08Java 22~25：新 LTS 25 与最新演进 ⭐（2026 年的区分度题）

JDK 25（2025-09 发布）是继 8/11/17/21 之后的第五个 LTS。面试聊到它不要求精通，但要能说出两三个特性和方向——这直接证明你的知识停在"现役"，而不是停在 JDK 8/17。

版本时间值得面试提的点
JDK 222024-03未命名变量 _ 转正（JEP 456：catch (Exception _) ）；FFM API 转正（443→454，替代 Unsafe 调本地库）；G1 区域固定（423）
JDK 232024-09分代 ZGC 成为默认（474，非分代被废弃）；Markdown 文档注释预览（467）；字符串模板被撤回——21/22 预览过、23 说不做了，"预览特性 ≠ 承诺"的活教材
JDK 242025-03虚拟线程不再固定载体线程（491：synchronized 块内 park 也不再钉住平台线程——21 虚拟线程最大的痛点被修掉）；紧凑对象头转正（450）；Stream Gatherers 转正（485）；后量子密码转正（496/497）；SecurityManager 永久失效（486）
JDK 25 LTS2025-09紧凑对象头设为默认（519）；AOT 缓存系列（514/515，启动加速）；结构化并发第五次预览（505）、Scoped Values 转正（506）；构造器灵活方法体转正（513）；简单源文件与实例 main 转正（512：void main() 直接能跑）；模块导入声明转正（511）；基本类型模式转正（507）；32 位 x86 移植移除（503）

三个能展开 30 秒的亮点

  • 紧凑对象头（Compact Object Headers，JEP 450→519）：把 Mark Word + klass pointer 从 12~16 字节压到一个 8 字节字（锁定状态、GC 元数据、类指针压缩进一个 64 位编码）。默认开启后堆里几十亿小对象普遍省 10%~20% 内存，对象越碎收益越大——和第 02 章的 Mark Word 布局直接呼应："对象头的四种身份"被整体重新编码了。
  • 构造器灵活方法体（Flexible Constructor Bodies，JEP 513）：以前 super(...)/this(...) 必须是第一行；现在允许在调用父构造器之前先写字段赋值、参数校验等"不碰本实例成员"的代码——解决"参数先校验再传给 super"的老痛点，继承体系的初始化规则（02 章初始化顺序）不变，只是编译器多了更细的"不得访问未初始化实例"检查。
  • 简单源文件与实例 main（JEP 512）：void main() 不用类壳、不用 static、不用 String[] args——Java 终于有了"脚本式入口"，教学/原型/单文件工具（jshell 之外的另一条路）。配合 JEP 511 的模块导入声明，Java 25 起的"新手第一课"代码已经和 Python 一样短。
// JDK 25：第一个 Java 程序的全部（JEP 512 转正）
void main() {
    IO.println("Hello, JDK 25!");      // java Hello.java 直接跑
}

// 未命名变量（JEP 456）：
try { ... } catch (Exception _) { ... }        // 我知道会炸，但我不关心是谁
record Point(int x, int y) {}
if (obj instanceof Point(int x, _)) { ... }    // 模式匹配里只取要的组件

答题口径："我们 17/21 的存量 + 在评估 25：最想吃到的是紧凑对象头默认化（小对象多的服务直接省内存）和 JDK 24 修掉的虚拟线程 synchronized 钉住问题；另外提一句字符串模板被撤回、结构化并发还在预览——说明你知道预览特性怎么跟。"这段话覆盖了 5 个知识点，且全部是 2024-2025 的新鲜事。

预览特性纪律：Java 半年一版后，"预览（preview）/转正（final）/撤回（withdrawn）"成了独立的考点维度。可背案例：字符串模板 21/22 两轮预览后 23 撤回；结构化并发 19 起至今五轮预览未转正；record 却是 14/15 两轮预览后 16 准时转正——生产别上预览特性，评估时看它第几轮预览。

09sealed + record + 模式匹配：业务建模的新范式

三个特性单独看都只是语法，组合起来是 代数数据类型（ADT）：sealed 定义"和类型"（Payment = AliPay 或 WeChatPay 或 BankCard），record 定义"积类型"（AliPay = tradeNo 且 amount），模式匹配做"和类型的消费"。这是 21 时代写业务代码的新范式，也是本章最值得背的一段代码。

旧写法（Java 8 风格）

public interface Payment {}                               // 开放接口：谁都能实现
public class AliPay {
    private final String tradeNo;
    private final BigDecimal feeRate;
    // 构造器 / getter / equals / hashCode 手写或 Lombok…
}

BigDecimal fee(Payment p) {
    if (p instanceof AliPay) {
        AliPay a = (AliPay) p;                            // 强转
        return a.getFeeRate();
    } else if (p instanceof WeChatPay) {
        WeChatPay w = (WeChatPay) p;
        return w.getFeeRate().multiply(new BigDecimal("1.1"));
    }
    throw new IllegalArgumentException("unknown payment"); // 新增渠道时这里静默漏掉，运行期才炸
}

新写法（Java 21）

public sealed interface Payment permits AliPay, WeChatPay, BankCard {}
public record AliPay(String tradeNo, BigDecimal feeRate)      implements Payment {}
public record WeChatPay(String openId, BigDecimal feeRate)    implements Payment {}
public record BankCard(String cardNo, boolean domestic)       implements Payment {}

BigDecimal fee(Payment p) {
    return switch (p) {                                   // 对 sealed 类型 switch：编译器查穷尽性
        case AliPay(BigDecimal tradeNo, BigDecimal rate) -> rate;               // 记录模式解构
        case WeChatPay w -> w.feeRate().multiply(new BigDecimal("1.1"));
        case BankCard b when !b.domestic() -> new BigDecimal("3.00");          // when 守卫细分
        case BankCard b -> new BigDecimal("1.50");
    };
}
// 明年加新渠道 BankTransfer：implements Payment 一写，所有未覆盖的 switch 直接编译失败，
// IDE 一键定位所有要改的地方 —— 错误从"运行期线上事故"左移成"编译期必改项"。
维度旧写法sealed + record + 模式匹配
类型封闭性开放，分支永远写不全permits 白名单，编译器穷尽检查
样板代码构造器/getter/equals 手写或 Lombokrecord 一行全包，且不可变
取值方式instanceof + 强转 + getter模式匹配绑定 + 记录模式解构
新增实现的代价静默漏分支，运行期异常编译失败，改动点全部暴露

面试价值：能主动写出/讲出这段对比，等于同时证明了"跟到了 21"+"有建模品味"。可以补一句实战定位：对外暴露的 SPI 用不上 sealed（外部本来就该能扩展），内部业务分支建模（支付渠道、订单状态、消息类型）才是它的主场——这句边界感能再加一分。

10面试必问："你们生产用什么版本、为什么"

标准答法（骨架，按自己实际情况填充）：

  1. 现状："生产主体是 8 / 11 / 17（按事实说），国内多数公司分布也大致如此；我们是 __，新服务已经上 __。"
  2. 为什么选它：选 17/21 的动机——Spring Boot 3 生态门槛（17 起）、GC 与启动性能收益、虚拟线程解决 IO 密集吞吐（21）、record/模式匹配降低样板代码量；
  3. 为什么不激进：升级成本不在 JVM 本身，在生态——内部字节码增强框架（老版 ASM/CGLIB）、APM agent、JNI 原生库要逐个验证；模块强封装带来的 --add-opens 改造；回归测试成本。
  4. 落地节奏：灰度一台 → 观察 GC/内存/RT → 分批；新服务直接新 LTS，老服务按"有需求才动"原则排期。
  • 升级实战素材（背一两个）：8→11：javax.xml.bind 没了要补依赖 / Nashorn 删除；11→17：JDK 内部反射默认被封，老 ORM / 序列化框架报 InaccessibleObjectException，加 --add-opens 或升级框架版本解决；17→21：检查 synchronized 长阻塞导致虚拟线程 pinning、CMS GC 早被移除（8 里用了 CMS 的要先换 G1）。
  • 反问预判："如果让你推动升级你怎么做？"——答：先立收益（压测数据：启动时间、内存、吞吐），再盘生态兼容清单，最后灰度 + 回滚预案。这是在考工程推动能力，不只是技术。

11高频追问与陷阱

  • 追问链：record 能继承吗？→ 能实现接口吗？→ 不能被继承也 不能继承类（隐式 final，因为要保证 equals/hashCode 语义稳定）；可以实现接口、加静态工厂和普通方法。
  • 追问链：var 能用在 lambda 参数上吗？→ JDK 11 起可以（(var x, var y) -> ...），唯一价值是能给参数加注解 (@NonNull var x)；成员变量、方法参数（非 lambda）、返回值都不行。
  • 陷阱：switch 表达式的 case 后两种写法——-> 无 fall-through；老式 : 仍会 fall-through 必须 break。表达式里块分支用 yield 不是 return。
  • 陷阱：文本块第一行换行被忽略——""" 后必须换行，内容从下一行开始；尾部公共缩进以最后一行的缩进为基准剥离，格式不对时先看结尾 """ 的位置。
  • 追问链：虚拟线程能替代线程池吗？→ IO 密集高并发场景可以（任务粒度小、来多少开多少）；CPU 密集仍要平台线程池限流保护 CPU；也别拿它当"免费并行"用——细节（调度、pinning、结构化并发）见 02 并发板块 · 第 10 章。
  • 追问链：接口能定义构造器/成员变量吗？→ 不能构造器；成员变量只能 public static final 常量；能有的：抽象方法、default、static、私有方法（9+）、私有静态方法。
  • 陷阱：sealed 的子类和 permits 必须可互相访问（同模块或同包），且 permits 列表里的类漏写/多写都编译不过——它就是靠编译器强约束吃饭的。
  • 追问链：虚拟线程在 21 有什么坑，后来修了吗？→ synchronized 块内 park 会把虚拟线程"钉"在载体上（pinning），拖垮吞吐；JDK 24（JEP 491）改为不钉——评估虚拟线程时这是版本下限。另一坑：ThreadLocal 大量使用在百万虚拟线程下内存爆炸，官方替代是 Scoped Values（JDK 25 转正）。

12面试自查清单

  1. 能背出 LTS 链 8→11→17→21→25，并说出每 6 个月一版、LTS 每 2 年的节奏。
  2. Java 8 四大件（Lambda/Stream/default 方法/新日期）都能用"痛点+方案"讲，Lambda 字节码层面是 invokedynamic 知道即可。
  3. var 的本质（静态类型推断）与四条限制能一次说全。
  4. record 的自动生成清单、紧凑构造器、三条限制（final/不可变/不能继承）脱口而出，能对比 Lombok @Data。
  5. 能写一段 sealed + record + switch 模式匹配的完整例子，讲清穷尽性检查和错误左移。
  6. 虚拟线程能讲"是什么/挂载卸载/IO 密集收益/什么时候不适用"四点，并知道深入话题在哪。
  7. 分代 ZGC 能一句话说清它补了 ZGC 什么短板。
  8. "生产用什么版本、为什么"有自己版本的四段式答法，且备好一个升级踩坑故事（--add-opens / javax.xml.bind / pinning 任一）。
  9. 知道 JDK 25 是新 LTS：紧凑对象头默认化、构造器体前置代码、void main()；说得出字符串模板被撤回、结构化并发仍在预览、JDK 24 修了虚拟线程 pinning。
