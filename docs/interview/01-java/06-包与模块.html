01面试怎么考

  1. package 在 Java 里起哪些作用？和目录结构是什么关系？
  2. import java.util.* 会把子包也导进来吗？会影响运行性能吗？
  3. java.util.Date 和 java.sql.Date 都导入时会怎样？怎么解决？
  4. 静态导入（import static）是什么？为什么不建议滥用？
  5. default（包私有）权限的适用场景？和 protected 的边界在哪？⭐
  6. JDK 9 模块化（JPMS）解决什么问题？module-info.java 里写什么？（了解级）
  7. 升级 JDK 17 后，为什么反射访问 JDK 内部 API 报 InaccessibleObjectException？--add-opens 是干嘛的？

这章单独出大题的概率不高，但几乎每个知识点都能当"追问弹药"挂在别的题后面（封装题追修饰符、升级 JDK 题追模块强封装）。7 年经验的姿态：包的部分答出"设计视角"，模块部分答出"动机 + 现状"，不要在语法细节上背书。

02package：命名空间与封装边界

包同时扮演三个角色：

  1. 唯一命名空间：com.company.order.OrderService 这样的全限定名（FQCN）保证跨团队、跨三方库类名不冲突。包名惯例是倒写域名 + 全小写；java.* / javax.* 前缀保留给 JDK。
  2. 访问控制的边界单位：default（包私有）权限按包生效（第 04 节展开）——"同包"是 Java 里第一种比"公开/私有"更细的可见性刻度。
  3. 组织与复用单元：源码层面包对应目录路径（com/company/order/），编译产物对应 class 文件路径；一个包把"一起变化、一起复用"的类聚在一起。

规则细节

  • 一个 .java 文件最多一个 public 顶层类，类名必须与文件名相同；不加 public 的顶层类对同包可见。
  • package 语句必须是文件第一条语句（注释除外）；不写 package 的类落在"默认包/匿名包"里，默认包的类无法被任何有包名的类导入——所以正式代码永远要写包。
  • JVM 运行时按 class 文件里记录的 FQCN + classpath 根定位类，"目录必须与包一致"是 javac/构建工具对源码的约束。

跨包访问实证：default 的边界到底在哪

// ── com/order/PinChecker.java ──
package com.order;

class PinChecker {                        // default：包私有
    static boolean check(String pin) { return pin.length() == 6; }
}

// ── com/order/OrderService.java（同包，无需 import、直接用）──
package com.order;

public class OrderService {
    public boolean validate(String pin) {
        return PinChecker.check(pin);     // ✅ 同包：default 类可见
    }
}

// ── com/payment/PaymentService.java（另一个包）──
package com.payment;
import com.order.PinChecker;              // ❌ 编译错误：default 类对包外不可见

public class PaymentService {
    void pay(String pin) { /* PinChecker.check(pin) 用不了 */ }
}

经典陷阱：包不嵌套。com.order.internal 相对 com.order 是完全独立的两个包——名字前缀相同不带来任何访问特权，default 成员照样互相不可见，引用还要 import。"子包"只是命名惯例，Java 的包在语言层面是扁平的。

jar 与包的关系（正交的两件事）

  • 包是命名空间/可见性单位，jar 是物理打包/分发单位，两者互相独立：一个 jar 可以装多个包，一个包在 classpath 下也可以散落在多个 jar 里（这正是 split package 隐患的来源，第 05 节呼应）。
  • 运行期找类 = "classpath 根 + FQCN 路径"，和 jar 文件名无关；同名 FQCN 出现在多个 jar 时谁排前面用谁，纯靠运气——模块化要治的就是这个。

7 年视角：包是"组件"的雏形。分包的方式暴露设计品味：按技术分层（controller/service/dao）是最省事的分法，但改一个需求要横跨 N 个包；按业务域分包（order、payment、inventory 各自高内聚）才让"default 权限 + 同包协作"发挥作用——把强相关的类放一个包里互相暴露包内 API，对外只留 public 入口。这个思路放大就是模块化，第 05 节呼应。

src/main/java/com/company/
├── order/                              # 订单域
│   ├── api/OrderController.java        #   对外 public 入口
│   └── internal/OrderRepoHelper.java   #   包内协作细节（对别的包不可见）
├── payment/                            # 支付域：同构的 api/internal 结构
├── inventory/                          # 库存域
└── shared/                             # 跨域公共：只有这里允许被各域依赖

03import 与静态导入

import 的本质：编译期的名字解析

  • import 只是把"简单名 → 全限定名"的映射告诉编译器，不会触发类加载，更不会"把整个包加载进来"——类加载永远按需发生。所以通配符导入没有运行时性能差异，只有可读性差异。
  • 按需导入 import java.util.*; 不递归子包：util 下的子包 util.function 还得单独 import。
  • 两个包有同名类时（经典：两个 Date），通配符导入下直接用简单名会编译报错"引用不明确"，唯一解法是写全限定名消歧：
import java.util.*;
import java.sql.*;

Date d;              // ❌ 编译错误：java.util.Date 与 java.sql.Date 均匹配
java.util.Date d2;   // ✅ 全限定名消歧（import 了也可以写全名）

静态导入（JDK 5+）

import static java.lang.Math.PI;
import static java.lang.Math.max;
import static java.util.Collections.emptyList;
import static org.junit.jupiter.api.Assertions.assertEquals;   // 测试代码里的正当场景

double area = PI * r * r;
int hi = max(a, b);
List<String> none = emptyList();
assertEquals(expected, actual);

滥用问题（面试考点）

import static java.lang.System.out;

out.println("hello");   // 读代码的人不知道 out 从哪来：是字段？本地变量？
  • 静态导入把"成员属于谁"的信息藏掉了：调用来源不可见，code review 和排查时的定位成本上升。
  • 还有静态成员同名冲突的风险：两个类静态导入同一个名字（如两个工具类都有 of）直接编译错误。
  • 使用纪律：只对"语义自明、无人不知"的静态成员用——测试断言（assertEquals）、数学常量（PI）、枚举/常量类成员；System.out、业务工具类方法这类"需要知道归属"的一律不用。

答"通配符导入影响性能吗"——不影响（编译期符号解析，无运行时开销），但主流规约（含阿里规约）仍建议单类型导入，理由是可读性：一眼看清依赖了哪些类，重构时能精确感知影响面。别把"规约建议"和"性能事实"混为一谈。

04访问控制与包的组合 ⭐

第 05 章给过四种修饰符的范围表；这里从"和包组合"的视角再过一遍，考的是组合规则与设计用法：

修饰符本类同包其他包的子类其他包非子类与包的关系
private✓✗✗✗与包无关
default✓✓✗✗可见性 = 恰好同包，包外连子类都看不见
protected✓✓✓（仅经子类引用）✗= default 范围 + 跨包子类
public✓✓✓✓与包无关（模块化后受 exports 约束）

default = 包私有：被低估的封装工具

  • default 让"同包的类亲密协作，包外只认 public API"成为可能——JDK 标准库内部大量类就是包私有的（如 java.util 里的辅助类），对外只暴露必要入口。
  • 跨包想"只用不暴露"怎么办？把能力收到接口里（接口默认可见性更大），实现类留包内——这正是第 04 章"抽象与接口"的封装动机。
  • 代价：包没有继承机制、不能拆分（一个包横跨多个 jar 会出大问题，见 split package），可扩展性差——这正是后来要有模块的原因之一。

组合规则速查

位置可用的修饰符说明
顶层类 / 接口public / default只有两档；private/protected 仅成员可用
嵌套类 / 成员全部四种嵌套类能访问外部类的 private 成员（同一编译单元）
接口成员（JDK 8 前）隐式 public方法隐式 public abstract，字段隐式 public static final
接口成员（JDK 9+）允许 private 方法给 default 方法提取公共逻辑用，不外泄
局部变量不能加作用域天然限于方法块

答题口径：范围表 + 两个细节（"protected 含包访问"、"接口成员天然 public"）+ 一句设计观——public 是契约、default 是包内实现细节、protected 是给子类的扩展点，三者构成一个"可见性漏斗"。模块化之后 public 之上还多了一层 exports 闸门，顺势引出下一节。

05JPMS 模块系统（了解级）

JDK 9 的 Project Jigsaw 把"包"之上加了一层模块（Module）。面试定位：考得浅但常挂靠在"升级 JDK"的真实经历里，答出动机和影响即可，语法不必背全。

为什么要有模块：classpath 的三大病灶

  1. JAR 平铺、无结构：classpath 上所有 jar 被拍平成一张大网，同一个类出现在多个 jar（重复类/split package）时，加载哪个全凭 classpath 顺序，运行时才爆雷。
  2. public 即全公开：只要类是 public，任何人都能依赖——没有"只给内部用"的手段（default 只能挡包，挡不住别的包）。sun.misc.Unsafe 这类内部 API 被全生态滥用就是这么来的。
  3. 依赖不显式：代码用了哪个 jar 没有声明，缺依赖要到运行时抛 NoClassDefFoundError 才发现（不可靠配置 unreliable configuration）。

JPMS 的两根支柱：强封装 + 可靠依赖。模块 = 一组包 + 一个 module-info.java；启动时校验依赖图，缺模块直接 fail-fast；模块路径取代 classpath 的线性扫描，还能用 jlink 裁剪出最小运行时镜像。

module-info.java 长什么样

module com.order.service {
    requires java.sql;                    // 显式声明依赖的模块
    requires transitive com.common.core;  // 传递依赖：我的使用者也必然用到它
    exports com.order.service.api;        // 只导出 api 包：只有这里的 public 对外可见
    // com.order.service.internal 不导出 → 包外连 public 类都看不见（强封装）
    opens com.order.service.model;        // 运行期放行反射（给 Jackson / MyBatis / Spring 用）
}

对反射的影响（业务工程师真正会撞上的点）

  • JDK 自身被拆成 java.base 等模块后，内部包默认不开放：JDK 16（JEP 396）起默认强封装，JDK 17 正式化——反射访问 JDK 内部 API（如 java.lang 的私有字段）会抛 InaccessibleObjectException。
  • 解法就是启动参数 --add-opens java.base/java.lang=ALL-UNNAMED：把目标包对"无名模块"（classpath 世界）打开。升级 JDK 17/21 时 Spring / Lombok / Arthas 报的反射错误，十有八九落在这里——能讲清这个报错的来龙去脉，就是这题的高分点。
  • 自己的模块同理：不 opens 的包，深度反射（setAccessible）进不去；ORM/序列化框架处理实体需要 opens。

classpath vs module-path

classpath（传统）module-path（JPMS）
内容形态jar 平铺，jar 本身无身份每个模块有名字、有显式依赖图
依赖发现线性扫描，缺依赖运行时才抛 NoClassDefFoundError启动期校验 requires 图，缺了直接启动失败（fail-fast）
可见性public 即全公开exports 的包才公开，且只对依赖我的模块公开
split package靠类加载顺序"赌"赢家直接报错，拒绝启动
配套工具-cp 参数--module-path + jdeps（分析依赖）/ jlink（裁剪运行时）

现状判断（务实口径）：业务系统绝大多数仍以 classpath 方式跑（Spring Boot 主流用法不强制模块化），JPMS 的深度使用者是 JDK 自身与部分类库/中间件。面试回答抓两点：① 两大动机——强封装（exports 才可见）+ 可靠依赖（requires 显式化、启动期校验）；② --add-opens 解决的是"强封装挡住了反射"的兼容问题。再补一句"split package 在模块模式下直接启动失败，而 classpath 下靠加载顺序赌运气"，就够了。

现实：为什么业务系统基本没模块化（高级岗加分段）

  • Spring Boot fat jar 与模块语义冲突：Boot 的可执行 jar 是嵌套 jar 结构，靠自定义 LaunchedClassLoader 按 classpath 语义加载——模块路径模型装不下"jar 套 jar"，二者天然不兼容。
  • 生态消化慢：主流框架对模块化的支持长期停留在"不打扰"（Automatic-Module-Name 起步），Maven/Gradle 构建链没有把模块图纳入一等公民，jlink 裁剪对服务端吸引力有限（镜像分层/容器化已解决启动与体积痛点）。
  • 收益错位：模块化最大受益者是 JDK 自己（jlink 最小运行时、内部 API 封死）和类库作者（API 面收敛）。业务代码的依赖治理靠 Maven 依赖树 + 规约就能解决大半，切换成本却实打实。
  • 但强封装的"半成品"已强制落地：即便业务不模块化，JDK 16+ 的默认强封装也在影响所有人——这就是 --add-opens 成为升级 JDK 必备参数的原因。"用了半个 JPMS"是 2026 年的准确现状描述。

06高频追问与陷阱

  • 追问链：import 通配符 → 递归子包吗 → 不递归；→ 影响性能吗 → 不影响（编译期解析、类加载按需）；→ 那为什么规约建议单类型导入 → 可读性/重构感知，不是性能。
  • 追问链：classpath vs module-path → classpath 是平铺线性扫描、jar 无身份；module-path 每个模块有名字、依赖在启动期组图校验、缺了直接启动失败（fail-fast）。
  • 追问：split package 是什么 → 同一个包名出现在两个模块（或两个 jar）里。模块模式下直接报错拒绝启动；classpath 下则是"哪个 jar 排前面用哪个"的隐式赌博——这正是模块要治的病。
  • 陷阱：默认包（不写 package）的类无法被任何有包名的类引用，JSP/反射场景还会出各种诡异问题——正式代码必写包。
  • 陷阱：protected 同包可见常被误判——出个小题：同包非子类访问 protected 成员？能。跨包子类里拿"别的子类实例"访问？不能。
  • 陷阱：包不嵌套——com.order.internal 对 com.order 来说是外部包，default 成员互相不可见；"子包"只是命名惯例，包在语言层面是扁平的（第 02 节有实证代码）。
  • 陷阱：静态导入同名冲突——两个类静态导入同名成员（都是 of）直接编译错误，和普通 import 冲突一样处理。
  • 追问：requires transitive 什么时候用 → 我 exports 出去的 API 签名里用到了第三方模块的类型，我的使用者编译也需要它，就声明 transitive 免得每个使用者重复 requires。
  • 追问链：NoClassDefFoundError 怎么排查？→ 编译有、运行没有 = classpath 缺 jar 或版本被仲裁掉（Maven dependency:tree 查谁把它 exclude/降级了）；同 FQCN 两个版本 = split package 赌错了加载顺序，用 -verbose:class 看实际加载来源，Maven Enforcer 强制收敛。这题把"包与 jar 正交"的知识点落到了实战。

07面试自查清单

  1. 能说出 package 的三个作用（命名空间 / 访问控制边界 / 组织单元）与目录、FQCN 的关系。
  2. import 是编译期名字解析：不递归子包、无运行时开销、同名冲突用全限定名消歧。
  3. 静态导入的正反例能各举一个（断言 vs System.out）。
  4. 四修饰符范围表 + "protected 含包访问" + "顶层类只有两档" + 接口成员隐式 public。
  5. 能讲 default（包私有）的设计用法：包内协作、对外只留 public——"包是组件雏形"。
  6. JPMS 两大动机（强封装 + 可靠依赖）、module-info 五个关键字里至少认识 requires/exports/opens。
  7. 能讲清 --add-opens 的来龙去脉：模块强封装 → 反射 JDK 内部报 InaccessibleObjectException → 打开指定包。
  8. split package 在 classpath 和 module-path 下行为差异能说两句。
  9. 能讲"为什么业务没模块化"（fat jar 冲突、生态消化慢、收益错位）与 NoClassDefFoundError 的依赖冲突排查套路。
