一、LRU 是什么

缓存的容量是有限的,满了就必须删——按什么规则删,就是缓存的核心设计决策:

策略规则一句话点评
FIFO先进先出,删最老的实现最简单,但不区分"常用"和"用完就扔"
LRU删最久未被使用的核心假设:最近用过的,将来更可能再用
LFU删使用次数最少的统计更多信息,但"历史包袱"重,旧热点赶不走

LRU 的两个关键动作:

  • get(key) 命中后,要把这个 key 提到"最近使用"的位置——访问本身就是一种使用;
  • put(key, value) 时如果满了,淘汰最久未使用的那个。

1.1 为什么用 LinkedHashMap(accessOrder = true)

经典实现(LeetCode 146)是 HashMap + 手写双向链表:map 负责 O(1) 查找,链表负责维护"使用顺序"。LinkedHashMap 就是 JDK 替你维护了这条链表——第三个构造参数 accessOrder = true 之后,每次 get / put 都自动把该条目挪到"最近使用"一端:

// 迭代顺序 = 访问顺序:第一个是最久未使用(LRU),最后一个是最近使用(MRU)
map = new LinkedHashMap<>(capacity, 0.75f, true);
⚠ 陷阱卡 Java 21 起 LinkedHashMap 实现了 SequencedMap(JEP 431),新增了 firstEntry() / lastEntry()。在 accessOrder 模式下: firstEntry() 才是最久未使用(该淘汰的), lastEntry() 是最近刚用过的——拿反了,就会把刚访问的热数据赶出去。

二、加上 TTL:两个容易混淆的概念

概念常用名例子性质
存活时长ttl、ttlMillis、duration60_000(还能活 60 秒)相对时间,会"倒数"
过期时刻expireAt、deadline1730000000000(某个时间点)绝对时间,固定不变

换算关系,进门就做:

expireAt = System.currentTimeMillis() + ttlMillis;

现成的对照:HTTP Cookie 同时定义了 Max-Age=3600(时长)和 Expires=Wed, 30 Oct 2026 ...(时刻);Redis 的 EXPIRE key 60 对外是 TTL 语义,内部实现也是立刻换算成绝对时间戳。

✔ 为什么内部要存 expireAt 如果直接存 ttl(60 秒),判断过期时还得知道"什么时候存的",需要再记一个插入时间; 存绝对时刻,判断只要一步 now > expireAt,而且"续命"就是自然语义:重新覆盖 expireAt = now + ttl。

2.1 过期清理的两种姿势

  • 惰性(lazy):只有 get / put 摸到某个 key 时才顺手检查它。代价:过期条目在被摸到之前一直占内存,size() 虚高。
  • 顺带全清(scrub-on-access):每次 get / put 先把所有已过期的一次清掉(最小堆的 peek() 看谁最早过期)。代价:单次操作可能多做一点工作,但均摊很便宜。本实现用的就是这种。
  • (生产级还有第三种:后台线程定时扫,如 Guava/Caffeine,复杂度最高。)

三、设计点一:双索引结构——两套索引,互相欠信息

为什么一个数据结构不够?因为有两个互相独立的排序需求:

  • 查值 + LRU 顺序 → 需要 HashMap + 访问顺序链表(LinkedHashMap)
  • "谁先过期" → 需要按 expireAt 排序的结构(最小堆 / TreeSet)

所以用双索引:同一条数据,两套结构各挂一份。

LinkedHashMap (accessOrder) PriorityQueue (min-heap, 按 expireAt) ┌──────────────────────────┐ ┌──────────────────────────────┐ │ 2 → Val(v, expireAt) │ ← 最久未使用 │ Key(2, t₂) ← 堆顶 = 最早过期 │ │ 3 → Val(v, expireAt) │ │ Key(3, t₃) │ │ 1 → Val(v, expireAt) │ ← 最近使用 │ Key(1, t₁) │ └──────────────────────────┘ └──────────────────────────────┘ ▲ firstEntry():容量淘汰用 ▲ peek():过期清理用

这是生产级缓存(Caffeine、Guava Cache)的通用思路:一个结构干不了一件以上的事,就分两套索引各管一摊。方向没问题,但它有固有摩擦:

两套结构互相"欠"对方的信息。map 淘汰 LRU 时,需要 expireAt 才能从堆里定位并删掉对应条目;堆过期清理时,需要 key 才能从 map 里删。于是 (key, expireAt) 被迫复制进堆,expireAt 又复制进 Val——同一份事实存了两处(two sources of truth),每条更新路径都必须记得同步两边。

⚠ 同步坑实例 更新已有 key 时,堆里的旧条目是 Key(key, 旧 expireAt)。 record 的 equals 基于全部组件,拿新 expireAt 构造的 Key 永远删不掉旧条目——必须用 oldVal.expireAt 去删,再 add 新的。漏了任何一半,堆里就留下"尸体",之后 removeExpired() 会把刚续命的 key 冤枉地删掉。

工业解法:共享 Node。不复制两份,而是让一个 Node(key, value, expireAt) 对象同时被两边引用(map 存 K → Node,堆里存 Node 引用)。信息只有一份,"同步"这个问题就从根上消失了。Caffeine 内部就是这么组织的。

四、设计点二:PriorityQueue.remove(Object) 是 O(n)

直觉上"堆都是 O(log n)",但这是错觉。二叉堆只知道父子大小关系,不知道元素在数组哪个位置:

操作复杂度原因
offer / poll / peekO(log n) / O(log n) / O(1)只需从堆顶/堆尾调整
remove(Object)O(n)必须线性扫描整个数组找到它,再 O(log n) 调整

本实现里,每次更新已有 key、每次容量淘汰,都要 queue.remove(...)——这两条高频路径直接退化成 O(n)。

方案 A:换 TreeSet,拿到真正的 O(log n)

TreeSet<Key<K>> set = new TreeSet<>(
        Comparator.comparingLong((Key<K> k) -> k.expireAt)
                  .thenComparing(k -> k.k));   // ← 不加这行会出大事,见下
  • first() = 最早过期(替代 peek()),remove(精确对象) 是 O(log n);
  • 复杂度全面对数级,代码几乎不用改结构。
⚠ 精妙的坑:TreeSet 用 comparator 判等 TreeSet 判断"是不是同一个元素"不看 equals,看 compare 结果是否为 0。 如果 comparator 只比 expireAt,那么"同一毫秒过期的两个不同 key"会被当成同一个元素——第二个 add 直接消失,缓存凭空丢数据! 必须用 thenComparing 把 key 排进去做第二级比较。

方案 B:惰性删除(lazy deletion)

压根不删。给 Node 加一个"死亡"标记(或版本号):

  • map 淘汰 / 更新时,只标记,不动堆;
  • removeExpired() 从堆顶 poll 时,发现是尸体就丢弃,继续 poll;
  • 堆会比真实数据"虚胖",但每条真实数据最多产生一具尸体,均摊代价依然可控。

这是定时器、事件循环的经典手法,Caffeine 内部也大量使用。它还有一个隐藏福利:彻底消灭了 remove(Object) 和"两份真相同步"两个问题——不需要从堆里精确删某个东西了。

两个方案对比

现状(PriorityQueue)方案 A(TreeSet)方案 B(惰性删除)
插入/查询过期O(log n)O(log n)O(log n)
更新/淘汰时的删除O(n)O(log n)O(1) 标记
内存精确精确堆会虚胖(尸体)
主要风险性能comparator 判等坑逻辑稍绕(要标记+校验)

五、线程安全:从简单到复杂高效

先明确这个类并发下为什么会坏:accessOrder = true 的 LinkedHashMap,get 也会改链表结构(把节点挪到尾部);PriorityQueue 同样非线程安全;而且 map 和堆两份索引的同步横跨多条语句,并发交错必然失同步。四个方案,由简到繁:

方案 1:synchronized 粗锁 —— 正确性优先

public synchronized V get(K key) { ... }
public synchronized V put(K key, V value, long ttlMillis) { ... }
public synchronized int size() { ... }
  • 所有操作全局串行,一把锁同时罩住 map + queue 两个结构,绝不出错;
  • 吞吐最低:读读也互斥;
  • 适用:学习阶段、低并发场景——先把正确性立住,再谈优化。

方案 2:ReentrantReadWriteLock —— 本例的陷阱

直觉很美好:get 拿读锁、put 拿写锁,读读就能并行了。但本类有个致命细节:accessOrder 模式下 get 是"写"操作(移动链表节点 + removeExpired() 删条目),必须拿写锁——读写锁于是退化成一把全局写锁,白忙一场。

⚠ 教训 读写锁的前提是"读操作真的不修改共享结构"。LRU 这种"访问即修改"的语义天生不匹配, 除非像 Caffeine 那样把"访问记录"从 get 的关键路径上摘出去(见方案 4)。

顺带一句:ReentrantLock 相比 synchronized 提供的是 tryLock / 超时 / 可中断 / Condition 等能力,锁粒度不变,本类用不上。

方案 3:锁分段—— 把一把锁变成 N 把

既然一把锁罩所有人,那就切成 N 个独立的缓存,每个 key 按哈希落一个分片:

class ShardedLRUCache<K, V> {
    private final LRUCache<K, V>[] shards;   // 每片内部就是方案 1 的 synchronized 版
    private final int mask;                    // 分片数取 2 的幂,用位运算取模

    private LRUCache<K, V> shard(K key) {
        return shards[(key.hashCode() & 0x7fffffff) & mask];
    }
    public V get(K key) { return shard(key).get(key); }
    public V put(K key, V value, long ttlMillis) { return shard(key).put(key, value, ttlMillis); }
}
  • 并行度 ≈ 分片数:不同 key 大概率落不同片,片内仍是简单粗锁,正确性不打折;
  • 代价(语义放宽):"全局最久未使用"退化为"分片内最久未使用";总容量变成近似值;size() 是弱一致快照;
  • 老 ConcurrentHashMap 的 segment 设计、Redis 都是这么干的。自己实现高并发缓存,首选这条路。

方案 4:工业级 —— Caffeine 思路,读近乎无锁

  • 读路径不加锁:get 命中后,只把"这个 key 刚被访问"这一事件用 CAS 塞进一个环形缓冲,立刻返回——链表根本不动;
  • 写路径:同样先进写缓冲队列;
  • 后台线程异步把缓冲"排水",批量维护 LRU 顺序、执行淘汰和过期清理;
  • 结果:读接近无锁 O(1),写分摊;代价是复杂度高一个数量级,且 LRU 顺序短暂"陈旧"(最终一致)。

结论:生产环境别手搓,直接用 Caffeine 或 Guava Cache——API 里的 maximumSize、expireAfterWrite 正对应本文的 capacity 与 TTL。

方案并行度读-读读-写实现难度适用场景

六、细节打磨清单

  • 比较器永远别用减法:(a, b) -> a.expireAt - b.expireAt 会溢出,用 Long.compare 或 Comparator.comparingLong;
  • containsKey + put 是两次哈希查找,一次 put 用返回值就够了(oldVal != null 即更新);
  • 异常要带消息:throw new IllegalArgumentException("capacity must be positive: " + capacity);
  • API 参数命名自解释:ttlMillis,并在 javadoc 写明单位;对外暴露"时长",内部存储"时刻";
  • 该类非线程安全(LinkedHashMap 与堆都不是),javadoc 里注明;加锁的四种姿势见第五节;
